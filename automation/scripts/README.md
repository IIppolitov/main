# Утилиты чтения: Яндекс Трекер и Яндекс Вики

Регламенты, требования и задачи живут в Трекере и Вики. Эти скрипты вытаскивают
оттуда текст в markdown на stdout — чтобы работать с ним здесь, а не пересказывать
из браузера вручную.

| Скрипт | Что делает |
|---|---|
| [`tracker-issue.sh`](tracker-issue.sh) | выгружает задачу Трекера: поля, описание, комментарии, связи, вложения |
| [`tracker-project-report.py`](tracker-project-report.py) | отчёт по проекту (спринту): оценка, факт, возвраты на доработку, сроки |
| [`tracker-untagged.py`](tracker-untagged.py) | списания за период в задачи без тегов — дисциплина тегирования |
| [`tracker-tag.py`](tracker-tag.py) | **правит** теги: проставляет мнемонику, заменяет теги-двойники |
| [`tracker-create.py`](tracker-create.py) | **создаёт** задачу в Трекере по пресету проекта |
| [`tracker-update.py`](tracker-update.py) | **дописывает** к задаче комментарий (можно с вложением) либо замещает описание |
| [`wiki-page.sh`](wiki-page.sh) | выгружает страницу Вики: шапка + текст |
| [`wiki2md.py`](wiki2md.py) | переводит разметку Вики в чистый markdown |
| [`wiki-push.py`](wiki-push.py) | **публикует** наши markdown-документы обратно в Вики |
| [`check-links.py`](check-links.py) | проверяет относительные ссылки во всех markdown-файлах |
| [`md2rtf.py`](md2rtf.py) | переводит markdown в форматированный текст (RTF) для вставки в почту |

Оба принимают несколько объектов за вызов и понимают как ключ/slug, так и ссылку
целиком. Разделитель между объектами в выводе — строка `---`.

## Настройка (один раз на машину)

Нужны **OAuth-токен** и **ID организации**. В репозиторий не коммитится ничего:
скрипты лежат в git, учётные данные — в Keychain.

```bash
security add-generic-password -s yandex-tracker     -a "$USER" -w '<OAuth-токен>'
security add-generic-password -s yandex-tracker-org -a "$USER" -w '<ID организации>'
```

- Токен Трекера: https://yandex.ru/support/tracker/ru/concepts/access
- ID организации (Яндекс 360): https://admin.yandex.ru → главная, поле «ID организации»

**Отдельный токен для Вики обычно не нужен.** Организация та же, и если у
OAuth-приложения есть скоуп Вики, `wiki-page.sh` подхватывает трекерные креды
сам — проверено на рабочем контуре. Если понадобится разделить, заведи
`yandex-wiki` и `yandex-wiki-org` — они имеют приоритет.

Альтернатива Keychain: переменные окружения `YANDEX_TRACKER_TOKEN` /
`YANDEX_TRACKER_ORG_ID` (соответственно `YANDEX_WIKI_*`) или файл
`~/.config/yandex-tracker/env` (`~/.config/yandex-wiki/env`) с `chmod 600`.

> ⚠️ Сервисный аккаунт Yandex Cloud для API Вики не подходит — только
> пользовательский. Запросы идут от твоего имени и с твоими правами: скрипт
> покажет ровно то, что ты и так видишь в браузере.

## Задачи Трекера

```bash
./tracker-issue.sh SUPPORTDEV-1788
./tracker-issue.sh CRM-544 SUPPORTDEV-1788            # несколько за вызов
./tracker-issue.sh https://tracker.yandex.ru/CRM-544
./tracker-issue.sh CRM-544 --links                    # + тела связанных задач (1 уровень)
./tracker-issue.sh CRM-544 --attach-dir /tmp/att --all-attachments
```

`--links` выключен по умолчанию: `relates` в трекере вешают щедро, к одной
постановке липнет 5–15 задач из соседних контуров. Связи перечисляются всегда,
тела подтягиваются только по флагу и только на один уровень.

Вложения: изображения скачиваются автоматически, остальное — по
`--all-attachments`. Каталог по умолчанию `$TMPDIR/tracker-attachments/<KEY>`.

## Отчёт по проекту (спринту)

```bash
./tracker-project-report.py 926 930                  # markdown-таблица + итоги
./tracker-project-report.py https://tracker.yandex.ru/pages/projects/926/issues
./tracker-project-report.py 926 --returns            # + кто и когда возвращал задачу
./tracker-project-report.py 926 930 --save           # .md и .csv в reports/ (вне git)
./tracker-project-report.py 926 930 --format csv > sprint.csv
./tracker-project-report.py --changelog CRM-511      # сырая история статусов одной задачи
```

По каждой задаче собирается: клиент, исходная оценка, списанное время с разбивкой
по людям, отклонение, число возвратов на доработку (ревью / внутренний QA /
внешний тест / переоткрытие после закрытия), cycle time и lead time, время в
разработке, плановые даты и дедлайн. В конце — сводка по спринту, списание по
людям и по клиентам, список задач, числящихся сразу в нескольких спринтах.

Текущего исполнителя в отчёте нет намеренно: в задаче с возвратами он говорит
лишь о том, у кого она лежит сейчас. Кто в неё вложился — видно по колонке
«Кто списал, ч» (суммы сходятся с полем `spent`).

**Клиент** берётся из тега задачи — по регламенту мнемоника обязана стоять тегом
(список — [tracker-queues.md](../../docs/regulations/tracker-queues.md)). Если
тега нет, скрипт пробует опознать клиента по началу темы и помечает результат
знаком «?»; такие задачи перечисляются отдельной строкой в сводке — это
нарушение, а не техническая деталь.

**Возвраты считаются по `changelog`, а не по счётчику переоткрытий.** Возврат —
переход из стадии «ревью» / «тест» назад в разработку; категория определяется
статусом, **из** которого задача уехала.

Одно исключение разбирается особо. QA по [этапу 11](../../docs/regulations/crm-lifecycle/11-testirovanie-i-revju.md)
должен брать задачу переводом «Можно тестировать» → «Тестируется», но фактически
часто переводит в «В работе». Считать это возвратом нельзя — задачу не вернули
разработчику, а взяли на тест. Поэтому переход в «В работе» из тестового статуса,
сделанный тестировщиком (список — `QA_PEOPLE`, сверяется с
[org-structure.md](../../docs/company/org-structure.md)), выносится в отдельный
счётчик «QA взял в тест». Переход в **«На доработку»** остаётся возвратом всегда,
кто бы его ни сделал.

Карта статусов по стадиям — константы `DEV` / `REVIEW` / `QA` / `EXT` / `DONE` в
начале скрипта; при заведении нового статуса в workflow его надо дописать туда,
иначе переход просто не попадёт ни в одну категорию.

Оценки в Трекере хранятся в ISO-8601 (`P1DT2H30M`). Скрипт переводит их в часы из
расчёта **рабочий день = 8 часов, неделя = 5 дней** — иначе `P1D` читался бы как
24 часа и любая оценка в днях выглядела бы трёхкратным недорасходом.

`--save` кладёт отчёт в [`reports/`](../../reports/) под именем
`tracker-projects-<проекты>-<дата>.md` (плюс `.csv`) и всегда включает разбор
возвратов. Папка исключена из git: отчёт воспроизводится командой, содержит ФИО
и трудозатраты и устаревает за дни — [reports/README.md](../../reports/README.md).

В итогах отклонение считается только по задачам, где заполнены **и** оценка,
**и** факт. Задачи с пустой оценкой, но со списанным временем выносятся отдельной
строкой: смешивать их в общую сумму нельзя — получится фиктивный перерасход.

## Задачи без тегов

```bash
./tracker-untagged.py                          # текущий месяц, все очереди
./tracker-untagged.py 2026-07                  # конкретный месяц
./tracker-untagged.py --from 2026-08-01 --to 2026-08-14
./tracker-untagged.py --queue CRM DIGITAL      # только эти очереди
./tracker-untagged.py --no-client              # шире: нет тега-мнемоники клиента
./tracker-untagged.py --min 1                  # спрятать мелочь до часа
./tracker-untagged.py --save                   # .md и .csv в reports/
```

Мнемоника клиента по [регламенту очередей](../../docs/regulations/tracker-queues.md)
обязана стоять **тегом** — по нему собирается разрез трудозатрат по клиентам, в том
числе в [`tracker-project-report.py`](tracker-project-report.py). Задача без тега
уносит списанные в неё часы мимо этого разреза; отчёт показывает, сколько именно.

**Считаются часы, а не задачи.** Отчёт отвечает на вопрос «сколько списано за период
в задачи без тегов», поэтому берёт ворклоги периода и уже по ним поднимает задачи —
задача попадает в выборку по дате списания, а не по дате создания. Одна забытая
задача с 29 часами важнее двадцати с четвертью часа.

Дата списания — **дата работы** (`start`), не дата внесения в Трекер: списание за
31 июля, внесённое 1 августа, относится к июлю. Период считается по Москве.

**Два критерия нарушения.** По умолчанию — тегов нет вовсе. С `--no-client` —
клиентской мнемоники нет, хотя другие теги могут стоять; это надмножество, и в шапке
отчёта обе цифры печатаются всегда, каким бы флагом ни запускали.

Колонка «Клиент?» — **догадка по началу темы**, а не факт из Трекера: мнемонику в
названии пишут почти всегда, так что в большинстве строк сразу видно, какой тег
проставить. Догадка не заменяет тег и в статистику клиентов не идёт.

Сводки под таблицей отвечают на два управленческих вопроса: «По очередям» — где
практика не заведена вовсе (доля 100 % значит, что в очереди не тегируют в принципе),
«Кто списывал» — с кем разговаривать.

Список мнемоник берётся импортом из `tracker-project-report.py`, а не копией: новый
клиент добавляется в одном месте.

## Правка тегов

Обратная сторона `tracker-untagged.py`: тот находит нарушения, этот их закрывает.

```bash
./tracker-tag.py --set CRM-1102=ROC CONSOLE-10=PBE       # сухой прогон
./tracker-tag.py --set-file пары.txt --apply
./tracker-tag.py --rename Roche=ROC                      # массово, по всем задачам
./tracker-tag.py --normalize --apply                     # все известные двойники разом
```

**По умолчанию скрипт ничего не пишет** — печатает план. Запись включается `--apply`,
и тогда же в [`reports/`](../../reports/) ложится журнал: массовая правка тегов задним
числом иначе неотличима от того, что теги стояли всегда.

Два режима, потому что это две разные проблемы. `--set` закрывает пропуск: тега не
было, ставим. `--rename` закрывает расхождение: тег есть, но не тот. Тег-двойник
(`Roche` вместо `ROC`) хуже отсутствующего — задача выглядит протегированной, а в
разрез по клиентам не попадает.

Карта известных двойников — константа `ALIASES` в скрипте; новый двойник дописывать
туда, а не набирать руками в аргументах.

### Почему список тегов замещается целиком

**Поиск по тегам в Трекере регистронезависим:** `Tags: "Alcea"` находит и задачи с
каноническим `ALCEA`. Если снятие ведёт себя так же, то `remove: ["Alcea"]` на задаче
с `ALCEA` снял бы именно его — задача осталась бы вообще без тега. Поэтому скрипт не
пользуется `add`/`remove`, а собирает нужный список тегов и отправляет его целиком:
результат не зависит от того, как сервер сравнивает строки.

По той же причине решение принимается по фактическим тегам задачи, а не по тому, что
принёс поиск: тег меняется, только если отличается от канона посимвольно. Прочие теги
задачи (`OMNI`, `Angular`, `Email`) сохраняются — трогаются только клиентские.

### Чего скрипт не делает

Не выдумывает, какой тег ставить: пары `задача=тег` приходят снаружи. Определение
клиента по теме — подсказка `tracker-untagged.py`, и она требует глазами.

`SLV` (Сэлвим) в карту двойников намеренно не включён: в Трекере он встречается чаще
регламентного `SAL` — см. [К-18 в бэклоге](../../docs/backlog.md).

## Создание задач

```bash
./tracker-create.py pbeadmin   задача.md                        # сухой прогон
./tracker-create.py pbeadmin   задача.md --apply
./tracker-create.py pbeapp     задача.md --estimate 4h --apply
./tracker-create.py pbeconsole задача.md --assignee iippolitov --apply
```

**По умолчанию скрипт ничего не создаёт** — печатает, что было бы отправлено. Запись
включается `--apply`.

Текст берётся из markdown-файла: первый H1 — название задачи, всё после него — описание.
Так же устроен `wiki-push.py`, и по той же причине: формулировку задачи надо вычитать
до отправки, а в командной строке это неудобно.

### Пресеты

Реквизиты внутри проекта одинаковы, между проектами — разные. Руками их проставляют
через раз, отсюда пресеты: называется проект, остальное подставляется.

| Пресет | Очередь | Тип | Компонент | Тег | Префикс названия |
|---|---|---|---|---|---|
| `pbeadmin` | CRM | Разработка | Администрирование | PBE | PBE |
| `pbeapp` | CRM | Разработка | Приложение | PBE | PBE |
| `pbeconsole` | CONSOLE | Улучшение | — | — | — |

Мнемоника в начале названия — требование
[регламента очередей](../../docs/regulations/tracker-queues.md); скрипт добавляет её сам
и не дублирует, если она уже стоит. Компоненты резолвятся по имени в момент запуска: их id
живут в настройках очереди и меняются мимо репозитория.

### Оценка и исполнитель

`--estimate` заполняет **оба** поля Трекера — «Оценку» и «Первоначальную оценку»: в отчёте
по спринту нужны обе. Флаг не указан — не заполняется ни одна: пустая оценка это открытый
вопрос, а не ноль. Формат — `30m`, `4h`, `2d`, `1w`, `1d4h`; дни и недели уходят как есть,
Трекер считает их по рабочему календарю (день = 8 часов, неделя = 5 дней).

`--assignee` принимает логин без домена. В Трекере логины строчные, а в почте и оргструктуре
пишутся как придётся (`Iippolitov@powbee.ru`) — скрипт пробует и то, и другое написание.
Флаг не указан — задача остаётся без исполнителя.

### Защита от дубля

Перед созданием скрипт ищет в очереди задачу с точно таким же названием и, если находит,
отказывается создавать — печатает найденные ключи. Обойти можно флагом `--force`. Причина
простая: сухой прогон и боевой запуск отличаются одним флагом, и запустить дважды легче,
чем кажется.

## Комментарий и правка описания

```bash
./tracker-update.py CRM-1630 ответ.md --comment                 # сухой прогон
./tracker-update.py CRM-1630 ответ.md --comment --apply
./tracker-update.py CRM-1630 задача.md --description --apply    # замещает описание целиком
./tracker-update.py CRM-1629 CRM-1630 справка.md --comment --apply
```

Дополняет `tracker-create.py`: тот заводит задачу, этот дописывает к ней. Текст — из
markdown-файла целиком; ответы команде и уточнения постановки надо вычитывать до отправки,
а в командной строке это неудобно.

Ключей можно передать несколько — один текст уходит в каждую задачу. Типовой случай: ответ
одной команде и та же справка в соседние задачи. Порядок аргументов свободный, файл
опознаётся по тому, что существует на диске.

`--description` **замещает описание целиком**, прежний текст не сохраняется — поэтому перед
записью печатается, сколько символов было и станет. H1 из файла при этом отбрасывается:
заголовок задачи живёт в поле `summary`, в теле он был бы вторым. У `--comment` файл идёт
как есть.

Комментарий по умолчанию тихий, без уведомления подписчиков — как и `wiki-push.py`.
Уведомить: `--notify`.

Файл к комментарию — `--attach` (ключ можно повторить):

```bash
./tracker-update.py CRM-1030 ответ.md --comment --attach схема.html --apply
```

Файл грузится как временное вложение и становится постоянным в момент создания
комментария. Если задач несколько, он загружается заново под каждую — иначе вторая
задача получила бы ссылку на уже израсходованное вложение. Если вложение не
загрузилось, комментарий в эту задачу не уходит вовсе: текст со ссылкой «во вложении»
без самого вложения хуже, чем отсутствие комментария.

С `--description` вложения не работают — описание правится целиком, прикладывать
к нему нечего.

Приложить файл к самой задаче, а не к комментарию, — по-прежнему через API:

```bash
curl -X POST -H "Authorization: OAuth $TOKEN" -H "X-Org-Id: $ORG" \
     -F "file=@wiki-page.sh" \
     "https://api.tracker.yandex.net/v3/issues/CRM-1630/attachments"
```

## Страницы Вики

```bash
./wiki-page.sh homepage/klienty/valenta/trebovanija/registr
./wiki-page.sh https://wiki.yandex.ru/homepage/klienty/valenta/trebovanija/registr
./wiki-page.sh slug-1 slug-2
./wiki-page.sh <slug> --raw       # сырой JSON — если нужно поле, которого нет в шапке
```

Из ссылки отбрасываются схема, домен, `?query` и `#якорь`; `%`-кодировка
(кириллица из адресной строки) раскодируется.

### Что важно знать про формат

**Текст приходит в разметке Вики, а не в чистом markdown.** В выгрузке будут
`{% toc %}`, таблицы вида `#| ... |#`, цветовые конструкции `{orange}(...)`.
Для чтения это не мешает, но если текст переносится в наш регламент — разметку
надо переписывать, а не копировать.

API отдаёт тело страницы только при явном запросе полей. Рабочий набор —
`content`, `owner`, `attributes`; неизвестное поле даёт `400 BAD_REQUEST` без
указания, какое именно не подошло. Скрипт идёт от полного набора к минимальному,
поэтому переименование поля на стороне Яндекса приведёт к более бедной шапке,
но не к пустой выгрузке.

## Перевод разметки Вики в markdown

Когда страницу надо не прочитать, а забрать себе и дальше редактировать:

```bash
./wiki-page.sh <slug> --raw | jq -r .content | ./wiki2md.py > ../../docs/regulations/файл.md
```

`wiki2md.py` переводит: таблицы `#| || ячейка | ячейка || |#` → markdown-таблицы,
выноски `{% note info "Заголовок" %}…{% endnote %}` → цитаты, `++подчёркивание++`
→ обычный текст, картинки с размером `=1648x230` → ссылки на Вики (файлы там
закрыты авторизацией, встроить их в markdown нельзя), якорные сноски
`&[текст](12345)` → просто текст.

**Одно место требует ручной правки:** первая строка вики-таблицы становится
шапкой markdown-таблицы. Если в исходнике шапки не было, первая строка данных
уедет в заголовок — определить это автоматически нельзя. Так вышло с таблицей
мнемоник в [tracker-queues.md](../../docs/regulations/tracker-queues.md).

## Публикация обратно в Вики

Обратная операция к `wiki-page.sh`: тот выгружает страницу сюда, этот возвращает
правку в первоисточник.

```bash
./wiki-push.py ../../docs/regulations/crm-lifecycle/            # сухой прогон
./wiki-push.py ../../docs/regulations/crm-lifecycle/ --apply    # запись
./wiki-push.py ../../docs/regulations/crm-lifecycle/05-*.md --apply --notify
```

**По умолчанию скрипт ничего не пишет** — печатает, что было бы отправлено:
целевой адрес, заголовок, размер, список ссылок, которые не удалось сопоставить.
Запись включается `--apply`.

### Откуда берётся адрес страницы

Из шапки самого документа — строки «Выгружено из Вики», по которой файл когда-то
приехал. Отдельной карты соответствий нет намеренно: она разошлась бы с файлами
молча. Документ без такой строки не публикуется — скрипт сообщает и идёт дальше.

### Что делается с текстом

| Что | Зачем |
|---|---|
| Убирается H1 | Заголовок в Вики задаётся полем `title`; в теле он был бы вторым |
| Убирается выноска «Рабочая копия» | Это заметка о состоянии нашей копии, в первоисточнике она бессмысленна |
| Относительные ссылки → адреса Вики | Относительная ссылка в Вики ведёт в никуда |
| Ссылки без страницы в Вики → обычный текст | Бэклог, оргструктура, паспорта проектов живут только в репозитории. Каждый такой случай печатается в отчёте — не теряется молча |

Разметку переписывать не нужно: Вики понимает обычный markdown, включая таблицы
на пайпах, цитаты и блоки кода. Обратный конвертер к `wiki2md.py` не требуется.

### Флаги

| Флаг | Действие |
|---|---|
| `--apply` | Выполнить запись. Без него — сухой прогон |
| `--notify` | Уведомить подписчиков страниц. По умолчанию тихо: при заливке 15 страниц подряд иначе получается спам |
| `--create` | Создавать страницу, если её нет. По умолчанию такой документ пропускается — чтобы опечатка в slug не рождала страницу-дубль в чужом разделе |

Запись идёт от вашего имени и с вашими правами — как и чтение.

## Письмо из markdown в почту

Письма пишутся здесь в markdown, а отправляются из Mail — и разметка `##`, `**`,
`[текст](ссылка)` в отправленном письме выглядит мусором. `md2rtf.py` переводит
файл в форматированный текст: заголовки разделов жирные, списки списками, ссылки
кликабельные.

```bash
./md2rtf.py ../../reports/pismo-meropriyatiya-plus-2026-08-19.md
```

Рядом с `.md` появляется `.rtf`, он же кладётся в буфер обмена — в Mail
вставляется обычным Cmd+V. Флаги: `--no-copy` (не трогать буфер), `-o`
(другой путь результата), `--keep-html` (оставить промежуточный html, если надо
посмотреть, во что превратилась разметка).

Поддержано подмножество markdown, которого хватает для письма: заголовки,
абзацы, маркированные и нумерованные списки, цитаты, черта, жирный, курсив,
моноширинный, ссылки. **Таблицы не конвертируются** — скрипт предупреждает о них
в stderr; если таблица в письме нужна, вставляйте её в Mail отдельно.

Где хранить письма и почему в двух форматах — [reports/README.md](../../reports/README.md).

## Коды возврата

Одинаковые у обоих скриптов:

| Код | Значение |
|---|---|
| 0 | выгружен хотя бы один объект (частичные неудачи — в stderr) |
| 1 | не выгружено ничего |
| 2 | ошибка вызова (нет аргументов, неизвестный флаг) |
| 3 | не найдены учётные данные |

## Ограничения

- Разделитель `---` может встретиться и внутри текста страницы или задачи —
  при машинном разборе вывода опирайся на строку-заголовок `# КЛЮЧ:` /
  ссылку `https://wiki.yandex.ru/...`, а не на `---`.
- У Вики выгружается одна страница за обращение: обхода дерева подстраниц нет.
- Вложения страниц Вики не скачиваются (в Трекере — скачиваются).
