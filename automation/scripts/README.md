# Утилиты чтения: Яндекс Трекер и Яндекс Вики

Регламенты, требования и задачи живут в Трекере и Вики. Эти скрипты вытаскивают
оттуда текст в markdown на stdout — чтобы работать с ним здесь, а не пересказывать
из браузера вручную.

| Скрипт | Что делает |
|---|---|
| [`tracker-issue.sh`](tracker-issue.sh) | выгружает задачу Трекера: поля, описание, комментарии, связи, вложения |
| [`tracker-project-report.py`](tracker-project-report.py) | отчёт по проекту (спринту): оценка, факт, возвраты на доработку, сроки |
| [`tracker-untagged.py`](tracker-untagged.py) | списания за период в задачи без тегов — дисциплина тегирования |
| [`tracker-lint.py`](tracker-lint.py) | проверяет дерево задачи CRM на соответствие регламенту жизненного цикла |
| [`team-load.py`](team-load.py) | занятость и загрузка людей департамента: что делают, что ждёт их, часы против нормы |
| [`github-activity.py`](github-activity.py) | активность разработки в GitHub за период: PR открытые, влитые, зависшие |
| [`tracker-tag.py`](tracker-tag.py) | **правит** теги: проставляет мнемонику, заменяет теги-двойники |
| [`tracker-create.py`](tracker-create.py) | **создаёт** задачу в Трекере по пресету проекта, в том числе багрепорт и дефект прода |
| [`tracker-update.py`](tracker-update.py) | **правит** существующую задачу: комментарий (можно с вложением), описание целиком либо поля |
| [`wiki-page.sh`](wiki-page.sh) | выгружает страницу Вики: шапка + текст, по флагу — комментарии |
| [`wiki2md.py`](wiki2md.py) | переводит разметку Вики в чистый markdown |
| [`wiki-push.py`](wiki-push.py) | **публикует** наши markdown-документы обратно в Вики |
| [`db-query.sh`](db-query.sh) | читает MSSQL под работу с агентом: только SELECT, без персональных данных |
| [`db-profiles-init.sh`](db-profiles-init.sh) | **заводит** профили клиентов MSSQL в `~/.config/pbe-mssql/` — идемпотентно |
| [`check-links.py`](check-links.py) | проверяет относительные ссылки во всех markdown-файлах |
| [`md2rtf.py`](md2rtf.py) | переводит markdown в форматированный текст (RTF) для вставки в почту |

Оба принимают несколько объектов за вызов и понимают как ключ/slug, так и ссылку
целиком. Разделитель между объектами в выводе — строка `---`.

## Настройка (один раз на машину)

Нужны **OAuth-токен** и **ID организации**. В репозиторий не коммитится ничего:
скрипты лежат в git, учётные данные — в Keychain.

```bash
security add-generic-password -s yandex-tracker     -a "$USER" -w '<OAuth-токен>'
security add-generic-password -s yandex-tracker-org -a "$USER" -w '<ID организации>'
```

- Токен Трекера: https://yandex.ru/support/tracker/ru/concepts/access
- ID организации (Яндекс 360): https://admin.yandex.ru → главная, поле «ID организации»

**Отдельный токен для Вики обычно не нужен.** Организация та же, и если у
OAuth-приложения есть скоуп Вики, `wiki-page.sh` подхватывает трекерные креды
сам — проверено на рабочем контуре. Если понадобится разделить, заведи
`yandex-wiki` и `yandex-wiki-org` — они имеют приоритет.

Альтернатива Keychain: переменные окружения `YANDEX_TRACKER_TOKEN` /
`YANDEX_TRACKER_ORG_ID` (соответственно `YANDEX_WIKI_*`) или файл
`~/.config/yandex-tracker/env` (`~/.config/yandex-wiki/env`) с `chmod 600`.

> ⚠️ Сервисный аккаунт Yandex Cloud для API Вики не подходит — только
> пользовательский. Запросы идут от твоего имени и с твоими правами: скрипт
> покажет ровно то, что ты и так видишь в браузере.

## Задачи Трекера

```bash
./tracker-issue.sh SUPPORTDEV-1788
./tracker-issue.sh CRM-544 SUPPORTDEV-1788            # несколько за вызов
./tracker-issue.sh https://tracker.yandex.ru/CRM-544
./tracker-issue.sh CRM-544 --links                    # + тела связанных задач (1 уровень)
./tracker-issue.sh CRM-544 --attach-dir /tmp/att --all-attachments
```

`--links` выключен по умолчанию: `relates` в трекере вешают щедро, к одной
постановке липнет 5–15 задач из соседних контуров. Связи перечисляются всегда,
тела подтягиваются только по флагу и только на один уровень.

Вложения: изображения скачиваются автоматически, остальное — по
`--all-attachments`. Каталог по умолчанию `$TMPDIR/tracker-attachments/<KEY>`.

## Отчёт по проекту (спринту)

```bash
./tracker-project-report.py 926 930                  # markdown-таблица + итоги
./tracker-project-report.py https://tracker.yandex.ru/pages/projects/926/issues
./tracker-project-report.py 926 --returns            # + кто и когда возвращал задачу
./tracker-project-report.py 926 930 --save           # .md и .csv в reports/ (вне git)
./tracker-project-report.py 926 930 --format csv > sprint.csv
./tracker-project-report.py --changelog CRM-511      # сырая история статусов одной задачи
```

По каждой задаче собирается: клиент, исходная оценка, списанное время с разбивкой
по людям, отклонение, число возвратов на доработку (ревью / внутренний QA /
внешний тест / переоткрытие после закрытия), cycle time и lead time, время в
разработке, плановые даты и дедлайн. В конце — сводка по спринту, списание по
людям и по клиентам, список задач, числящихся сразу в нескольких спринтах.

Текущего исполнителя в отчёте нет намеренно: в задаче с возвратами он говорит
лишь о том, у кого она лежит сейчас. Кто в неё вложился — видно по колонке
«Кто списал, ч» (суммы сходятся с полем `spent`).

**Клиент** берётся из тега задачи — по регламенту мнемоника обязана стоять тегом
(список — [tracker-queues.md](../../docs/regulations/tracker-queues.md)). Если
тега нет, скрипт пробует опознать клиента по началу темы и помечает результат
знаком «?»; такие задачи перечисляются отдельной строкой в сводке — это
нарушение, а не техническая деталь.

**Возвраты считаются по `changelog`, а не по счётчику переоткрытий.** Возврат —
переход из стадии «ревью» / «тест» назад в разработку; категория определяется
статусом, **из** которого задача уехала.

Одно исключение разбирается особо. QA по [этапу 11](../../docs/regulations/crm-lifecycle/11-testirovanie-i-revju.md)
должен брать задачу переводом «Можно тестировать» → «Тестируется», но фактически
часто переводит в «В работе». Считать это возвратом нельзя — задачу не вернули
разработчику, а взяли на тест. Поэтому переход в «В работе» из тестового статуса,
сделанный тестировщиком (список — `QA_PEOPLE`, сверяется с
[org-structure.md](../../docs/company/org-structure.md)), выносится в отдельный
счётчик «QA взял в тест». Переход в **«На доработку»** остаётся возвратом всегда,
кто бы его ни сделал.

Карта статусов по стадиям — константы `DEV` / `REVIEW` / `QA` / `EXT` / `DONE` в
начале скрипта; при заведении нового статуса в workflow его надо дописать туда,
иначе переход просто не попадёт ни в одну категорию.

Оценки в Трекере хранятся в ISO-8601 (`P1DT2H30M`). Скрипт переводит их в часы из
расчёта **рабочий день = 8 часов, неделя = 5 дней** — иначе `P1D` читался бы как
24 часа и любая оценка в днях выглядела бы трёхкратным недорасходом.

`--save` кладёт отчёт в [`reports/`](../../reports/) под именем
`tracker-projects-<проекты>-<дата>.md` (плюс `.csv`) и всегда включает разбор
возвратов. Папка исключена из git: отчёт воспроизводится командой, содержит ФИО
и трудозатраты и устаревает за дни — [reports/README.md](../../reports/README.md).

В итогах отклонение считается только по задачам, где заполнены **и** оценка,
**и** факт. Задачи с пустой оценкой, но со списанным временем выносятся отдельной
строкой: смешивать их в общую сумму нельзя — получится фиктивный перерасход.

## Задачи без тегов

```bash
./tracker-untagged.py                          # текущий месяц, все очереди
./tracker-untagged.py 2026-07                  # конкретный месяц
./tracker-untagged.py --from 2026-08-01 --to 2026-08-14
./tracker-untagged.py --queue CRM DIGITAL      # только эти очереди
./tracker-untagged.py --no-client              # шире: нет тега-мнемоники клиента
./tracker-untagged.py --min 1                  # спрятать мелочь до часа
./tracker-untagged.py --save                   # .md и .csv в reports/
```

Мнемоника клиента по [регламенту очередей](../../docs/regulations/tracker-queues.md)
обязана стоять **тегом** — по нему собирается разрез трудозатрат по клиентам, в том
числе в [`tracker-project-report.py`](tracker-project-report.py). Задача без тега
уносит списанные в неё часы мимо этого разреза; отчёт показывает, сколько именно.

**Считаются часы, а не задачи.** Отчёт отвечает на вопрос «сколько списано за период
в задачи без тегов», поэтому берёт ворклоги периода и уже по ним поднимает задачи —
задача попадает в выборку по дате списания, а не по дате создания. Одна забытая
задача с 29 часами важнее двадцати с четвертью часа.

Дата списания — **дата работы** (`start`), не дата внесения в Трекер: списание за
31 июля, внесённое 1 августа, относится к июлю. Период считается по Москве.

**Два критерия нарушения.** По умолчанию — тегов нет вовсе. С `--no-client` —
клиентской мнемоники нет, хотя другие теги могут стоять; это надмножество, и в шапке
отчёта обе цифры печатаются всегда, каким бы флагом ни запускали.

Колонка «Клиент?» — **догадка по началу темы**, а не факт из Трекера: мнемонику в
названии пишут почти всегда, так что в большинстве строк сразу видно, какой тег
проставить. Догадка не заменяет тег и в статистику клиентов не идёт.

Сводки под таблицей отвечают на два управленческих вопроса: «По очередям» — где
практика не заведена вовсе (доля 100 % значит, что в очереди не тегируют в принципе),
«Кто списывал» — с кем разговаривать.

Список мнемоник берётся импортом из `tracker-project-report.py`, а не копией: новый
клиент добавляется в одном месте.

## Занятость и загрузка людей

```bash
./team-load.py                              # БА и тестирование, последние 14 дней
./team-load.py --team all                   # весь департамент
./team-load.py --team qa dev-admin
./team-load.py --who vshuvaev mbardyuzhina
./team-load.py --from 2026-08-18 --to 2026-09-01
./team-load.py --days 30
./team-load.py --format json                # под команду /pbe-zagruzka
./team-load.py --save                       # .md и .json в reports/
```

Отвечает по каждому человеку на четыре вопроса: **что делает сейчас**, **что ждёт
его**, **что закрыл за период**, **сколько часов списал против нормы**. Плюс два
вопроса по команде тестирования: **что придёт** и **что ничьё**.

Снимок фактов, а не план. Суждение — «кто перегружен», «кому отдать следующую
задачу», отпуска — живёт в [team-load.md](../../docs/company/team-load.md);
скрипт его не знает и знать не должен.

**Очередь у разных ролей разная.** Подзадача «Тестирование» в статусе «Готово к
разработке» назначена на тестировщика по [этапу 9](../../docs/regulations/crm-lifecycle/09-raspredelenie-zadach.md)
(4.3.1), но взять её он не может: разработка не сдана. Считать такую задачу
очередью значит увидеть у тестировщика «42 в очереди» и не разглядеть за ними те
три, что ждут его сегодня. Поэтому для тестирования очередь сужена до «Можно
тестировать» / «На доработку» / «Готов к ревью», остальное уходит в корзину
**«в плане»** — назначено, но работа ещё не пришла. Разложение статусов по
корзинам — константы `ACTIVE` / `QUEUE` / `WAITING` / `QUEUE_BY_TEAM` в начале
скрипта; новый статус workflow надо дописать туда, иначе он попадёт в «прочее»
(корзина печатается, молча статус не теряется).

**Норма — календарная**, Пн–Пт минус список праздников `HOLIDAYS`, по 8 часов.
Отпуска и больничные скрипт не знает: они ведутся руками в `team-load.md`.
Поэтому «списал 40 из 80» одинаково означает и просадку, и две недели отпуска —
цифра ставит вопрос, а не выносит приговор. Список праздников обновляется руками
раз в год.

**«Что придёт» считается по полю «Оценка: тестирование» основной задачи.**
Подзадачи «Тестирование» в спринт разработки не набираются
([этап 8](../../docs/regulations/crm-lifecycle/08-nabor-sprintov.md), 4.3),
поэтому объём теста в самом спринте не лежит — он поднимается по родителю каждой
подзадачи спринта. Поле локальное, язык запросов Трекера его не видит
([К-29](../../docs/backlog.md)), но **прочитать значение в теле задачи можно** —
на этом раздел и стоит. Незаполненное поле считается отдельно и печатается
числом: иначе набранный объём выглядел бы меньше, чем он есть.

**«Ничьё»** — задачи в статусах «Можно тестировать» и «Тестируется», где
исполнитель не тестировщик. Ограничено очередями `CRM`, `BUGREPORTS`,
`SUPPORTDEV` и задачами, тронутыми за последние 90 дней: без этого в отчёт лезут
задачи 2025 года из `ANALYTIC` и `ADMINISTRATION`, к планированию тестирования
отношения не имеющие.

Списание относится к **дате работы** (`start`), не к дате внесения в Трекер;
период считается по Москве — как в [`tracker-untagged.py`](tracker-untagged.py).

Справочник людей — константа `PEOPLE` в скрипте, состав сверяется с
[org-structure.md](../../docs/company/org-structure.md).

## Активность в GitHub

```bash
./github-activity.py                        # организация powbee, последние 14 дней
./github-activity.py --days 30
./github-activity.py --from 2026-08-01 --to 2026-08-31
./github-activity.py --who vznaida RusGosuNagib
./github-activity.py --format json
./github-activity.py --save
```

Второй контур к `team-load.py`: чем занята разработка. Для планирования
тестирования это важнее собственных цифр тестировщиков — объём теста задаёт не
тестировщик, а темп сдачи разработки. Пик открытых PR на этой неделе — очередь на
тест на следующей.

**В GitHub есть только разработчики.** БА и тестировщики в организацию `powbee`
не входят, их активности здесь нет и быть не может: по ним смотрим Трекер. Это
ограничение источника, а не пробел в отчёте.

Считается по организации целиком, а не по трём продуктовым репозиториям: модули
админки (`pbeadmin_omni`, `pbeadmin_id360` и ещё десяток) — отдельные
репозитории, и работа в них относится к продукту ровно так же.

Соответствие логинов людям берётся из `PEOPLE` в [`team-load.py`](team-load.py),
чтобы состав команд жил в одном месте. Логин, которого там нет, печатается как
«нет в справочнике» — это либо внешний контрибьютор, либо забытый человек, и то
и другое надо видеть.

Нужен авторизованный `gh` (скоуп `repo`). Поиск GitHub ограничен 30 запросами в
минуту: на превышении `gh` не падает, а ждёт снятия лимита, поэтому таймаут в
скрипте щедрый (300 с).

## Проверка дерева задачи на регламент

```bash
./tracker-lint.py CRM-131                      # отчёт по дереву задачи
./tracker-lint.py CRM-131 --errors-only        # только нарушения
./tracker-lint.py CRM-131 CRM-1121             # несколько деревьев за вызов
./tracker-lint.py CRM-131 --format json        # машиночитаемо — под UI консоли
./tracker-lint.py CRM-131 --stage 5            # проверить по этапу вручную
./tracker-lint.py --rules                      # каталог правил, без обращения к Трекеру
```

Отвечает на один вопрос: **всё ли в дереве задачи заведено так, как требует
[жизненный цикл задачи CRM](../../docs/regulations/crm-lifecycle/)** — состав
подзадач, типы, компоненты, мнемоника, поля оценки, форма привязки багрепортов.
Ничего не правит, только читает.

**Правила привязаны к этапам.** Задача на бизнес-анализе не обязана иметь
заполненные поля оценки, и ругать её за это бессмысленно. Этап определяется по
статусам всего дерева — максимально достигнутый, а не статус основной задачи:
основная висит в «Открыт» весь жизненный цикл, работа идёт в подзадачах.
Закрытая подзадача засчитывает ровно свой этап: закрытый бизнес-анализ — это
этап 4, а не 13. Ручное переопределение — `--stage`.

**Два уровня.** `error` — прямое нарушение пункта регламента, у каждого правила
проставлена ссылка на пункт. `warn` — расхождение, которое регламент явно не
запрещает, но которое ломает отчётность или воспроизводимость: разнобой в форме
привязки багрепортов, отсутствие компонента у подзадачи тестирования, нулевая
оценка. Код возврата 1 — есть нарушения; предупреждения на код возврата не
влияют.

Дали ключ подзадачи — скрипт поднимается к основной задаче: дерево проверяется
целиком, а в разговоре чаще звучит ключ подзадачи.

**Дерево обходится на два уровня.** Багрепорт по доработке живёт подзадачей своей
подзадачи «Разработка» ([этап 11](../../docs/regulations/crm-lifecycle/11-testirovanie-i-revju.md),
4.5.2), то есть на втором уровне. Правила состава и оценки смотрят только на
первый — подзадачи «Разработка» и «Тестирование» там и живут; правила по
багрепортам и закрытию обходят оба. Глубже двух уровней не идём.

Формат `json` — заготовка под UI в [pbeconsole](../../docs/systems/pbeconsole.md):
состав дерева, найденные нарушения, коды правил и ссылки на пункты регламента.

**Каталог правил — в самом скрипте**, декоратором `@rule` рядом с проверкой.
Новое правило добавляется одной функцией; `--rules` печатает каталог таблицей.
Правила читают регламент, а не наоборот: если проверка расходится с текстом
[docs/regulations/](../../docs/regulations/), правит скрипт, а не регламент.

## Правка тегов

Обратная сторона `tracker-untagged.py`: тот находит нарушения, этот их закрывает.

```bash
./tracker-tag.py --set CRM-1102=ROC CONSOLE-10=PBE       # сухой прогон
./tracker-tag.py --set-file пары.txt --apply
./tracker-tag.py --rename Roche=ROC                      # массово, по всем задачам
./tracker-tag.py --normalize --apply                     # все известные двойники разом
```

**По умолчанию скрипт ничего не пишет** — печатает план. Запись включается `--apply`,
и тогда же в [`reports/`](../../reports/) ложится журнал: массовая правка тегов задним
числом иначе неотличима от того, что теги стояли всегда.

Два режима, потому что это две разные проблемы. `--set` закрывает пропуск: тега не
было, ставим. `--rename` закрывает расхождение: тег есть, но не тот. Тег-двойник
(`Roche` вместо `ROC`) хуже отсутствующего — задача выглядит протегированной, а в
разрез по клиентам не попадает.

Карта известных двойников — константа `ALIASES` в скрипте; новый двойник дописывать
туда, а не набирать руками в аргументах.

### Почему список тегов замещается целиком

**Поиск по тегам в Трекере регистронезависим:** `Tags: "Alcea"` находит и задачи с
каноническим `ALCEA`. Если снятие ведёт себя так же, то `remove: ["Alcea"]` на задаче
с `ALCEA` снял бы именно его — задача осталась бы вообще без тега. Поэтому скрипт не
пользуется `add`/`remove`, а собирает нужный список тегов и отправляет его целиком:
результат не зависит от того, как сервер сравнивает строки.

По той же причине решение принимается по фактическим тегам задачи, а не по тому, что
принёс поиск: тег меняется, только если отличается от канона посимвольно. Прочие теги
задачи (`OMNI`, `Angular`, `Email`) сохраняются — трогаются только клиентские.

### Чего скрипт не делает

Не выдумывает, какой тег ставить: пары `задача=тег` приходят снаружи. Определение
клиента по теме — подсказка `tracker-untagged.py`, и она требует глазами.

`SLV` (Сэлвим) в карту двойников намеренно не включён: в Трекере он встречается чаще
регламентного `SAL` — см. [К-18 в бэклоге](../../docs/backlog.md).

## Создание задач

```bash
./tracker-create.py pbeadmin   задача.md                        # сухой прогон
./tracker-create.py pbeadmin   задача.md --apply
./tracker-create.py pbeapp     задача.md --estimate 4h --apply
./tracker-create.py pbeconsole задача.md --assignee iippolitov --apply
```

**По умолчанию скрипт ничего не создаёт** — печатает, что было бы отправлено. Запись
включается `--apply`.

Текст берётся из markdown-файла: первый H1 — название задачи, всё после него — описание.
Так же устроен `wiki-push.py`, и по той же причине: формулировку задачи надо вычитать
до отправки, а в командной строке это неудобно.

### Пресеты

Реквизиты внутри проекта одинаковы, между проектами — разные. Руками их проставляют
через раз, отсюда пресеты: называется проект, остальное подставляется.

| Пресет | Очередь | Тип | Компонент | Тег | Префикс названия |
|---|---|---|---|---|---|
| `pbeadmin` | CRM | Разработка | Администрирование | PBE | PBE |
| `pbeapp` | CRM | Разработка | Приложение | PBE | PBE |
| `pbeconsole` | CONSOLE | Улучшение | — | — | — |
| `bugreport-admin` | BUGREPORTS | Ошибка | Администрирование | `--client` | мнемоника |
| `bugreport-app` | BUGREPORTS | Ошибка | Приложение | `--client` | мнемоника |
| `supportdev-admin` | SUPPORTDEV | **Инцидент** | Администрирование | `--client` | — |
| `supportdev-app` | SUPPORTDEV | **Инцидент** | Приложение | `--client` | — |

Мнемоника в начале названия — требование
[регламента очередей](../../docs/regulations/tracker-queues.md); скрипт добавляет её сам
и не дублирует, если она уже стоит. Компоненты резолвятся по имени в момент запуска: их id
живут в настройках очереди и меняются мимо репозитория.

### Пресеты дефектов

```bash
./tracker-create.py bugreport-admin дефект.md --client VLT --parent CRM-1651 --apply
./tracker-create.py supportdev-app  дефект.md --client BAY --apply
```

Очередь между ними выбирается двумя вопросами: **вышел ли функционал на прод** и, если вышел,
**нужен ли хотфикс**. Не на проде — `BUGREPORTS`; на проде и хотфиксом — `SUPPORTDEV`;
на проде, но подождёт планового релиза — `BUGREPORTS`. Первый вопрос — из
[описания очередей](../../docs/regulations/tracker-queues.md#граница-между-bugreports-и-очередями-поддержки),
второй туда пока не записан (см. [бэклог](../../docs/backlog.md)).

Пресет за пользователя этого не решает: он лишь не даёт заполнить реквизиты неверно, когда
очередь уже выбрана.

Три вещи, которые в пресетах зашиты не по вкусу, а по регламенту и по факту Трекера:

- **Тип в `SUPPORTDEV` — «Инцидент», а не «Ошибка».** Типа «Ошибка» в этой очереди нет;
  сверено с Трекером 2026-08-31. В `BUGREPORTS` тип «Ошибка» есть, и он там же и требуется
  ([этап 11](../../docs/regulations/crm-lifecycle/11-testirovanie-i-revju.md), 4.5.4).
- **Багрепорт назначается на тимлида команды** — это реквизит по 4.5.4, поэтому исполнитель
  стоит умолчанием пресета. Задачи `SUPPORTDEV` уходят **без исполнителя**: кому чинить и
  выпускать ли хотфиксом, решает разбор беклога поддержки, а не автор задачи.
- **Мнемоника в названии — только у багрепортов.** У задач поддержки своё правило имени —
  `[Клиент]. [Компонент]. [Описание]`, — и мнемоника там уходит только тегом
  (см. [бэклог](../../docs/backlog.md), расхождение по шаблону названия).

`--parent` у багрепорта не формальность: багрепорт привязывается **подзадачей**, а не связью
`relates`, и родитель — это подзадача «Разработка», в которой сделан дефектный функционал.
Родителя нет — сухой прогон печатает предупреждение: по 4.5.2 это означает «дефект не по
доработкам задачи», и если это не так, задача заведена с потерянным адресом.

### Клиент: `--client`

```bash
./tracker-create.py bugreport-admin дефект.md --client VLT
```

Мнемоника проверяется по справочнику [`MNEMONICS`](tracker-create.py) — списку из
[регламента очередей](../../docs/regulations/tracker-queues.md). Неизвестное значение —
отказ, а не предупреждение: цена ошибки несимметричная. Неверная мнемоника задачу не ломает,
она молча выкидывает её из всех клиентских фильтров и отчётов, и обнаруживается это через
месяц. Клиент новый — внеси его в `MNEMONICS`; разово обойти можно `--force`.

Пресеты дефектов без `--client` не работают вовсе: тег с мнемоникой обязателен в любой
очереди, а «завести сейчас, тег проставить потом» на практике означает «не проставить».

### Оценка и исполнитель

`--estimate` заполняет **оба** поля Трекера — «Оценку» и «Первоначальную оценку»: в отчёте
по спринту нужны обе. Флаг не указан — не заполняется ни одна: пустая оценка это открытый
вопрос, а не ноль. Формат — `30m`, `4h`, `2d`, `1w`, `1d4h`; дни и недели уходят как есть,
Трекер считает их по рабочему календарю (день = 8 часов, неделя = 5 дней).

`--assignee` принимает логин без домена. В Трекере логины строчные, а в почте и оргструктуре
пишутся как придётся (`Iippolitov@powbee.ru`) — скрипт пробует и то, и другое написание.
Флаг не указан — задача остаётся без исполнителя.

### Защита от дубля

Перед созданием скрипт ищет в очереди задачу с точно таким же названием и, если находит,
отказывается создавать — печатает найденные ключи. Обойти можно флагом `--force`. Причина
простая: сухой прогон и боевой запуск отличаются одним флагом, и запустить дважды легче,
чем кажется.

## Комментарий, описание и правка полей

```bash
./tracker-update.py CRM-1630 ответ.md --comment                 # сухой прогон
./tracker-update.py CRM-1630 ответ.md --comment --apply
./tracker-update.py CRM-1630 задача.md --description --apply    # замещает описание целиком
./tracker-update.py CRM-1629 CRM-1630 справка.md --comment --apply
```

Дополняет `tracker-create.py`: тот заводит задачу, этот дописывает к ней. Текст — из
markdown-файла целиком; ответы команде и уточнения постановки надо вычитывать до отправки,
а в командной строке это неудобно.

Ключей можно передать несколько — один текст уходит в каждую задачу. Типовой случай: ответ
одной команде и та же справка в соседние задачи. Порядок аргументов свободный, файл
опознаётся по тому, что существует на диске.

`--description` **замещает описание целиком**, прежний текст не сохраняется — поэтому перед
записью печатается, сколько символов было и станет. H1 из файла при этом отбрасывается:
заголовок задачи живёт в поле `summary`, в теле он был бы вторым. У `--comment` файл идёт
как есть.

Комментарий по умолчанию тихий, без уведомления подписчиков — как и `wiki-push.py`.
Уведомить: `--notify`.

Файл к комментарию — `--attach` (ключ можно повторить):

```bash
./tracker-update.py CRM-1030 ответ.md --comment --attach схема.html --apply
```

Файл грузится как временное вложение и становится постоянным в момент создания
комментария. Если задач несколько, он загружается заново под каждую — иначе вторая
задача получила бы ссылку на уже израсходованное вложение. Если вложение не
загрузилось, комментарий в эту задачу не уходит вовсе: текст со ссылкой «во вложении»
без самого вложения хуже, чем отсутствие комментария.

С `--description` вложения не работают — описание правится целиком, прикладывать
к нему нечего.

Приложить файл к самой задаче, а не к комментарию, — по-прежнему через API:

```bash
curl -X POST -H "Authorization: OAuth $TOKEN" -H "X-Org-Id: $ORG" \
     -F "file=@wiki-page.sh" \
     "https://api.tracker.yandex.net/v3/issues/CRM-1630/attachments"
```

### Правка полей

Третий режим того же скрипта. Файла не требует, с `--comment` и `--description`
не совмещается — режим один за вызов.

```bash
./tracker-update.py CRM-1240 CRM-1241 --component Администрирование   # сухой прогон
./tracker-update.py CRM-131 --assignee "Антонова Диана" --apply
./tracker-update.py BUGREPORTS-150 --parent CRM-1225 --apply
./tracker-update.py CRM-131 --field "Срочность БА=3" --apply
```

| Флаг | Что правит |
|---|---|
| `--assignee ЛОГИН` | исполнитель: логин, почта или «Фамилия Имя» |
| `--component ИМЯ` | компонент команды, флаг можно повторить |
| `--parent KEY` | родитель: задача становится подзадачей `KEY` |
| `--field ИМЯ=ЗНАЧЕНИЕ` | любое другое поле по русскому названию либо id |

Появился под отчёты [`tracker-lint.py`](tracker-lint.py): нарушения П-3, П-4, О-3 и
Б-4 закрываются одним полем каждое, и вбивать их по одному в вебе — то же самое
действие, только без следа. Ключей можно передать несколько — одно значение уходит
в каждую задачу: типовой случай, когда у четырёх подзадач не проставлен компонент.

**Значения проверяются до записи по справочникам Трекера.** Исполнитель ищется среди
сотрудников (имя — без учёта регистра и порядка слов: в отчёте линта человек назван
«Антонова Диана», в Трекере — «Диана Антонова»), компонент — среди компонентов
очереди задачи, поле — среди полей организации **и локальных полей очереди**.
Последнее существенно: «Срочность БА» и все семь полей разбивки оценки заведены
локальными в `CRM`, в общем справочнике их нет.

```
✗ CRM-1240: в очереди CRM нет компонента «Администрировние».
  Есть: OMNI, Администрирование, Аналитика данных, Бизнес анализ, Конфигурация, Приложение
```

Опечатка отсекается на сухом прогоне, а не уезжает в задачу молча. Сухой прогон
печатает «было → станет» по каждой задаче, `--apply` кладёт в `reports/` журнал:
правка полей задним числом иначе неотличима от того, что поля были заполнены всегда.

Чего скрипт не умеет: снимать связи `relates` (нарушение Б-1) — это отдельная
операция `DELETE /issues/{key}/links/{id}`, пока руками.

## Страницы Вики

```bash
./wiki-page.sh homepage/klienty/valenta/trebovanija/registr
./wiki-page.sh https://wiki.yandex.ru/homepage/klienty/valenta/trebovanija/registr
./wiki-page.sh slug-1 slug-2
./wiki-page.sh <slug> --comments  # + раздел «Комментарии» под текстом страницы
./wiki-page.sh <slug> --raw       # сырой JSON — если нужно поле, которого нет в шапке
```

Из ссылки отбрасываются схема, домен, `?query` и `#якорь`; `%`-кодировка
(кириллица из адресной строки) раскодируется.

### Комментарии

Комментарии не приходят вместе со страницей — это отдельная ручка
`/pages/{id}/comments`, поэтому и отдельный флаг: без `--comments` скрипт делает
один запрос, с ним — два на страницу. Признак того, что смотреть есть что, виден
и без флага: в `--raw` поле `attributes.comments_count`.

По каждому комментарию выгружаются автор, дата, ссылка-якорь `#comment-<id>`
(открывает то же место, что и в Вике), фрагмент текста, к которому комментарий
привязан (`inline_text`), и пометка «Ответ на комментарий #…» для веток.
Удалённые комментарии пропускаются, решённые помечаются. С `--raw` всё это
уходит в поле `comments` того же JSON:

```bash
./wiki-page.sh <slug> --comments --raw | jq -r '.comments[] | .body'
```

Ответ страничный, скрипт идёт по `next_cursor` до конца. Если выгрузить удалось
не всё, в stderr будет предупреждение, а в выводе — то, что успело прийти:
молча обрезанный список комментариев хуже честно неполного.

### Что важно знать про формат

**Текст приходит в разметке Вики, а не в чистом markdown.** В выгрузке будут
`{% toc %}`, таблицы вида `#| ... |#`, цветовые конструкции `{orange}(...)`.
Для чтения это не мешает, но если текст переносится в наш регламент — разметку
надо переписывать, а не копировать.

API отдаёт тело страницы только при явном запросе полей. Рабочий набор —
`content`, `owner`, `attributes`; неизвестное поле даёт `400 BAD_REQUEST` без
указания, какое именно не подошло. Скрипт идёт от полного набора к минимальному,
поэтому переименование поля на стороне Яндекса приведёт к более бедной шапке,
но не к пустой выгрузке.

## Перевод разметки Вики в markdown

Когда страницу надо не прочитать, а забрать себе и дальше редактировать:

```bash
./wiki-page.sh <slug> --raw | jq -r .content | ./wiki2md.py > ../../docs/regulations/файл.md
```

`wiki2md.py` переводит: таблицы `#| || ячейка | ячейка || |#` → markdown-таблицы,
выноски `{% note info "Заголовок" %}…{% endnote %}` → цитаты, `++подчёркивание++`
→ обычный текст, картинки с размером `=1648x230` → ссылки на Вики (файлы там
закрыты авторизацией, встроить их в markdown нельзя), якорные сноски
`&[текст](12345)` → просто текст.

**Одно место требует ручной правки:** первая строка вики-таблицы становится
шапкой markdown-таблицы. Если в исходнике шапки не было, первая строка данных
уедет в заголовок — определить это автоматически нельзя. Так вышло с таблицей
мнемоник в [tracker-queues.md](../../docs/regulations/tracker-queues.md).

## Публикация обратно в Вики

Обратная операция к `wiki-page.sh`: тот выгружает страницу сюда, этот возвращает
правку в первоисточник.

```bash
./wiki-push.py ../../docs/regulations/crm-lifecycle/            # сухой прогон
./wiki-push.py ../../docs/regulations/crm-lifecycle/ --apply    # запись
./wiki-push.py ../../docs/regulations/crm-lifecycle/05-*.md --apply --notify
```

**По умолчанию скрипт ничего не пишет** — печатает, что было бы отправлено:
целевой адрес, заголовок, размер, список ссылок, которые не удалось сопоставить.
Запись включается `--apply`.

### Откуда берётся адрес страницы

Из шапки самого документа — строки «Выгружено из Вики», по которой файл когда-то
приехал. Отдельной карты соответствий нет намеренно: она разошлась бы с файлами
молча. Документ без такой строки не публикуется — скрипт сообщает и идёт дальше.

### Что делается с текстом

| Что | Зачем |
|---|---|
| Убирается H1 | Заголовок в Вики задаётся полем `title`; в теле он был бы вторым |
| Убирается выноска «Рабочая копия» | Это заметка о состоянии нашей копии, в первоисточнике она бессмысленна |
| Относительные ссылки → адреса Вики | Относительная ссылка в Вики ведёт в никуда |
| Ссылки без страницы в Вики → обычный текст | Бэклог, оргструктура, паспорта проектов живут только в репозитории. Каждый такой случай печатается в отчёте — не теряется молча |

Разметку переписывать не нужно: Вики понимает обычный markdown, включая таблицы
на пайпах, цитаты и блоки кода. Обратный конвертер к `wiki2md.py` не требуется.

### Флаги

| Флаг | Действие |
|---|---|
| `--apply` | Выполнить запись. Без него — сухой прогон |
| `--notify` | Уведомить подписчиков страниц. По умолчанию тихо: при заливке 15 страниц подряд иначе получается спам |
| `--create` | Создавать страницу, если её нет. По умолчанию такой документ пропускается — чтобы опечатка в slug не рождала страницу-дубль в чужом разделе |

Запись идёт от вашего имени и с вашими правами — как и чтение.

## Письмо из markdown в почту

Письма пишутся здесь в markdown, а отправляются из Mail — и разметка `##`, `**`,
`[текст](ссылка)` в отправленном письме выглядит мусором. `md2rtf.py` переводит
файл в форматированный текст: заголовки разделов жирные, списки списками, ссылки
кликабельные.

```bash
./md2rtf.py ../../reports/pismo-meropriyatiya-plus-2026-08-19.md
```

Рядом с `.md` появляется `.rtf`, он же кладётся в буфер обмена — в Mail
вставляется обычным Cmd+V. Флаги: `--no-copy` (не трогать буфер), `-o`
(другой путь результата), `--keep-html` (оставить промежуточный html, если надо
посмотреть, во что превратилась разметка).

Поддержано подмножество markdown, которого хватает для письма: заголовки,
абзацы, маркированные и нумерованные списки, цитаты, черта, жирный, курсив,
моноширинный, ссылки. **Таблицы не конвертируются** — скрипт предупреждает о них
в stderr; если таблица в письме нужна, вставляйте её в Mail отдельно.

Где хранить письма и почему в двух форматах — [reports/README.md](../../reports/README.md).

## Комментарии Pull Request'а

```bash
automation/scripts/pr-comments.sh 1232 -R powbee/pbeadmin
automation/scripts/pr-comments.sh https://github.com/powbee/pbeapp/pull/842
automation/scripts/pr-comments.sh powbee/pbeadmin#1232 --raw     # сырой JSON
```

Комментарии PR отдают **три разных эндпоинта**, и `gh pr view --comments` читает только один
из них — ленту обсуждения внизу страницы:

| Что | Эндпоинт |
|---|---|
| Лента обсуждения | `GET /issues/<N>/comments` |
| Тела ревью (approve / changes requested) | `GET /pulls/<N>/reviews` |
| **Замечания на строках кода** | `GET /pulls/<N>/comments` |

Третья строка — содержательная часть любого ревью, и именно она теряется. Потеря молчаливая:
команда отрабатывает успешно, просто половины данных в выводе нет. Вторая грабля того же рода —
пагинация: без `--paginate` видно первые 30 записей, а обрыв ничем не обозначен.

Скрипт печатает шапку PR (включая **head SHA**), инлайновые замечания **тредами**, тела ревью
и ленту обсуждения. Замечание на строке, которая с тех пор изменилась, помечается `outdated`.

`-R` **указывай явно для сабмодулей**: без него `gh` берёт репозиторий из текущего каталога,
и вызов из корня `pbeadmin` молча уйдёт туда, хотя речь про PR модуля `powbee/pbeadmin_<module>`.

## Публикация ревью в Pull Request

```bash
automation/scripts/pr-review-post.sh 1232 -R powbee/pbeadmin --input review.json --dry-run
automation/scripts/pr-review-post.sh 1232 -R powbee/pbeadmin --input review.json
```

Публикует ревью одним уведомлением автору: шапка плюс замечания, привязанные к строкам кода.
Формат входного файла — `{"body": "<шапка>", "comments": [{"path", "line", "side", "body"}]}`.

**Зачем обёртка, а не `gh api --method POST .../pulls/<N>/reviews`.** Этот эндпоинт умеет три
вещи: комментарий (`event=COMMENT`), approve и request-changes. Правила `permissions` в Claude
Code матчатся **по префиксу команды**, а `event` лежит в теле запроса — значит разрешить
комментарий и запретить вердикт через `settings.json` физически нельзя, префикс у них общий.
Обёртка разрывает узел тем, что `event` из входного файла **не читает вовсе**: проставляет
`COMMENT` сама и отклоняет файл, где это поле задано. Тот же приём, что `db-query.sh` вместо
голого `sqlcmd` — гарантию даёт код обёртки, а не список разрешений.

`--dry-run` печатает готовое тело и ничего не отправляет. Пользоваться им стоит всегда перед
первой публикацией: типовая ошибка — замечание на строке, которой нет в диффе, и GitHub
в этом случае отклоняет **весь** запрос, а не одно замечание.

Учётные данные для обоих скриптов — `gh auth login`, делает человек один раз на машину.

## Коды возврата

Одинаковые у обоих скриптов:

| Код | Значение |
|---|---|
| 0 | выгружен хотя бы один объект (частичные неудачи — в stderr) |
| 1 | не выгружено ничего |

## Чтение из MSSQL

`db-query.sh` — единственный разрешённый способ подключиться к боевой базе из-под
агента. Прямой `sqlcmd` закрыт deny-листом во всех проектах.

**Обёртка делает ровно одно: подставляет сервер, логин и пароль.** Флаги и SQL
пишет тот, кто вызывает, — это обычный `sqlcmd`.

```bash
./db-query.sh --profiles                                   # список клиентов
./db-query.sh --profile srv -Q "SELECT name FROM sys.databases ORDER BY name"
./db-query.sh --profile srv -d crmAdmin -Q "SELECT TOP 5 Id FROM consents.tPersonConsent"
./db-query.sh --profile srv -d crmAdmin -i sql/checks/mdlp-stock-diff.sql
```

Обёртке принадлежат только длинные флаги — `--profile`, `--profiles`, `--help`.
Короткие уходят в `sqlcmd` как есть: `-d`, `-Q`, `-i`, `-h`, `-W`, `-y`, `-s`.

### Зачем обёртка, если есть `sqlcmd`

Чтобы **пароль не попадал в контекст агента**. Собери агент команду сам — ему
пришлось бы прочитать пароль и написать его в `-P`, то есть отправить во внешний
сервис, в каждой сессии у каждого из четырнадцати человек. Здесь пароль читает
шелл из Keychain, модель его не видит ни разу.

Это единственная причина её существования. Всё остальное — не её работа.

### Чего обёртка не делает

Не проверяет текст запроса, не ограничивает выборку, не форматирует вывод,
не фильтрует персональные данные. Раньше делала — и это оказалось иллюзией
защиты: три собственных дефекта за один день обкатки, а реальные гарантии
всё равно живут не здесь.

**Гарантия «только чтение» — это права учётной записи, а не текст скрипта.**
Категория `AI Agent` — `db_datareader` и ничего кроме. Проверено на боевом
сервере: `UPDATE` не разрешён, `SELECT` разрешён, роль одна.

Проверять это надо регулярно, а не предполагать:

```bash
# под учётной записью DBA, не через обёртку
sqlcmd -S <сервер> -d DBAProvisioning -i ../../../pbe-dba/sql/provisioning/check-ai-agents.sql
```

Скрипт обходит все базы из списка провижининга и печатает отклонения — членство
в лишних ролях, права сверх `SELECT` / `VIEW DEFINITION` / `CONNECT`. Пустой
результат означает, что всё в порядке.

**Персональные данные технически не защищены.** Пока не сделан `DENY SELECT`
на ПД-колонки (долг И-11), от выгрузки ФИО удерживает только правило
в инструкциях команд.

### Профили — список клиентов

```
~/.config/pbe-mssql/common.env       PBE_MSSQL_USER=svc_ai_<фамилия>   учётка, одна на все контуры
~/.config/pbe-mssql/<мнемоника>.env  PBE_MSSQL_SERVER=pbesql03p        сервер клиента
                                     PBE_MSSQL_DB=<база>               необязательно: база по умолчанию
```

**Профиль называется мнемоникой клиента** — `vlt`, `srv`, `bay`, тестовый контур
с суффиксом `-qa` (`srv-qa`). Мнемоника та же, что в тегах Трекера и в консоли
(«Клиентская мнемоника и Теги» в
[регламенте очередей](../../docs/regulations/tracker-queues.md)), только строчными:
`--profile srv`, тег `SRV` и клиент в консоли — про одного клиента, а не про трёх.
Общая дев-среда клиентом не является и зовётся `dev`.

Учётные данные задаются один раз: логин в `common.env`, пароль в Keychain
(`pbe-mssql`). Добавить клиента — одна строка, а не ещё одна пара логин-пароль.
Профиль клиента при необходимости перекрывает общую учётку своей — так живёт
дата-инженерия, где под витрины заведены отдельные записи.

`PBE_MSSQL_DB` в профиле — умолчание, а не ограничение: заданный в вызове `-d`
всегда сильнее.

`--profile` обязателен и умолчания не имеет: серверов несколько, они выглядят
одинаково, и запрос, ушедший не в тот, возвращает чужие цифры — правдоподобные
и не те.

#### Завести профили на новой машине

Руками файлы не пишем — есть [`db-profiles-init.sh`](db-profiles-init.sh):

```bash
./db-profiles-init.sh --list                    # какие профили и серверы знает скрипт
./db-profiles-init.sh --dry-run                 # что сделает, ничего не трогая
./db-profiles-init.sh --user svc_ai_<фамилия>   # завести всё: common.env + профили клиентов
security add-generic-password -s pbe-mssql -a "$USER" -w '<пароль>'
```

**Прогонять можно сколько угодно раз.** Профиль с тем же сервером не
переписывается — только чинится `chmod 600`. Дублей не бывает: на клиента один
файл, имя файла и есть ключ. Прочие строки профиля (`PBE_MSSQL_DB`, своя
`PBE_MSSQL_USER`) сохраняются — правится ровно строка `PBE_MSSQL_SERVER`.

Если в файле стоит **другой** сервер, скрипт его не трогает: печатает
расхождение и выходит с кодом 1. Молча переписать нельзя — запрос уйдёт не в тот
контур. Прав скрипт — прогнать с `--force`; прав файл — поправить список
`PROFILES` в самом скрипте. Профили, которых в списке нет, скрипт не трогает
и перечисляет отдельно.

Список серверов живёт в скрипте, а не в этом README: одна копия, которую
исполняет машина, вместо двух, которые расходятся. Новый клиент — строка
в `PROFILES` и коммит.

### Платформы

Работает на macOS, Linux, WSL2 и в Git Bash. Нативно в Windows — нет.
Зависимости только базовые (`grep`, `sed`, `basename`, `date`); `python3`
и `jq` больше не нужны, поэтому Git Bash теперь тоже годится. `security`
(Keychain) — только macOS и опционально: на Linux пароль берётся из файла
профиля или `PBE_MSSQL_PASSWORD`.

Каждый вызов пишется в `logs/db-query.log` (вне git): кто, к какому серверу,
с какими аргументами. Пароль в журнал не попадает.

Настройка по шагам, смена пароля и разбор типовых ошибок — п. 2.6
[основ работы с Claude Code](../../docs/regulations/claude-code/osnovy.md).
Границы использования агентом — п. 4.5 там же.
