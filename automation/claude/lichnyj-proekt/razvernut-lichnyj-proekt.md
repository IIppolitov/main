# Развернуть личный рабочий проект

> **Это сообщение для агента, а не инструкция для человека.**
> Человеку достаточно открыть папку с комплектом в Claude Code и сказать:
> «Прочитай `razvernut-lichnyj-proekt.md` и сделай, что там написано».

Ты разворачиваешь человеку его личное рабочее пространство в Claude Code.

**Считай, что перед тобой не программист.** Скорее всего, это менеджер или руководитель:
он не знает, что такое git, не работал с терминалом и не обязан этому учиться. Твоя
задача — не «выполнить установку», а провести его по шагам так, чтобы в конце он понимал,
что у него получилось и как этим пользоваться.

---

## Как себя вести

1. **Иди по шагам и не забегай вперёд.** Закончил шаг — скажи одной строкой, что сделано,
   и переходи к следующему. Не вываливай весь план сразу.
2. **Объясняй простыми словами, зачем шаг нужен** — одно предложение, не лекция.
   Слова «репозиторий», «коммит», «токен» при первом появлении расшифровывай.
3. **Спрашивай по одному-два вопроса за раз.** Список из десяти вопросов человек
   не прочитает.
4. **Ничего не делаешь наружу без явного «да»:** не создаёшь аккаунты, не создаёшь
   репозиторий на GitHub, не публикуешь, не отправляешь. Внутри папки проекта работай
   свободно.
5. **Не выдумывай факты.** Не знаешь имя, должность, адрес — спроси или оставь
   `TODO: уточнить`. Придуманная фамилия в `CLAUDE.md` будет всплывать месяцами.
6. **Язык — русский**, документы деловые, без воды.
7. Что-то не получается (нет `git`, нет прав, не отвечает API) — **скажи прямо, что
   именно не вышло и что делать**, а не продолжай молча.

## Шаг 1. Познакомиться

Без этого шага проект бессмыслен: всё содержимое `CLAUDE.md` берётся отсюда.
Спрашивай по два вопроса, своими словами, и **записывай ответы** — они понадобятся
на шаге 5.

1. Как зовут, должность, рабочая почта. Кому подчиняешься, кто подчиняется тебе.
2. Чем занимается твоё подразделение — двумя-тремя предложениями, как объяснил бы
   новому коллеге.
3. С кем работаешь чаще всего: люди, отделы, подрядчики, клиенты.
4. Какие системы и инструменты используешь каждый день (Трекер, Вики, почта,
   мессенджер, консоль, что-то ещё).
5. Какие очереди Трекера твои, по каким задачам к тебе приходят.
6. Что отнимает больше всего времени и что из этого хотелось бы делать с агентом:
   письма, разбор задач, сводки, документы, заметки.
7. Как ты пишешь письма и сообщения: длинно или коротко, на «ты» или на «вы»,
   что выделяешь, чего не пишешь никогда. Попроси показать одно-два своих недавних
   письма — из них стиль виден лучше, чем из описания.
8. Чего агент делать **не** должен: темы, документы, действия.

Если человек отвечает «не знаю» или «потом» — не дави. Ставь `TODO: уточнить`
и иди дальше, это дописывается за неделю работы.

## Шаг 2. Проверить, что есть на машине

Проверь и скажи человеку результат простым списком «есть / нет»:

```bash
git --version          # журнал изменений, нужен
python3 --version      # нужен утилитам из комплекта (3.9 и новее)
gh --version           # клиент GitHub, нужен для копии проекта на GitHub
```

Чего нет — предложи поставить и дай готовую команду (`brew install git gh` на macOS).
Ставит человек, ты не устанавливаешь ничего без «да».

Отдельно скажи, что VPN должен быть включён — без него Claude Code не работает, — а Трекер
и Вики, наоборот, ходят мимо туннеля.

## Шаг 3. Ликбез: git и GitHub

**Не пропускай этот шаг и не заменяй его ссылкой.** Человек должен понимать, что
происходит с его файлами. Объясни коротко, своими словами, примерно это:

- **git** — журнал изменений для папки. Он запоминает, как файлы выглядели в каждый
  момент, и позволяет вернуться к любому из них. Живёт прямо в папке проекта.
- **коммит** — сохранённая точка: «вот так файлы выглядели, и вот почему». Делаешь их ты,
  человеку достаточно сказать «сохрани».
- **GitHub** — сайт, где лежит копия папки. Нужен на случай «сломался ноутбук» и чтобы
  открыть проект на другой машине.
- **пуш** — отправить сохранённые точки в эту копию.
- **приватный репозиторий** — копия, которую видит только он.

Скажи прямо: **всё это делаешь ты, от человека требуется понимать четыре слова,
а не уметь ими пользоваться.**

### Аккаунт GitHub

Спроси, есть ли у него аккаунт GitHub.

**Нет** — проведи по шагам, но регистрацию человек делает сам, своими руками:

1. Открыть `https://github.com/signup`.
2. Зарегистрироваться **на рабочую почту** — ту, на которой рабочая переписка.
3. Подтвердить почту, включить двухфакторную аутентификацию (GitHub попросит сам —
   это не опция, а требование сайта).
4. Вернуться и сказать тебе логин.

**Есть** — проверь, что клиент авторизован:

```bash
gh auth status
```

Не авторизован — дай команду `gh auth login` и скажи, что выполняет её **человек**:
это его учётная запись и его права. Сам `gh auth login` не запускай.

Отдельно предупреди: репозиторий будет **приватным**, и рабочие записи в публичном
репозитории — это утечка.

## Шаг 4. Создать структуру

Работай в **текущей папке** — той, из которой запущен Claude Code. Если в ней уже есть
`CLAUDE.md` или каталог `.claude/`, остановись и спроси, что делать: возможно, проект
уже разворачивали.

```
CLAUDE.md              контекст: кто владелец, чем занимается, правила работы
docs/                  документы, которые ведём
  company/             люди, роли, контакты, кто за что отвечает
  notes/               рабочие записи, разборы, конспекты
  templates/           шаблоны: письмо, служебка, протокол встречи
  backlog.md           единый список открытых вопросов
reports/               черновики и выгрузки, по папке на день (вне git)
  README.md
automation/scripts/    утилиты: Трекер, Вики, письма
.claude/
  commands/            свои команды, вызываются через /
  settings.json        что тебе разрешено без вопросов, что только с подтверждения
.gitignore
```

Две вещи объясни человеку сразу, иначе они выглядят произволом:

- **`reports/` — папка на день** (`reports/2026-09-14/pismo-valenta.md`). Дата в имени
  папки, в имени файла её нет: одно и то же имя в разных днях и есть история.
- **`reports/` не попадает в git.** Там черновики и выгрузки — сырьё, которое устаревает
  за дни и может содержать клиентские данные. То, что надо сохранить, переносится
  в `docs/`.

Положи в `reports/README.md` две строки про это же правило.

## Шаг 5. Написать `CLAUDE.md`

Главный файл. Он читается **в каждой сессии автоматически**, поэтому пишется коротко
и по делу: чем он длиннее, тем хуже работает.

Собери его из ответов шага 1 по такой структуре:

```markdown
# Рабочее пространство <должность>

Личный рабочий проект <имя>. Claude здесь работает как персональный ассистент:
<что именно делает — из ответов>.

## Кто я
Должность, подразделение, кому подчиняюсь, кто подчиняется мне, зона ответственности.
Отдельно — что **вне** моей зоны и к кому с этим идти.

## Компания и продукт
Три-четыре предложения: чем занимается компания, кто клиенты, как называется продукт.

## С кем работаю
Люди и отделы, с которыми чаще всего пересекаюсь, — с ролями, а не только с именами.

## Инструменты
Трекер (какие очереди мои), Вики (какие разделы), консоль, почта, мессенджер.

## Как я пишу
Стиль писем и сообщений: длина, тон, что выделяю, чего не пишу никогда.
Письма — всегда в двух форматах: .md для вычитки и .rtf для вставки в почту.

## Правила работы для Claude
- Язык — русский, документы деловые, без воды.
- Не выдумывать факты: не хватает вводных — спросить или оставить `TODO: уточнить`.
- Никаких секретов в репозитории: пароли, токены, строки подключения — только
  в парольном менеджере, в документах — плейсхолдеры.
- Персональных данных клиентов и врачей в проекте нет.
- Запись наружу — в Трекер, в Вики, в мессенджер — только с моего явного «да»,
  после показа черновика.
- Черновики и отчёты — в папку сегодняшнего дня в `reports/`.
- Перед созданием документа проверить, нет ли похожего: обновить, а не плодить дубли.
```

Написал — **покажи файл целиком и попроси поправить**. Это его контекст, а не твой;
спорную формулировку правит он, а не ты.

Заодно заведи `docs/company/` с тем, что он рассказал про людей, и `docs/backlog.md`
с открытыми вопросами (туда же — все `TODO: уточнить`, которые накопились).

## Шаг 6. Разложить утилиты и команды

Из комплекта, который лежит рядом с этим файлом:

| Откуда | Куда | Что это |
|---|---|---|
| `scripts/tracker-issue.sh` | `automation/scripts/` | прочитать задачу Трекера целиком |
| `scripts/tracker-create.py` | `automation/scripts/` | **создать** задачу |
| `scripts/tracker-update.py` | `automation/scripts/` | **написать** комментарий, поправить поля |
| `scripts/wiki-page.sh` | `automation/scripts/` | прочитать страницу Вики |
| `scripts/wiki2md.py` | `automation/scripts/` | перевести разметку Вики в markdown |
| `scripts/wiki-push.py` | `automation/scripts/` | **опубликовать** страницу обратно в Вики |
| `scripts/md2rtf.py` | `automation/scripts/` | собрать письмо для вставки в почту |
| `scripts/check-links.py` | `automation/scripts/` | проверить ссылки между документами |
| `commands/*.md` | `.claude/commands/` | команды `/pbe-issue`, `/pbe-wiki`, `/pbe-draft`, `/pbe-note` |
| `settings.json` | `.claude/settings.json` | разрешения: что можно без вопросов, что с подтверждения |

После копирования — `chmod +x automation/scripts/*.sh automation/scripts/*.py`.

Объясни человеку разницу, она важнее, чем кажется: **три скрипта пишут наружу**
(`tracker-create.py`, `tracker-update.py`, `wiki-push.py`). У всех трёх по умолчанию
сухой прогон — без флага `--apply` они только показывают, что было бы отправлено.
В `settings.json` они стоят «с подтверждения»: перед запуском появится вопрос.
Этот порядок не меняем.

**Скрипты ведутся в рабочем пространстве директора департамента ИТ.** Копия здесь —
именно копия: если что-то не работает или нужна доработка, это задача в очередь `CRM`,
а не правка файла у себя. Иначе через полгода у пяти человек пять разных версий.

## Шаг 7. Проверить доступ к Трекеру и Вики

Утилиты ходят в Трекер и Вики **от имени человека и с его правами**. Нужны два значения
(третье — для заметок в консоли):

| Что | Где взять |
|---|---|
| OAuth-токен Трекера | на странице `https://console.powbeecrm.com/tracker` — там ссылка на выдачу и поле, куда его сохранить |
| ID организации | у директора департамента информационных технологий |
| Токен консоли | там же, нужен для заметок и напоминаний |

Проверь, есть ли они уже:

```bash
security find-generic-password -s yandex-tracker -w >/dev/null 2>&1 && echo "токен есть" || echo "токена нет"
```

Нет — дай человеку команды и скажи, что **токен вводит он сам**, а ты его не видишь
и не записываешь:

```bash
security add-generic-password -s yandex-tracker     -a "$USER" -w '<OAuth-токен>'
security add-generic-password -s yandex-tracker-org -a "$USER" -w '<ID организации>'
security add-generic-password -s pbe-console        -a "$USER" -w '<токен консоли>'
```

Имена сервисов (`-s`) менять нельзя — скрипты ищут ровно эти. На Linux вместо Keychain
файлы `~/.config/yandex-tracker/env` и `~/.config/pbe-console/env` с `chmod 600`.

Проверка боем — попроси у человека ключ любой его задачи и выгрузи её:

```bash
automation/scripts/tracker-issue.sh <ключ>
```

Вернулась задача — доступ есть. Вернулось «нет доступа» — разбирайся с токеном,
а не иди дальше: без этого половина команд бесполезна.

**Токены не печатай в вывод, не пиши в файлы, не коммить.**

## Шаг 8. Взять папку под git

```bash
git init
git branch -M main
```

`.gitignore` — минимум:

```
reports/*
!reports/README.md
.env
.claude/settings.local.json
.DS_Store
```

Перед первым коммитом **проверь глазами**, что в него не попадают токены, пароли
и персональные данные: `git status`, затем `git diff --staged`. Файлы перечисляй явно,
`git add -A` не используй.

```bash
git add CLAUDE.md docs .claude automation reports/README.md .gitignore
git commit -m "Личный рабочий проект: структура, контекст, утилиты"
```

Скажи человеку одной фразой, что только что произошло: «первая сохранённая точка
сделана, теперь любую правку можно откатить».

## Шаг 9. Копия на GitHub

**Только с явного «да».** Спроси, нужна ли копия (ответ почти всегда «да» — это
единственная защита от потери ноутбука), и объясни, что репозиторий будет приватным.

```bash
gh repo create <имя> --private --source=. --remote=origin
git push -u origin main
```

Имя предложи короткое и понятное: `moj-proekt`, `rabochee-prostranstvo`.

После пуша **проверь и скажи вслух, что репозиторий приватный** (`gh repo view --json visibility`).
Это то место, где ошибка дороже всего.

Если человек отказался — ничего не создавай, но скажи, что без копии проект живёт
только на этом ноутбуке, и предложи вернуться к этому позже.

## Шаг 10. Показать, что получилось

Заверши коротким разбором — это последнее, что человек прочитает, поэтому без воды:

1. **Что теперь есть** — четыре-пять строк: контекст, свои команды, утилиты Трекера
   и Вики, история изменений, копия на GitHub.
2. **Как начать работу** — открыть эту папку в VS Code (или зайти в неё в терминале)
   и запустить Claude Code. Запускать надо **из папки проекта**, иначе контекст
   не подхватится.
3. **Какие команды есть** — по одной строке на каждую:
   - `/pbe-issue <ключ>` — прочитать и разобрать задачу Трекера, ответить в неё;
   - `/pbe-wiki <ссылка>` — прочитать страницу Вики, забрать себе, опубликовать правку;
   - `/pbe-draft <кому и о чём>` — черновик письма или сообщения;
   - `/pbe-note <что и когда>` — напоминание в консоли.
4. **Три правила**, которые он должен унести:
   - персональные данные врачей и сотрудников клиентов, пароли и токены в проект
     не кладутся;
   - наружу — в Трекер, в Вики, в почту — уходит только то, что он подтвердил;
   - отвечает за отправленное он, а не агент: цифры и формулировки проверяются глазами.
5. **Что делать дальше** — рассказывать про свою работу по ходу дела: каждый такой
   рассказ, попавший в `docs/`, делает следующий ответ точнее.

Предложи сразу попробовать одну команду на реальной задаче — так это запоминается
лучше любого рассказа.

## Чего не делать ни при каких условиях

- Не создавать аккаунты и не авторизовываться за человека (`gh auth login`,
  регистрация на GitHub — только его руками).
- Не создавать публичный репозиторий. Только `--private`.
- Не коммитить токены, пароли, `.env` и персональные данные. Сомневаешься — не коммить
  и спроси.
- Не отправлять ничего наружу без явного «да»: ни комментарий в задачу, ни страницу
  в Вики, ни письмо.
- Не переписывать существующие файлы человека молча. Есть файл — покажи, спроси,
  потом правь.
- Не выдумывать имена, должности, сроки и адреса. `TODO: уточнить` лучше правдоподобной
  выдумки.
