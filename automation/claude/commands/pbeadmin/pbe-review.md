Проведи ревью кода по задаче из Яндекс Трекера: **$ARGUMENTS**

> Это **ревью, а не разработка**. Код не правишь, файлы не создаёшь, ветки не заводишь —
> даже если дефект очевиден и фикс в одну строку. Вывод — замечания и вердикт.
> К исправлению переходить только с флагом `--fix` или по отдельной просьбе — и только
> на своём PR (шаг 8).
>
> Формальный вердикт по PR (approve / request-changes), мердж и закрытие ставит **человек**.
> Тебе доступен ровно один вид записи в GitHub — ревью-комментарий, и публикуешь ты его
> только по явному согласию пользователя (шаг 7).

## 1. Выгрузи задачу

```
bash .claude/scripts/tracker-issue.sh $ARGUMENTS --attach-dir <твой scratchpad>/tracker
```

**Аргументы передавай как есть, без кавычек** — там может быть несколько ключей и флаги.
Флаги `--post` и `--fix` (шаги 7 и 8) в скрипт **не передавай**: это твои флаги, не его.

Читай так же, как в `/pbe-task`: описание, кастомные поля очереди, комментарии целиком,
вложения через **Read** (в постановках это макеты и таблицы полей — именно по ним потом
сверяется реализация). Ссылки на Вики выгружай через `.claude/scripts/wiki-page.sh`.

Ключевые поля именно для ревью:

- **`linksToPullRequests`** — основной источник ссылок на PR (см. шаг 2);
- **`testPlan`** — готовый чек-лист приёмки, по нему строится матрица в шаге 6;
- **`externalChanges`** — что обещано клиенту. Ревью проверяет реализацию против **этого**,
  а не против того, что удобно было написать;
- **`releaseActions`** — если там значатся действия на сервере (поставить бинарник, прописать
  env), проверь в шаге 5, что код без них деградирует **понятно**, а не молчаливой 500-кой.

Задача не выгрузилась (маркер `‼️ KEY`) — скажи об этом и разбирай то, что есть. Нет токена
(код 3) — покажи инструкцию скрипта и остановись.

## 2. Найди PR

PR может быть где угодно, поэтому ищи по всем источникам, а не по первому сработавшему.

**Источник 1 — поле задачи.** В очереди CRM ссылки лежат в кастомном поле вида
`<id>--linksToPullRequests`. Там **часто больше одной ссылки** — и это самое важное, что даёт
этот шаг (см. ниже про парные PR).

**Источник 2 — описание и комментарии.** Разработчики кидают ссылку репликой в обсуждение.
Греп по выводу скрипта: `github.com/powbee/`.

**Источник 3 — поиск по ветке.** Ссылок нет или они устарели — ищи по ключу задачи, ветки
называют по нему:

```
gh pr list -R powbee/pbeadmin --search "CRM-1641" --state all
gh pr list -R powbee/pbeadmin_<module> --search "CRM-1641" --state all
```

### ⚠️ Проверь ОБА репозитория — ядро и модуль

Каждый модуль — **отдельный репозиторий** `powbee/pbeadmin_<module>` (строчными:
`modules/ContentFactory` → `powbee/pbeadmin_content_factory`). Одна задача сплошь и рядом
разъезжается на **два PR**: функционал в модуле, а проводка в ядре — зависимость в
`composer.json`, сьют в `phpunit.xml`, `autoload-dev`, роут, хук, конфиг.

**Ревью одного PR из пары бессмысленно и даёт ложный вердикт.** Модульный PR, которому нужна
новая библиотека, без ядрового просто фаталит на проде, а его собственные контрактные тесты
падают — и ни то, ни другое в диффе модуля не видно. Нашёл PR в модуле — **обязательно**
проверь, нет ли парного в ядре, и наоборот. Нашёл только один и уверен, что второй не нужен, —
напиши в отчёте, почему уверен.

`gh`-команды из корня ядра по умолчанию уходят в `powbee/pbeadmin` — для модуля **всегда**
указывай `-R powbee/pbeadmin_<module>` явно, иначе молча получишь не тот репозиторий.

### Что вытащить по каждому найденному PR

```
gh pr view <N> -R <repo> --json number,title,author,state,baseRefName,headRefName,body,additions,deletions,changedFiles,commits
gh pr diff <N> -R <repo>
```

- **head SHA последнего коммита** — понадобится для публикации замечаний (шаг 7);
- **база PR** — в этом проекте целевая ветка `main`, не `master`. PR в `master` или
  в чужую фича-ветку — это находка сама по себе, а не деталь;
- **автор PR** — от него зависит, чем ревью закончится: замечаниями или правками (шаг 8).

**Уже существующие замечания** — чтобы не дублировать чужую работу и не постить второе ревью
поверх своего же:

```
bash .claude/scripts/pr-comments.sh <N> -R powbee/pbeadmin_<module>
bash .claude/scripts/pr-comments.sh https://github.com/powbee/pbeadmin/pull/1232
```

Скрипт забирает **все три сорта** комментариев и печатает шапку PR (включая head SHA для шага 7),
инлайновые замечания тредами, тела ревью и ленту обсуждения. Пользуйся им, а не `gh pr view
--comments`: тот показывает только ленту, а инлайновые замечания на строках — то есть
содержательную часть любого ревью — молча теряет. Пагинация в скрипте тоже учтена, иначе
видно лишь первые 30 записей и обрыв ничем не обозначен.

⚠️ Если всё-таки идёшь в `gh api` руками — **всегда передавай метод явно: `gh api --method GET`.**
Без него `gh api` с любым `-f`/`-F` молча уходит в POST, то есть форма, которая читается
как чтение, окажется записью.

### Подтяни ветку локально

Дифф из `gh` показывает изменения, но не даёт прочитать файл целиком и соседний код:

```
cd modules/<Module> && git fetch origin <headRefName>     # для модульного PR
git fetch origin <headRefName>                            # для ядрового
git show origin/<headRefName>:<путь>                      # читать файлы ветки
```

Ветку **не переключай** (`checkout`/`switch` в чужую ветку запрещены и не нужны) — читай
через `git show origin/<branch>:<file>`. Для новых файлов удобно выгрузить их в scratchpad
и оттуда же прогнать `php -l`.

## 3. Вычитай бизнес-логику ДО чтения кода

Это то, чем `/pbe-review` отличается от обычного `/code-review`: тот проверяет код сам по
себе, а здесь есть постановка, и главный вопрос — **сделано ли то, что заказано**.

Выпиши до похода в дифф:

- **Критерии приёмки** — из описания, `testPlan`, `externalChanges`, из спеки в Вики.
  Нумеруй: по ним строится матрица в шаге 6;
- **Ожидаемое поведение и его источник.** Регламент из Вики и реплика в комментарии — источники
  разного веса; комментарии часто отменяют исходное описание, тогда рабочей считается более
  свежая версия, и это надо назвать явно;
- **Чей это контур.** Админка (наш репозиторий), приложение `pbeapp` (чужой), интеграция.
  Требование не к нашему коду — так и скажи, не ищи его в диффе;
- **Клиент и его конфиги.** Поведение расходится по значениям `pbe`-конфигов, а не по коду:
  `bash .claude/scripts/client-env.sh <мнемоника> --config <ключ>`. Фича за флагом, которого
  у клиента нет, «работает» только в теории — это находка;
- **Что осталось за скоупом сознательно** — чтобы не выкатить это как дефект.

**Выведи этот блок пользователю первым, до замечаний.** Пользователь должен успеть поправить
понимание требований до того, как ты полчаса меряешь код не той линейкой.

## 4. Прочитай код, а не только дифф

Дифф показывает изменение, но не показывает, во что оно попало. Почти каждая существенная
находка в этом проекте берётся из соседнего кода, которого в диффе нет.

- **Открывай изменённые файлы целиком** и вызываемые методы тоже. Проверка вида
  `Content::canView()` может оказаться грубым флотским правом, а не проверкой доступа
  к конкретной записи — из диффа это не видно никак;
- **Ядро или модуль.** Доменный функционал — `modules/<Module>/App/...`, общий — `app/`.
  Симптом в модуле может идти от ядрового сервиса и наоборот;
- **Схема БД — MSSQL, database-first.** Именованные схемы, `schema.tPascalCase`, колонки
  PascalCase, soft-delete `DeleteDate`. Не предполагай Laravel-конвенций — смотри миграцию
  и модель. Новые сущности — паттерн «Fields»;
- **Маршруты и middleware.** Новый роут — проверь группу (`auth`?), `external.php`/`hook.php`
  вообще отдельный разговор (шаг 5), порядок объявления и биндинг моделей;
- **Проводка новых зависимостей.** Появился `use` внешней библиотеки — проверь, что она
  реально объявлена (`composer.json` **и** `composer.lock`, `ls vendor/<vendor>`). Появились
  тесты в `modules/<M>/tests/` — проверь, что каталог включён в `phpunit.xml` и, по принятому
  в репозитории порядку, в `autoload-dev`. Тест, который не запускается, не тест;
- **Прогони проверки, а не верь диффу**: `php -l` по изменённым файлам; там, где можно,
  `vendor/bin/phpunit --testsuite Unit`. Если прогнать нельзя (нет зависимостей, нужна dev-БД) —
  так и напиши, это часть отчёта.

## 5. Гейты

Чеклист ревью и триггеры аудита — в [.claude/agents/reviewer.md](.claude/agents/reviewer.md)
и [.claude/agents/security.md](.claude/agents/security.md); используй их как список того,
что нельзя не посмотреть.

**Безопасность обязательна**, если PR трогает: маршруты (всегда для `external.php`/`hook.php`),
auth/SSO/JWT, raw SQL, загрузку файлов, запуск внешних процессов, интеграции, выдачу PII/PHI.
Вердикт бинарный: **PASS** (блокеров нет) или **FAIL** (есть 🔴). 🟡 HIGH по PII/PHI или auth
приравнивается к 🔴.

Отдельно смотри **эксплуатацию** — она чаще всего и не описана в PR:

- нужны ли новые бинарники/пакеты на серверах и что будет, если их нет;
- нужны ли новые env-переменные и попали ли они в `.env.example`;
- **порядок выкатки**, если PR парный: что катится первым и что сломается при обратном порядке;
- миграция или правка данных — отдельной строкой, это меняет процедуру релиза.

Находки, которые ты нашёл рядом, но которые к этому PR не относятся, **выноси отдельным
блоком «вне скоупа PR»** и предлагай завести тикетом. Не смешивай их с замечаниями по диффу:
автор PR за них не отвечает, и требовать их починки в этом ревью нечестно.

## 6. Отчитайся в терминал — до всякой публикации

1. **Вердикт**: `ПРИНЯТО` / `ПРИНЯТО С ПРАВКАМИ` / `ОТКЛОНЕНО`, одной строкой с причиной.
   Помни, что формально его в GitHub ставит человек — ты даёшь оценку, не approve;
2. **Найденные PR** — все, с ролью каждого («функционал», «проводка в ядре») и порядком выкатки;
3. **Что хорошо** — коротко и по делу. Ревью, состоящее только из претензий, читают хуже,
   и автор теряет сигнал о том, что не надо переделывать;
4. **Замечания по severity** (🔴 блокер / 🟠 надо починить / 🟡 стоит починить), каждое:
   файл и строки кликабельной ссылкой, механизм отказа (конкретный вход → конкретный
   неверный результат), предложение фикса. Без «стоит подумать» — либо дефект, либо не пиши;
5. **Матрица приёмки**: каждый критерий из шага 3 → чем подтверждён (автотест `<Test::method>` /
   ручная проверка с результатом / «не проверен» с причиной). Зелёный phpunit сам по себе
   не означает выполнения постановки — непокрытые критерии называй явно;
6. **Эксплуатация и релиз** — из шага 5;
7. **Вне скоупа PR** — если нашлось.

Не дошёл до вывода по какому-то куску — скажи прямо, что не проверял и почему.
Правдоподобная догадка в ревью хуже честного пробела: по ней начнут переделывать код.

## 7. Публикация в GitHub — только по явному согласию

**По умолчанию ничего не публикуй.** Отчёт в терминал — законченный результат этой команды.
Публикуй, если пользователь передал флаг `--post` или попросил словами после отчёта.
Молчание согласием не считается.

Формат — **одно ревью**: общая шапка плюс замечания, привязанные к строкам, одним
уведомлением автору. Публикуется обёрткой:

```
bash .claude/scripts/pr-review-post.sh <N> -R <repo> --input <scratchpad>/review.json
bash .claude/scripts/pr-review-post.sh <N> -R <repo> --input <scratchpad>/review.json --dry-run
```

Тело собирай файлом (руками такой JSON не написать — используй скрипт-генератор, чтобы
не воевать с экранированием переводов строк и кавычек):

```json
{
  "body": "<шапка: вердикт, что хорошо, эксплуатация, безопасность>",
  "comments": [
    {"path": "App/Services/X.php", "line": 458, "start_line": 442,
     "side": "RIGHT", "start_side": "RIGHT", "body": "<замечание>"}
  ]
}
```

Что здесь важно:

- **Поля `event` в файле быть не должно.** Обёртка ставит `event=COMMENT` сама и отказывается
  работать, если поле задано снаружи. Так и задумано: тот же эндпоинт `/pulls/<N>/reviews`
  умеет approve и request-changes, а permissions различают вызовы только по префиксу команды —
  то есть никак. Гарантию даёт обёртка, а не список разрешений. Не обходи её сырым
  `gh api --method POST .../reviews`;
- **`commit_id` не нужен** — обёртка берёт head SHA у самого PR. Флаг `--commit` есть на случай,
  когда ревью делалось по конкретному коммиту, а автор с тех пор дописал;
- **`line` должен попадать в дифф.** Для нового файла годится любая строка, для изменённого —
  только добавленные или контекстные строки внутри ханка. Промахнулся — GitHub отклонит
  весь запрос целиком, а не одно замечание. Перед публикацией прогони `--dry-run` и сверь
  строки с `gh pr diff <N> -R <repo>`;
- **проверь результат**: `bash .claude/scripts/pr-comments.sh <N> -R <repo>` — все ли замечания
  легли на нужные строки;
- **парные PR — два ревью**, каждое в свой репозиторий. Замечание по ядру в модульном PR
  автор не увидит;
- **не публикуй второй раз то же самое.** Перед отправкой перечитай существующие замечания
  (шаг 2): если твоё ревью уже висит, отправляй только новое, ответом в нужный тред
  (`gh api --method POST .../pulls/<N>/comments` с `in_reply_to`).

🚫 Чего не делаешь никогда: `gh pr review` (approve / request-changes), `gh pr merge`,
`gh pr edit|close|ready`, `event=APPROVE`, `event=REQUEST_CHANGES`. Ставит человек.

## 8. Два выхода: замечания или правки

У ревью есть ровно два продолжения, и **выбор между ними определяется авторством PR**,
а не тем, насколько находки очевидны.

### Чужой PR (автор — не пользователь) → только замечания

Дефолт. Ветка PR — это работа другого разработчика в другом репозитории, и он с ней
одновременно работает. Молча править её нельзя даже с лучшими намерениями: пушить мы всё равно
не умеем, значит правки лягут локальными коммитами, которые разъедутся с тем, что автор в это
же время делает у себя. Получится конфликт, который разбирать дороже, чем починить по замечанию.

Здесь работа заканчивается отчётом и, по согласию, публикацией (шаг 7). Даже однострочный фикс —
это замечание с готовым куском кода в теле, а не коммит.

### Свой PR (автор — пользователь) → можно править

Тогда правки уместны, и порядок такой:

1. **Ветка от head PR**, не от `main` — точку отсчёта указывай явно, иначе `git switch -c`
   отведёт от текущей ветки, то есть чаще всего от `main`:

   ```
   git fetch origin <headRefName>
   git switch -c <TICKET>-fixes origin/<headRefName>
   ```

   В нужном репозитории (для модуля — внутри сабмодуля). В саму ветку PR не коммить:
   она уже на remote, а пушить мы не можем, и локальное расхождение с ней ничем хорошим
   не кончится;
2. **Правит профильный агент** — тот, что писал бы этот код: `backend` (сервисы, контроллеры,
   Jobs), `frontend` (blade/JS/Vue), `database` (**любые** миграции и структура моделей).
   Передавай ему находку целиком: файл, строки, механизм отказа и предложенный фикс — субагент
   не видит диалог;
3. **`qa`** — тесты на критерии, которые в матрице приёмки помечены как непокрытые;
4. **Повторный гейт** `reviewer` (+ `security` по триггерам), если правились 🔴-находки;
5. **Пуш и обновление PR — человек.** Ты заканчиваешь коммитами в локальной ветке, списком
   того, что в них лежит, и **готовой командой пуша**:

   ```
   git push -u origin <TICKET>-fixes
   ```

   Строку приводи для каждого затронутого репозитория отдельно — ядро и модуль пушатся
   по одному.

### Обе ветки сразу — нормально

Опубликовать замечания и починить их же — не противоречие, а хороший тон на своём PR:
комментарии остаются как объяснение, почему код изменился, и ревьюер видит логику, а не
только дифф. Если публикуешь и правишь, публикуй **до** правок — иначе замечания будут
указывать на строки, которых в ветке уже нет.

### Чего не делаем ни в каком случае

Не правим то, что не относится к находкам этого ревью, — «раз уж открыл файл». Всё, что нашлось
рядом, идёт в блок «вне скоупа PR» отдельным тикетом. Расширение диффа чужой задачи ломает
и ревью, и матрицу приёмки.
