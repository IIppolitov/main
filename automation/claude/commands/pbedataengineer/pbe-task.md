# Разбор задачи: $ARGUMENTS

Команда **только читает**: не правит SQL, не трогает Superset, не создаёт файлов
кроме папки задачи с разбором. Её цель — понять, что просят и где смотреть,
до того как потрачен день на запрос не к тем данным.

## Шаг 1. Собрать материал

```bash
.claude/scripts/tracker-issue.sh $ARGUMENTS
```

Несколько ключей — это **один** разбор: типовой случай, когда тикет
`SUPPORTANALYTIC` («цифра не бьётся») и запрос `ANALYTIC` («поправьте дэшборд»)
описывают одну проблему с разных сторон. Расхождения между задачами вынеси
отдельным блоком и скажи, какую версию взял за рабочую.

Есть ссылка на Вики — выгрузи страницу (`wiki-page.sh`) и перечисли, что
прочитал. Молча пропущенная ссылка — разбор по неполным требованиям.

Скриншоты из тикета открывай: в задачах «цифра не бьётся» половина информации
именно там — какой фильтр стоял, какой период, какое значение видит клиент.

## Шаг 2. Определить клиента и его контур

Клиент определяется по домену админки, тегу задачи, мнемонике в теме.
Дальше — конфиги:

```bash
.claude/scripts/client-env.sh --resolve <домен или имя>
.claude/scripts/client-env.sh <мнемоника> --config BI
```

Зафиксируй: клиент, мнемоника, инстанс (prod / dev), какие BI-ключи включены.
Дэшборд показывается через админку — часть симптомов «пусто» и «не то»
объясняется настройкой клиента, а не датасетом.

## Шаг 3. Понять тип задачи

От типа зависит всё дальнейшее:

| Тип | Признак | Куда смотреть первым делом |
|---|---|---|
| Расхождение в цифрах | «не бьётся», «задвоение», «пусто в фильтре» | сверочный запрос к источнику, границы периода, дубли в join |
| Новый дэшборд или график | «сделайте дэшборд по …» | какие метрики, какая гранулярность, кто увидит (RLS) |
| Витрина и загрузка | «добавьте поле», «обновите витрину» | регламент загрузки, зависимости, что сломается ниже по потоку |
| Разовая выгрузка | «пришлите список …» | что именно, в каком разрезе, кому уходит (ПДн!) |
| Правка данных в PROD | «перевесьте согласие», «верните статус» | **делает человек руками**; агент готовит запрос и оценку охвата |

## Шаг 4. Сверка понимания — главный результат

Выведи блок, который человек читает **до** всего остального:

```
СВЕРКА ПОНИМАНИЯ
Прочитано: <задачи, страницы Вики, скриншоты>
Клиент: <имя, мнемоника, инстанс>
Тип задачи: <из таблицы выше>
Как понял проблему: <2–4 предложения на языке данных, а не на языке тикета>
Что проверю и чем: <запросы, источники, ожидаемый признак «сошлось»>
В чём не уверен: <явно>
Открытые вопросы: <каждый — с адресатом>
```

Дальше — план: какие запросы прогнать, к каким таблицам, что считать
доказательством. Запросы на этом шаге **не выполняются**: сначала человек
подтверждает, что копаем в ту сторону.

## Шаг 5. Завести папку задачи

`tasks/<КЛЮЧ>/` — туда кладётся разбор (`analysis.md`), туда же потом лягут
рабочие запросы и заметки. Раскладка — [tasks/README.md](../../tasks/README.md).

Боевых данных в папке быть не должно: результаты запросов идут в `out/`,
в разбор — только агрегаты и выводы.
