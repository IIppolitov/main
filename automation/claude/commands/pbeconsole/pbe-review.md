Проведи ревью кода по задаче из Яндекс Трекера: **$ARGUMENTS**

> Это **ревью, а не разработка**. Код не правишь, файлы не создаёшь, ветки не заводишь —
> даже если дефект очевиден и фикс в одну строку. Вывод — замечания и вердикт.
> К исправлению переходить только с флагом `--fix` или по отдельной просьбе (шаг 8).
>
> Формальный вердикт по PR (approve / request-changes), мердж и закрытие ставит **человек**.
> Тебе доступен ровно один вид записи в GitHub — ревью-комментарий, и публикуешь ты его
> только по явному согласию пользователя (шаг 7).

⚠️ **Особенность этого проекта: разработчик здесь один** — владелец продукта, он же
пользователь. Значит ветка «свой PR» из шага 8 будет срабатывать почти всегда, а «чужой PR»
почти никогда. Это не повод пропускать проверку авторства: ревью собственного кода тем
и ценно, что находит то, что автор уже перестал видеть. Сначала отчёт, потом правки —
порядок не меняется.

## 1. Выгрузи задачу

```
bash .claude/scripts/tracker-issue.sh $ARGUMENTS --attach-dir <твой scratchpad>/tracker
```

**Аргументы передавай как есть, без кавычек.** Флаги `--post` и `--fix` (шаги 7 и 8)
в скрипт **не передавай**: это твои флаги, не его.

Читай описание, комментарии целиком, вложения через **Read**. Ссылки на Вики выгружай
через `.claude/scripts/wiki-page.sh`. Основная очередь проекта — `CONSOLE`.

Задача не выгрузилась (маркер `‼️ KEY`) — скажи об этом и разбирай то, что есть. Нет токена
(код 3) — покажи инструкцию скрипта и остановись.

## 2. Найди PR

Репозиторий один — `powbee/pbeconsole`, сабмодулей здесь нет.

```
gh pr list -R powbee/pbeconsole --search "CONSOLE-42" --state all
gh pr view <N> --json number,title,author,state,baseRefName,headRefName,body,additions,deletions,changedFiles,commits
gh pr diff <N>
```

Если ссылки на PR нет ни в задаче, ни в комментариях — ищи по ключу задачи, ветки называют
по нему. Из корня репозитория `gh` сам определит проект, `-R` можно не указывать.

- **head SHA последнего коммита** — понадобится для публикации замечаний (шаг 7);
- **база PR** — целевая ветка проекта; PR в чужую фича-ветку это находка сама по себе.

**Уже существующие замечания** — чтобы не постить второе ревью поверх своего же:

```
bash .claude/scripts/pr-comments.sh <N>
```

Скрипт забирает **все три сорта** комментариев и печатает шапку PR (включая head SHA для
шага 7), инлайновые замечания тредами, тела ревью и ленту обсуждения. Пользуйся им, а не
`gh pr view --comments`: тот показывает только ленту, а инлайновые замечания на строках —
то есть содержательную часть любого ревью — молча теряет.

⚠️ Если всё-таки идёшь в `gh api` руками — **всегда передавай метод явно: `gh api --method GET`.**
Без него `gh api` с любым `-f`/`-F` молча уходит в POST.

### Подтяни ветку локально

```
git fetch origin <headRefName>
git show origin/<headRefName>:<путь>
```

Ветку **не переключай** — читай через `git show origin/<branch>:<file>`.

## 3. Вычитай бизнес-логику ДО чтения кода

Это то, чем `/pbe-review` отличается от обычного `/code-review`: тот проверяет код сам по
себе, а здесь есть постановка, и главный вопрос — **сделано ли то, что заказано**.

Выпиши до похода в дифф:

- **Критерии приёмки** — из описания задачи и спеки в Вики. Нумеруй: по ним строится матрица
  в шаге 6;
- **Ожидаемое поведение и его источник.** Комментарии часто отменяют исходное описание —
  тогда рабочей считается более свежая версия, и это надо назвать явно;
- **Чей это контур.** Консоль ведёт учёт клиентов, релизов и мониторинга; данные о клиентах
  она **читает** из инстансов, а не порождает. Требование, которое на деле про `pbeadmin`
  или `pbeapp`, — так и назови, не ищи его здесь;
- **Кто пользователь этой функции.** Консоль внутренняя, и у неё разные читатели: ИТ,
  поддержка, менеджеры. Функция, доступная не той роли, — это находка, а не мелочь;
- **Что осталось за скоупом сознательно** — чтобы не выкатить это как дефект.

**Выведи этот блок пользователю первым, до замечаний.**

## 4. Прочитай код, а не только дифф

- **Открывай изменённые файлы целиком** и вызываемые сервисы тоже;
- **Схема БД — MSSQL.** Не предполагай Laravel-конвенций: смотри миграцию и модель.
  Отдельно проверяй `v`-столбцы, триггеры и `JSON_VALUE` — они ведут себя иначе, чем кажется
  по коду модели;
- **Тесты и SQLite.** Feature-тесты здесь упираются в то, что тестовая SQLite не умеет части
  MSSQL-специфики. Тест, который «зелёный», потому что молча обошёл проверяемое поведение,
  хуже отсутствующего: он создаёт ложную уверенность. Смотри не только на статус, но и на то,
  что тест реально утверждает;
- **Маршруты и права.** Новый роут — проверь группу middleware, доступ по ролям и то, что
  страница не отдаёт наружу данные клиента лишним;
- **Тёмная тема.** В этом проекте это не косметика, а конвенция: сырые цветовые утилиты без
  `dark:`-варианта и `hover:` без парного `dark:hover:` — типовая находка;
- **Прогони проверки**: `php -l` по изменённым файлам, `composer test`. Если прогнать нельзя —
  так и напиши, это часть отчёта.

## 5. Гейты

Чеклист ревью и триггеры аудита — в [.claude/agents/reviewer.md](.claude/agents/reviewer.md)
и [.claude/agents/security.md](.claude/agents/security.md).

**Безопасность обязательна**, если PR трогает: маршруты, auth, raw SQL, загрузку файлов,
запуск внешних процессов, обращения к API инстансов, выдачу данных клиентов. Вердикт бинарный:
**PASS** или **FAIL** (есть 🔴).

⚠️ **Токены и доступы к инстансам — отдельная строка проверки.** Консоль ходит в чужие
окружения, и утечка её учётных данных стоит дороже большинства дефектов. Секрет в коде,
в конфиге под git или в логе — блокер без обсуждения.

Отдельно смотри **эксплуатацию**:

- нужны ли новые env-переменные и попали ли они в `.env.example`;
- миграция или правка данных — отдельной строкой, это меняет процедуру выкатки;
- меняется ли схема или частота опроса инстансов: консоль опрашивает боевые стенды клиентов,
  и лишняя нагрузка отсюда видна там.

Находки, которые ты нашёл рядом, но которые к этому PR не относятся, **выноси отдельным
блоком «вне скоупа PR»**.

## 6. Отчитайся в терминал — до всякой публикации

1. **Вердикт**: `ПРИНЯТО` / `ПРИНЯТО С ПРАВКАМИ` / `ОТКЛОНЕНО`, одной строкой с причиной;
2. **Найденный PR** и его состояние;
3. **Что хорошо** — коротко и по делу;
4. **Замечания по severity** (🔴 блокер / 🟠 надо починить / 🟡 стоит починить), каждое:
   файл и строки кликабельной ссылкой, механизм отказа (конкретный вход → конкретный
   неверный результат), предложение фикса. Без «стоит подумать» — либо дефект, либо не пиши;
5. **Матрица приёмки**: каждый критерий из шага 3 → чем подтверждён (автотест `<Test::method>` /
   ручная проверка с результатом / «не проверен» с причиной). Зелёный `composer test` сам
   по себе не означает выполнения постановки;
6. **Эксплуатация и выкатка** — из шага 5;
7. **Вне скоупа PR** — если нашлось.

Не дошёл до вывода по какому-то куску — скажи прямо, что не проверял и почему.

## 7. Публикация в GitHub — только по явному согласию

**По умолчанию ничего не публикуй.** Отчёт в терминал — законченный результат этой команды.
Публикуй, если пользователь передал флаг `--post` или попросил словами после отчёта.

Формат — **одно ревью**: общая шапка плюс замечания, привязанные к строкам:

```
bash .claude/scripts/pr-review-post.sh <N> --input <scratchpad>/review.json --dry-run
bash .claude/scripts/pr-review-post.sh <N> --input <scratchpad>/review.json
```

```json
{
  "body": "<шапка: вердикт, что хорошо, эксплуатация, безопасность>",
  "comments": [
    {"path": "app/Services/X.php", "line": 128, "side": "RIGHT", "body": "<замечание>"}
  ]
}
```

- **Поля `event` в файле быть не должно.** Обёртка ставит `event=COMMENT` сама и отказывается
  работать, если поле задано снаружи. Так и задумано: тот же эндпоинт `/pulls/<N>/reviews`
  умеет approve и request-changes, а permissions различают вызовы только по префиксу команды —
  то есть никак. Гарантию даёт обёртка, а не список разрешений;
- **`commit_id` не нужен** — обёртка берёт head SHA у самого PR;
- **`line` должен попадать в дифф**, иначе GitHub отклонит весь запрос целиком. Перед
  публикацией прогони `--dry-run` и сверь строки с `gh pr diff <N>`;
- **проверь результат**: `bash .claude/scripts/pr-comments.sh <N>`.

⚠️ **Ревью на своём же PR публикуется не всегда осмысленно.** Разработчик здесь один, и если
ты правишь находки прямо сейчас (шаг 8), комментарии в GitHub пригодятся только как объяснение
для будущего читателя истории. Это законная причина публиковать — но спроси, а не решай сам.

🚫 Чего не делаешь никогда: `gh pr review` (approve / request-changes), `gh pr merge`,
`gh pr edit|close|ready`, `event=APPROVE`, `event=REQUEST_CHANGES`. Ставит человек.

## 8. Правки по находкам

Порядок:

1. **Ветка от head PR**, не от целевой — точку отсчёта указывай явно:

   ```
   git fetch origin <headRefName>
   git switch -c <TICKET>-fixes origin/<headRefName>
   ```

   В саму ветку PR не коммить: она уже на remote, а пушить мы не можем;
2. **Правит профильный агент** — `developer` (контроллеры, сервисы, Blade), `dba` (**любые**
   миграции и структура моделей), `designer` (вёрстка и тёмная тема). Передавай ему находку
   целиком: файл, строки, механизм отказа и предложенный фикс — субагент не видит диалог;
3. **`qa`** — тесты на критерии, которые в матрице приёмки помечены как непокрытые.
   Порядок проекта: `qa` → фикс → (`reviewer` ‖ `security`) → фикс;
4. **Повторный гейт** `reviewer` (+ `security` по триггерам), если правились 🔴-находки;
5. **Пуш и обновление PR — человек.** Ты заканчиваешь коммитами в локальной ветке, списком
   того, что в них лежит, и **готовой командой пуша**:

   ```
   git push -u origin <TICKET>-fixes
   ```

Если публикуешь замечания и правишь их же, публикуй **до** правок — иначе замечания будут
указывать на строки, которых в ветке уже нет.

Не правим то, что не относится к находкам этого ревью, — «раз уж открыл файл». Всё, что
нашлось рядом, идёт в блок «вне скоупа PR» отдельным тикетом.
