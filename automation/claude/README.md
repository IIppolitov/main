Здесь лежат **эталонные версии** команд и настроек Claude Code для проектов.
Копии живут в `.claude/` каждого репозитория, но ведутся отсюда — тот же
порядок, что и для скриптов в [../scripts/](../scripts/), см. п. 3.1
[основ](../../docs/regulations/claude-code/osnovy.md).

```
commands/<проект>/pbe-bug.md    команда разбора бага
commands/<проект>/pbe-task.md   команда разбора постановки
commands/<проект>/pbe-review.md команда ревью PR против постановки
settings/<проект>.json          permissions: что агенту запрещено, что разрешено, хуки
hooks/                          PreToolUse-хук на git — общий для всех проектов
```

Скрипты, которые эти команды вызывают, лежат не здесь, а в [../scripts/](../scripts/) —
там же, где остальные утилиты: `pr-comments.sh` (все три сорта комментариев PR)
и `pr-review-post.sh` (публикация ревью).

## Почему эталон здесь, а не в проекте

Команда — это инструкция, по которой агент работает у всей команды разом.
Правка в одном репозитории не видна в трёх остальных, и расхождение
обнаруживается не по diff'у, а по тому, что разбор бага в админке идёт иначе,
чем в приложении. Здесь же расхождение видно сразу — файлы лежат рядом.

Настройки вынесены по той же причине и ещё по одной: `permissions.deny` — это
единственный предохранитель, который агент не может обойти уговорами. Он должен
быть одинаково полным во всех проектах, а не там, где до него дошли руки.

**Хук — там же и по той же логике.** `hooks/guard_protected_branch.py` проверяет то,
что списком префиксов выразить нельзя: коммит в защищённую ветку, `git checkout`
по путям, `reset --hard`, флаг не в начале команды. Файл общий, при копировании
в проект правится **одна** строка — константа `PROTECTED`. В продуктовых
репозиториях это `main`/`master`/`pre-prod`/`prod`; в рабочих пространствах
(`pbeba`, `pbemanual`, `pbedataengineer`) она **пустая**: ветвления там нет, работа
идёт прямо в `main`, и защищать её означало бы запретить работу. Остальные проверки
хука там продолжают действовать.

## Порядок правки

1. Правишь файл здесь.
2. Заводишь задачу в очередь проекта (`CRM` для админки и приложения,
   `CONSOLE` для консоли) с текстом правки.
3. Разработчик переносит копию в `.claude/` своего репозитория через PR.

Напрямую из этого пространства продуктовые репозитории не правятся —
`../pbeadmin`, `../pbeapp`, `../pbeconsole` открыты только на чтение.

**Копия — это копия, а не форк.** Починить у себя и не отдать назад нельзя:
через полгода получим четыре версии одного файла с разным поведением.

## Расхождения с тем, что сейчас в репозиториях

Проверять так (из корня рабочего пространства):

```bash
diff -u automation/claude/commands/pbeadmin/pbe-bug.md ../pbeadmin/.claude/commands/pbe-bug.md
diff -u automation/claude/settings/pbeadmin.json       ../pbeadmin/.claude/settings.json
```

Расхождение — это либо не перенесённая правка отсюда, либо правка, сделанная
в проекте мимо порядка. Второе разбирать отдельно: молча забрать её сюда
значит узаконить обход.

## Что здесь не лежит

Агенты (`.claude/agents/`) и `CLAUDE.md` проектов. Они привязаны к коду
конкретного репозитория и ведутся там же — источник истины по коду это
`CLAUDE.md` в корне проекта, а не документ отсюда.

Команды бизнес-аналитиков (`../pbeba`) и дата-инженеров (`../pbedataengineer`)
живут в своих репозиториях: это рабочие пространства, а не продукты, и правятся
напрямую. Сюда вынесена только `pbedataengineer/pbe-task.md` — она попала
в общий контур `/pbe-task` и должна сверяться с остальными.
