## Назначение

«ID-360» исключает фармацевтов и провизоров из клиентской базы Data360.
У Servier есть потребность продолжать работу с ними, поэтому CRM должна уметь
валидировать такие контакты сама и собирать по ним согласия.

Механизм состоит из четырёх частей:

1. **Определение пути валидации.** По настраиваемым правилам (атрибуты карточки
   врача И атрибуты организации — места работы) DCR уходит либо в Data360, либо
   на внутреннюю валидацию — автоматическую или ручную. Есть глобальный
   выключатель: при выключении всё идёт стандартным путём в Data360.
2. **Контроль дублей.** Переиспользуемая проверка на уникальность по правилам
   из конфига. Вызывается при создании DCR, по кнопке администратора и
   автоматически перед созданием контакта.
3. **Контроль сбора согласий.** Контакт, созданный без валидации Data360,
   получает запись Consent и счётчик дней (по умолчанию 30). Согласие не
   собрано в срок — контакт помечается удалённым (soft delete).
4. **Администрирование.** GUI правил для ролей `Admin` и `ClientAdmin`,
   количество дней на сбор согласия, глобальный выключатель.

## Схемы процесса

Пять BPMN-схем: маршрут запроса, автоматическая валидация, ручная валидация,
контроль сбора согласия, конфигурация правил. Плюс таблицы статусов DCR
и переходов между ними.

**Где лежат:** файл `dcr-validation-bpmn.html` приложен к комментарию
в [CRM-1030](https://tracker.yandex.ru/CRM-1030) от 14.08.2026 — это рабочая
копия, открывается в браузере без интернета. В репозиторий не кладём:
здесь текстовые документы, а не бинарные вложения.

## Решения по развилкам постановки

Приняты 14.08.2026, учтены в схемах. Постановка допускала два и более прочтения
в каждом пункте — без фиксации это разошлось бы на этапе разработки.

| # | Развилка | Решение |
|---|---|---|
| 1 | DCR на изменение существующего контакта | Контакт обновляется, а не создаётся заново. Из проверки на дубли исключается сам изменяемый контакт (self-match по ID) |
| 2 | Отклонение по дублям при создании | Не тупик: запрос редактируется и отправляется заново, тот же DCR возвращается в статус «Новый» (0), проверка на уникальность выполняется повторно |
| 3 | Пустой блок атрибутов в правиле маршрута | Условием не считается — правило проверяется по заполненному блоку |
| 4 | Порядок перебора правил | Не задаётся: фиксируется любое первое сработавшее правило |
| 5 | Срок сбора согласия | Фиксируется в записи Consent при её создании, ретроактивно не пересчитывается. Счётчик существует только у контактов, созданных внутренней валидацией |
| 6 | Сбой внутренней валидации | DCR переводится в «На ручной проверке» (6), причина сбоя — в комментарий. Статус «Ошибка» (10) не используется |
| 7 | Выключение внутренней валидации | Действует только на новые отправки; DCR в статусах 1 и 6 дорабатываются как есть |

## Риски

- **Оценки нет, срок есть.** 01.10.2026 назван клиенту, `estimation` в задаче
  нулевая. Объём зависит от того, насколько богатыми будут правила на
  справочниках — Семков предупреждал об этом ещё 15.06.
- **Часть требований у DPO.** Задача висит в «Требуется информация» с 14.08;
  чем дольше ответа нет, тем меньше остаётся от срока.
- **Единственный разработчик.** Проект, как и «Мероприятия+», замкнут лично
  на директора департамента. Два таких проекта одновременно конкурируют
  за одно и то же время.

Открытые вопросы по существу — в [backlog](../backlog.md#внутренняя-валидация-dcr-servier),
