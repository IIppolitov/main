Что получается на выходе и кому — [README.md](README.md). Здесь порядок работы.
Разбор отдельной задачи вынесен в [razbor-zadachi.md](razbor-zadachi.md): это

Ориентир по трудоёмкости: релиз на 15–20 задач — половина рабочего дня, если
проходить по шагам и не начинать с текста.

## 0. Что нужно на входе

- **Номера проектов Трекера** с задачами релиза. Проект берётся из ссылки:
  `https://tracker.yandex.ru/pages/projects/895/issues` → `895`.
- **Дата релиза** — она попадает в имена файлов и в шапку.
- **Доступ к API Трекера** — токен и ID организации, порядок настройки в
  [automation/scripts/README.md](../../automation/scripts/README.md).
- **Чекаут `pbeadmin` (и `pbeapp`, если релиз его затрагивает)** рядом с рабочим
  пространством — **если есть доступ к коду**. Нужен не для правок, а чтобы сверять
  слова задачи с тем, что реально уезжает на продуктив (шаг 3).

Начинать имеет смысл, когда подзадачи «Разработка» уже в «Готово к релизу»
([этап 13](../regulations/crm-lifecycle/13-reliz.md), 4.1). Раньше — перечень задач ещё поедет.

## 1. Собрать перечень задач

```bash
automation/scripts/tracker-project-report.py 895 926 > reports/2026-08-18/release-list.md
```

Скрипт принимает и ссылки целиком, и несколько проектов за вызов. В таблице
интересны три колонки: **Задача**, **Клиент**, **Тема**.

> ⚠️ **Знак `?` в колонке «Клиент» — не опечатка.** Мнемоника клиента по
> регламенту стоит тегом задачи; если тега нет, скрипт берёт её из начала темы и
> помечает `?`. Такую задачу проверять руками: в релизе 18.08.2026 CRM-1217
> приехала как Bayer, а по мнемонике `BSN` и содержанию относилась к Besins.
> Ошибка стоила бы включённых конфигов не на том инстансе.

Перечень задач — единственный список, по которому потом сверяется полнота обоих
документов. Задача из него не исчезает: если по ней нечего делать, она попадает
в раздел «Без действий релиза» или «Без видимых изменений на экранах».

## 2. Выгрузить тела задач

```bash
automation/scripts/tracker-issue.sh CRM-594 CRM-914 CRM-980 > reports/2026-08-18/release-issues.md
```

Ключи перечисляются через пробел, все задачи релиза — одним вызовом. Флаг
`--links` подтягивает тела связанных задач: он нужен там, где постановка лежит в
отдельной задаче БА, и **обязателен**, если у задачи есть подзадача «Релиз» — в
ней лежит план выкатки, который в release actions первичен.

## 3. База сверки — актуальный prod-тег

Сверка по коду ведётся **по тегу продуктива, а не по `main` и не по рабочему
дереву**. В `main` лежит и то, что в этот релиз не едет; рабочее дерево вдобавок
отстаёт. «Влито в `main`» и «уедет клиенту» — разные утверждения, и путать их
дорого: документ покажет зелёную галочку там, где на проде изменения нет.

```bash
git -C ../pbeadmin fetch --tags --prune origin
git -C ../pbeadmin for-each-ref --sort=-creatordate \
  --format='%(creatordate:short) %(refname:short)' 'refs/tags/prod-v*' | head -5
```

Верхняя строка — то, что сейчас на продуктиве (`prod-v8.0`, `prod-v7.41` и так
далее). Это и есть база: код читаем на ней, принадлежность задачи проверяем ей.

**Тег пишется в шапку обоих документов.** Без него читатель не знает, что именно
проверялось, и через неделю проверить заново нельзя.

Если документы готовятся до простановки релизного тега, базой служит кандидат —
последний `pre-prod-v*` (после выкатки он и станет очередным `prod-vN.0`). Так и
писать в шапке: сверено по `pre-prod-v8.34`, тег продуктива на момент подготовки —
`prod-v8.0`. Подменять базу молча нельзя.

> `fetch` обновляет только ссылки и теги, дерево не трогает. `pull`, `checkout` и
> правки в `../pbeadmin` — не наша работа: продуктовые репозитории читаем.

**Если кода нет.** Шаг и вся сверка по коду выполняются тимлидом; релиз-менеджер
берёт факты из подзадачи «Релиз» и тела задачи, а в шапке документа отмечает:
«сверка по коду не проводилась». Это осознанный размен — без сверки не ловятся
ровно те ошибки, ради которых документ и пишется (невыполненный бамп сабмодуля,
дефолт ключа, `env()` в миграции), — а не мелочь, о которой можно умолчать.

## 4. Разобрать каждую задачу

По одной карточке из [razbor-zadachi.md](razbor-zadachi.md) на задачу. Порядок
внутри карточки не случайный: сначала «что увидит пользователь», потом «при каком
условии видно», и только потом код. Обратный порядок даёт patch notes, написанные
языком коммитов.

Итог разбора — заметки по задаче, из которых потом механически собираются оба
документа. Писать сразу в готовый документ не надо: половина задач по итогам
разбора переезжает в разделы «без действий» и «без видимых изменений».

## 5. Собрать документы

По шаблонам [release-actions.md](../templates/release-actions.md) и
[patch-notes.md](../templates/patch-notes.md), в папке дня сборки:

```
reports/2026-08-18/RELEASE_ACTIONS.md
reports/2026-08-18/PATCH_NOTES.md
```

**Группировка в обоих — по клиентам**, в конце отдельный блок «Все клиенты» для
задач, которые едут всем. Внутри клиента — по возрастанию номера задачи.

Порядок сборки: сначала release actions (там факты из кода), потом patch notes
(там их пересказ для человека). Наоборот — и в patch notes попадут условия
видимости, которых в коде нет.

## 6. Самопроверка перед отправкой

- [ ] В шапке обоих документов указано, **по какому тегу сверялись** (или что
      сверки по коду не было).
- [ ] Все задачи из перечня шага 1 присутствуют в **обоих** документах — хотя бы
      строкой в разделе «без действий» / «без видимых изменений».
- [ ] По каждому конфиг-ключу написано: **где объявлен, какой дефолт, какое
      значение ставим**. Дефолт обязателен: он отвечает на вопрос «а что будет у
      остальных клиентов, если ничего не делать».
- [ ] Там, где порядок шагов важен (миграция после `.env`, сабмодуль перед
      ядром), он записан нумерованным списком, а не набором галочек.
- [ ] Каждая миграция названа полным именем файла и привязана к соединению
      (ядро или модуль).
- [ ] Для каждой задачи в patch notes указано **где смотреть** — экран, раздел
      или URL. «Доработан механизм X» без места — не patch note.
- [ ] Пункты, требующие клиента до выкатки, переданы менеджеру клиента, а не оставлены на
      день релиза ([этап 5](../regulations/crm-lifecycle/05-ocenka-zadachi.md), 4.3.1).
- [ ] Расхождения (клиент в выгрузке, план подзадачи «Релиз» против кода) не
      подчищены молча, а вынесены явной строкой в текст.

## 7. Что делать с расхождениями

Расхождение — ценный результат работы, а не помеха. Правило одно: **фиксировать
явно в документе и адресовать**, а не приводить текст к красивому виду.

| Что нашлось | Куда |
|---|---|
| Клиент в выгрузке не тот | Строкой в оба документа + поправить тег задачи в Трекере |
| План подзадачи «Релиз» разошёлся с кодом | К тимлиду задачи до релиза; молча верить коду нельзя |
| Задачи нет в теге сверки | Блокер релиза: релиз-менеджеру, задача снимается или ждёт. «Есть в `main`» здесь не оправдание |
| Не хватает вводных (какая база, чей планировщик, кто гоняет загрузки) | Раздел «Открытые вопросы до релиза» в release actions с адресатом |
