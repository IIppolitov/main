| **Область действия** | Релиз-менеджер, тимлиды, технический директор; продукты `pbeadmin` и `pbeapp` |

К каждому релизу готовятся **два документа** — по одному на каждого читателя.
Их нельзя заменять один другим: у них разные адресаты и разная цена ошибки.

| Документ | Кому | Отвечает на вопрос | Шаблон |
|---|---|---|---|
| `RELEASE_ACTIONS_<дата>.md` | Технический директор, тимлиды, релиз-менеджер | что руками сделать на инстансе, чтобы релиз поехал | [release-actions.md](../templates/release-actions.md) |
| `PATCH_NOTES_<дата>.md` | Менеджеры клиента, поддержка, клиент | зачем это делали, что и где изменилось, при каком условии видно | [patch-notes.md](../templates/patch-notes.md) |
| `RELEASE_REPORT_<дата>.md` | директор департамента ИТ, тимлиды | сколько планировали, сколько потратили, где споткнулись | [release-report.md](../templates/release-report.md) |

Пропущенный пункт в release actions — релиз не поехал или поехал наполовину.
Пропущенный пункт в patch notes — поддержка и менеджер клиента узнают об изменении от клиента.
Пропущенный раздел в отчёте — та же причина перерасхода повторится в следующем релизе.

**Первые два готовятся до выкатки, отчёт — после (T+2):** часы дописывают ещё
день-два, и собранный заранее отчёт врёт в главной своей цифре.

Автоматизация для тех, у кого стоит Claude Code, — команда `/release-notes`
(`.claude/commands/release-notes.md` в этом репозитории). Она проходит по тому
же процессу; правила первичны, команда вторична. Разошлись — прав `process.md`.

## Вход и выход

**Вход:** номера проектов Трекера с задачами релиза (например
[895](https://tracker.yandex.ru/pages/projects/895/issues) и
[926](https://tracker.yandex.ru/pages/projects/926/issues)), дата релиза.

Сверка по коду — по **актуальному тегу продуктива** (`prod-v*`), а не по `main`:
влитая в `main` задача не обязана ехать этим релизом. Порядок — [process.md](process.md), 3.
Доступа к коду нет — сверку делает тимлид, и в шапке документа это отмечается.

**Выход:** два файла в `reports/` (папка вне git — документы релиза
воспроизводятся командой и устаревают, см. [reports/README.md](../../reports/README.md)).

## Место в жизненном цикле

Работа идёт на [этапе 13 «Релиз»](../regulations/crm-lifecycle/13-reliz.md), пункт 4.2
«Подготовка к релизу»: release actions — это сводный план выкатки, patch notes —
те самые release notes, которые релиз-менеджер готовит перед выпуском.

**Подзадачу «Релиз» эти документы не заменяют.** Если у задачи есть подзадача
«Релиз» ([этап 5](../regulations/crm-lifecycle/05-ocenka-zadachi.md), 4.3.1), её план —
первоисточник: release actions его пересказывают в общей сводке, а не переписывают
заново. Расхождение плана и кода — повод идти к тимлиду, а не чинить текст.

## Кто что делает

| Роль | Вклад |
|---|---|
| Релиз-менеджер | Ведёт все три документа, собирает перечень задач, сводит и проверяет полноту, ведёт разбор отклонений |
| Тимлид | Отвечает за техническую часть по задачам своей команды: конфиги, миграции, сабмодули, порядок шагов. Проверяет на ревью блок «Изменения для пользователя». Даёт причины отклонений на разборе |
| Разработчик | Пишет в задаче блоки «Изменения для пользователя» и «Действия при релизе» по критерию из [otchet-o-relize.md](otchet-o-relize.md), 3 |
| Технический директор | Исполняет release actions на продуктивном окружении |
| Менеджер клиента | Получает patch notes, доносит до клиента; закрывает предрелизные пункты, требующие клиента |

Открытые вопросы по процессу — в [docs/backlog.md](../backlog.md), раздел
«Релизные документы».
