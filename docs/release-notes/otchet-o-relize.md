# Отчёт о релизе

| | |
|---|---|
| **Версия** | 1.0 |
| **Дата** | 2026-08-21 |
| **Владелец** | Ипполитов Иван, директор департамента информационных технологий |
| **Статус** | draft |
| **Область действия** | Релиз-менеджер, тимлиды, разработчики; продукты `pbeadmin` и `pbeapp` |

Третий релизный документ рядом с двумя существующими ([README.md](README.md)).
Отвечает на вопрос, на который не отвечают ни release actions, ни patch notes:
**во что нам обошёлся релиз и что мы из него узнали.**

| Документ | Читатель | Когда | Вопрос |
|---|---|---|---|
| `RELEASE_ACTIONS_<дата>.md` | Технический директор, тимлиды | до выкатки | что руками сделать на инстансе |
| `PATCH_NOTES_<дата>.md` | Менеджеры клиента, поддержка, клиент | до выкатки | что и где изменилось на экранах и зачем |
| **`RELEASE_REPORT_<дата>.md`** | директор департамента ИТ, тимлиды | **T+2 после выкатки** | сколько планировали, сколько потратили, где споткнулись |

**Отчёт готовится после выкатки, а не до.** Часы дописывают ещё день-два, и
собранный до релиза отчёт врёт в главной своей цифре. Два первых документа —
до, третий — после.

**Наружу отчёт не идёт.** Клиенту и менеджеру клиента нужен другой срез — «зачем это делали
и как включить», без часов. Он собирается не отдельным документом, а блоком
«Бизнес-проблема» в [patch notes](../templates/patch-notes.md).

## 1. Состав: шесть полей и откуда каждое берётся

Главное, что надо понимать про этот отчёт: **четыре поля из шести уже
существуют в Трекере.** Их не надо ни у кого выспрашивать — их надо забирать.
Спрашивать человека надо про два, и только один из них новый.

| Поле | Где лежит | Когда появляется | Нужен человек |
|---|---|---|---|
| **Бизнес-проблема** | описание **основной задачи**: постановка менеджера клиента ([этап 1](../regulations/crm-lifecycle/01-sozdanie-zadachi.md)) и проработка БА ([этап 3](../regulations/crm-lifecycle/03-biznes-analiz.md)) | за месяцы до релиза | Нет — выгрузка. Пусто — это находка, см. 6 |
| **Как решили** | блок «Изменения для пользователя» в подзадаче **«Разработка»** | закрытие разработки | Пишется уже сейчас; нормируется качество, см. 3 |
| **Как настраивается** | подзадача **«Релиз»**, блок «Действия при релизе», разбор по коду ([razbor-zadachi.md](razbor-zadachi.md), 3–7) | до релиза | Нет — то же, из чего собираются release actions |
| **Сколько запланировали** | «Первоначальная оценка» **всех подзадач дерева** + семь полей разбивки **основной задачи** ([этап 5](../regulations/crm-lifecycle/05-ocenka-zadachi.md), 4.5) | этап 5 | Нет — скрипт |
| **Сколько потратили** | записи учёта времени по **всему дереву**, включая связанные «Консультации» | по факту | Нет — скрипт |
| **Где возникли проблемы** | цифры — скрипт по подзадачам «Разработка»; причина — [разбор отклонений](razbor-otklonenij.md) | закрытие и T+3 | Только по задачам-триггерам |

### 1.1. Единица отчёта — основная задача, а не то, что лежит в спринте

Это главная ловушка сборки, и в неё попадает любая автоматизация, сделанная «по
проекту спринта».

**В спринт кладут подзадачи «Разработка»** — на них считается ёмкость
([этап 8](../regulations/crm-lifecycle/08-nabor-sprintov.md)). Выгрузка по проекту
спринта отдаёт именно их. А почти всё, что нужно отчёту, лежит не в них:

| Что нужно | Где лежит | Есть ли в проекте спринта |
|---|---|---|
| Бизнес-проблема, семь полей разбивки, тег клиента | Основная задача («Улучшение») | Нет |
| Как настраивается | Подзадача «Релиз» | Нет — в спринт не кладётся |
| Часы тестирования | Подзадача «Тестирование» | Нет — по [К-25](../backlog.md) в спринт разработки не идёт |
| Часы БА | Подзадача «Бизнес Анализ» + связанные «Консультации» | Нет |
| Часы дизайна | Подзадача «Дизайн» | Нет |
| Как решили, действия при релизе, возвраты | Подзадача «Разработка» | Да |

**Порядок сборки поэтому такой:** от задачи из спринта подняться к родителю,
и уже от родителя собрать всё дерево — все подзадачи и связанные
«Консультации». Отчёт пишется по родителю, одна карточка на основную задачу.

Две частности, на которых спотыкаются:

- **Задача без родителя.** Иногда в спринт кладут основную задачу целиком —
  известное расхождение практики и регламента ([этап 8](../regulations/crm-lifecycle/08-nabor-sprintov.md)).
  Такая задача сама себе корень, ломаться на ней нельзя.
- **Клиент определяется по тегу основной задачи.** У подзадачи тега может не
  быть — отсюда часть знаков `?` в колонке «Клиент» выгрузки
  ([process.md](process.md), 1). Смотреть тег родителя, а не подзадачи.

Половина отчёта — одна команда:

```bash
automation/scripts/tracker-project-report.py <проекты релиза> --save
```

Она отдаёт по каждой задаче оценку, факт, отклонение в часах и процентах, кто
сколько списал, возвраты отдельно с ревью, с тестирования и с внешнего теста,
переоткрытия, длительность цикла и время в статусах.

> **Скрипт выгружает проект, то есть подзадачи спринта.** Часы по «Тестированию»,
> «Бизнес Анализу», «Дизайну» и «Релизу» в его выгрузку не попадают: этих
> подзадач в спринте нет. Для полного плана и факта по задаче их добирают по
> дереву — см. 1.1. Пока это ручной шаг; он и есть главная причина автоматизации
> в консоли (8).

### 1.2. Релиз приложения — тот же отчёт, плюс две задачи

Всё выше одинаково для админки и приложения. Отличий три:

- **Состав** берётся не из карточки релиза админки, а из спринта клиента
  ([этап 13](../regulations/crm-lifecycle/13-reliz.md), 4.2).
- **Группировка** в отчёте не по клиентам: релиз приложения идёт одному
  клиенту. Внутри — по типу изменения: доработки, исправления, регресс.
- **Две обязательные задачи релиза** — «Подготовка релиза» и «Регресс
  приложения» ([этап 7](../regulations/crm-lifecycle/07-sbor-v-proekty.md), 4.5) —
  выносятся **отдельной строкой сводки**, а не разбираются как задачи: показывать
  по ним пользователю нечего.

Последнее — не формальность. Норматива по этим двум задачам нет, и по
[долгу К-27](../backlog.md) он «выводится из факта списаний за несколько
релизов». Отчёт — ровно тот инструмент, который его и даст: строка «подготовка
N ч, регресс M ч» в каждом отчёте, и через три релиза норматив есть.

## 2. Принцип: собирать по ходу, а не в день релиза

Вопрос «где были сложности» через три недели после закрытия задачи даёт ответ
«да нормально всё». Поэтому:

- **что сделали и как настраивается** — пишется разработчиком при переводе
  подзадачи «Разработка» в «Готово к релизу» ([этап 11](../regulations/crm-lifecycle/11-testirovanie-i-revju.md)),
  пока помнит;
- **цифры** — считаются сами, спрашивать некого;
- **причина отклонения** — обсуждается на одной встрече после релиза, и только
  по задачам, которые прошли числовой порог.

Никто, кроме разработчиков, новой писанины не получает, а разработчики получают
не новый артефакт, а требование к качеству существующего.

## 3. Единственное новое требование к командам

Разработчики уже пишут в задаче два блока: **«Изменения для пользователя»** и
**«Действия при релизе»**. Второй работает — из него собираются release actions.
Первый пишется как придётся: у одного это готовый абзац для patch notes, у
другого — строка «доработан механизм».

Требование не «писать ещё», а **писать по критерию**. Блок «Изменения для
пользователя» считается заполненным, если в нём есть три вещи:

1. **Что изменилось** — языком пользователя, без имён классов, таблиц и методов.
   Не «добавлен `FieldsSnapshotLog` для KOL-визитов», а «у визитов, связанных с
   КОЛ, появился журнал изменений: кто, когда и какое поле поменял».
2. **Где смотреть** — экран, раздел меню или URL.
3. **При каком условии видно** — конфиг, право, тип данных, подключённый модуль.
   Если видно всем и всегда — так и написать.

Проверяет тимлид на ревью, вместе с кодом. Блок без этих трёх вещей — такой же
повод вернуть задачу, как несобирающийся код: и в том, и в другом случае работу
придётся доделывать, вопрос только — кому и когда.

> **Где именно живут оба блока — в описании подзадачи «Разработка», в комментарии
> или в основной задаче — по командам сложилось по-разному.** Единое место
> фиксирует релиз-менеджер вместе с тимлидами до начала сбора; без этого не
> строится ни проверка полноты, ни автоматизация. См. открытый вопрос ОР-1.

## 4. Кто что даёт

| Роль | Вклад | Когда |
|---|---|---|
| Менеджер клиента, бизнес-аналитик | Бизнес-проблема — в теле задачи | этапы 1 и 3, задолго до релиза |
| Разработчик | Блоки «Изменения для пользователя» и «Действия при релизе» по критерию из 3 | перевод в «Готово к релизу» |
| Тимлид | Проверяет блоки на ревью; отвечает за причины отклонений своей команды на разборе | ревью и T+3 |
| Технический директор | Факт по деплою — против «Оценки: деплой» | после выкатки |
| **Релиз-менеджер** | **Не добывает знание, а сводит:** гоняет скрипт, проверяет наличие блоков, назначает разбор по порогу, собирает документ | по календарю из 5 |

Роль релиз-менеджера здесь принципиально исполнительская: каждый её шаг — это
либо команда, либо сверка списка со списком, либо рассылка по готовому тексту.
Ни на одном шаге не требуется догадаться, что пора что-то сделать.

## 5. Порядок работы релиз-менеджера

Отсчёт от даты выкатки (T).

| Когда | Шаг | Результат |
|---|---|---|
| Разово, до старта | Согласовать с тимлидами: единое место блоков, критерий заполнения, пороги разбора | Договорённость письмом всем командам |
| Еженедельно | Прогнать перечень задач релиза, найти закрытые подзадачи без блока «Изменения для пользователя» → напоминание исполнителю и тимлиду | Пустых блоков к релизу не остаётся |
| **T−7** | Первый прогон `tracker-project-report.py` по проектам релиза | Черновые план/факт, предварительный список кандидатов на разбор |
| **T−4** | Сборка [release actions и patch notes](process.md) — включая блок «Бизнес-проблема» в patch notes | Два документа до выкатки |
| **T** | Выкатка | — |
| **T+2** | Финальный прогон скрипта: часы дописаны. Сборка отчёта по [шаблону](../templates/release-report.md) | Отчёт без раздела «Причины» |
| **T+3** | [Разбор отклонений](razbor-otklonenij.md): одна встреча, подзадачи «Разбор», протоколы | Причины и решения с адресатами |
| **T+7** | Выпуск отчёта директору департамента ИТ и тимлидам | Отчёт целиком |

## 6. Пустое поле — это результат, а не пробел

Отчёт ценен ровно тем, чего в нём не хватает. Ни одно поле не выдумывается и не
заглаживается формулировкой.

| Чего нет | Как пишется в отчёте | Кому адресуется |
|---|---|---|
| Бизнес-проблемы в теле задачи | «Постановка не содержит бизнес-проблемы» | Менеджеру клиента задачи; повтор — в [долг](../backlog.md) |
| Оценки, а факт есть | «Задача прошла мимо этапа 5» | Релиз-менеджеру, это её этап |
| Блока «Изменения для пользователя» | «Описание изменений от разработчика отсутствует» | Тимлиду команды |
| Подзадачи «Релиз» там, где она обязательна | «План выкатки собран из кода» | Тимлиду; см. [долг РД-2](../backlog.md) |

Сводка таких строк в конце отчёта — самая полезная его часть: она показывает не
отдельную задачу, а место процесса, где регулярно рвётся.

## 7. Самопроверка перед выпуском

- [ ] Все задачи перечня релиза в отчёте — включая те, по которым все шесть
      полей пусты.
- [ ] Цифры плана и факта взяты из финального прогона **после** релиза, а не из
      черновика T−7.
- [ ] По каждой задаче, прошедшей порог, есть либо протокол разбора, либо запись
      «причина разовая, действий нет».
- [ ] Каждое решение из разбора имеет адресата и срок.
- [ ] Сводка по процессу (раздел 6) заполнена, а не пропущена как «мелочи».
- [ ] Часы в клиентский срез не попали: наружу идут patch notes, не отчёт.

## 8. Куда это едет: сборка в консоли

Сейчас отчёт собирается руками по этому регламенту, а цифры даёт
`tracker-project-report.py`. Целевое место сборки — **карточка релиза в
[pbeconsole](../systems/pbeconsole.md)**, обоих типов: и админки, и приложения.
Там уже лежит снапшот задач релиза с первоначальной оценкой, списанием,
статусами и клиентами по тегам, и по нему уже считаются часы и перерасход.

Консоль обращается к модели **сама**, через наш шлюз — тот же
OpenAI-совместимый прокси, которым уже пользуется модуль `Insights` в
[pbeadmin](../systems/pbeadmin.md). Порядок:

1. **достраивает объём релиза до полного дерева задач** (1.1) — сегодня в
   снапшоте лежат подзадачи спринта, и этого мало; забирает тела задач и историю
   статусов;
2. по каждой корневой задаче отправляет запрос со **строгой схемой ответа**:
   форму держит схема шлюза, а не уговоры в тексте промпта, поэтому «данных нет»
   выражается честным пустым полем, а не выдуманным абзацем;
3. раскладывает ответ по карточкам, цифры подставляет сама, отчёт собирает по
   [шаблону](../templates/release-report.md).

Ручной режим — «скопировать запрос, принести ответ» — остаётся запасным входом
на случай, когда шлюз недоступен в день релиза.

Разделение жёсткое: **модель переформулирует текст, который ей дали, и не
трогает ни одного числа.** План, факт, отклонение, возвраты — из снапшота.
Причина отклонения и решение — от человека на [разборе](razbor-otklonenij.md):
модель, которой скормить «план 16, факт 39», уверенно напишет «задача оказалась
сложнее ожидаемого» — ровно то, что регламент запрещает считать причиной.

Каждая сгенерированная карточка требует отметки «проверено»; непроверенное идёт
в отчёт с видимой пометкой, а не тихо. Расход считается по журналу вызовов,
лимиты — общий котёл на инстанс, умолчание на пользователя и персональное
значение поверх него; всё настраивается из интерфейса.

Постановка — [CONSOLE-13](https://tracker.yandex.ru/CONSOLE-13) с десятью
подзадачами (CONSOLE-14…23). Черновики тел — `reports/zadachi-console/`.

> **Вопрос ИБ отложен осознанно.** Тела задач содержат данные
> клиентов-фармкомпаний, и если за прокси стоит внешний провайдер, они уходят
> наружу. Решением директора департамента ИТ от 21.08.2026 это не считается
> блокером: шлюз свой и уже используется модулем `Insights` в проде. К разбору
> возвращаемся после запуска — [долг ОР-5](../backlog.md).

**Релиз 15.09.2026 идёт без консоли:** руками по разделам 1–7, цифры скриптом.
Консоль догоняет к следующему релизу — и первый ручной заход как раз покажет,
что в ней автоматизировать, а что оказалось лишним.

## Открытые вопросы

Ведутся в [долге](../backlog.md), раздел «Релизные документы».

- **ОР-1.** Единое место блоков «Изменения для пользователя» и «Действия при
  релизе» не зафиксировано — по командам сложилось по-разному.
- **ОР-2.** Пороги разбора (Δ ≥ +50 % или ≥ +8 ч, ≥ 2 возвратов) взяты как
  первое приближение и калибруются по факту двух-трёх релизов.
- **ОР-3.** Проверка «закрытые подзадачи релиза без блока» пока делается
  глазами: локальные поля и тела комментариев фильтрами API не берутся
  ([долг К-29](../backlog.md)).
- **ОР-5.** Не согласовано с ИБ, какой ИИ-сервис допустим для промпта с телами
  задач и что именно можно в него выносить. Блокер внедрения сборки в консоли.
