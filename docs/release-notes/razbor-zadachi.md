Карточка на одну задачу. Девять вопросов: первые три — для patch notes, остальные
— для release actions. Порядок работы целиком — [process.md](process.md).

Правило разбора: **описание задачи говорит, что хотели; код говорит, что
выкатывается.** Расходятся — это находка, её место в документе, а не в правках
текста (см. [process.md](process.md), 7).

## Первая команда: что задача реально изменила

Задаём базу сверки один раз на весь разбор — тот тег, который возьмёт `deploy.sh`
([process.md](process.md), 3). Сортировка **по версии**, не по дате:

```bash
TAG=$(git -C ../pbeadmin tag -l 'prod-v*' | sort -V | tail -1)

git -C ../pbeadmin log "$TAG" --grep='CRM-594' --name-only --pretty=format:'' \
  | sort -u | grep -v '^$'
```

Список файлов отвечает почти на все технические вопросы карточки сразу:

| Что в списке | О чём говорит |
|---|---|
| `database/migrations/*` | миграция ядра — **прогоняется деплоем**, в приложение документа |
| `modules/<M>/database/migrations/*` | миграция модуля, своё соединение — **тоже деплоем**, в приложение |
| `database/seeders/*Seeder.php` | новое право — сидер прогоняется деплоем, а вот **выдача права людям** это ручной пункт |
| `.env.example` | появился env-ключ: ставится в `.env` инстанса, не в админке |
| `config/pbe.php` или `modules/<M>/config/pbe.php` | ключ настроек: значение ставится в админке |
| `resources/views/*`, `app/Http/Controllers/*` | видимая часть — отсюда берётся «где смотреть» |
| пусто в ядре | задача целиком в сабмодуле, ищем там (вопрос 7) |

Если задача не нашлась ни в ядре, ни в модулях — **она не в релизе**. Прежде чем писать
блокер, перепроверь двумя способами: ключ задачи в сообщении коммита стоит не всегда, а в
релизную ветку коммиты приезжают перебазированными, с другим SHA.

```bash
git -C ../pbeadmin log "$TAG" --oneline --grep='<текст темы>' -i    # по теме
git -C ../pbeadmin log "$TAG" --oneline --grep='#1192)'             # по номеру PR из задачи
```

Сравнивать SHA из `origin/main` с тегом через `merge-base --is-ancestor` — ненадёжно
ровно из-за перебазирования: даст «не входит» там, где задача входит.

Не нашлась и так — блокер: задача влита, но ни в один тег не входит, на продуктиве её нет
и в ближайшую выкатку не будет.

## 1. Клиент и инстансы

Мнемоника клиента — тег задачи; в отчёте шага 1 знак `?` означает, что тег не
проставлен и клиент опознан по началу темы. Такие проверять руками: у мнемоник
есть устойчивое значение (`BSN` — Besins, `VLT` — Валента, `MAY` — Майоли),
и оно надёжнее выгрузки.

У клиента может быть **несколько инстансов** (РФ, КЗ, УЗ). Если доработка едет не
на все — это отдельная строка «Раскатка: РФ» и в patch notes, и в release actions.
Перечень инстансов клиента — в [pbeconsole](../systems/pbeconsole.md).

## 2. Что увидит пользователь и где

Формулировка для patch notes — двумя абзацами:

- **Что изменилось** — одним–двумя предложениями, языком пользователя. Не
  «добавлен `FieldsSnapshotLog` для KOL-визитов», а «у визитов, связанных с КОЛ,
  появился журнал изменений: кто, когда и какое поле поменял».
- **Где смотреть** — экран, раздел меню или URL (`/kol/show/{id}/visits`).
  Путь берётся из роутов и вьюх задачи, а не из головы.

Отдельно стоит написать **«что НЕ изменилось»**, если задача трогает знакомый
экран: это снимает половину обращений в поддержку («а почему у прошлого года нет
месяца?» — потому что строка годовая).

## 3. Условие видимости

Ответ на вопрос «почему у меня этого нет». Варианты:

| Условие | Как выглядит в тексте |
|---|---|
| Конфиг выключен | «Конфиг `USE_SUBBRICK_EXTENDED`. При выключенном — поведение прежнее» |
| Нужны права | «Доступ регулируется правами `visits.store.matrix`» |
| Зависит от типа данных | «Чекбокс появляется, только если тип поля — "Да/нет"» |
| Модуль не подключён | «Только для инстансов с включённым модулем Bi» |
| Видно всем | помечается значком «все клиенты» |

Задачи, закрытые конфигом, в patch notes помечаются значком — читатель сразу
видит, что без включения у него ничего не поменяется.

## 4. Переключатели: два разных вида

Их постоянно путают, а действия у них разные.

**env-ключ.** Объявлен в `.env.example`, читается через `env()`. Ставится в `.env`
инстанса, силами технического директора, до миграций и сидеров.

```bash
grep -rn "USE_STORE_MATRIX" --include="*.php" --include="*.example" ../pbeadmin | grep -v vendor
```

**Ключ настроек админки.** Объявлен в `config/pbe.php` ядра или модуля блоком с
`title` / `default` / `description`, читается как `config('pbe.KEY.value')`.
Значение живёт в настройках инстанса и ставится через интерфейс админки — в коде
только объявление и дефолт.

```bash
grep -rn "PROMO_CYCLES_MASS_TL_STATUS_CHANGE" ../pbeadmin/config/pbe.php ../pbeadmin/modules/*/config/pbe.php
```

По каждому ключу в release actions пишутся три вещи: **где объявлен, какой дефолт,
что ставим**. Дефолт — не формальность: он определяет, надо ли что-то делать
остальным клиентам. Ключ с дефолтом `1` меняет поведение у всех молча; ключ с
дефолтом `null` (как `BI_DEFAULT_DASHBOARD_ID`) молча выключает то, к чему
пользователи привыкли.

Ключ типа JSON или массив — выписать структуру и проверить дефолт по коду: список
контейнеров, типов активностей и подобное почти всегда требует сверки с
справочником на самом инстансе, иначе функция просто не покажется.

## 5. Миграции

Миграции прогоняет `deploy.sh` (`php artisan migrate --force`) — и ядровые, и модульные.
Действием релиза они **не являются**: их место в приложении документа, где выписываются
полное имя файла, что создаёт и чьё соединение (ядро или модуль).

Два исключения, которые всё-таки идут в чек-лист:

- **миграция читает `env()`** — тогда порядок жёсткий: значение в `.env` должно стоять
  до запуска деплоя, иначе миграция запишется выполненной, ничего не создав;
- **миграция правит данные** (схлопывание дублей, пересчёт, уникальный индекс поверх
  существующих строк) — на больших базах это планируется отдельно, а не «заодно с деплоем».

Про `env()` в миграции:

> `2026_08_05_112302_create_store_matrix_tables.php` выходит из `up()`, если не
> заполнены `USE_STORE_MATRIX` и `DB_DATABASE_PBE`. Прогон до правки `.env`
> запишет миграцию как выполненную, а таблиц не создаст. Чинится удалением записи
> из таблицы `migrations` и повторным прогоном.

## 6. Права и сидеры

`RightSeeder` прогоняет `deploy.sh` — «прогнать сидер» действием релиза **не является**.

Действие релиза здесь другое и его постоянно забывают: **сидер право заводит, но никому
его не выдаёт**. Новое право выписывается точным ключом (`application.mobile.auth`,
`visits.store.matrix`) и сопровождается строкой «раздать таким-то ролям или людям» — без
неё функция не работает ни у кого, и это выглядит как несработавший релиз.

Права, создаваемые под условием (`if (env('USE_STORE_MATRIX'))`), появятся только
после включения ключа. Это ещё одна причина держать порядок шагов.

Права, которые заводятся не сидером, а в коде клиента
(`App\Clients\<Client>\Client::getSpecialRights()`), сидером не появятся вовсе — это
отдельная строка, и адресат у неё тот же.

## 7. Модули

Каждый модуль `pbeadmin` — отдельный репозиторий со своими тегами. `deploy.sh` переключает
каждый активный модуль на **его собственный последний тег**, поэтому вопрос ровно один:
входит коммит задачи в тег своего модуля или нет.

**Указатели сабмодулей не отслеживаются** — деплой их не читает, сверять по ним нельзя.

```bash
for m in ../pbeadmin/modules/*/; do
  MT=$(git -C "$m" tag -l 'prod-v*' | sort -V | tail -1)
  [ -n "$MT" ] && git -C "$m" log "$MT" --oneline --grep='CRM-1089' -i -1 \
    | sed "s|^|$(basename $m) $MT |"
done
```

Две ловушки при обходе:

- **каталог модуля подключён к чужому репозиторию.** Сверь `git -C <m> remote get-url origin`
  с `.gitmodules` в теге: каталог, смотрящий на `pbeadmin.git`, даёт ложные совпадения по
  коммитам ядра;
- **модуль без единого `prod-*` тега.** Деплой откатит его на ветку по умолчанию и втащит
  всё, что там лежит. Это пункт release actions «проверить до запуска деплоя».

Одна задача может лежать в нескольких модулях сразу — порядок «ядро → модули → миграции»
`deploy.sh` держит сам, отдельным пунктом его писать не надо.

В сводке по модулям полезно свести таблицей: модуль → дельта тегов → задачи релиза внутри.
Это приложение, а не чек-лист.

## 8. Ручные шаги и порядок

Всё, что не делается релиз-тегом:

- создание пользовательских полей и справочных значений руками;
- запуск загрузок и разовых команд;
- живой планировщик на инстансе (если статусы пересчитываются по расписанию, без
  планировщика после раскатки «ничего не поедет», и это не баг);
- предрелизные пункты, требующие клиента, — они идут менеджеру клиента заранее, не в день
  релиза.

Если у задачи есть подзадача «Релиз» — её план первичен, и ручные шаги берутся
оттуда ([этап 5](../regulations/crm-lifecycle/05-ocenka-zadachi.md), 4.3.1).

## 9. Как проверить после выкатки

Одна–две проверяемые строки: на каком экране, при каких данных, что должно быть
видно. Берётся из плана тестирования задачи. Если сценарий на тестовой среде не
воспроизводится (интеграция, дубли из внешней системы) — так и писать:
«наблюдаем по проду», честнее, чем пустая галочка.

## Типовые ловушки

| Ловушка | Чем кончается |
|---|---|
| Сверка по `main`, а не по тегу продуктива | Зелёная галочка там, где на проде изменения нет |
| Выбор тега по дате (`--sort=-creatordate`), а не по версии (`sort -V`) | Сверка идёт не по тому тегу, который возьмёт деплой |
| Сравнение SHA из `main` с тегом через `merge-base` | Ложный блокер: в релизной ветке коммит перебазирован, SHA другой |
| Поиск только по ключу задачи | Задача «не найдена», хотя коммит есть — ключ в сообщении стоит не всегда |
| Миграции и сидер выписаны как действия релиза | Чек-лист тонет в том, что деплой делает сам |
| Новое право отмечено как «заведено сидером» и на этом всё | Право есть, никому не выдано, функция не работает ни у кого |
| Сверка по рабочему дереву | «Ключа нет в коде» — а он есть, каталог модуля отстал |
| Конфиг включён не на том инстансе | Клиент видит чужую функциональность; корень — клиент из выгрузки без тега |
| Миграция прогнана до правки `.env` | Миграция «выполнена», таблиц нет |
| Забыт бамп сабмодуля | Ядро приехало, поведение прежнее, задача «не работает» |
| Названия контейнеров/справочников взяты из дефолта в коде | Кнопка не появляется, дефолт не совпал с данными инстанса |
| Patch note без «где смотреть» | Менеджер клиента не может показать клиенту, что оплачено |
