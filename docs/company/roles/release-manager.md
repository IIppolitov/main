## Часть 1. Обязанности по регламенту

Роль участвует в **девяти этапах из четырнадцати**
[жизненного цикла задачи CRM](../../regulations/crm-lifecycle/README.md) и
отвечает за два целиком. Ещё на одном — оценке — она держатель очереди: все
задачи компании, ждущие оценки, физически стоят на ней.

| Этап | Роль | Что делает |
|---|---|---|
| [2. Валидация](../../regulations/crm-lifecycle/02-validacija.md) | Получатель | Принимает в очередь на оценку подзадачи задач **ускоренного порядка** — они приходят от PO сразу в статус «Оценка задачи», минуя бизнес-анализ |
| [4. Согласование проработки](../../regulations/crm-lifecycle/04-soglasovanie-prorabotki.md) | Получатель | Принимает в очередь на оценку подзадачи после согласования постановки клиентом. Очередь ведётся FIFO, если иное не согласовано |
| [5. Оценка задачи](../../regulations/crm-lifecycle/05-ocenka-zadachi.md) | Координатор | **Держатель очереди:** исполнитель всех подзадач на этапе. Организует сессии, заполняет семь **полей разбивки** основной задачи, беря экспертизу у тимлида (ревью), CTO (деплой) и закладывая риски сама. Складывает часы закрытых «Консультаций» в поле «Оценка: БА». При наличии подзадачи «Релиз» — её исполнитель: запрашивает у CTO оценку деплоя и передаёт КАМу предрелизные пункты клиента |
| [6. Согласование оценки](../../regulations/crm-lifecycle/06-soglasovanie-ocenki.md) | Консультант | Разъясняет состав оценки. При возврате задачи с вопросом к оценке принимает её обратно в «Оценка задачи» |
| [7. Сбор задач в проекты](../../regulations/crm-lifecycle/07-sbor-v-proekty.md) | Участник | Сообщает КАМу о доступности ресурсов. **Вместе с КАМом заводит две обязательные задачи релиза приложения** (4.5) — «Подготовка релиза» и «Регресс приложения»: кто раньше увидел приближающийся релиз |
| [8. Набор спринтов](../../regulations/crm-lifecycle/08-nabor-sprintov.md) | **Ответственный** | Сессия планирования с тимлидами и PO, расчёт ёмкости, проверка критериев готовности, утверждение состава, добавление объектов в проект спринта. **Админка:** при наборе первого из двух спринтов релиза заводит проект `Релиз Админка <NN>-<NN>. Вне спринта`. **Прилага:** сверяет с КАМом, что задачи релиза заведены, и включает «Подготовку релиза» в спринт |
| [9. Распределение задач](../../regulations/crm-lifecycle/09-raspredelenie-zadach.md) | Консультант | Сообщает тимлиду состав спринта и приоритеты; при перегрузе вместе с ним исключает наименее приоритетные задачи |
| [10. Разработка](../../regulations/crm-lifecycle/10-razrabotka.md) | Координатор | Мониторит прогресс спринта. Срочная задача внутрь спринта — только с её согласия и с заменой на эквивалентную по трудоёмкости |
| [11. Тестирование и ревью](../../regulations/crm-lifecycle/11-testirovanie-i-revju.md) | Точка решения | Решает вместе с тимлидом: **ждать исправление или выпускать релиз без задачи.** У приложения пересобирается вся QA-сборка, поэтому цена задержки — весь релиз |
| [13. Релиз](../../regulations/crm-lifecycle/13-reliz.md) | **Ответственный** | Собирает состав **из проектов, а не по памяти**: админка — два спринта плюс проект «Вне спринта», прилага — спринт клиента. Открывает подзадачи «Релиз» и проверяет, что предрелизные пункты клиента закрыты. Готовит release notes, включая хотфиксы из «Вне спринта». Проверяет конфигурации, согласует время, уведомляет. После выкатки переводит подзадачи «Разработка» в «Демонстрация заказчику» и проставляет отметки в связанных задачах «Документация» |

Дополнительно в [процессе техподдержки](../../regulations/support-process.md),
этап 4 «Разбор беклога» — консультант: даёт график релизов и доступные окна для
хотфиксов.

### Ритмы релизов, за которые отвечает роль

| Команда | Спринт | Схема выпуска |
|---|---|---|
| Администрирование | 2 недели, плюс проект «Вне спринта» на каждый релиз | Спринт N + N+1 → 2 недели на фиксы → релиз |
| Приложение | 1 месяц; формат — помесячно на всех клиентов или один спринт на клиента — [открытый вопрос К-26](../../backlog.md) | Пилот (минимум неделя, ограниченная группа) → полный релиз |

## Часть 1а. Как следить за исполнением

Контроль за тем, что регламент выполняется, закреплён за ролью. Смысл не в том,
чтобы держать процесс в голове, а в том, чтобы смотреть в готовые фильтры с
понятной периодичностью.

Запросы ниже проверены в Трекере 19.08.2026, приведённые числа — масштаб на тот
день.

### Ежедневно — две минуты

**Очередь на оценку не растёт?**
```
Queue: CRM Status: "Оценка задачи" "Sort by": Created ASC
```
На 19.08.2026 — **32 задачи**. Смотреть на хвост: если самая старая ждёт больше
недели, сессий оценки не хватает.

**Что заблокировано и кем?**
```
Queue: CRM Status: "Требуется информация" Updated: <= today()-3d
```
На 19.08.2026 — **42 задачи из 51** не двигались три дня и дольше. Самая
запущенная зона: статус ставится легко, а снимать его никто не обязан.

### Еженедельно

**Запас готовых к набору:**
```
Queue: CRM Type: "Разработка" Status: "Готово к разработке"
```
На 19.08.2026 — **103 подзадачи**. Если запас тает, проблема выше по потоку — на
оценке или у БА.

**Внутренние дефекты, не вышедшие на прод:**
```
Queue: BUGREPORTS Resolution: empty()
```
На 19.08.2026 — **141 открытая**. Каждая — кандидат в ближайший спринт.

**Обращения поддержки, ждущие релиза:**
```
Queue: SUPPORTDEV Status: "Требуется релиз"
```
Должны попасть либо в спринт, либо в проект «Вне спринта».

### Раз в спринт

- Набор следующего ([этап 8](../../regulations/crm-lifecycle/08-nabor-sprintov.md)).
- Отчёт по закрывшемуся:
  ```bash
  automation/scripts/tracker-project-report.py <номер проекта>
  ```
  Даёт оценку, факт, возвраты на доработку и сроки. Возвраты считаются по истории
  статусов — по ним видно, где проседает качество: на ревью или на тесте.

### Раз в релиз

Состав из всех проектов релиза, включая «Вне спринта»; release notes; после
выкатки — перевод статусов и отметки в задачах «Документация».

### Раз в квартал

- Сходится ли «Оценка: деплой» с фактом по подзадачам «Релиз».
- Статистика по «Подготовке релиза» и «Регрессу приложения» — из неё выводится
  норматив, которого сейчас нет.

### Чего пока нельзя проверить фильтром

**Поля разбивки в фильтры API не попадают.** «Согласованная оценка», «Оценка:
тестирование», «Срочность БА» и остальные заведены как локальные поля очереди
`CRM`. Проверено 19.08.2026: язык запросов API их не видит ни по ключу, ни по
названию. Запрос «задачи в спринте без согласованной оценки» скриптом не
строится — автоматического контроля заполнения нет.

В интерфейсе Трекера фильтр по локальным полям обычно доступен, но проверяется
только в браузере. Вопрос вынесен в долг, К-29.

### Когда норма разошлась с практикой

Не подгонять одно под другое молча. Расхождение — факт, который фиксируется:
сообщить директору департамента ИТ, что по регламенту X, а фактически Y.
Открытые вопросы копятся в [долге](../../backlog.md) и разбираются там, а не
решаются каждый раз заново.

Известные на сегодня:

- **основные задачи в спринтах** — иногда вместо подзадачи «Разработка» кладут
  задачу целиком, и ёмкость считается неверно;
- **формат спринта прилаги не выбран** (К-26);
- **планирование работы QA не описано** — решено, что подзадачи «Тестирование» в
  спринт разработки не идут, чем заменить, ещё не выбрано (К-25).

## Часть 2. Должностные обязанности

*Связный текст без ссылок на этапы — для онбординга, договора, ответа на аудит.*

Релиз-менеджер отвечает за планирование, комплектование и выпуск релизов
CRM-системы.

**Планирование.** Организует и ведёт сессии оценки задач: формирует очередь
рассмотрения, обеспечивает участие тимлидов, бизнес-аналитиков и QA. Сводит
полученные оценки в поля разбивки задачи — по видам работ, включая буфер на
риски, — из которых складывается итоговая цифра для согласования с клиентом.

**Набор спринтов.** Проводит планирование совместно с тимлидами и Product Owner.
Оценивает доступную ёмкость команд с учётом текущей загрузки, отпусков и
технического долга. Проверяет готовность задач к работе: согласованность
проработки, утверждённость дизайна, согласованность оценки с клиентом. Утверждает
состав спринта и фиксирует его в системе управления задачами.

**Сопровождение разработки.** Отслеживает прогресс спринта, выявляет отставания,
информирует тимлидов и руководство о рисках срыва сроков.

**Выпуск релизов.** Формирует состав релиза, готовит release notes с описанием
изменений и затронутых компонентов, проверяет готовность конфигураций,
согласовывает время выпуска с командами и уведомляет заинтересованные стороны.
Соблюдает установленные ритмы выпуска, различные для команд администрирования и
приложения.

**Контроль исполнения процесса.** Отслеживает соблюдение регламента жизненного
цикла задачи по всей цепочке: полноту заполнения оценок, движение задач по
статусам, отсутствие зависших и потерянных задач. Регулярно проверяет состояние
очередей по установленным фильтрам и выносит расхождения нормы и практики
руководителю департамента.

**Информационное обеспечение.** Предоставляет коллегам сведения о доступности
ресурсов, составе спринтов, графике релизов и доступных окнах для срочных
исправлений. Ведёт очередь `SUPPORTINFO` — запросы, по которым требуется
информация.

## Что в роль не входит

Разграничение, чтобы не спорить в рабочем порядке.

| Не входит | К кому идти |
|---|---|
| Оценка трудоёмкости задач | Тимлиды и команды — роль сводит их оценки, но своих не даёт |
| Приоритизация задач клиента | КАМ клиента; приоритеты продукта — Product Owner |
| Назначение исполнителей на задачи | Тимлид на [этапе 9](../../regulations/crm-lifecycle/09-raspredelenie-zadach.md) |
| Деплой на продакшн | CTO ([этап 13](../../regulations/crm-lifecycle/13-reliz.md)) — роль координирует выпуск, но не выполняет его технически |
| Решение о выпуске хотфикса | Тимлид на разборе беклога; роль лишь сообщает доступные окна |
| Приёмка результата клиентом | КАМ ([этапы 12 и 14](../../regulations/crm-lifecycle/12-testirovanie-klientom.md)) |
| Качество кода и тестирование | Тимлид (ревью) и QA-инженер |
| Принуждение к соблюдению регламента | Роль **видит и фиксирует** расхождения, но не применяет мер: спор и дисциплина — к директору департамента ИТ |

## Взаимодействие

| С кем | По каким вопросам |
|---|---|
| Тимлиды разработки | Оценка, ёмкость команд, готовность задач, техническое обеспечение релиза |

## Открытые вопросы

- **Замещения нет.** Роль исполняется одним человеком, участвует в девяти этапах
  из четырнадцати, отвечает за два и держит очередь на оценку. При отсутствии
  останавливаются набор спринтов и релизы — [долг](../../backlog.md), С-10.
- Разное описание назначения очереди `SUPPORTINFO` в регламентах — К-1 в долге.
- **Автоматического контроля заполнения полей оценки нет** — локальные поля
  очереди не фильтруются через API, К-29.
- **Оценки для «Подготовки релиза» и «Регресса приложения» нет** — норматив
  выводится из факта списаний за несколько релизов, К-27.
