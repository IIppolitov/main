Разбор запроса на оцифровку ресурсов (письмо от 12.08.2026): что из
запрошенного измеримо сегодня, что измеримо после доработки консоли, а что не
измеримо в принципе, пока не изменится процесс.

Инструмент — раздел «Ресурсы и загрузка» в [pbeconsole](../projects/pbeconsole.md).
Постановка: [pbeconsole/docs/specs/capacity-analytics.md](../../../pbeconsole/docs/specs/capacity-analytics.md).

---

## Главный тезис для разговора

Цифры по большинству блоков **уже лежат в Трекере** — не хватает не данных, а
витрины и историчности. Это закрывается доработкой консоли.

Но три вещи из запроса не считаются никаким инструментом, потому что данных не
существует: **контрактные обязательства, время первой реакции по SLA и причины
инцидентов**. Это решения по процессу, а не задача на разработку, и без них
соответствующие блоки закроются частично.

И отдельно: точность любой метрики упирается в дисциплину заполнения полей
(оценка, списание часов, мнемоника клиента). Поэтому первое, что нужно показать, —
**покрытие данными**, а не графики: «эта цифра посчитана по 60 % задач» меняет
разговор сильнее, чем сама цифра.

## Готовность по блокам запроса

Условные обозначения: 🟢 есть сейчас · 🟡 данные есть, нужна витрина ·
🔴 данных нет, нужно менять процесс.

### Блок 1. Объём бэклога и динамика по месяцам

| Метрика | Источник | Готовность |
|---|---|---|
| Бэклог в задачах и часах: всего, по клиентам, по очередям, по типам | Трекер, поля `Оценка` / `Затрачено` | 🟡 этап 1 |
| Динамика по месяцам, тренд на рост/снижение | Восстанавливается назад по датам создания и закрытия задач — **история доступна сразу, ждать накопления не нужно** | 🟡 этап 1 |
| Возраст бэклога (сколько задач висит больше полугода) | То же | 🟡 этап 1 |
| Бэклог **по подписанным контрактам** | Источника нет: проданный объём по договору живёт у КАМов, в Трекер не попадает | 🔴 нужно решение |

Ограничение по часам: задачи без оценки в сумму не попадают, поэтому «объём в
часах» — оценка снизу. Размер невидимой части показываем рядом.

### Блок 2. Время на закрытие «хвостов» (min/max) с учётом Roche и Servier

Это не измерение, а расчёт: `остаток бэклога в часах / доступная мощность`.

| Что нужно | Готовность |
|---|---|
| Остаток бэклога в часах | 🟡 этап 1 |
| Фактическая пропускная способность (сколько команда реально списывает в месяц и куда) | 🟢 ночной синк часов Трекера в консоли уже работает |
| Справочник мощности: FTE по командам, доступные часы, отпуска | 🟡 этап 4, справочник заводится руками |
| Объём новых проектов Roche и Servier | 🔴 **их ещё не оценивали** |

Последнее — принципиально. Оценка появляется только на [этапе 5 жизненного цикла](../regulations/crm-lifecycle/05-ocenka-zadachi.md),
после бизнес-анализа и согласования проработки. Пока новые проекты не прошли БА,
любая цифра по ним — экспертное предположение, а не расчёт. На встрече это стоит
проговорить прямо: либо мы даём интервал с широкими допущениями, либо сначала
прогоняем скоуп новых проектов через БА и оценку — и это само по себе загрузка
команды бизнес-анализа, которую нужно спланировать.

Интервал min/max будет широким ровно настолько, насколько велика доля
неоценённого бэклога. Сузить его можно только оценкой, не расчётом.

### Блок 3. Данные по разработке

| Метрика | Источник | Готовность |
|---|---|---|
| Lead time (от создания до закрытия), медиана и P85 | Даты создания/закрытия задачи — приходят из API бесплатно | 🟡 этап 2, история сразу |
| Cycle time (время в работе) | История смены статусов — начинает копиться с запуска синка, точность сутки | 🟡 этап 2, вперёд |
| **Время по этапам жизненного цикла**: сколько задача ждала валидации, БА, согласования КАМ, оценки | То же | 🟡 этап 2, вперёд |
| Дефекты до релиза | Очередь `BUGREPORTS` | 🟡 этап 2 |
| Дефекты, утёкшие на прод | Очереди `SUPPORTDEV` / `SUPPORTANALYTIC` / `SUPPORTDIGITAL` | 🟡 этап 2 |
| Возвраты релиза со стадии на стадию | Консоль, карточка релиза | 🟢 есть сейчас |
| Возвраты задач (тестирование → разработка и т. п.) | История статусов | 🟡 этап 2, вперёд |

Отдельно стоит выделить «время по этапам». В разговоре о нехватке ресурсов это
самая содержательная метрика: она показывает, стоит ли очередь на разработке или
на согласованиях. По [регламенту](../regulations/crm-lifecycle/README.md) из
14 этапов задачи только два — собственно разработка; ожидание согласований
и оценки может оказаться больше, и тогда ответ на вопрос «нужны ли ещё люди в
разработку» будет другим.

### Блок 4. Работа с клиентами: тикеты, SLA, инциденты

| Метрика | Источник | Готовность |
|---|---|---|
| Категории и приоритеты тикетов, объём по клиентам и месяцам | Очереди поддержки | 🟡 этап 3 |
| Доля решённых **в срок SLA** | Норматив оцифрован в консоли (SLA клиента), дедлайн проставляется в задачу при создании — факт сверяется с ним | 🟡 этап 3 |
| Время **первой реакции** | Нигде не фиксируется | 🔴 нужно решение |
| Повторные обращения | Эвристика: тот же клиент + компонент в окне N дней либо связь задач | 🟡 этап 3, как оценка снизу |
| Эскалации | Определения «эскалация» в регламенте нет | 🔴 нужно определить |
| **Причины инцидентов** | Поля «причина» в очередях нет — данных не существует | 🔴 нужен атрибут в очереди |
| Доля milestones в срок | Что считать milestone — не определено | 🔴 уточнить у автора запроса |

SLA решения — хорошая новость: норматив по каждому клиенту уже заведён в консоли
(категории, время реакции и решения, единицы), и при создании задачи техподдержки
дедлайн считается по рабочему календарю и проставляется в Трекер. То есть
сравнивать факт с нормативом можно, дополнительной разметки не требуется.

SLA реакции — плохая: норматив есть, факта нет. Честно измерить его можно только
если в очередях поддержки появится явная отметка «принято в работу». Суррогат по
смене статуса даёт точность в сутки, что для норматива «1 час» бессмысленно.

Причины инцидентов — типовой запрос, который невозможно закрыть задним числом.
Пока в очереди `SUPPORTDEV` нет обязательного поля с классификатором причин,
статистики не будет никогда, сколько бы витрин мы ни построили. Решение —
организационное: согласовать перечень причин и сделать поле обязательным при
закрытии. Смежно с [Р-3 в бэклоге](../backlog.md) (классификация категорий в
регламенте техподдержки уже двоится).

### Блок 5. План-факт трудозатрат

| Метрика | Источник | Готовность |
|---|---|---|
| План-факт по проекту: оценка / затрачено / отклонение | Консоль, «Аналитика трекера → Итоги по проекту» | 🟢 есть сейчас |
| План-факт по релизу админки и приложения | Консоль, карточки релизов | 🟢 есть сейчас |
| Списанные часы по сотрудникам и дням | Консоль, ночной синк worklog | 🟢 есть сейчас |
| Куда ушли часы: по очередям, проектам и **клиентам** (мнемоника в теге) | То же | 🟢 есть сейчас |
| Сводный план-факт по клиентам и месяцам, с историей | — | 🟡 этап 4 |
| **Покрытие**: какая доля работы вообще списывается в Трекер | — | 🟡 этап 0 |

Последняя строка важнее остальных: пока неизвестно, какая доля рабочего времени
попадает в списания, план-факт нельзя предъявлять как аргумент — его первым делом
оспорят. Поэтому этап 0 («Качество данных») в постановке идёт раньше графиков.

## Что можно показать уже на встрече, без разработки

1. **План-факт по клиентским проектам** — экран «Аналитика трекера → Итоги по
   проекту» в консоли: оценка, затрачено, отклонение, где вылезли за оценку.
   Работает по любому квартальному проекту клиента.
2. **Куда уходят часы** — дашборд «Активности по сотрудникам»: списанные часы за
   период, топ проектов, очередей и клиентов.
3. **Релизы** — карточки релизов приложения и админки: готовность, часы, стадии,
   возвраты.
4. **Разовая выгрузка lead time** по очереди `CRM` за 12 месяцев — считается
   скриптом по датам создания и закрытия задач, не требует доработки консоли.
   Стоит подготовить к встрече: это единственная метрика из блока 3, которую можно
   показать сразу и с историей.

Остальное честнее показать не цифрами, а этой таблицей готовности: она объясняет,
почему часть ответов появится через доработку, а часть — только через изменение
процесса.

## Порядок работ

| Этап | Что даёт | Закрывает блок |
|---|---|---|
| 0. Качество данных | На какой доле задач цифрам можно верить | сквозной |
| 1. Бэклог и динамика | Объём, тренд по месяцам, возраст бэклога | 1 |
| 2. Поток разработки | Lead/cycle time, время по этапам, дефекты, возвраты | 3 |
| 3. Клиенты и SLA | Тикеты, SLA-факт, повторные обращения | 4 |
| 4. Мощность и сценарии | Расчёт сроков min/max, сводный план-факт | 2, 5 |

Этапы 0–1 закрывают бо́льшую часть запроса и дают историю сразу, без ожидания
накопления данных. Оценка трудозатрат — после уточнения объёма задач в рабочих
очередях и ответа по вопросу 1.

Ограничение по ресурсу: консоль разрабатывает один человек (ИТ-директор,
см. [П-2 в бэклоге](../backlog.md)). Раздел, на котором будет строиться
управленческая аргументация, этот риск усиливает — это стоит проговорить в том же
разговоре о ресурсах.
