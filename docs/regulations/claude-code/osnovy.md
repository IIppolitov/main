## 1. Зачем нам это

Claude Code — не автодополнение и не «пишет код за тебя». Мы берём его ради трёх вещей,
и именно они определяют, как выстроен процесс ниже.

**Разбор до кода.** Задача из Трекера приходит с комментариями, скриншотами, ссылками
на спеку и половиной контекста в головах. Агент выгружает всё это, читает целиком
и возвращает: как он понял задачу, чего в ней не хватает и где, по его мнению, копать.
Это дешёвая проверка постановки — до того, как кто-то потратил на неё три дня.

**Ревью.** Отдельный агент, который читает diff свежим взглядом, не устаёт к пятому файлу
и не жалеет автора. Он не заменяет человека, он снимает с человека механический слой:
регрессии в соседних брендах, забытые ветки конфигов, несогласованные контракты.

**Документация.** Самая нелюбимая часть работы и самая ценная для остальных: сводка
изменений для пользователя, план ручного тестирования, отчёт по багфиксу для техподдержки,
сообщение клиенту. Агент делает это за минуты и не «забывает» — если ему дали понятную
задачу и результат работы.

Обратная сторона у всех трёх одна: **качество на выходе не выше качества постановки
на входе.** Если ты сам не понимаешь, что и как надо сделать, — агент не поймёт и подавно.
Он не остановится и не скажет «я не понял»: он выдаст уверенный, связный и неверный текст.
Отсюда всё, что написано ниже.

## 2. Первый запуск

### 2.1. Доступ

**Подписка приходит подарком на личную gmail-почту** (решено 14.08.2026). Заявка —
директору департамента информационных технологий: от тебя нужен адрес gmail, на него
уходит подарочная подписка, дальше ты активируешь её сам и входишь под этой учётной
записью. Корпоративных seat'ов у нас нет.

**При регистрации обязательно отключи использование данных для обучения.** На шаге
создания учётной записи (и позже в `Settings → Privacy`) есть переключатель, разрешающий
использовать твои переписки и приложенные материалы для обучения моделей. Его надо снять
до первой рабочей сессии: через агента проходят код, выгрузки Трекера и Вики, конфиги
клиентов — то есть чужая коммерческая информация, распоряжаться которой мы не вправе.
Проверить состояние переключателя — минута; сделать это задним числом для уже отправленных
данных нельзя. Если сомневаешься, что снял, — зайди и посмотри ещё раз, прежде чем работать.

Без VPN инструмент не работает; конфигурацию для него выпускает технический директор — это второе обращение,
не то же самое, см. п. 2.2.

Следствие, которое надо понимать обеим сторонам: учётная запись личная, и при увольнении
она остаётся у сотрудника — отзывается не она, а всё остальное (репозитории, Трекер, VPN)
плюс прекращается оплата следующего периода. Отсюда правило: **рабочие данные живут
в рабочих системах, а не в переписке с агентом.** Что именно нельзя отдавать агенту —
п. 4.5, и это не формальность, а прямое следствие выбранной схемы выдачи.

### 2.2. VPN

Для работы Claude Code нужен включённый VPN — клиент **Happ** и **отдельное подключение**
под этот инструмент, со своими правилами роутинга: рабочие ресурсы (Трекер, Вики, стенды,
GitHub) ходят мимо туннеля напрямую.

Установка, добавление конфигурации и обязательная настройка роутинга — в отдельном
документе: [«VPN Happ: подключение и роутинг»](../vpn/happ.md). Настройка одноразовая,
занимает несколько минут; пропущенный шаг с роутингом заворачивает в туннель весь трафик
машины, поэтому его не пропускаем.

VLESS-строка персональная и равносильна паролю: в парольный менеджер, не в чат, не в задачу,
не в репозиторий.

### 2.3. Установка

Claude Code ставится один раз на машину и работает в терминале; есть расширения для VS Code
и JetBrains — ставь то, в чём работаешь. Вход — командой `/login` под той учётной записью,
на которую пришла подписка (п. 2.1).

#### `gh` — консольный клиент GitHub

Ставится отдельно и нужен затем, чтобы агент **читал Pull Request'ы**: дифф, обсуждение
и — главное — замечания ревьюера на строках кода. Без него разбор замечаний выглядит так:
человек копирует комментарии в чат руками, с потерями и без привязки к строкам.

```bash
brew install gh          # macOS
sudo apt install gh      # Ubuntu / WSL2
gh auth login            # один раз на машину, дальше логин помнится
```

**Авторизацию делает человек, не агент.** `gh auth login`, `logout` и `token` агенту
запрещены: это твоя учётная запись GitHub и твои права в ней. Проверить, что всё встало:
`gh auth status`.

Что агент с этим делает: читает PR и все три сорта комментариев к нему, комментирует PR
и публикует ревью. **Создание PR, мердж, approve, request-changes и закрытие остаются
за человеком** — они запрещены технически, см. п. 4.7.

### 2.4. Запускать из каталога проекта — не из папки-обёртки

Claude Code ищет `CLAUDE.md` и каталог `.claude/` от того места, откуда его запустили.
Запуск из родительского каталога (`Powbee/`) даёт сессию **без** контекста проекта: без
агентов, без `/pbe-bug` и `/pbe-task`, без ограничений. Внешне всё работает — просто хуже и опаснее.

```bash
cd ~/…/pbeadmin && claude      # правильно
cd ~/…/Powbee   && claude      # неправильно: обвязка не подхватится
```

Проверка, что всё на месте: в сессии набери `/` — в списке должны быть `/pbe-bug` и `/pbe-task`.
Нет — ты не в том каталоге.

### 2.5. Доступ к Яндекс Трекеру и Вики

`/pbe-bug` и `/pbe-task` ходят в Трекер за задачей, комментариями и вложениями, а в Вики —
за страницами, на которые задача ссылается. Часть команд ходит ещё и в консоль мониторинга
за конфигом клиента. Нужны три значения. Хранить их можно по-разному — Keychain на macOS,
файл в `~/.config/` или `libsecret` на Linux, общая база KeePass (все варианты ниже), —
но **не в репозитории и не в `.env` проекта**. Способ по умолчанию, на macOS:

```bash
security add-generic-password -s yandex-tracker     -a "$USER" -w '<OAuth-токен>'
security add-generic-password -s yandex-tracker-org -a "$USER" -w '<ID организации>'
security add-generic-password -s pbe-console        -a "$USER" -w '<токен консоли>'
```

Имена сервисов (`-s`) менять нельзя — скрипты ищут ровно эти. Делается один раз на машину;
проверка — `security find-generic-password -s yandex-tracker -w` должна вернуть токен.

**На Linux** команды `security` нет — это утилита macOS. Скрипты ищут учётные данные
в трёх местах по порядку: переменные окружения → файл в `~/.config/` → Keychain. На Linux
работает второй способ — файлы вне репозитория с `chmod 600`:

```bash
mkdir -p ~/.config/yandex-tracker ~/.config/pbe-console
printf 'YANDEX_TRACKER_TOKEN=<OAuth-токен>\nYANDEX_TRACKER_ORG_ID=<ID организации>\n' \
  > ~/.config/yandex-tracker/env
printf 'PBE_CONSOLE_TOKEN=<токен консоли>\n' > ~/.config/pbe-console/env
chmod 600 ~/.config/yandex-tracker/env ~/.config/pbe-console/env
```

Пути и имена переменных менять нельзя — скрипты читают ровно их. Проверка та же, что
на macOS: `automation/scripts/tracker-issue.sh CRM-1 | head -5` должен вернуть задачу,
а не «нет доступа».

Кому мало файла с правами `600` — храни токены в системном хранилище (GNOME Keyring /
KWallet через `libsecret`) и экспортируй их в окружение при старте оболочки:

```bash
secret-tool store --label='yandex-tracker' service yandex-tracker      # ввод токена — с клавиатуры
secret-tool store --label='yandex-tracker-org' service yandex-tracker-org
secret-tool store --label='pbe-console' service pbe-console

# в ~/.bashrc или ~/.zshrc
export YANDEX_TRACKER_TOKEN=$(secret-tool lookup service yandex-tracker)
export YANDEX_TRACKER_ORG_ID=$(secret-tool lookup service yandex-tracker-org)
export PBE_CONSOLE_TOKEN=$(secret-tool lookup service pbe-console)
```

Сами скрипты в `libsecret` не ходят — они видят только готовые переменные окружения,
поэтому строки с `export` обязательны. Токены с клавиатуры, не из истории команд: строка
вида `secret-tool store … <токен>` осядет в `~/.bash_history`, а вариант с `printf` выше —
разово и в файл, который потом закрыт правами.

**Вариант с KeePass** — если ты и так держишь пароли в `.kdbx` и не хочешь третьего места
хранения. Работает одинаково на macOS, Linux и в WSL, нужен `keepassxc-cli` (входит
в KeePassXC). Заводишь в базе три записи с полем «пароль» и любым удобным именем — здесь
они лежат в группе `powbee`:

```
powbee/yandex-tracker       → пароль = OAuth-токен
powbee/yandex-tracker-org   → пароль = ID организации
powbee/pbe-console          → пароль = токен консоли
```

Достаём их в окружение одной командой — база открывается один раз, мастер-пароль
спрашивается один раз за сессию терминала:

```bash
# в ~/.bashrc или ~/.zshrc
pbe-secrets() {
  local db="$HOME/…/powbee.kdbx" pw
  read -rsp "KeePass: " pw; echo
  export YANDEX_TRACKER_TOKEN=$(printf '%s\n' "$pw" | keepassxc-cli show -q -s -a Password "$db" powbee/yandex-tracker)
  export YANDEX_TRACKER_ORG_ID=$(printf '%s\n' "$pw" | keepassxc-cli show -q -s -a Password "$db" powbee/yandex-tracker-org)
  export PBE_CONSOLE_TOKEN=$(printf '%s\n' "$pw" | keepassxc-cli show -q -s -a Password "$db" powbee/pbe-console)
  unset pw
}
```

Дальше перед работой — `pbe-secrets`, ввёл мастер-пароль, и в этом терминале `/pbe-bug`,
`/pbe-task` и остальные скрипты видят токены. Ключевое слово — «в этом»: переменные видны
только процессам, запущенным из той же оболочки, поэтому `claude` поднимай в том же окне,
уже после `pbe-secrets`. Сессия, открытая кнопкой в IDE, о них не знает — там работают
только Keychain и файл в `~/.config/`. Переменные живут только в текущей сессии
оболочки: закрыл окно — токены исчезли, на диск в открытом виде не попали. Цена — вводить
мастер-пароль после каждого перезапуска терминала; тем, кого это раздражает, лучше подойдёт
Keychain (macOS) или файл в `~/.config/` (Linux).

Что важно не сделать: не подставлять мастер-пароль в команду аргументом
(`keepassxc-cli … --password …`) и не класть его в отдельный файл рядом с базой — тогда
`.kdbx` перестаёт быть защищённым и превращается в тот же файл с токенами, только длиннее.

| Что | Где взять |
|---|---|
| `yandex-tracker` — OAuth-токен | получаешь сам в консоли Яндекса: [инструкция Трекера](https://yandex.ru/support/tracker/ru/concepts/access). Токен персональный, никому не передаётся |
| `yandex-tracker-org` — ID организации | у директора департамента информационных технологий |
| `pbe-console` — токен консоли мониторинга | у директора департамента информационных технологий |

Токен консоли выдаётся под человека и отзывается при увольнении — не пересылай его коллеге
«чтобы быстрее», пусть придёт за своим.

Отдельный токен для Вики обычно не нужен: организация та же, и если у OAuth-приложения есть
скоуп Вики, подходят трекерные учётные данные.

Детали по конкретному проекту — в `.claude/scripts/README.md` твоего репозитория: там же
описано, что именно каждый скрипт запрашивает и какие права нужны токену консоли.

Токен персональный: под ним агент видит ровно то, что видишь в Трекере и Вики ты. Ни одного
документа, закрытого для тебя, он не откроет — и наоборот, всё, что открыто тебе, попадёт
в контекст сессии. Второе важнее: смотри, что выгружаешь.

### 2.6. Доступ к базе данных

`/pbe-bug` и `/pbe-task` умеют смотреть в боевую базу, когда симптом задачи про данные.
Ходят они туда не напрямую, а через `.claude/scripts/db-query.sh` — обёртка подставляет
сервер, логин и пароль, а `sqlcmd` и текст запроса пишет агент. Смысл обёртки один:
**пароль не попадает в контекст сессии и не уезжает во внешний сервис.** Поэтому прямой
`sqlcmd` закрыт deny-листом, и обходить его нельзя.

Границы использования — п. 4.5. Здесь только настройка.

#### Шаг 1. Поставить `sqlcmd` — один раз на машину

```bash
# macOS
brew tap microsoft/mssql-release https://github.com/Microsoft/homebrew-mssql-release
brew install mssql-tools18

# Ubuntu / WSL2 — по инструкции Microsoft для mssql-tools18
# https://learn.microsoft.com/sql/tools/sqlcmd/sqlcmd-utility
```

Проверка: `sqlcmd -?` печатает версию. Нативно в Windows обвязка не работает — нужен
WSL2 или Git Bash; в WSL держи `~/.config` в домашнем каталоге Linux, а не в `/mnt/c/...`,
иначе `chmod 600` ничего не значит.

#### Шаг 2. Прописать учётную запись — один раз на машину

Учётка личная, вида `svc_ai_<фамилия>`, одна на все контуры. Логин и пароль выдаёт
директор департамента информационных технологий.

```bash
mkdir -p ~/.config/pbe-mssql
echo 'PBE_MSSQL_USER=svc_ai_<фамилия>' > ~/.config/pbe-mssql/common.env
chmod 600 ~/.config/pbe-mssql/common.env

# macOS — пароль в Keychain, в файле его нет
security add-generic-password -s pbe-mssql -a "$USER" -w '<пароль>'
```

Имя сервиса `pbe-mssql` менять нельзя — скрипт ищет ровно его. Проверка:
`security find-generic-password -s pbe-mssql -w | wc -c` должно вернуть длину пароля.

**На Linux и в WSL** команды `security` нет. Пароль кладётся в тот же файл:

```bash
printf 'PBE_MSSQL_USER=svc_ai_<фамилия>\nPBE_MSSQL_PASSWORD=<пароль>\n' \
  > ~/.config/pbe-mssql/common.env
chmod 600 ~/.config/pbe-mssql/common.env
```

#### Шаг 3. Добавить сервер клиента

Профиль — это просто имя клиента и его сервер, одна строка. Мнемоника берётся
из консоли мониторинга: `vlt`, `srv`, `kz`.

```bash
echo 'PBE_MSSQL_SERVER=<сервер>' > ~/.config/pbe-mssql/<клиент>.env
chmod 600 ~/.config/pbe-mssql/<клиент>.env
```

Новый клиент — ещё один такой файл. Ни логина, ни пароля в нём быть не должно:
они одни на все контуры и лежат в `common.env`.

Руками это делать обычно не нужно: список серверов ведётся централизованно, и вместе
с учётной записью директор департамента информационных технологий выдаёт скрипт, который
заводит все профили разом и идемпотентен — прогонять его можно сколько угодно раз. Ручной
вариант выше нужен, только если твоего клиента в списке ещё нет.

Посмотреть, что уже настроено:

```bash
bash .claude/scripts/db-query.sh --profiles
```

#### Шаг 4. Проверить, что всё работает

```bash
# под кем подключились
bash .claude/scripts/db-query.sh --profile <клиент> -h -1 -W \
  -Q "SELECT SUSER_NAME()"

# какие базы видно
bash .claude/scripts/db-query.sh --profile <клиент> -h -1 -W \
  -Q "SET NOCOUNT ON; SELECT name FROM sys.databases ORDER BY name"
```

Первая команда должна вернуть твой логин `svc_ai_<фамилия>`. Если вернула чужой —
в профиле клиента остался лишний `PBE_MSSQL_USER`, убери его.

#### Как этим пользоваться

Обёртка подставляет сервер, логин и пароль — и больше ничего. Всё остальное это обычный
`sqlcmd`: флаги и текст запроса пишет тот, кто вызывает. Чаще всего вызывает агент сам,
по ходу разбора задачи; руками это те же команды.

```bash
# какие клиенты настроены и под какой учёткой ходим
bash .claude/scripts/db-query.sh --profiles

# запрос к базе клиента
bash .claude/scripts/db-query.sh --profile srv -d crmAdmin \
  -Q "SET NOCOUNT ON; SELECT COUNT(*) FROM consents.tPersonConsent WHERE RegionId IS NULL"

# запрос из файла — когда он длинный или пригодится ещё раз
bash .claude/scripts/db-query.sh --profile srv -d crmAdmin -i /tmp/proverka.sql

# справка по самой обёртке
bash .claude/scripts/db-query.sh --help
```

Четыре вещи, которые надо держать в голове.

**`--profile <клиент>` обязателен и умолчания не имеет.** Мнемоника та же, что в тегах
Трекера и в консоли, только строчными: `srv`, `vlt`, `bay`; тестовый контур — с суффиксом
`-qa` (`srv-qa`), общая дев-среда зовётся `dev` и клиентом не является. Умолчания нет
намеренно: серверы выглядят одинаково, и запрос, ушедший не в тот, вернёт чужие цифры —
правдоподобные и не те.

**База задаётся флагом `-d`.** На сервере клиента их несколько — своя под админку, своя
под согласия, — поэтому одного профиля мало. Какие базы видно, показывает запрос из шага 4.
Если у клиента база всегда одна и та же, её можно вписать в профиль строкой
`PBE_MSSQL_DB=<база>`: она подставится, когда `-d` не задан. Заданный `-d` всегда сильнее —
профиль задаёт умолчание, а не ограничение.

**Длинные флаги принадлежат обёртке, короткие уходят в `sqlcmd` как есть.** Обёрткиных
всего три: `--profile`, `--profiles`, `--help`. `-d`, `-Q`, `-i`, `-h`, `-W`, `-y`, `-s`
и прочее — это `sqlcmd`, и его документация применима целиком. Для читаемого вывода
пригодятся `-h -1` (заголовки один раз), `-W` (без хвостовых пробелов) и `SET NOCOUNT ON;`
в начале запроса. `-W` и `-y` вместе нельзя — вызов упадёт до подключения.

**Обёртка не проверяет, что ты спрашиваешь.** Она не разбирает текст запроса, не режет
выборку и не фильтрует персональные данные — раньше пыталась, и это оказалось иллюзией
защиты. Гарантия «только чтение» — это права учётной записи (`db_datareader` и ничего
кроме), а не текст скрипта. Что спрашивать можно, а что нельзя — п. 4.5; там правило,
а не предохранитель.

#### Сменить пароль

Меняется в двух местах, и порядок важен — сначала сервер, потом машина, иначе
между шагами доступ отвалится.

```bash
# 1. На сервере (это делает DBA, не ты):
#    ALTER LOGIN [svc_ai_<фамилия>] WITH PASSWORD = N'<новый>';

# 2. У себя, macOS: -U перезаписывает существующую запись
security add-generic-password -U -s pbe-mssql -a "$USER" -w '<новый>'

# 2. У себя, Linux / WSL: правишь строку PBE_MSSQL_PASSWORD в common.env
```

Пароль скомпрометирован — сообщи директору департамента информационных технологий
сразу, не жди удобного момента: учётка личная, и по журналу видно, что читали под ней.

#### Убрать клиента или всё разом

```bash
rm ~/.config/pbe-mssql/<клиент>.env          # больше не ходим к этому клиенту
rm -rf ~/.config/pbe-mssql                   # отключиться от баз совсем
security delete-generic-password -s pbe-mssql -a "$USER"   # macOS: убрать пароль
```

#### Если не работает

| Что видишь | Что это |
|---|---|
| `Не указан клиент` (код 3) | забыл `--profile <клиент>` |
| `Нет профиля клиента` (код 3) | нет файла `~/.config/pbe-mssql/<клиент>.env` — шаг 3 |
| `Профиль неполон` (код 3) | нет логина или пароля — шаг 2 |
| `Не найден sqlcmd` (код 4) | шаг 1 |
| `Login failed for user` | пароль разошёлся с сервером, либо учётку ещё не завели |
| `Cannot open database` | к этой базе доступа нет. Имя базы видно в списке — это не то же, что доступ |
| `The y and the W options are mutually exclusive` | флаги `sqlcmd`: `-y 0` и `-W` вместе нельзя, выбирай одно |

#### Тому, кто выдаёт доступ

Учётки заводятся в рабочем пространстве директора департамента информационных
технологий, файл `automation/sql/DBAProvisioning/init.sql`.

```sql
-- завести агента разработчику
EXEC dbo.spProvisionAiAgent @LoginName = 'svc_ai_<фамилия>', @Password = '<пароль>';
EXEC dbo.spProvisionUsers @DryRun = 1;   -- посмотреть план
EXEC dbo.spProvisionUsers @DryRun = 0;   -- применить

-- отозвать при увольнении
UPDATE dbo.tUserProvisioningList SET IsActive = 0 WHERE LoginName = 'svc_ai_<фамилия>';
EXEC dbo.spProvisionUsers @DryRun = 0;

-- сменить пароль
ALTER LOGIN [svc_ai_<фамилия>] WITH PASSWORD = N'<новый>';
```

Пароли раздаются через парольный менеджер — не почтой и не в чат. После первого
успешного прогона `spProvisionUsers` затирает пароль в таблице, в базе он открытым
текстом не остаётся.

**Проверять, что учётки действительно только на чтение — обязательно и регулярно.**
Обёртка текст запроса не проверяет; вся гарантия держится на правах учётной записи.
Скрипт проверки — `automation/sql/DBAProvisioning/check-ai-agents.sql`, запускается
под DBA, обходит все базы и печатает отклонения. Пустой результат — всё в порядке.

## 3. Из чего состоит наша обвязка

В каждом репозитории лежит одинаковый по составу набор. Понимать его надо, чтобы отличать
«агент так решил» от «ему так написано».

| Что | Где | Что это |
|---|---|---|
| Контекст проекта | `CLAUDE.md` в корне | Стек, архитектура, конвенции, чего не делать. Читается автоматически в каждой сессии. **Источник истины по коду проекта** |
| Суб-агенты | `.claude/agents/*.md` | Роли со своими инструкциями и правами: разработчик, тестировщик, ревьюер, безопасник. Вызываются по имени |
| Команды | `.claude/commands/pbe-*.md` | Готовые сценарии, вызываются через `/`. У нас это `/pbe-bug`, `/pbe-task` и `/pbe-review` |
| Скрипты | `.claude/scripts/` | Выгрузка из Трекера и Вики, конфиги клиента из консоли мониторинга, чтение и публикация комментариев PR |
| Предохранители | `.claude/settings.json` | Список команд, запрещённых агенту технически (см. п. 4.7) |
| Хуки | `.claude/hooks/` | Исполняемая проверка перед запуском команды — там, где списка запретов не хватает (см. п. 4.7) |

Всё это лежит в репозитории и версионируется вместе с кодом. Это не чья-то личная настройка —
это общий инструмент команды.

**Три команды — три точки жизненного цикла задачи.** `/pbe-task` работает до разработки
(разобрать постановку), `/pbe-review` — после (проверить, что сделано именно заказанное),
`/pbe-bug` — когда уехавшее в прод сломалось. Подробности по каждой — в документе своей
команды.

**Почему `pbe-` в имени.** Имя команды — это имя файла без расширения: `pbe-bug.md`
вызывается как `/pbe-bug`. Префикс тут не для красоты — у самого Claude Code есть встроенные
команды, и `/bug` у него занят (это отправка отчёта в Anthropic, а не разбор задачи). Свой
префикс разводит наши команды со встроенными: что бы Anthropic ни добавила в следующих
версиях, с `/pbe-*` оно не столкнётся. **Все наши команды начинаются с `pbe-`** — заводя
новую, держись того же правила.

Про подкаталоги стоит сказать отдельно, потому что вопрос всплывёт. Claude Code умеет делать
из подкаталога `.claude/commands/pbe/` неймспейс `/pbe:bug` — это проверено на версии 2.1.170
и видно в коде CLI. Но в документации такого контракта нет: там сказано только «имя файла без
расширения», а документированный неймспейс есть лишь у плагинов. Опираться на поведение,
которое не обещано, ради косметики двоеточия мы не стали — плоское имя даёт ту же защиту
и не отвалится на обновлении.

### 3.1. Первоисточник обвязки — рабочее пространство ИТ-директора

Скрипты выгрузки (`tracker-issue.sh`, `wiki-page.sh`, `db-query.sh`) лежат в
`.claude/scripts/` каждого проекта, но **ведутся в одном месте** — в рабочем пространстве
директора департамента ИТ, каталог `automation/scripts/`. Там же живут утилиты, которых
у команд нет вовсе: публикация в Вики, отчёты по спринтам, создание задач.

**То же самое с командами.** Эталонные версии `/pbe-bug`, `/pbe-task` и `/pbe-review` всех
проектов лежат в `automation/claude/commands/<проект>/`, туда же вынесены `settings.json`
и хук из `.claude/hooks/`. Причина та же,
что и со скриптами, только острее: команда — это инструкция, по которой агент работает
у всей команды разом, и расхождение между проектами замечается не по diff'у, а по тому,
что в одном репозитории разбор бага делается иначе, чем в соседнем.

Порядок такой: правка сначала туда, потом копия расходится по проектам задачей в Трекер.
Копия в `.claude/` — именно копия, а не форк: чинить у себя и не отдавать назад нельзя,
иначе через полгода четыре версии одного файла ведут себя по-разному.

## 4. Ядро: правила, обязательные для всех

| # | Правило |
|---|---|
| 1 | Задача начинается с `/pbe-task` или `/pbe-bug` — не с кода |
| 2 | Ревью-агент перед PR обязателен |
| 3 | Человеческое ревью PR обязательно всегда |
| 3а | Наружу отправляет человек: пуш, PR и мердж агент не делает |
| 4 | Артефакты в Трекер обязательны — без них задача не закрыта |
| 5 | Код — можно, боевые данные — нельзя |
| 6 | `CLAUDE.md` и `.claude/` правятся только через PR с согласованием директора департамента ИТ |

### 4.1. Задача начинается с `/pbe-task` или `/pbe-bug`

Любая задача из Трекера, за которую ты садишься с агентом, начинается с разбора:
`/pbe-task CRM-544` для постановки, `/pbe-bug SUPPORTDEV-1788` для бага. Обе команды **только читают**:
они не правят код, не создают файлов, не заводят веток — даже когда причина очевидна
и фикс в одну строку.

На выходе — блок «сверка понимания»: что агент прочитал, как понял задачу, в чём не уверен,
где собирается копать. **Этот блок надо прочитать и подтвердить или поправить.** Он и есть
главная ценность шага: остановить не туда идущую работу стоит одну минуту сейчас
и три дня потом.

Реализация начинается отдельной командой, после разбора. Подробности по своей команде —
в проектном документе.

Исключение: правка опечатки, вопрос по коду, эксперимент на выброс. Здравого смысла никто
не отменял — но «задача из Трекера, которую делаем и мержим» под исключение не подпадает.

**Страницы Вики разбор читает сам.** Постановки, требования и спецификации живут в Вики,
и задача обычно на них только ссылается. Раньше эту ссылку человек открывал руками
и пересказывал агенту — с потерями. Теперь, если в задаче или её комментариях есть ссылка
на Вики, разбор выгружает страницу и учитывает её, а в сверке понимания перечисляет,
что именно прочитал.

Из этого следует то, что надо проверять глазами:

- **Список прочитанных страниц — часть сверки понимания.** Пусто там, где ты ждал спеку,
  значит разбор шёл по одному тексту задачи, и выводы стоят соответственно.
- **Страницу, которую не удалось открыть, агент обязан назвать явно.** Молча пропущенная
  ссылка — это разбор по неполным требованиям, и заметить это позже дороже всего.
- **Скрипт только читает.** Записи в Вики нет: правку в первоисточник вносит человек.
- Текст приходит в разметке Вики (`{% note %}`, таблицы `#| |#`), а не в чистом markdown.
  Для разбора это не мешает, но при переносе в документ разметку переписывают, а не копируют.

### 4.2. Ревью-агент перед PR

Перед открытием PR изменения проходят ревью-агента проекта (`reviewer` в админке,
`code-reviewer` + `convention-reviewer` в приложении), плюс `security` / `security-auditor`
по триггерам, описанным в проектном документе. Замечания либо исправляются, либо явно
отклоняются с обоснованием в PR — молча проигнорировать нельзя.

Правки по замечаниям вносит тот, кто писал код (или его агент), после чего замечание
подтверждается снятым. Ревьюеры сами ничего не правят — это намеренно: тот, кто чинит,
не проверяет себя же.

**После открытия PR есть вторая команда — `/pbe-review`.** Она делает то, чего встроенный
`/code-review` не умеет: находит PR по ключу задачи, вычитывает критерии приёмки из постановки
и меряет реализацию **по ним**, а не по общим представлениям о хорошем коде. Вопрос «сделано
ли то, что заказано» встроенная команда задать не может — она не видит задачу. На выходе —
замечания с матрицей приёмки: каждый критерий и чем он подтверждён.

Замечания она по умолчанию **никуда не публикует** — печатает в терминал. Публикация в PR
только по явной просьбе или флагу `--post`. И даже опубликованное остаётся комментарием:
approve, request-changes и мердж ставит человек (п. 4.7).

### 4.3. Человеческое ревью PR — всегда

Агентское ревью — предварительный фильтр, а не замена человеку. Порядок ревью PR
не меняется: как было, так и остаётся, для всех изменений.

Из этого следует главное правило ответственности:

> **Ты автор кода, который принёс. Не «агент написал».** Если ты не можешь объяснить строку
> в своём PR — она не готова к мержу, независимо от того, кто её набрал.

Ревьюер-человек не обязан догадываться, что кусок сгенерирован, и не обязан ревьюить
за двоих. Практическое следствие: читай diff целиком перед тем, как коммитить, а не
после замечаний.

### 4.4. Артефакты в Трекер

Задача не закрыта, пока в неё не положены артефакты, описанные в `CLAUDE.md` проекта:
в приложении это четыре артефакта задачи (изменения для пользователя, изменения в коде,
план ручного тестирования, при необходимости сообщение для клиентов) либо отчёт по багфиксу;
в админке — матрица приёмки по критериям приёмки постановки.

Это ровно та часть работы, которую агент делает хорошо и быстро, и ровно та, которую
раньше писали в последний день или не писали вовсе. Отговорка «времени не было» с появлением
инструмента закрыта.

Артефакт пишется **на языке адресата**: техподдержке — без имён файлов и классов, клиенту —
без внутренних терминов, разработчику — со ссылками на код. Требования к каждому — в `CLAUDE.md`.

### 4.5. Данные: код — можно, боевые данные — нельзя

**Можно отдавать в контекст:** исходный код и схему БД, тексты задач Трекера, комментарии
и вложения из них, страницы Вики, на которые задача ссылается, логи и стектрейсы без
персональных данных, конфигурацию окружений без секретов, синтетические и обезличенные примеры.

**Нельзя:**

- выгрузки из боевых баз **мимо `db-query.sh`** — в любом виде, включая «пару строк
  для примера». Про сам `db-query.sh` — отдельный подпункт ниже;
- реальные персональные данные врачей, сотрудников фармкомпаний, пациентов: ФИО, контакты,
  адреса, идентификаторы, данные согласий;
- пароли, токены, ключи, строки подключения — ни в промпте, ни в файле, который читает агент;
- документы клиентов, попадающие под NDA, вне рамок конкретной задачи. Это же относится
  к Вики: выгружается страница, на которую ссылается задача, а не всё, что нашлось рядом
  по разделу.

Если для разбора нужен пример данных — обезличь: замени ФИО и контакты на выдуманные,
идентификаторы — на произвольные. Структура данных при этом сохраняется, а именно она
и нужна для анализа.

Скриншот из багрепорта с боевыми данными открывать агенту допустимо — это рабочий материал
задачи, и без него `/pbe-bug` бессмыслен. Но пересылать такие данные куда-либо ещё, складывать
в репозиторий или в постоянные файлы нельзя.

#### Чтение боевой базы через `db-query.sh`

Настройка доступа — п. 2.6, там же готовые команды на заведение, смену пароля и отзыв.
Здесь — когда этим можно пользоваться, а когда нет.

Часть багов не разбирается по коду в принципе: «пусто вместо данных», задвоение, не тот
статус, не бьются цифры. Причина там не в ветке кода, а в конкретной строке. Для таких
случаев есть контролируемый доступ на чтение — и он **единственный разрешённый**.

Границы:

- **Только через `.claude/scripts/db-query.sh`.** Прямой `sqlcmd`, `bcp`, `osql` запрещены
  и закрыты deny-листом. Обёртка — не удобство: это место, где остаётся пароль и ведётся журнал.
- **Только под своей учётной записью** `svc_ai_<фамилия>`: она read-only, одна на человека
  и работает во всех контурах. Учётные данные — один раз в `~/.config/pbe-mssql/common.env`,
  `chmod 600`, пароль в Keychain; в файле контура только сервер и база.
  Учётка **личная**: не передавать её коллеге и не заводить «общую на команду».
  В аудите MSSQL видно именно логин, поэтому чужой учёткой ты подписываешь чужим именем
  свой запрос. При увольнении отзывается одной строкой.
- **Только когда симптом задачи про данные.** «Посмотрю на всякий случай» — не основание.
- **По идентификаторам из задачи, а не по людям.** `SELECT *` и выборка колонок
  с персональными данными (`LastName`, `Email`, `Phone`, `Address` и подобных) — нельзя.
  Технически это **не закрыто**: обёртка текст запроса не разбирает, а `DENY SELECT`
  на ПД-колонки пока не выставлен. Держится на правиле и на том, что запрос виден
  в журнале. Нужно значение ПД, чтобы ответить на вопрос задачи, — его смотрит человек
  своими глазами, а не агент.
- **Результат живёт в ответе агента.** В отчёт и в комментарий задачи идёт вывод
  («у 412 записей из 15 тысяч пустой `RegionId`»), а не строки выборки. В файл, в репозиторий,
  во вложение задачи выгрузка не кладётся.
- **Каждый запрос пишется в журнал** `logs/db-query.log`. Журнал вне git и нужен ровно для
  одного: ответить на вопрос аудита, какие обращения к боевым данным были.

Это исключение из правила, а не отмена правила. Всё, что не подпадает под перечисленное,
остаётся под общим запретом.

Мы поставщик фармкомпаний, и они проводят аудиты поставщиков. Вопрос «что ваши разработчики
отправляют во внешние сервисы» на таком аудите звучит обязательно, и ответ на него должен
быть письменным и правдивым.

### 4.6. Обвязка правится через PR

`CLAUDE.md`, `.claude/agents/`, `.claude/commands/`, `.claude/settings.json` — общий инструмент
всей команды. Правки предлагает кто угодно, но **через PR и с согласованием директора
департамента информационных технологий**.

Причина простая: инструкция агента — это код, который исполняется у всех. Строчка «не гоняй
полные сборки, это долго», добавленная из лучших побуждений, тихо отключает проверку у восьми
человек. Заметить это по diff'у может только тот, кто держит картину целиком.

Локальные личные настройки — `.claude/settings.local.json`, он не версионируется. Что-то,
что помогло лично тебе, — повод предложить это команде, а не оставить у себя.

### 4.7. Технические предохранители

Граница проведена **не** по «пишет / не пишет в git», а по двум признакам: **уходит ли
действие наружу** и **уничтожает ли оно работу**.

Логика простая. Локальный git обратим: коммит, ветка, слияние, даже неудачный ребейз лежат
в reflog и достаются оттуда. Пуш необратим по-другому — его видят все. А `git clean`,
`git reset --hard` и откат файла уничтожают то, чего нет нигде: ни в объекте git, ни в reflog.
Поэтому запрещено ровно это, а не работа с гитом вообще.

| | Что | Примеры |
|---|---|---|
| ✅ | Локальная работа — свободно | `add`, `commit`, `switch`, `checkout` ветки, `branch`, `merge`, `rebase`, `stash`, `fetch`, `pull`, все читающие команды |
| ⚠️ | С подтверждения | `reset`, удаление и переименование веток, `git config`, миграции, полный прогон тестов, сборка |
| 🚫 | Наружу — никогда | `git push`, `gh pr create`, `gh pr merge`, `gh pr review`, `gh pr edit`, `gh release` |
| 🚫 | Уничтожает работу | `git clean`, `reset --hard`, `restore`/`checkout` по путям, `stash drop`, `rm -rf`, `migrate:fresh`, `db:wipe` |

**Массовый стейдж (`git add -A`, `git add .`, `git commit -a`) запрещён отдельно.** Не потому
что опасен сам по себе, а потому что втягивает в коммит то, чего там быть не должно: `.env`,
дампы, временные файлы, указатели сабмодулей. Агент обязан перечислять файлы явно — и это
заодно делает его коммиты читаемыми.

**Коммит агент делает сам, пуш — нет.** Держать результат дня в незакоммиченном рабочем
каталоге опаснее, чем закоммитить его в ветку задачи: пока коммита нет, правки не
восстановимы ничем. При этом наружу без человека ничего не уедет. Закончив работу, агент
обязан выдать **готовую команду пуша** — `git push -u origin <ветка>` — чтобы её осталось
скопировать. Формулировка «пуш делает человек» без самой команды это половина ответа.

**Коммит в защищённую ветку заблокирован.** `main`, `master`, `pre-prod`, `prod`, в приложении
ещё и `release/*`. Работа идёт в ветке задачи, названной по её ключу.

#### Два рубежа, и они разные

1. **Списки в `.claude/settings.json`** — deny / ask / allow. Дёшево и быстро, но матчатся
   **по префиксу команды**: правило видит начало строки и больше ничего.
2. **Хук `.claude/hooks/guard_protected_branch.py`** — исполняемая проверка перед запуском
   команды. Умеет то, чего префикс не умеет в принципе: посмотреть текущую ветку, заглянуть
   в индекс, найти флаг не в начале команды.

Разделение не бюрократическое, а вынужденное. `git checkout <ветка>` и `git checkout <файл>`
начинаются одинаково, а по последствиям противоположны: первое безобидно, второе стирает
несохранённую правку. Списком их не разделить — только кодом. Ровно так же `git commit -m "x" -a`
проходит мимо префиксного запрета на `git commit -a`, а «не коммить в `main`» вообще не
условие о команде, это условие о состоянии репозитория.

#### Предохранитель не обходить

Оба рубежа пробиваются тривиально — `sh -c '…'`, алиасы, `xargs`, плумбинг. **Именно поэтому
обход считается не находчивостью, а нарушением**: техника здесь страхует от случайности,
а не от намерения. Если правило мешает делу — это повод обсудить его и поправить в PR,
а не обойти в конкретной сессии.

Полные списки — в `settings.json` своего проекта; они одинаковы во всех репозиториях,
кроме того, что специфично для проекта.

## 5. Как работать: приёмы

### 5.1. Сначала понять, потом делать

Порядок, который экономит больше всего времени:

1. **Разбор** — `/pbe-task` или `/pbe-bug`. Читаешь сверку понимания, поправляешь.
2. **План** — попроси план до кода: какие файлы, какими шагами, что проверяем.
   В Claude Code для этого есть режим планирования (переключение режимов — `Shift+Tab`):
   агент исследует и предлагает план, но не правит файлы.
3. **Утверждение** — читаешь план. Если ты не согласен или не понял — правишь сейчас.
   Плохой план на этом шаге стоит минуту, на шаге реализации — рабочий день.
4. **Реализация** — по утверждённому плану, шагами.
5. **Проверки и ревью** — тесты, сборка, ревью-агент.
6. **Артефакты** — в Трекер.

После того как PR открыт и на него пришли замечания, есть седьмой шаг: `/pbe-review` —
разобрать замечания ревьюера (в том числе инлайновые, которые иначе теряются) и сверить
реализацию с критериями приёмки. См. п. 4.2.

Пропускать шаги 1–3 можно ровно там, где ты уже точно знаешь ответ. Признак, что пропускать
не стоит: ты не можешь одним предложением сказать, что именно изменится в продукте.

### 5.2. Проверка на понимание — работает в обе стороны

Простой приём: попроси агента объяснить задачу своими словами и назвать, чего ему не хватает.
Если объяснение расходится с тем, что в голове у тебя, — расходятся не слова, а понимание,
и дальше пойдёт не та работа.

Второй приём, ещё полезнее: **если агент не может внятно объяснить постановку — скорее всего,
она сырая**. Это не проблема агента, это сигнал вернуть задачу аналитику. Открытые вопросы,
которые `/pbe-task` собирает в конце разбора, для этого и нужны: пять точных вопросов аналитику
дешевле, чем реализация догадки.

### 5.3. Контекст: одна сессия — одна задача

Контекст сессии — ограниченный ресурс, и в нём накапливается мусор от предыдущих тем.
Закончил задачу — `/clear`, начинай следующую с чистого листа. Смешивать в одной сессии
багфикс по одному клиенту и фичу по другому — верный способ получить фикс, «улучшенный»
идеями из соседней задачи.

Признаки, что пора сбросить контекст: агент ссылается на файлы из прошлой задачи, повторяет
уже исправленные ошибки, начинает отвечать общими словами.

### 5.4. Небольшими шагами

Одна задача — одна ветка — обозримый diff. Просьба «сделай задачу целиком» на большой
постановке даёт полотно, которое невозможно ни отревьюить, ни откатить по частям.
Дели на шаги сам или руками планировщика (`task-planner` в приложении, `analyst` в админке)
и проверяй каждый шаг.

### 5.5. Читай diff

Своими глазами, целиком. Не «пробежать», а прочитать. Типовое, что там находится: тронутые
попутно соседние файлы, «заодно поправленное» форматирование в чужом коде, закомментированный
тест, `TODO` вместо реализации, изменённая сигнатура, которую использует кто-то ещё.

**Момент чтения сместился.** Раньше единственной точкой контроля был коммит: агент не коммитил,
и человек читал `git diff` перед тем, как зафиксировать. Теперь коммитит агент, и точка
контроля — **пуш**: читай `git log -p origin/<база>..HEAD` перед тем, как выполнить выданную
команду пуша. Это к лучшему, а не к худшему: агент коммитит осмысленными порциями, и читать
три коммита по теме легче, чем одно полотно на весь день.

Что это **не** отменяет: ответственность. Ты автор кода, который принёс, независимо от того,
кто набрал строки и кто сделал коммит (п. 4.3).

### 5.6. Когда агент буксует

Если после двух-трёх попыток результат не улучшается, дальше давить бесполезно — меняй заход:

- **Сбрось контекст** (`/clear`) и переформулируй задачу с нуля, добавив то, что выяснилось.
- **Дай факты, а не оценки**: не «не работает», а текст ошибки, шаги, файл, ожидаемое поведение.
- **Сузь**: попроси сначала объяснить механизм, потом чинить.
- **Сделай сам.** Правка на одну строку, которую ты знаешь, — это тридцать секунд руками
  и двадцать минут переписки. Инструмент не обязателен к применению везде.

Отдельно: агент, который третий раз подряд «уверенно» чинит одно и то же место, — сигнал,
что неверна постановка, а не реализация. Возвращайся к шагу 1.

## 6. Анти-паттерны

| Так делать не надо | Почему | Как надо |
|---|---|---|
| «Сделай CRM-544» — и ушёл | Агент достроит недостающее сам, уверенно и молча | `/pbe-task CRM-544`, прочитать сверку понимания, потом реализация |
| Мержить то, чего не понимаешь | Ответственность за код остаётся на тебе; ревьюер не догадается, что кусок сгенерирован | Прочитать diff, объяснить себе каждую строку, спросить агента про непонятное |
| Отключать предохранители, чтобы «не мешали» | Deny-лист, хук и режимы разрешений — единственное, что реально держит границы | Мешает — обсудить и поправить в PR |
| Пушить, не прочитав, что агент накоммитил | Коммит теперь делает агент; если не читать перед пушем, контроля не остаётся вовсе | `git log -p origin/<база>..HEAD` перед пушем |
| Разбирать замечания ревью через `gh pr view --comments` | Он молча теряет инлайновые замечания на строках — содержательную часть ревью | `/pbe-review` или `pr-comments.sh` |
| Копировать в чат выгрузку из прод-базы | ПДн врачей и сотрудников фармкомпаний, вопрос на аудите заказчика | Обезличить, оставить структуру |
| Одна сессия на весь день и все задачи | Контекст засоряется, ошибки перетекают между задачами | `/clear` между задачами |
| Просить «сделай всю задачу» на крупной постановке | Diff нечитаем, ревью формальное, откат невозможен | Шагами, с проверкой каждого |
| Править `.claude/` под себя молча | Инструкция агента исполняется у всей команды | PR + согласование |
| Спорить с ревью-агентом до победы | Он не устанет раньше тебя | Исправить либо отклонить с обоснованием в PR |

## 7. Чего этот документ не покрывает

- Порядок ревью и мержа PR, ветвление, релизы — существующий процесс команды, он не меняется.
  Агент в него встроен, а не заменяет его: коммитит в ветку задачи, но PR открывает,
  апрувит и мержит человек.
- Жизненный цикл задачи CRM — отдельный регламент компании.
- Технический контекст проектов — `CLAUDE.md` в репозитории проекта, он же источник истины
  по коду.
- Работа с `pbeconsole` — консоль ведёт директор департамента информационных технологий лично.

## 8. Обратная связь

Инструмент новый, документ первой версии, и часть написанного наверняка окажется неудобной
на практике. Что с этим делать:

- нашёл ошибку в инструкции или в агенте — задача в очередь `CRM` или напрямую директору
  департамента информационных технологий;
- придумал приём, который экономит время, — расскажи команде, хороший приём попадёт в агента
  и станет общим;
- считаешь правило из «Ядра» вредным — приходи с аргументом, правила не священны. Но до
  изменения они действуют.

Отдельно интересны два наблюдения: **где агент уверенно ошибся** (это материал для правки
`CLAUDE.md` — значит, в контексте чего-то не хватает) и **где он сэкономил больше всего** —
это подсказывает, куда расширять обвязку дальше.
