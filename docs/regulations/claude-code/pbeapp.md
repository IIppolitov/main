## 1. Что важно знать про этот проект

Три особенности, из которых растёт почти вся специфика работы с агентом.

**Мультибренд.** 15+ брендов, около 47 build- и 46 serve-конфигураций. Брендовый код —
в `src/app/modules/<код>/`, общий — в `commons/`, `components/`, `services/`, `directives/`,
`utils/`. Правка в общем коде доезжает до всех брендов, включая тех, кто задачу не заказывал.
Отсюда два постоянных вопроса к любому изменению: **каких брендов это коснётся** и **надо ли
предупредить клиентов**.

**Три платформы.** web, iOS, Android. Симптом «только на iOS» или «только офлайн» —
это не уточнение, а половина диагноза. Нативная часть (`src/plugins/`, `ios/`, `android/`)
обычной сборкой не проверяется вовсе.

**Проект в состоянии перехода.** Гибрид NgModule + standalone, zone.js, RxJS 6, Angular 18
при цели 22. Конвенции в `CLAUDE.md` — **целевые**: обязательны для нового кода и кода,
проходящего миграцию; легаси приводится к ним по мере миграции, а не попутными правками.
Агент, которому дали волю, охотно «заодно причешет» соседний файл — это надо ловить в diff.

## 2. Команда агентов

Десять ролей в `.claude/agents/`, две группы.

**Плановая разработка** — повседневные фичи, баги, техдолг:

| Агент | За что отвечает | Пишет код |
|---|---|---|
| `task-planner` | Декомпозиция: шаги, затронутые бренды и платформы, риски, критерии готовности | нет |
| `feature-developer` | Реализация одной задачи за запуск, по плану и конвенциям | да |
| `qa-tester` | Unit-тесты на изменённое поведение + сценарии ручной проверки | тесты |
| `code-reviewer` | Ревью по существу: корректность, регрессии в других брендах, асинхронщина, платформы | нет |
| `convention-reviewer` | Ревью diff'а на соответствие конвенциям `CLAUDE.md` | нет |
| `security-auditor` | Секреты, хранение токенов, auth, HTTP-слой, permissions, npm audit | нет |
| `build-verifier` | Прогон брендовых сборок и тестов | нет |

**Модернизация** — `upgrade-auditor`, `standalone-migrator`, `capacitor-native`. Это дорожка
Angular 18→22 / Capacitor 6→8 / NgModule→standalone. **Самостоятельно её не начинают**:
шаги идут по решению директора департамента информационных технологий, по одному мажору
за раз, и на время апгрейда плановые задачи приостанавливаются, чтобы не конфликтовать
с массовым diff'ом.

Суб-агент **не видит твой диалог** — всё нужное передаётся в промпт явно. Ревьюеры и аудиторы
ничего не правят: нашли — доложили, чинит владелец зоны.

## 3. `/pbe-bug` — разбор бага

```
/pbe-bug SUPPORTDEV-963                 # один баг
/pbe-bug SUPPORTDEV-963 SUPPORTDEV-1024 # один баг, описанный с разных сторон
/pbe-bug SUPPORTDEV-963 --links         # + тела связанных задач, один уровень
```

Выгружает задачу с комментариями и вложениями, **открывает скриншоты** (в багрепортах там
половина информации), сводит несколько задач в одну картину, затем ищет причину в коде.
Только чтение: код не правит, веток не заводит — даже если фикс в одну строку.

Первым в ответе идёт **сверка понимания**: что прочитано, как понята проблема, окружение
(бренд, платформа, версия, роль), где агент собирается копать и в чём не уверен. Прочитай
этот блок раньше разбора кода — здесь ловится «взял не тот бренд» и «разбирает не ту платформу».

В разборе агент обязан ответить на два вопроса, которые в багрепорте почти никогда не заданы:
**затронутые бренды и платформы** — список строится по коду, а не по тому, кто прислал
обращение (репортит один клиент, а общий код ломается у всех), и **при каких условиях**
проявляется (данные, состояние, офлайн, первый запуск).

### Конфиги клиента: `client-config.sh`

Отвечает на вопрос «как оно настроено у того клиента, про которого задача», не заходя
в админку — конфиг приложения (`config.tApplication`) через Fleet-API консоли мониторинга:

```bash
.claude/scripts/client-config.sh --resolve vltadmin.powbeecrm.com  # кто это: клиент, мнемоника, инстансы
.claude/scripts/client-config.sh Valenta --config menu             # конфиги клиента по подстроке ключа
.claude/scripts/client-config.sh --fleet menu                      # тот же ключ у остальных клиентов
```

`--fleet` — самый полезный флаг: он отличает общий дефект от клиентской настройки, а это
ровно тот вопрос про бренды, на который агент обязан ответить. Данные — снимки мониторинга
(до 5 минут), помеченные устаревшими брать как ориентир, а не как факт. Пусто в выдаче —
значит ключ не переопределён и действует дефолт из кода. Отказ скрипта разбор не
останавливает: агент помечает «окружение не проверено» и явно называет выводы, которые
от этого зависят.

Нужен токен консоли в Keychain — см. п. 2.5 основ.


### Боевая база: `db-query.sh`

Часть багов по коду не разбирается в принципе: «пусто вместо списка», задвоение, не тот
статус, не бьются цифры. Причина там не в ветке кода, а в конкретной строке. На таких
симптомах `/pbe-bug` и `/pbe-task` смотрят в базу — по идентификатору из задачи:

```bash
.claude/scripts/db-query.sh --profile servier -Q "SELECT name FROM sys.databases ORDER BY name"
.claude/scripts/db-query.sh --profile servier -d crmAdmin -Q "SELECT TOP 20 Id, StatusId FROM consents.tPersonConsent WHERE PersonId = 483920"
```

Обёртка подставляет сервер, логин и пароль — дальше обычный `sqlcmd`, флаги и SQL пишет
агент. Смысл обёртки один: **пароль не попадает в контекст сессии.** Поэтому прямой
`sqlcmd` закрыт deny-листом.

Записать в базу нельзя: учётная запись — `db_datareader` и ничего кроме. Это единственная
настоящая гарантия, текст запроса обёртка не проверяет. **Персональные данные технически
не защищены** — ФИО, телефоны и адреса не запрашиваются потому, что так написано в правилах,
а не потому, что что-то это отклонит. Разбор идёт по идентификаторам.

Схему не угадывать: `dbo` часто пустышка. На боевом сервере `dbo.tPersonConsent` содержит
0 строк, а данные лежат в `consents.tPersonConsent`. Пустая выборка — повод проверить схему,
а не вывод «данных нет».

В отчёт идёт вывод, а не выборка: «у 412 записей из 15 340 пустой `RegionId`» — факт;
таблица на 40 строк с боевыми данными — утечка в задачу.

Настройка доступа и смена пароля — п. 2.6 основ, границы использования — п. 4.5.

## 4. `/pbe-task` — разбор постановки

```
/pbe-task SUPPORTDEV-963                 # постановка
/pbe-task SUPPORTDEV-963 SUPPORTDEV-1024 # спека аналитика + задача на разработку = ОДНА постановка
/pbe-task SUPPORTDEV-963 --links
```

Главный шаг — **разделение контура**. Бизнес-аналитик пишет постановку на всю систему,
а этот репозиторий — только клиентское приложение. Агент раскладывает требования на три
корзины: **наше** (экраны, поведение, состояние, локальное хранение, нативные возможности),
**не наше** (админка, бэкенд, отчётность, права на сервере, интеграции — перечислить,
но не проектировать) и **стык** (контракты API, новые поля в ответах, справочники, флаги
доступа — по каждому: существует уже или это блокер на бэкенде).

Дальше — сверка с кодом, брендовый и платформенный охват, и **открытые вопросы к аналитику**.
Вопросы — ценная часть ответа, а не признак неудачи: пять точных вопросов дешевле недели
работы по догадке.

Отдельным пунктом на этом шаге решается, понадобится ли **сообщение для клиентов**
(артефакт 4, см. п. 6). Решается именно здесь, а не в конце реализации: клиентов
предупреждают заранее.

**Спека из Вики подтягивается сама.** Бизнес-аналитик описывает поведение экранов на
странице Вики, а в задаче оставляет ссылку. Разбор такие ссылки выгружает через
`.claude/scripts/wiki-page.sh` и в сверке понимания перечисляет прочитанные страницы.
Проверяй этот список: без спеки разделение контура и брендовый охват построены по одному
тексту задачи. Общее правило и ограничения — п. 4.1 основ.

## 5. Как идёт задача — конвейер плановой разработки

Одна задача = одна ветка `feature/<…>` или `fix/<…>` от master.

```
/pbe-task или /pbe-bug → разбор, сверка понимания, открытые вопросы
task-planner           → план: шаги, бренды, платформы, риски, критерии готовности
   ↓ открытые вопросы в плане закрываются ДО старта; план утверждает человек
feature-developer      → реализация по плану
qa-tester              → тесты + сценарии ручной проверки
                         дефекты → обратно feature-developer → qa-tester повторно
build-verifier         → сборка: режим affected (затронутые конфигурации) или full
                         FAIL → фикс → повторная проверка
capacitor-native       → ОБЯЗАТЕЛЕН, если задача тронула src/plugins/, ios/ или android/:
                         build-verifier гоняет только ng build и нативную поломку не увидит
code-reviewer ∥ convention-reviewer
security-auditor       → обязателен, если задача трогает auth, хранение данных,
                         HTTP-слой, нативные permissions, пользовательский ввод
   ↓
человек                → ручная проверка по чек-листу, коммит, PR, ревью человеком
```

**Сжатый вариант** для мелкого багфикса — `feature-developer → build-verifier (affected)
→ code-reviewer` — допустим только при выполнении **всех** условий: 1–2 файла, один бренд,
и изменение не трогает auth, хранение данных (Preferences / sqlite / токены), HTTP-слой
и interceptors, пользовательский ввод (`innerHTML`, `bypassSecurityTrust*`, sqlite-запросы)
и нативный код. Любое касание — полный конвейер. Сомнение решается в пользу полного.

**Цикл исправления замкнут.** Замечание закрывает не тот, кто его исправил, а тот, кто выдал:
после правки повторно запускается тот же агент. Иначе «замечание снято» и «снято частично»
неразличимы. Если правка меняет поведение, а не только стиль, — повторно и `qa-tester`.

**Красная сборка — стоп-сигнал.** Новые итерации не начинаются, пока текущая не зелёная.

## 6. Артефакты задачи — то, ради чего всё

Задача, меняющая продукт, не закрыта, пока в Трекер не положены четыре артефакта. Полные
требования — в `CLAUDE.md` («Обязательные артефакты задачи»), здесь суть и типовые ошибки.

| # | Артефакт | Кому | Ошибка, которую делают чаще всего |
|---|---|---|---|
| 1 | **Изменения для пользователя** — что заметит пользователь приложения, 3–5 предложений | Менеджер клиента, ТП, клиент | Пишут именами файлов и классов вместо продуктового языка |
| 2 | **Изменения в коде** — файлы ссылками, новые сервисы и контракты, охват, проверки | разработчикам | Раздувают до отчёта: обоснования и альтернативы идут в PR, не сюда |
| 3 | **План тестирования** — только ручная проверка, пошаговые сценарии по брендам и платформам | Тестировщики | Пишут чек-лист «проверить, что работает» вместо шагов с исходным состоянием и ожидаемым результатом |
| 4 | **Сообщение для клиентов** — готовый текст, шесть блоков | клиентам | Пишут описание того, что стоит сообщить, вместо самого сообщения |

Артефакты 1 и 2 идут в поля задачи — там мало места, это короткая сводка в пределах экрана.

**Артефакт 4 обязателен**, если правка легла в общий код и по факту доезжает до других брендов.
Если правка строго внутри `modules/<бренд>/` — он не нужен, но это надо сказать явно,
а не молча пропустить.

**Багфикс — исключение**: у него один артефакт вместо четырёх — **отчёт по багфиксу**
для команды технической поддержки. Адресат определяет всё: никаких файлов, классов, коммитов
и стектрейсов, язык — как для пользователя. Четыре блока: в чём была проблема, откуда возникла
(бытовым языком), кого затрагивало (бренды, платформы, версии, роли — по коду, а не по тому,
кто пожаловался), как решили (с какой версии, нужно ли действие пользователя, что с данными,
испорченными до фикса). Для ТП самый ценный блок — третий: по нему видно, кому ещё отвечать.

Это ровно та работа, которую агент делает хорошо, а люди делают в последний день или не делают.

## 7. Сборка: `affected` против `full`

47 конфигураций — полный прогон долгий, поэтому у `build-verifier` два режима.

**`affected`** — конфигурации ищутся **по цепочке импортов** до environment-файлов
и `fileReplacements` в `angular.json`, а не по имени папки бренда. Это важно: `vlt.module`
тянут `valenta`, `bnf` и `demo`. Проверка «собрал бренд из задачи» ничего не доказывает.

**`full`** — сквозная механика (маршруты, interceptors, environment, `app.module`), апгрейды,
и любая неоднозначность.

Запуск — через npm-скрипты (`<бренд>:<serve|build>:<среда>`), не `ng build --configuration`
руками. Легаси-бренды `bnf`, `prima`, `sal` намеренно без скриптов — «дополнять» их не надо.

Нативную часть сборка не проверяет: тронул `src/plugins/`, `ios/`, `android/` — нужен
`capacitor-native` и проверка на устройстве.

## 8. Предохранители: в этом проекте их пока нет

В админке `.claude/settings.json` технически запрещает агенту изменяющие git-команды
и разрушительные операции. **В приложении такого списка нет** — есть только разрешение
на скрипт Трекера. Значит, правила «агенты не коммитят, не пушат и не создают PR» держатся
здесь исключительно на инструкциях агентов и на тебе.

Практические следствия до момента, пока список не заведён:

- не переключай сессию в режим автоматического принятия правок (`acceptEdits`,
  `bypassPermissions`) — особенно пока идут ревью или аудит: режим родительской сессии
  наследуется суб-агентами и отменяет их read-only контракт;
- коммит, пуш и PR — руками, всегда;
- перед коммитом читай `git diff` целиком.

## 9. Типичные ошибки в этом проекте

| Симптом | Что происходит на самом деле |
|---|---|
| Правка в `services/` под один бренд | Общий код доезжает до всех. Спроси охват и нужно ли сообщение клиентам |
| «Собрал бренд заказчика, всё зелено» | Модуль тянут и другие конфигурации. Режим `affected` ищет по импортам, а не по имени |
| Агент «заодно» переписал соседний легаси-компонент | Конвенции целевые: легаси мигрируется отдельной задачей, не попутно |
| `localStorage` в новом коде | Запрещено — на iOS WebView его чистит. Только `@capacitor/preferences`; секреты — вообще не туда |
| `*ngIf` / `*ngFor` / `constructor(private x)` в новом коде | Новый Control Flow и `inject()`; `@for` всегда с `track` |
| Тронул нативную часть, прогнал только `ng build` | Нативную поломку это не поймает. Нужен `capacitor-native` и устройство |
| Агент предлагает мигрировать брендовый модуль на standalone | Нужен пререквизит по `optionalModules` — до него миграция таких модулей запрещена |

## 10. Примеры

```
/pbe-bug SUPPORTDEV-963 SUPPORTDEV-1024
/pbe-task SUPPORTDEV-963 --links

используй task-planner: спланируй CRM-601 — фильтр аптек по сетям для бренда bay
используй feature-developer: реализуй по плану выше, шаги 1–4
используй qa-tester: покрой изменения текущей ветки, сценарии по bay, web + iOS
используй build-verifier в режиме affected
используй code-reviewer: ревью изменений текущей ветки (diff от merge-base + untracked)
используй security-auditor в режиме diff
```
