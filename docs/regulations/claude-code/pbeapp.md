## 1. Что важно знать про этот проект

Три особенности, из которых растёт почти вся специфика работы с агентом.

**Мультибренд.** 15+ брендов, около 47 build- и 46 serve-конфигураций. Брендовый код —
в `src/app/modules/<код>/`, общий — в `commons/`, `components/`, `services/`, `directives/`,
`utils/`. Правка в общем коде доезжает до всех брендов, включая тех, кто задачу не заказывал.
Отсюда два постоянных вопроса к любому изменению: **каких брендов это коснётся** и **надо ли
предупредить клиентов**.

**Три платформы.** web, iOS, Android. Симптом «только на iOS» или «только офлайн» —
это не уточнение, а половина диагноза. Нативная часть (`src/plugins/`, `ios/`, `android/`)
обычной сборкой не проверяется вовсе.

**Проект в состоянии перехода.** Гибрид NgModule + standalone, zone.js, RxJS 6, Angular 18
при цели 22. Конвенции в `CLAUDE.md` — **целевые**: обязательны для нового кода и кода,
проходящего миграцию; легаси приводится к ним по мере миграции, а не попутными правками.
Агент, которому дали волю, охотно «заодно причешет» соседний файл — это надо ловить в diff.

## 2. Команда агентов

Десять ролей в `.claude/agents/`, две группы.

**Плановая разработка** — повседневные фичи, баги, техдолг:

| Агент | За что отвечает | Пишет код |
|---|---|---|
| `task-planner` | Декомпозиция: шаги, затронутые бренды и платформы, риски, критерии готовности | нет |
| `feature-developer` | Реализация одной задачи за запуск, по плану и конвенциям | да |
| `qa-tester` | Unit-тесты на изменённое поведение + сценарии ручной проверки | тесты |
| `code-reviewer` | Ревью по существу: корректность, регрессии в других брендах, асинхронщина, платформы | нет |
| `convention-reviewer` | Ревью diff'а на соответствие конвенциям `CLAUDE.md` | нет |
| `security-auditor` | Секреты, хранение токенов, auth, HTTP-слой, permissions, npm audit | нет |
| `build-verifier` | Прогон брендовых сборок и тестов | нет |

**Модернизация** — `upgrade-auditor`, `standalone-migrator`, `capacitor-native`. Это дорожка
Angular 18→22 / Capacitor 6→8 / NgModule→standalone. **Самостоятельно её не начинают**:
шаги идут по решению директора департамента информационных технологий, по одному мажору
за раз, и на время апгрейда плановые задачи приостанавливаются, чтобы не конфликтовать
с массовым diff'ом.

Суб-агент **не видит твой диалог** — всё нужное передаётся в промпт явно. Ревьюеры и аудиторы
ничего не правят: нашли — доложили, чинит владелец зоны.

## 3. `/pbe-bug` — разбор бага

```
/pbe-bug SUPPORTDEV-963                 # один баг
/pbe-bug SUPPORTDEV-963 SUPPORTDEV-1024 # один баг, описанный с разных сторон
/pbe-bug SUPPORTDEV-963 --links         # + тела связанных задач, один уровень
```

Выгружает задачу с комментариями и вложениями, **открывает скриншоты** (в багрепортах там
половина информации), сводит несколько задач в одну картину, затем ищет причину в коде.
Только чтение: код не правит, веток не заводит — даже если фикс в одну строку.

Первым в ответе идёт **сверка понимания**: что прочитано, как понята проблема, окружение
(бренд, платформа, версия, роль), где агент собирается копать и в чём не уверен. Прочитай
этот блок раньше разбора кода — здесь ловится «взял не тот бренд» и «разбирает не ту платформу».

В разборе агент обязан ответить на два вопроса, которые в багрепорте почти никогда не заданы:
**затронутые бренды и платформы** — список строится по коду, а не по тому, кто прислал
обращение (репортит один клиент, а общий код ломается у всех), и **при каких условиях**
проявляется (данные, состояние, офлайн, первый запуск).

### Конфиги клиента: `client-config.sh`

Отвечает на вопрос «как оно настроено у того клиента, про которого задача», не заходя
в админку — конфиг приложения (`config.tApplication`) через Fleet-API консоли мониторинга:

```bash
.claude/scripts/client-config.sh --resolve vltadmin.powbeecrm.com  # кто это: клиент, мнемоника, инстансы
.claude/scripts/client-config.sh Valenta --config menu             # конфиги клиента по подстроке ключа
.claude/scripts/client-config.sh --fleet menu                      # тот же ключ у остальных клиентов
```

`--fleet` — самый полезный флаг: он отличает общий дефект от клиентской настройки, а это
ровно тот вопрос про бренды, на который агент обязан ответить. Данные — снимки мониторинга
(до 5 минут), помеченные устаревшими брать как ориентир, а не как факт. Пусто в выдаче —
значит ключ не переопределён и действует дефолт из кода. Отказ скрипта разбор не
останавливает: агент помечает «окружение не проверено» и явно называет выводы, которые
от этого зависят.

Нужен токен консоли в Keychain — см. п. 2.5 основ.


### Боевая база: `db-query.sh`

Часть багов по коду не разбирается в принципе: «пусто вместо списка», задвоение, не тот
статус, не бьются цифры. Причина там не в ветке кода, а в конкретной строке. На таких
симптомах `/pbe-bug` и `/pbe-task` смотрят в базу — по идентификатору из задачи:

```bash
.claude/scripts/db-query.sh --profile srv -Q "SELECT name FROM sys.databases ORDER BY name"
.claude/scripts/db-query.sh --profile srv -d crmAdmin -Q "SELECT TOP 20 Id, StatusId FROM consents.tPersonConsent WHERE PersonId = 483920"
```

Обёртка подставляет сервер, логин и пароль — дальше обычный `sqlcmd`, флаги и SQL пишет
агент. Смысл обёртки один: **пароль не попадает в контекст сессии.** Поэтому прямой
`sqlcmd` закрыт deny-листом.

Записать в базу нельзя: учётная запись — `db_datareader` и ничего кроме. Это единственная
настоящая гарантия, текст запроса обёртка не проверяет. **Персональные данные технически
не защищены** — ФИО, телефоны и адреса не запрашиваются потому, что так написано в правилах,
а не потому, что что-то это отклонит. Разбор идёт по идентификаторам.

Схему не угадывать: `dbo` часто пустышка. На боевом сервере `dbo.tPersonConsent` содержит
0 строк, а данные лежат в `consents.tPersonConsent`. Пустая выборка — повод проверить схему,
а не вывод «данных нет».

В отчёт идёт вывод, а не выборка: «у 412 записей из 15 340 пустой `RegionId`» — факт;
таблица на 40 строк с боевыми данными — утечка в задачу.

Настройка доступа и смена пароля — п. 2.6 основ, границы использования — п. 4.5.

## 4. `/pbe-task` — разбор постановки

```
/pbe-task SUPPORTDEV-963                 # постановка
/pbe-task SUPPORTDEV-963 SUPPORTDEV-1024 # спека аналитика + задача на разработку = ОДНА постановка
/pbe-task SUPPORTDEV-963 --links
```

Главный шаг — **разделение контура**. Бизнес-аналитик пишет постановку на всю систему,
а этот репозиторий — только клиентское приложение. Агент раскладывает требования на три
корзины: **наше** (экраны, поведение, состояние, локальное хранение, нативные возможности),
**не наше** (админка, бэкенд, отчётность, права на сервере, интеграции — перечислить,
но не проектировать) и **стык** (контракты API, новые поля в ответах, справочники, флаги
доступа — по каждому: существует уже или это блокер на бэкенде).

Дальше — сверка с кодом, брендовый и платформенный охват, и **открытые вопросы к аналитику**.
Вопросы — ценная часть ответа, а не признак неудачи: пять точных вопросов дешевле недели
работы по догадке.

Отдельным пунктом на этом шаге решается, понадобится ли **сообщение для клиентов**
(артефакт 4, см. п. 6). Решается именно здесь, а не в конце реализации: клиентов
предупреждают заранее.

**Спека из Вики подтягивается сама.** Бизнес-аналитик описывает поведение экранов на
странице Вики, а в задаче оставляет ссылку. Разбор такие ссылки выгружает через
`.claude/scripts/wiki-page.sh` и в сверке понимания перечисляет прочитанные страницы.
Проверяй этот список: без спеки разделение контура и брендовый охват построены по одному
тексту задачи. Общее правило и ограничения — п. 4.1 основ.

## 4а. `/pbe-review` — ревью PR против постановки

```
/pbe-review CRM-1641          # найти PR по задаче и проверить реализацию
/pbe-review CRM-1641 --post   # + опубликовать замечания в PR
/pbe-review CRM-1641 --fix    # + починить найденное (только на своём PR)
```

Три команды закрывают три разные точки: `/pbe-task` — до разработки, `/pbe-review` — после,
`/pbe-bug` — когда уехавшее в прод сломалось.

**Чем отличается от встроенного `/code-review`.** Тот смотрит на код сам по себе. Этот
начинается с постановки: находит PR по ключу задачи, выписывает критерии приёмки из
`testPlan` / `externalChanges` / спеки в Вики и меряет реализацию **по ним**. Ответ на вопрос
«сделано ли то, что заказано» встроенная команда дать не может — она не видит задачу.

**Специфика приложения — бренды.** Матрица приёмки здесь идёт с отдельной колонкой «на каких
брендах проверено»: «работает» без указания бренда в этом проекте не значит ничего. Команда
отдельно смотрит, заведён ли новый ключ во **всех** брендовых environment-файлах, которых
касается требование, — пропущенный ключ ломает сборку одного бренда из шестнадцати или молча
даёт `undefined` в рантайме.

**Вторая специфика — порядок выкатки.** Часть требований постановки почти всегда реализуется
в админке. Приложение, ушедшее в стор раньше API, откатить нельзя — поэтому парную правку
в `pbeadmin` команда обязана назвать, даже если ревьюить её здесь нечем, и указать, что
катится первым.

**Замечания ревьюера видно целиком.** Комментарии PR отдают три разных эндпоинта GitHub,
а `gh pr view --comments` читает только ленту обсуждения — инлайновые замечания на строках
в его вывод не попадают вовсе, и потеря молчаливая. Скрипт `pr-comments.sh` забирает все три.

### Границы

- **Ничего не публикуется по умолчанию** — отчёт в терминал. В PR замечания уходят только
  по флагу `--post` или явной просьбе.
- **Вердикт ставит человек.** Агент комментирует, но не апрувит и не запрашивает изменения.
  Это подстраховано технически: публикация идёт через обёртку `pr-review-post.sh`, которая
  проставляет `event=COMMENT` сама и не принимает его извне.
- **Чужой PR агент не правит** — даже однострочный фикс это замечание, а не коммит. `--fix`
  работает только на своём PR.

## 4б. `/pbe-bugreport` и `/pbe-supportdev` — завести дефект задачей

```
/pbe-bugreport при импорте специальность сперва создаётся, потом удаляется
/pbe-supportdev у Валенты на проде в Тихоликвидах количество аптек всегда 0
```

Все команды выше требуют **ключа задачи**. Эти две его создают: собирают постановку прямо
там, где дефект найден, и заводят задачу в Трекере по реквизитам регламента.

**Зачем.** До сих пор человек с проблемой в руках шёл заводить задачу руками — и по дороге
терял две вещи разом. Реквизиты регламента (мнемоника клиента тегом, компонент, тип,
родитель-подзадача) и контекст репозитория (ветка, сборка, значение конфига у этого клиента,
место в коде). Первое обнаруживается на разборе беклога, второе — не обнаруживается никогда.

**Какую из двух запускать.** Два вопроса, в этом порядке:

| | Вопрос | Ответ | Куда |
|---|---|---|---|
| 1 | Функционал уже на проде? | нет | `/pbe-bugreport` → `BUGREPORTS` |
| 2 | Если да: чинить надо хотфиксом, вне планового релиза? | да | `/pbe-supportdev` → `SUPPORTDEV` |
| | | нет, подождёт | `/pbe-bugreport` → `BUGREPORTS` |

Первый вопрос — граница из [описания очередей](../tracker-queues.md): признак прод,
а не то, кто нашёл, поэтому дефект, найденный клиентом на внешнем тесте, всё ещё багрепорт.
Второй вопрос — правило владельца очередей, и в описании очередей его пока нет: там граница
проведена одним признаком. Расхождение ведётся в долге; до его закрытия действует порядок выше.

Команда проверяет развилку первым шагом и, если не сходится, отправляет ко второй, а не
заводит задачу «куда попало, потом перенесём»: перенос между контурами задним числом
не восстанавливает ни приоритет, ни срок.

**Обращение клиента по почте — не ваш случай.** Такую задачу заводит техподдержка из
`SUPPORT`, со связью с исходным обращением и дедлайном по договору. Есть номер `SUPPORT-…` —
передайте его в поддержку, а не заводите дубль.

### Что команда делает за вас

- **Реквизиты по регламенту.** Очередь, тип, компонент, тег с мнемоникой клиента.
  Тип в `SUPPORTDEV` — «Инцидент»: типа «Ошибка» в этой очереди нет.
- **Исполнителя багрепорта** — тимлид команды, как требует
  [этап 11](../crm-lifecycle/11-testirovanie-i-revju.md) (4.5.4). Задачи `SUPPORTDEV` уходят
  без исполнителя: кому чинить и выпускать ли хотфиксом, решает разбор беклога поддержки.
- **Родителя багрепорта.** Багрепорт вешается **подзадачей**, а не связью `relates`.
  Команда спросит подзадачу «Разработка», в которой сделан дефектный функционал, — если
  вы её знаете, называйте: багрепорт уровнем выше при десятке подзадач не адресует ничего.
  Дефект найден при проверке релиза, а не доработки, — родителем называйте релизную
  задачу: «Регресс приложения», «Подготовку релиза» или «Обратную связь клиента»
  ([этап 11](../crm-lifecycle/11-testirovanie-i-revju.md), 4.5.2.2).
- **Контекст репозитория** — ветка, коммит, значение переопределённого конфига у клиента
  и место в коде, если вы его назвали. Место в коде идёт в задачу **гипотезой автора**,
  помеченной как непроверенная: причину разбирают по заведённой задаче, а не в момент её
  создания.

### Границы

- **Без вашего «да» задача не создаётся.** Команда показывает черновик целиком, потом делает
  сухой прогон, и только потом пишет. Задачу нельзя отменить — можно только закрыть.
- **Приоритет и дедлайн команда не ставит.** SLA у каждого клиента свой, по договору, и
  в репозитории его нет. Её работа — дать факты, по которым приоритет выставят: массовость,
  что именно не работает, есть ли обходной путь.
- **Шаги воспроизведения не выдумываются.** Не дали — команда спросит. Выдуманные шаги хуже
  отсутствующих: по ним пойдут проверять.
- **Боевых данных в задаче не будет.** Вывод — да («у 412 записей из 15 340 пустой
  `RegionId`»), выборка строками — нет. ФИО, телефоны, адреса не переносятся вообще.
- **Код команда не правит.** Её результат — ключ задачи, а не фикс.

### Дальше

Заведённая задача — вход в остальную обвязку, и разбор запускается **новой сессией**:

```
/pbe-bug BUGREPORTS-177
```

Не следом за созданием, а именно новой: в сессии, где вы формулировали проблему, агент
будет искать подтверждение вашей же гипотезе, а не причину.

## 5. Как идёт задача — конвейер плановой разработки

Одна задача = одна ветка `feature/<…>` или `fix/<…>` от master.

```
/pbe-task или /pbe-bug → разбор, сверка понимания, открытые вопросы
task-planner           → план: шаги, бренды, платформы, риски, критерии готовности
   ↓ открытые вопросы в плане закрываются ДО старта; план утверждает человек
feature-developer      → реализация по плану
qa-tester              → тесты + сценарии ручной проверки
                         дефекты → обратно feature-developer → qa-tester повторно
build-verifier         → сборка: режим affected (затронутые конфигурации) или full
                         FAIL → фикс → повторная проверка
capacitor-native       → ОБЯЗАТЕЛЕН, если задача тронула src/plugins/, ios/ или android/:
                         build-verifier гоняет только ng build и нативную поломку не увидит
code-reviewer ∥ convention-reviewer
security-auditor       → обязателен, если задача трогает auth, хранение данных,
                         HTTP-слой, нативные permissions, пользовательский ввод
   ↓
   ↓ (агент коммитит в ветку задачи по ходу работы)
человек                → ручная проверка по чек-листу, пуш по выданной команде, PR, ревью человеком
   ↓
/pbe-review            → разбор замечаний ревьюера и сверка с критериями приёмки
/pbe-results           → артефакты в Трекер; статус и часы — руками человека
```

**Коммитит агент, пушит человек.** Коммит в ветку задачи — часть работы, а не шаг сдачи;
наружу при этом без человека ничего не уедет. Агент обязан закончить готовой строкой
`git push -u origin <ветка>`. Гейты (`code-reviewer`, `convention-reviewer`,
`security-auditor`, `build-verifier`) не коммитят: тот, кто чинит, не проверяет себя же.

**Сжатый вариант** для мелкого багфикса — `feature-developer → build-verifier (affected)
→ code-reviewer` — допустим только при выполнении **всех** условий: 1–2 файла, один бренд,
и изменение не трогает auth, хранение данных (Preferences / sqlite / токены), HTTP-слой
и interceptors, пользовательский ввод (`innerHTML`, `bypassSecurityTrust*`, sqlite-запросы)
и нативный код. Любое касание — полный конвейер. Сомнение решается в пользу полного.

**Цикл исправления замкнут.** Замечание закрывает не тот, кто его исправил, а тот, кто выдал:
после правки повторно запускается тот же агент. Иначе «замечание снято» и «снято частично»
неразличимы. Если правка меняет поведение, а не только стиль, — повторно и `qa-tester`.

**Красная сборка — стоп-сигнал.** Новые итерации не начинаются, пока текущая не зелёная.

## 6. Артефакты задачи — то, ради чего всё

Задача, меняющая продукт, не закрыта, пока в Трекер не положены обязательные артефакты.
Собирает и кладёт их команда `/pbe-results` — по ключу задачи, после реализации и создания
Pull Request'а. Полные требования к содержанию — в `CLAUDE.md` («Обязательные артефакты
задачи»), здесь суть, адресаты и типовые ошибки.

**Пять артефактов идут в поля задачи очереди CRM:**

| # | Артефакт | Кому | Ошибка, которую делают чаще всего |
|---|---|---|---|
| 1 | **Изменения для пользователя** — что заметит пользователь приложения, 3–5 предложений | Менеджер клиента, ТП, клиент | Пишут именами файлов и классов вместо продуктового языка |
| 2 | **Изменения в коде** — файлы, новые сервисы и контракты, охват, проверки | разработчикам | Раздувают до отчёта: обоснования и альтернативы идут в PR, не сюда |
| 3 | **План тестирования** — ручная проверка через интерфейс, пошаговый сценарий | Тестировщики | Пишут чек-лист «проверить, что работает» вместо шагов с исходным состоянием и ожидаемым результатом |
| 4 | **Действия релиза** — только то, чего не делает деплой-скрипт | Релиз-менеджеру | Пересказывают процедуру выкатки: миграции, установку зависимостей, сборку |
| 5 | **Ссылки на Pull Requests** | ревьюеру, тимлиду | Оставляют пустым, когда PR ещё не создан, — и не возвращаются |

**Поля разметку не рендерят.** Заголовки, жирный текст, таблицы и markdown-ссылки приезжают
туда символами и делают текст нечитаемым. Артефакты 1, 2, 4 и 5 — плоский текст в пределах
экрана: это короткая сводка, а не отчёт.

**План тестирования — исключение, и по умолчанию он уходит комментарием**, где разметка
работает; в поле остаётся отсылка с датой комментария. Коротким планом можно заполнить
и само поле — это выбор автора задачи, а не умолчание. Сам план описывает **ручную проверку
через интерфейс**, максимум — со взглядом в базу: в большинстве случаев достаточно одного
положительного сценария из трёх шагов «зайти, нажать, увидеть», с брендом и платформой
в исходном состоянии. Перебор негативных случаев, офлайна и регрессии «на всякий случай»
в план не идёт — его должно хватать на один заход.

**Действия релиза описывают только ручные шаги**: включить конфиг, проставить переменную
окружения, заполнить данные, запустить команду, сделать что-то в базе или в админке.
Всё, что делает деплой-скрипт, в артефакт не идёт. Делать ничего не нужно — в поле ставится
дефис: пустое поле значит «не заполнили», и по нему релиз-менеджер идёт спрашивать в день
релиза, а дефис значит «посмотрели, ручных действий нет».

**Сообщение для клиентов** — шестой артефакт, в поля не идёт: это отдельный комментарий
готовым текстом из шести блоков. Обязателен, если правка легла в общий код и по факту
доезжает до брендов помимо заказчика задачи; правка строго внутри `modules/<бренд>/` —
не нужен, но это говорится явно, а не пропускается молча. Нужен ли он, решается на разборе
или планировании, где брендовый охват уже определён, а не в конце реализации: клиентов
информируют заранее.

**Багфикс — исключение**: у него один артефакт вместо пяти — **отчёт для команды технической
поддержки**, комментарием в задачу. Адресат определяет всё: никаких файлов, классов, коммитов
и стектрейсов, язык — как для пользователя. Четыре блока: что было, как исследовали
(бытовым языком, а не механизмом в коде), как починили, какой охват — бренды, платформы,
версии, роли, определённые по коду, а не по тому, кто пожаловался. Сроков и обещаний
(«ждём релиз», «выйдет на следующей неделе») в отчёте нет: их пересказывают клиенту дословно,
а решает выпуск не разработчик. Просьбы к поддержке или менеджеру выносятся отдельным блоком
явными словами — «нужно спросить», «нужно попросить», «нужно сделать», — а не прячутся
в тексте.

**Ничего не уходит в Трекер без вычитки.** Текст сперва показывается человеку целиком, и
только по явному согласию попадает в задачу. **Статус задачи агент не переводит и часы
не списывает** — то и другое делает человек: перевод статуса означает «я отвечаю за то, что
работа сделана», это подпись. Команда об этом напоминает и показывает, сколько времени шла
работа, — но вносит часы человек.

Это ровно та работа, которую агент делает хорошо, а люди делают в последний день или не делают.

## 7. Сборка: `affected` против `full`

47 конфигураций — полный прогон долгий, поэтому у `build-verifier` два режима.

**`affected`** — конфигурации ищутся **по цепочке импортов** до environment-файлов
и `fileReplacements` в `angular.json`, а не по имени папки бренда. Это важно: `vlt.module`
тянут `valenta`, `bnf` и `demo`. Проверка «собрал бренд из задачи» ничего не доказывает.

**`full`** — сквозная механика (маршруты, interceptors, environment, `app.module`), апгрейды,
и любая неоднозначность.

Запуск — через npm-скрипты (`<бренд>:<serve|build>:<среда>`), не `ng build --configuration`
руками. Легаси-бренды `bnf`, `prima`, `sal` намеренно без скриптов — «дополнять» их не надо.

Нативную часть сборка не проверяет: тронул `src/plugins/`, `ios/`, `android/` — нужен
`capacitor-native` и проверка на устройстве.

## 8. Что запрещено технически

Раньше в этом разделе стояло «предохранителей здесь нет» — теперь они заведены и совпадают
с админкой. Общая логика в п. 4.7 основ: граница по «уходит наружу» и «уничтожает работу»,
а не по «пишет в git». Ниже только специфика приложения.

**Два рубежа.** `.claude/settings.json` (списки deny / ask / allow) и PreToolUse-хук
`.claude/hooks/guard_protected_branch.py`. Оба действуют и на основную сессию, и на всех
суб-агентов.

Запрещено (deny): `git push` и `gh pr create|merge|review|edit|close` — наружу отправляет
человек; `git clean`, `reset --hard`, `restore`/`checkout` по путям, `stash drop|clear`,
`rm -rf` — уничтожают несохранённое; массовый стейдж `git add -A|.|-u` и `git commit -a` —
втягивают в коммит собранные бандлы, `.env` и платформенные артефакты Capacitor.

Разрешено без подтверждения: обычная локальная работа с гитом, читающие команды,
`gh pr view|list|diff|comment` и скрипты из `.claude/scripts/`.

**Хук отклоняет то, чего список не видит:** коммит в `master`/`main` и в ветки `release/*`
(с учётом смены ветки в той же цепочке), `git checkout` по путям, `reset --hard`
и `restore` без `--staged` — на любой позиции флага, а также `git commit --amend` поверх
уже запушенного коммита (см. п. 4.7 основ). Защита веток здесь шире, чем в админке,
именно из-за `release/*`: релизная ветка бренда живёт долго и коммит в неё мимо процесса
уезжает клиенту.

Что **не** закрывается техникой и остаётся на тебе:

- не переключай сессию в режим автоматического принятия правок (`acceptEdits`,
  `bypassPermissions`) — особенно пока идут ревью или аудит: режим родительской сессии
  наследуется суб-агентами и отменяет их read-only контракт;
- читай, что агент накоммитил, **перед пушем**: `git log -p origin/master..HEAD`. Точка
  контроля сместилась с коммита на пуш, и если её пропустить, контроля не остаётся вовсе;
- обход предохранителя (`sh -c '…'`, алиасы) — нарушение, а не смекалка.

## 9. Типичные ошибки в этом проекте

| Симптом | Что происходит на самом деле |
|---|---|
| Правка в `services/` под один бренд | Общий код доезжает до всех. Спроси охват и нужно ли сообщение клиентам |
| «Собрал бренд заказчика, всё зелено» | Модуль тянут и другие конфигурации. Режим `affected` ищет по импортам, а не по имени |
| Агент «заодно» переписал соседний легаси-компонент | Конвенции целевые: легаси мигрируется отдельной задачей, не попутно |
| `localStorage` в новом коде | Запрещено — на iOS WebView его чистит. Только `@capacitor/preferences`; секреты — вообще не туда |
| `*ngIf` / `*ngFor` / `constructor(private x)` в новом коде | Новый Control Flow и `inject()`; `@for` всегда с `track` |
| Тронул нативную часть, прогнал только `ng build` | Нативную поломку это не поймает. Нужен `capacitor-native` и устройство |
| Агент предлагает мигрировать брендовый модуль на standalone | Нужен пререквизит по `optionalModules` — до него миграция таких модулей запрещена |
| Ревью нашло замечания, которых ревьюер не писал | Смотрел ленту обсуждения вместо инлайновых замечаний на строках. `/pbe-review` или `pr-comments.sh` |
| «Работает», но не сказано на каком бренде | Здесь 16 брендов; проверка без указания бренда не значит ничего |
