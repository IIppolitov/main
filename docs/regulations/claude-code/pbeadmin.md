## 1. Что важно знать про этот проект

Четыре особенности, на которых агент ошибается чаще всего. Держи их в голове, когда
проверяешь его вывод.

**Это не CRM «визитов и врачей».** Основные сущности — `Person` (HCP), `Org` (HCO),
`Consent`, `Campaign`/`PromoCycle`, `Staff`/`User`, `Message`/`Template`, `DrugBrand`/`DrugSKU`,
`Survey`. Слова «визиты», «врачи», «аптеки» в постановках — бизнес-термины, а не таблицы.
Агент, не прочитавший это предупреждение, начнёт искать `visits`.

**MSSQL, database-first.** Именованные схемы, таблицы `schema.tPascalCase`, колонки PascalCase.
Laravel-конвенции здесь не действуют — не давай агенту предполагать имена, пусть смотрит
миграцию и модель. Для новых сущностей — паттерн «Fields».

**Модули — отдельные git-сабмодули.** Правка в `modules/<Module>/` меняет **чужой репозиторий**:
своя ветка, свой PR, свой пуш — из каталога сабмодуля. Агент обязан называть это в отчёте;
если не назвал — спроси прямо, ядро это или модуль.

⚠️ **Шага «бампнуть указатель» в этом проекте нет.** В `.gitmodules` у модулей стоит
`ignore = all`, изменения указателей команда намеренно выкидывает из коммитов, и `git status`
их не показывает. Закоммиченный указатель на непушенный коммит ломает `git submodule update`
у всех — этим уже сломан `modules/Export`. Если агент предлагает «обновить указатель», он
неправ, и это подстраховано технически: хук проверяет индекс перед коммитом и блокирует его,
если там оказался гитлинк. Как модули попадают на стенды, решает деплой, а не указатель.

**Поведение зависит от конфигов клиента.** Один и тот же код ведёт себя по-разному
у Валенты и Байера — из-за значений `pbe`-конфигов, которых локально не видно. Отсюда
`client-env.sh` в разборе (п. 3) и вопрос «это у всех так или только у него» в каждом баге.

## 2. Команда агентов

Восемь ролей в `.claude/agents/`. Вызываются по имени или подхватываются автоматически
по описанию.

| Агент | За что отвечает | Пишет код |
|---|---|---|
| `backend` | Laravel: API, контроллеры, сервисы, модели, Jobs, очереди, интеграции | да |
| `database` | MSSQL: **все миграции монопольно**, схема, структура моделей, паттерн «Fields» | да |
| `frontend` | Blade + AdminLTE 3, jQuery/select2/DataTables, Vue 3, Mix | да |
| `qa` | Контрактные и Feature-тесты, тест-кейсы, регрессия | тесты |
| `analyst` | Постановки, критерии приёмки, User Stories, глоссарий — до разработки | нет |
| `reviewer` | Code review — **обязательный гейт перед PR** | нет |
| `security` | Аудит уязвимостей (SQLi, IDOR, PII/PHI, SSRF) — гейт по триггерам | нет |
| `documentation` | Руководства, Release Notes, техописания; пишет только в `docs/` и `*.md` | нет |

Два правила, которые стоит запомнить сразу:

- **Миграции пишет только `database`.** Не проси `backend` «заодно накинуть миграцию» —
  разделение монопольное и намеренное.
- **Ревьюеры не правят код и не коммитят.** Нашли — доложили, чинит владелец зоны. Просьба
  «ты же видишь ошибку, поправь» ломает смысл гейта. Пишущие агенты (`backend`, `database`,
  `frontend`, `qa`) коммитят свою работу сами — гейты нет.

Суб-агент **не видит твой диалог**. Всё нужное — файлы, имя таблицы `schema.tName`, пункт ТЗ,
вывод предыдущего агента — передаётся в промпт явно. Каждый агент возвращает статус:
`DONE` / `PARTIAL` (что не сделано и почему) / `BLOCKED` (чего не хватает).

## 3. `/pbe-bug` — разбор бага

```
/pbe-bug SUPPORTDEV-1788                 # один баг
/pbe-bug SUPPORTDEV-1788 SUPPORTDEV-1790 # дубли одного симптома от разных клиентов
/pbe-bug SUPPORTDEV-1788 --links         # + тела связанных задач, один уровень
```

Что делает: выгружает задачу с комментариями и вложениями, **открывает скриншоты**
(в багрепортах половина информации именно там), определяет клиента по домену админки,
тегу или префиксу темы, снимает его конфиги через `client-env.sh` — и только потом идёт
в код искать причину.

**Несколько ключей — это один разбор, а не два.** Типовой случай: один автор дал шаги
воспроизведения, другой — скриншот с ошибкой и версию; вместе они дают воспроизведение,
которого нет ни в одной задаче по отдельности. Расхождения между задачами агент выносит
отдельным блоком и говорит, какую версию взял за рабочую.

**Команда только читает.** Код не правит, миграции не пишет, веток не заводит — даже если
фикс в одну строку.

### Что делать с результатом

Первым в ответе идёт **сверка понимания**: что прочитано, окружение клиента, как понята
проблема, в чём агент не уверен. Прочитай его до того, как читать разбор кода — именно здесь
ловятся «разбирает не тот экран» и «взял не того клиента».

Дальше — причина со ссылками на файлы и строки, охват (ядро или модуль, один клиент или все),
что чинить и нужна ли миграция. Отчёт технический, для разработчика.

По итогу починки в задачу идёт **нетехнический отчёт** — но его пишут после фикса, не на этом
шаге: без фикса нет блока «как решили».

### Конфиги клиента: `client-env.sh`

Отвечает на вопрос «как оно настроено у того клиента, про которого задача», не заходя в админку:

```bash
.claude/scripts/client-env.sh --resolve vltadmin.powbeecrm.com   # кто это: клиент, мнемоника, инстансы
.claude/scripts/client-env.sh vlt --config LOW_LIQUID            # конфиги админки по подстроке ключа
.claude/scripts/client-env.sh vlt --app --config menu            # конфиги приложения, если симптом там
.claude/scripts/client-env.sh --fleet LOW_LIQUID                 # тот же ключ у остальных клиентов
```

`--fleet` — самый полезный флаг: он отличает общий дефект от клиентской настройки.
Данные — снимки мониторинга (до 5 минут), помеченные ⚠️ устаревшие брать как ориентир,
а не как факт. Отказ скрипта разбор не останавливает: агент помечает «окружение не проверено»
и явно называет выводы, которые от этого зависят.


### Боевая база: `db-query.sh`

Часть багов по коду не разбирается в принципе: «пусто вместо списка», задвоение, не тот
статус, не бьются цифры. Причина там не в ветке кода, а в конкретной строке. На таких
симптомах `/pbe-bug` и `/pbe-task` смотрят в базу — по идентификатору из задачи:

```bash
.claude/scripts/db-query.sh --profile srv -Q "SELECT name FROM sys.databases ORDER BY name"
.claude/scripts/db-query.sh --profile srv -d crmAdmin -Q "SELECT TOP 20 Id, StatusId FROM consents.tPersonConsent WHERE PersonId = 483920"
```

Обёртка подставляет сервер, логин и пароль — дальше обычный `sqlcmd`, флаги и SQL пишет
агент. Смысл обёртки один: **пароль не попадает в контекст сессии.** Поэтому прямой
`sqlcmd` закрыт deny-листом.

Записать в базу нельзя: учётная запись — `db_datareader` и ничего кроме. Это единственная
настоящая гарантия, текст запроса обёртка не проверяет. **Персональные данные технически
не защищены** — ФИО, телефоны и адреса не запрашиваются потому, что так написано в правилах,
а не потому, что что-то это отклонит. Разбор идёт по идентификаторам.

Схему не угадывать: `dbo` часто пустышка. На боевом сервере `dbo.tPersonConsent` содержит
0 строк, а данные лежат в `consents.tPersonConsent`. Пустая выборка — повод проверить схему,
а не вывод «данных нет».

В отчёт идёт вывод, а не выборка: «у 412 записей из 15 340 пустой `RegionId`» — факт;
таблица на 40 строк с боевыми данными — утечка в задачу.

Настройка доступа и смена пароля — п. 2.6 основ, границы использования — п. 4.5.

## 4. `/pbe-task` — разбор постановки

```
/pbe-task CRM-544                 # постановка
/pbe-task CRM-544 SUPPORTDEV-1788 # спека аналитика + задача на разработку = ОДНА постановка
/pbe-task CRM-544 --links
```

Главный шаг этой команды — **разделение контура**. Аналитик пишет постановку на всю систему,
а этот репозиторий — только админка и её API. Агент раскладывает требования по корзинам:
ядро (`app/`) — модуль `modules/<Module>` — конфиг и гейтинг — схема БД — **не наше**
(приложение `pbeapp`, IQVIA, МДЛП, Mindbox, SAP) — **стык** (контракты, от которых зависят
соседи).

Дальше он сверяет требования с кодом («реализовано / частично / нет»), определяет охват
(всем клиентам или одному, чем включается, каким должен быть дефолт, кого заденет регрессия)
и собирает **открытые вопросы к аналитику**.

Про вопросы стоит сказать отдельно: это не признак того, что агент не справился. Пять точных
вопросов, отвеченных аналитиком за десять минут, дешевле недели работы по догадке. Возвращать
сырую постановку — нормальная часть процесса, а не конфликт.

**Спека из Вики подтягивается сама.** Постановки аналитиков в CRM почти всегда ссылаются
на страницу Вики, а не пересказывают требования в теле задачи. Разбор такие ссылки
выгружает через `.claude/scripts/wiki-page.sh` и в сверке понимания перечисляет прочитанные
страницы. Проверяй этот список: пусто там, где ты ждал спеку, — значит разделение контура
и охват построены по одному тексту задачи. Общее правило и ограничения — п. 4.1 основ.

## 4а. `/pbe-review` — ревью PR против постановки

```
/pbe-review CRM-1641          # найти PR по задаче и проверить реализацию
/pbe-review CRM-1641 --post   # + опубликовать замечания в PR
/pbe-review CRM-1641 --fix    # + починить найденное (только на своём PR)
```

Три команды закрывают три разные точки: `/pbe-task` — до разработки, `/pbe-review` — после,
`/pbe-bug` — когда уехавшее в прод сломалось.

**Чем отличается от встроенного `/code-review`.** Тот смотрит на код сам по себе. Этот
начинается с постановки: находит PR по ключу задачи, выписывает критерии приёмки из
`testPlan` / `externalChanges` / спеки в Вики и меряет реализацию **по ним**. Ответ на вопрос
«сделано ли то, что заказано» встроенная команда дать не может — она не видит задачу.

**Главное, ради чего стоит запускать именно её: PR почти всегда два.** Одна задача сплошь
и рядом разъезжается на функционал в модуле и проводку в ядре — зависимость в `composer.json`,
сьют в `phpunit.xml`, роут, конфиг. Модуль и ядро это **разные репозитории**
(`powbee/pbeadmin_<module>` и `powbee/pbeadmin`), и ревью одного PR из пары даёт ложный
вердикт: модульный PR, которому нужна новая библиотека, без ядрового просто фаталит на проде.
Команда проверяет оба репозитория и требует объяснить, если нашла только один.

**Вторая причина — замечания ревьюера видно целиком.** Комментарии PR отдают три разных
эндпоинта GitHub, а `gh pr view --comments` читает только ленту обсуждения. Инлайновые
замечания на строках кода — то есть содержательная часть любого ревью — в его вывод
не попадают вовсе, и потеря молчаливая. Скрипт `pr-comments.sh` забирает все три.

### Что делать с результатом

Первым идёт блок **бизнес-логики**: критерии приёмки, чей это контур, конфиги клиента.
Прочитай его до замечаний — здесь ловится «меряет код не той линейкой».

Дальше вердикт, найденные PR с ролью каждого и порядком выкатки, что хорошо, замечания
по severity со ссылками на строки и **матрица приёмки**: каждый критерий → чем подтверждён.
Зелёный phpunit сам по себе не означает выполнения постановки — непокрытые критерии команда
называет явно.

### Границы

- **Ничего не публикуется по умолчанию.** Отчёт в терминал — законченный результат. В PR
  замечания уходят только по флагу `--post` или явной просьбе.
- **Вердикт ставит человек.** Агент может оставить комментарий, но не approve и не
  request-changes. Это подстраховано технически: публикация идёт через обёртку
  `pr-review-post.sh`, которая проставляет `event=COMMENT` сама и не принимает его извне.
- **Чужой PR агент не правит.** Даже однострочный фикс — это замечание, а не коммит: ветка
  чужая, автор в ней работает, и локальные правки с ней разъедутся. `--fix` работает только
  на своём PR.

## 4б. `/pbe-bugreport` и `/pbe-supportdev` — завести дефект задачей

```
/pbe-bugreport при импорте специальность сперва создаётся, потом удаляется
/pbe-supportdev у Валенты на проде в Тихоликвидах количество аптек всегда 0
```

Все команды выше требуют **ключа задачи**. Эти две его создают: собирают постановку прямо
там, где дефект найден, и заводят задачу в Трекере по реквизитам регламента.

**Зачем.** До сих пор человек с проблемой в руках шёл заводить задачу руками — и по дороге
терял две вещи разом. Реквизиты регламента (мнемоника клиента тегом, компонент, тип,
родитель-подзадача) и контекст репозитория (ветка, сборка, значение конфига у этого клиента,
место в коде). Первое обнаруживается на разборе беклога, второе — не обнаруживается никогда.

**Какую из двух запускать.** Два вопроса, в этом порядке:

| | Вопрос | Ответ | Куда |
|---|---|---|---|
| 1 | Функционал уже на проде? | нет | `/pbe-bugreport` → `BUGREPORTS` |
| 2 | Если да: чинить надо хотфиксом, вне планового релиза? | да | `/pbe-supportdev` → `SUPPORTDEV` |
| | | нет, подождёт | `/pbe-bugreport` → `BUGREPORTS` |

Первый вопрос — граница из [описания очередей](../tracker-queues.md): признак прод,
а не то, кто нашёл, поэтому дефект, найденный клиентом на внешнем тесте, всё ещё багрепорт.
Второй вопрос — правило владельца очередей, и в описании очередей его пока нет: там граница
проведена одним признаком. Расхождение ведётся в долге; до его закрытия действует порядок выше.

Команда проверяет развилку первым шагом и, если не сходится, отправляет ко второй, а не
заводит задачу «куда попало, потом перенесём»: перенос между контурами задним числом
не восстанавливает ни приоритет, ни срок.

**Обращение клиента по почте — не ваш случай.** Такую задачу заводит техподдержка из
`SUPPORT`, со связью с исходным обращением и дедлайном по договору. Есть номер `SUPPORT-…` —
передайте его в поддержку, а не заводите дубль.

### Что команда делает за вас

- **Реквизиты по регламенту.** Очередь, тип, компонент, тег с мнемоникой клиента.
  Тип в `SUPPORTDEV` — «Инцидент»: типа «Ошибка» в этой очереди нет.
- **Исполнителя багрепорта** — тимлид команды, как требует
  [этап 11](../crm-lifecycle/11-testirovanie-i-revju.md) (4.5.4). Задачи `SUPPORTDEV` уходят
  без исполнителя: кому чинить и выпускать ли хотфиксом, решает разбор беклога поддержки.
- **Родителя багрепорта.** Багрепорт вешается **подзадачей**, а не связью `relates`.
  Команда спросит подзадачу «Разработка», в которой сделан дефектный функционал, — если
  вы её знаете, называйте: багрепорт уровнем выше при десятке подзадач не адресует ничего.
- **Контекст репозитория** — ветка, коммит, значение переопределённого конфига у клиента
  и место в коде, если вы его назвали. Место в коде идёт в задачу **гипотезой автора**,
  помеченной как непроверенная: причину разбирают по заведённой задаче, а не в момент её
  создания.

### Границы

- **Без вашего «да» задача не создаётся.** Команда показывает черновик целиком, потом делает
  сухой прогон, и только потом пишет. Задачу нельзя отменить — можно только закрыть.
- **Приоритет и дедлайн команда не ставит.** SLA у каждого клиента свой, по договору, и
  в репозитории его нет. Её работа — дать факты, по которым приоритет выставят: массовость,
  что именно не работает, есть ли обходной путь.
- **Шаги воспроизведения не выдумываются.** Не дали — команда спросит. Выдуманные шаги хуже
  отсутствующих: по ним пойдут проверять.
- **Боевых данных в задаче не будет.** Вывод — да («у 412 записей из 15 340 пустой
  `RegionId`»), выборка строками — нет. ФИО, телефоны, адреса не переносятся вообще.
- **Код команда не правит.** Её результат — ключ задачи, а не фикс.

### Дальше

Заведённая задача — вход в остальную обвязку, и разбор запускается **новой сессией**:

```
/pbe-bug BUGREPORTS-177
```

Не следом за созданием, а именно новой: в сессии, где вы формулировали проблему, агент
будет искать подтверждение вашей же гипотезе, а не причину.

---

## 5. Как идёт задача

```
/pbe-task или /pbe-bug → разбор, сверка понимания, открытые вопросы
   ↓ (реализация — отдельной командой, после того как разбор принят)
analyst                → критерии приёмки и User Stories, если постановка сырая
database               → только если меняется схема или нужна новая таблица
backend ∥ frontend     → реализация; контракт между ними фиксируется ДО параллельного запуска
qa                     → контрактные и точечные тесты
reviewer ∥ security    → гейты; security — по триггерам
   ↓ (агент коммитит в ветку задачи по ходу работы)
человек                → пуш по выданной команде, PR, ревью человеком
   ↓
/pbe-review            → разбор замечаний ревьюера и сверка с критериями приёмки
```

**Коммитит агент, пушит человек.** Коммит в ветку задачи — часть работы, а не шаг сдачи:
незакоммиченный результат дня не восстановим ничем. Наружу при этом без человека ничего
не уедет. Агент обязан закончить готовой строкой `git push -u origin <ветка>` — по одной
на каждый затронутый репозиторий, ядро и модуль пушатся отдельно.

**Контракт `backend` ∥ `frontend`.** Перед параллельным запуском фиксируются имена маршрутов
и HTTP-методы, форма payload'а (поля JSON — как их отдаёт JsonResource), права `@can`
и имя blade-шаблона. Владелец контракта — `backend`, фронт его не придумывает. Если контракта
ещё нет — сначала короткий шаг `backend` (маршруты + FormRequest + JsonResource, без логики),
потом параллель. Параллелить «вслепую, потом состыкуем» запрещено: стыковка дороже скелета.

Тривиальное не делегируй: правка одной строки, ответ на вопрос по коду — быстрее сделать
самому.

## 6. Гейты приёмки

Задача с кодом готова, только когда выполнено всё:

1. **Тесты зелёные** — минимум `vendor/bin/phpunit --testsuite Unit` плюс точечные тесты
   затронутого кода. Полный прогон (Feature) — только при доступной dev MSSQL: сьют ходит
   в неё. Не гонял полный — это фиксируется в сводке явно, а не умалчивается.
   ⚠️ `--filter` может зацепить Feature-тест модуля, который тоже пойдёт в dev MSSQL.
2. **Пройден `reviewer`.** Вердиктов, закрывающих задачу, два: «✅ ПРИНЯТО» и
   «⚠️ ПРИНЯТО С ПРАВКАМИ» — во втором случае задача готова только после внесения правок
   и построчной сверки внесённого с предложенным. Отклонилась правка от предложенного —
   идёт повторное ревью. «❌ ОТКЛОНЕНО» — цикл фикс → повторное ревью.
3. **Пройден `security`** по его триггерам: новые и изменённые маршруты (для `external.php`
   и `hook.php` — всегда), auth/SSO/JWT, raw SQL, загрузка файлов, интеграции, выдача PII/PHI.
   Гейт бинарный: PASS или FAIL. HIGH-находка по PII/PHI или auth равна блокеру.
   **Принять риск может только уполномоченный человек** — владелец продукта или ответственный
   за ИБ, названный поимённо. Ни агент, ни разработчик этого не могут; «ладно, выпускаем» —
   не принятие риска.
4. **Новые ключи настроек, статусы и константы покрыты контрактным тестом** (`qa`).
5. **Изменения перечислены пофайлово** с разделением «ядро / `modules/<Module>`» — это разные
   репозитории, и коммиты в них разные. Правки модуля коммитятся **внутри сабмодуля**.
6. **Матрица приёмки**: каждый критерий приёмки из постановки → чем подтверждён (автотест,
   ручная проверка с результатом, «не проверен» с причиной). Зелёный phpunit сам по себе
   не означает, что постановка выполнена.

7. **Готовая команда пуша** приведена для каждого затронутого репозитория.

Коммит в ветку задачи **входит** в Definition of Done и делается по ходу работы. Пуш, PR
и мердж — нет: наружу отправляет человек.

## 7. Что запрещено технически

Общая логика — в п. 4.7 основ: граница проходит по «уходит наружу» и «уничтожает работу»,
а не по «пишет в git». Здесь только специфика админки.

**Два рубежа.** `.claude/settings.json` (списки deny / ask / allow) и PreToolUse-хук
`.claude/hooks/guard_protected_branch.py`. Оба действуют и на основную сессию, и на всех
суб-агентов.

Запрещено (deny):

- **наружу** — `git push`, `gh pr create|merge|review|edit|close|ready`, `gh release`;
- **уничтожает работу** — `git clean`, `reset --hard`, `restore`/`checkout` по путям,
  `stash drop|clear`, `git rm`, `rm -rf` и его формы, `git submodule deinit`;
- **массовый стейдж** — `git add -A|.|-u`, `git commit -a`: втягивают `.env`, дампы
  и указатели сабмодулей;
- релизные скрипты (`make-pre-prod-release.sh`, `make-prod-hotfix.sh`, `checkout-prod.sh`, …);
- разрушительные artisan-команды: `migrate:fresh`, `migrate:refresh`, `migrate:reset`,
  `db:wipe`, `db:seed`, `queue:flush`, `tinker`;
- `composer update`, `npm install/update`, прямой `sqlcmd`.

С подтверждением (ask): `git reset`, удаление и переименование веток, `git config`,
`git submodule update`, `php artisan migrate`, полный `phpunit`, `composer install`,
`npm ci`, `npm run prod`, `git -C`/`--git-dir`/`--work-tree`, пишущие вызовы `gh api`.

Разрешено без подтверждения: вся обычная локальная работа с гитом (`add`, `commit`, `switch`,
`checkout`, `branch`, `merge`, `rebase`, `stash`, `fetch`, `pull`), читающие команды,
`gh pr view|list|diff|comment` и скрипты из `.claude/scripts/`.

**Что делает хук, чего не может список.** Списки матчатся по префиксу команды и не видят
ни ветку, ни индекс, ни флаг не в начале строки. Хук отклоняет:

1. коммит в `main`/`master`/`pre-prod`/`prod` и в detached HEAD — с учётом смены ветки
   в той же цепочке (`git switch main && git commit` тоже отклоняется);
2. коммит, в индексе которого оказался **указатель сабмодуля** — авторитетная проверка
   по содержимому индекса, а не по буквальному написанию `git add modules/...`;
3. `git checkout` по путям (от `git checkout <ветка>` префиксом неотличим, а последствия
   противоположны), `git reset --hard|--keep|--merge` и `git restore` без `--staged` —
   на любой позиции флага;
4. `git commit --amend` поверх коммита, который уже есть на сервере — переписывание
   опубликованной истории. Пока коммит только локальный, amend разрешён (см. п. 4.7 основ).

Оба рубежа обходятся тривиально (`sh -c '…'`, алиасы, `xargs`) — поэтому обход считается
нарушением, а не смекалкой (см. п. 4.7 основ).

## 8. Типичные ошибки в этом проекте

| Симптом | Что происходит на самом деле |
|---|---|
| Агент ищет таблицы `visits`, `doctors` | Взял бизнес-термины за имена таблиц. Направь в реальную схему |
| Предполагает Laravel-конвенции имён | Здесь database-first и PascalCase. Пусть смотрит миграцию и модель |
| Правит `modules/<Module>/` и молчит | Это сабмодуль, отдельный репозиторий и отдельный PR. Спроси охват явно |
| Предлагает «бампнуть указатель сабмодуля» | Такого шага в проекте нет: `ignore = all`, деплой решает сам. Указатель на непушенный коммит ломает `git submodule update` у всех |
| Ревью нашло замечания, которых ревьюер не писал | Смотрел ленту обсуждения вместо инлайновых замечаний. `/pbe-review` или `pr-comments.sh` |
| «Работает у всех» — а у клиента нет | Не сверил ветку кода с реальным значением `pbe`-конфига. `--fleet` |
| Пусто вместо данных | Смотри фильтры и join-ы, soft-delete (`DeleteDate`), скоуп по правам пользователя |
| Раздел не виден пользователю | Чаще упирается в `@can` и права, а не в логику |
| Предлагает новый сервис с нуля | Не посмотрел `app/Services/` и сервисы модулей: движок кампаний живёт в `modules/Omni/App/Services/Campaign/` |
