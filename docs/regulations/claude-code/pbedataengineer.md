## 1. Чем эта работа отличается от разработки

Четыре особенности, из которых следует всё остальное.

**Типовая задача — не «сломался код», а «цифра не бьётся».** Неполный месяц
в выбытии, задвоение остатков, уволенный сотрудник в дэшборде, «пусто» в фильтре
региона. Отсюда порядок: сначала доказательство запросом, потом правка.
Утверждение «сошлось» без числа не принимается.

**Дэшборд живёт в двух местах сразу.** Сам он в Superset, а пользователю
показывается через модуль `Bi` админки CRM: она выпускает guest-токен и
подставляет параметры RLS. «У меня пусто» одинаково часто означает и ошибку
в датасете, и настройку клиента в админке — поэтому в разборе всегда есть шаг
с `client-env.sh`.

**RLS — не деталь, а граница между клиентами.** Дэшборды видят сотрудники разных
фармкомпаний через одно встраивание, и строчная фильтрация — единственное, что
разделяет их данные. Правило привязано к датасету и его таблицам: переименовал
таблицу — потенциально снял фильтрацию, молча. Любая правка датасета
заканчивается ответом на вопрос, какое правило на нём работает и работает ли оно
после правки.

**Работа идёт в боевой базе.** У отдела законные права на запись в PROD
(`db_datareader` + `db_datawriter` + `EXECUTE`), и часть потока — ручные правки
данных по обращениям клиентов. Именно поэтому агенту дан отдельный, урезанный
доступ: только чтение и только через обёртку с журналом.

## 2. Обвязка

Репозиторий `pbedataengineer`, каталог `.claude/`.

| Команда | Что делает |
|---|---|
| `/pbe-task ANALYTIC-123` | разбор задачи: что просят, какой клиент, где смотреть. Только читает |
| `/pbe-dataset <имя>` | датасет: SQL в `sql/datasets/`, обязательные проверки, вопрос про RLS |
| `/pbe-dash <id>` | дэшборд: выгрузка YAML, правка, diff, команда импорта |
| `/pbe-kb` | занести в базу знаний факт о данных, добытый по ходу разбора |

| Скрипт | Что делает |
|---|---|
| `db-query.sh` | подключение к MSSQL: подставляет сервер и учётные данные, ведёт журнал; контур — `--profile` |
| `superset-api.sh` | Superset: список объектов, выгрузка в YAML, импорт (только с `--apply`); стенд — `--profile` |
| `client-env.sh` | конфиги клиента из консоли: кто это, какие инстансы, значения ключей |
| `tracker-issue.sh`, `wiki-page.sh`, `wiki2md.py` | выгрузка задач и страниц Вики |

**Отдел работает на Windows, обвязка — bash.** Рабочая среда для неё —
WSL2 с Ubuntu: в Git Bash нет `jq` и `python3`, без которых `superset-api.sh`
не работают (`db-query.sh` с недавних пор обходится
базовым набором и пошёл бы и там, но `superset-api.sh` — нет). Репозиторий и файлы с токенами живут в домашнем
каталоге WSL, а не в `/mnt/c/...`: на дисках Windows не действуют права доступа.

Доступы настраиваются один раз на машину: Трекер, консоль, профиль подключения
к MSSQL и учётная запись Superset. Хранилища паролей macOS в Windows нет —
скрипты читают учётные данные из файлов в `~/.config/` с правами `600`, менять
для этого ничего не нужно. Порядок по шагам, проверка каждого доступа и
подводные камни (CRLF в файле с токеном, токен в истории команд) —
`README.md` и `.claude/scripts/README.md` репозитория.

**Профиль называет контур, а не окружение.** Контуров у нас несколько: свой у каждого клиента (Валента, Сервье), свой
у каждой страны (KZ, UZ), плюс дев-контуры. Все выглядят одинаково, все боевые.
Поэтому подключение и к базе, и к Superset задаётся **профилем** — файлом на
контур в `~/.config/pbe-mssql/` и `~/.config/pbe-superset/`. Имя профиля —
мнемоника клиента из консоли, чтобы `--profile vlt` и `client-env.sh vlt`
указывали на одного и того же клиента, а не на разных.

Пароль ищется везде в одном порядке: переменная окружения → файл профиля →
Keychain (`pbe-mssql-<профиль>`, `pbe-superset-<профиль>`). На Windows Keychain
нет, его место занимают те же файлы в `~/.config/` — раздел про WSL и Git Bash
в `.claude/scripts/README.md`. Что настроено на машине — `--profiles` у обоих
скриптов.

**У базы умолчания нет.** `db-query.sh` без `--profile` (или
`PBE_MSSQL_PROFILE`) не запускается: останавливается и перечисляет доступные
контуры. Причина не в формализме — забытый флаг вернул бы не ошибку, а
правдоподобные цифры чужого клиента, и заметили бы это уже в дэшборде
у заказчика. Профиль на всю задачу удобнее задать один раз:
`export PBE_MSSQL_PROFILE=vlt`.

**У Superset умолчание есть, но только на чтение.** `--list`, `--export`,
`--get`, `--whoami` без профиля идут на общий стенд `common`, где клиенты
разделены RLS. Запись — с явным профилем, см. п. 3.4.

⚠️ В базу обёртка ходит **логином и паролем SQL Server**: доменная
аутентификация Windows ей недоступна. Учётная запись для агента и так заводится
отдельная — только `db_datareader` (см. п. 3.1), так что ограничение совпадает
с правилом.

## 3. Правила, обязательные в этом репозитории

### 3.1. В базу — только чтение

Запросы идут через `db-query.sh`. Обёртка подставляет сервер, логин и пароль,
дальше обычный `sqlcmd` — флаги и SQL пишет тот, кто вызывает. Каждый вызов
пишется в `logs/db-query.log`.

**Текст запроса обёртка не проверяет.** Единственная гарантия «только чтение» —
права учётной записи: `db_datareader`, без записи и без `EXECUTE`. Держать её
такой и регулярно это проверять — обязанность того, кто ведёт матрицу доступов,
а не свойство скрипта. Проверка — `check-ai-agents.sql` в рабочем пространстве
директора департамента информационных технологий.

Обходить его прямым `sqlcmd`, `bcp` или питоном с драйвером **нельзя** — это
запрещено и технически, в `settings.json`. Причина не в недоверии: журнал нужен,
чтобы через полгода можно было письменно ответить, что именно инструмент делал
в боевой базе. Такой вопрос на аудите заказчика звучит обязательно.

**Учётная запись для агента — отдельная и read-only.** Не рабочая учётка
дата-инженера с правом записи. Права — `db_datareader`, без `db_datawriter`
и без `EXECUTE`. Проверка внутри скрипта — второй рубеж, а не первый.

**Учётка заводится на каждый контур своя** (`svc_bi_reader_vlt`,
`svc_bi_reader_srv`), а не одна на все сразу: одна утёкшая пара логин-пароль
иначе открывает данные всех клиентов. Отсюда же требование называть контур
явно — вызов без `--profile` скрипт отклоняет (п. 2).

### 3.2. Правки данных в PROD делает человек

Перевесить согласие, вернуть статус, поправить ФИО — штатная работа отдела.
Агент такую правку **готовит**: текст запроса, оценка охвата (сколько строк
заденет), обратный запрос на случай отката. Выполняет её человек, руками,
и фиксирует в задаче.

### 3.3. Боевые данные не попадают в репозиторий и в контекст

В git идут SQL, выгрузки Superset, карточки базы знаний, разборы и выводы
в агрегатах: «расходится 412 строк из 5 048 221, все за март, все по одному
дистрибьютору». Результаты запросов — в `out/`, он вне git.

В git и в контекст не идут построчные выгрузки, ФИО и контакты врачей и
сотрудников фармкомпаний, данные МДЛП и продаж, скриншоты с данными клиента.
Строка с ПДн, попавшая в коммит, остаётся в истории навсегда. Общее правило —
п. 4.5 основ.

### 3.4. Запись в Superset — с подтверждения человека

`superset-api.sh --import` без `--apply` ничего не отправляет. Импорт идёт
с `overwrite=true` и заменяет объект целиком, поэтому порядок жёсткий:
**выгрузить текущее состояние → посмотреть diff → править → импортировать.**
Пропущенная выгрузка стирает чужие правки, сделанные в интерфейсе.

Сухой прогон (`--import` без `--apply`) на стенд не ходит вовсе: план того, что
поедет, читается офлайн, без соединения и без VPN. Первой строкой он печатает
`стенд: <профиль>` — адрес назначения видно **до** записи, а не после.

**Стенд при записи называется явно.** `--apply` без `--profile` отклоняется,
умолчание на чтение сюда не распространяется: дэшборд выделенного стенда,
молча уехавший на общий, становится виден сотрудникам чужих фармкомпаний.
Это утечка клиентских данных (п. 4.5 основ), а не опечатка в команде.

### 3.5. RLS проверяется всегда

Дэшборд, который видят несколько клиентов, не считается готовым, пока
не проверено разграничение — под пользователем клиента, а не под собой.

### 3.6. Коммит, push и импорт делает человек

Как и в остальных проектах: фиксация изменений — точка ответственности.

## 4. Как идёт задача

```
/pbe-task ANALYTIC-123     → разбор, сверка понимания, план проверки
   ↓ (человек подтверждает, что копаем в ту сторону)
/pbe-dataset <имя>         → SQL в sql/datasets/, проверки в sql/checks/
db-query.sh --profile … -i … → доказательство: сошлось / не сошлось, числом
/pbe-dash <id>             → выгрузка YAML, правка, diff
   ↓
человек                    → --apply с профилем стенда, проверка, RLS, коммит
   ↓
/pbe-kb                    → факт, добытый по дороге, — в базу знаний
артефакты в задачу         → что было, что стало, чем доказано
```

Порядок и его обоснование — `docs/playbook.md` репозитория, чек-лист приёмки
дэшборда — `docs/checklist.md`.

## 5. Гейты приёмки

Дэшборд готов, когда выполнено всё. Полный список — `docs/checklist.md`, здесь
то, что чаще всего пропускают:

1. **Гранулярность строки названа явно** и совпадает с тем, что ждёт заказчик.
2. **Дубли и NULL посчитаны**, границы периода проверены (неполный месяц,
   будущие даты, старт проекта).
3. **Метрика сошлась с независимым источником**, расхождение названо числом
   и долей.
4. **RLS проверено** под пользователем клиента.
5. **SQL датасета лежит в `sql/datasets/`** под тем же именем, что датасет
   в Superset, а выгрузка объекта закоммичена после импорта.
6. **В задаче есть отчёт на языке адресата**: что было, что стало, чем доказано,
   что проверить глазами.

Пункт, который не проверен, отмечается как непроверенный — не как выполненный.

## 6. Что запрещено технически

`.claude/settings.json` репозитория:

- прямые `sqlcmd`, `bcp`, `osql`, `isql` — в обход обёртки и журнала;
- изменяющие git-команды (`push`, `reset`, `rebase`, `merge`, `clean`, …),
  `gh pr merge`, `gh release`;
- правка файлов в `../pbeadmin`, `../pbeapp`, `../pbeconsole`;
- `rm -rf` и его формы.

С подтверждением: `superset-api.sh --import`, `curl`, `rm`.

**Флаг режима (`--list`, `--export`, `--import`) ставится первым** — и это
проверяет сам скрипт, отклоняя вызов, где `--import` спрятан за `--profile`.
Правило в `settings.json` работает по префиксу команды: без такой проверки
запись прошла бы мимо подтверждения человека, оставаясь формально разрешённым
чтением.

Список работает по префиксу команды и обходится тривиально — поэтому обход
считается нарушением, а не смекалкой (п. 4.7 основ).

## 7. Типичные ошибки в этом контуре

| Симптом | Что происходит на самом деле |
|---|---|
| «Цифра не бьётся» — агент сразу правит запрос | Причина не найдена, а подогнана. Сначала сверочный запрос, потом правка |
| Задвоение после «безобидного» join | Несогласие в гранулярности: одна строка — это врач или визит? |
| «Пусто в фильтре» | NULL в ключевом поле, фильтр удалённых, либо настройка клиента в админке — `client-env.sh` |
| Дэшборд импортирован поверх чужих правок | Пропущена выгрузка перед правкой; `overwrite=true` стёр то, что делали в интерфейсе |
| Дубль дэшборда на стенде | Сменили `uuid` в YAML — Superset посчитал объект новым |
| Запрос ушёл не в тот контур | Профиль забыт или остался от прошлой задачи. Цифры выглядят нормально — расхождение находит заказчик в своём дэшборде |
| Дэшборд клиента уехал на общий стенд | Импорт без `--profile`. Скрипт такой вызов отклоняет; в сухом прогоне сверять строку `стенд:` |
| Клиент видит чужие данные | Переименовали таблицу или датасет, RLS-правило перестало матчиться |
| Выгрузка на 200 тысяч строк в контексте | Проверять надо агрегатами. Заодно это ПДн, которых в контексте быть не должно |
| Запрос считается минуту | В дэшборде это превращается в жалобу. Время выполнения — часть приёмки |

## 8. Чего этот документ не покрывает

- **Yandex DataLens.** Вторая BI-платформа контура в репозиторий не заведена:
  у неё другая модель встраивания и свой формат. Работа с ней идёт как раньше.
- **Регулярные загрузки и витрины.** Ведутся вне репозитория.
- **Порядок фиксации ручных правок данных в PROD.** Отдельная тема: права
  на такие правки законны, но порядок их фиксации этим документом не задаётся.
- **Порядок ревью и мержа, ветвление, релизы** — существующий процесс команды,
  он не меняется.
- **Технический контекст** — `CLAUDE.md` репозитория, он же источник истины.
