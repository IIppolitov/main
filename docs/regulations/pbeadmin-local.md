# Локальный стенд админки (pbeadmin): инструкция для тестировщиков

Как поднять админку `pbeadmin` у себя на машине, подключить её к тестовой базе,
включить нужные модули и переключаться между версиями. Инструкция рассчитана на
того, кто делает это в первый раз и не разрабатывает код.

Источник истины по самому коду — `CLAUDE.md` и `README.md` в репозитории
`pbeadmin`. Здесь — порядок действий, а не описание архитектуры.

## 0. Главное правило: боевые данные

**Локальный стенд подключается только к тестовой базе. Тестировать на боевых
данных запрещено.**

Это не формальность. Локальный стенд — это полноценная админка с правами на
запись: рассылка, изменение согласий, перезапись мастер-данных. Данные в базах
клиента — персональные данные врачей и сотрудников фармкомпаний, за которые мы
отвечаем перед заказчиком. Одна проверка «а что будет, если нажать» на боевой
базе — это инцидент, а не баг.

Как не ошибиться:

- **хост и имя базы для локального стенда спрашивайте у директора департамента
  информационных технологий.** Первые разы — каждый раз, дальше вы запомните,
  какие базы ваши;
- **признак тестовой базы — суффикс `_dev` в имени.** Тестовые копии называются
  `crmAdmin_dev`, `Consent_dev`, `Bi_dev`; боевые — те же имена **без** суффикса.
  Увидели в `.env` базу без `_dev` — это боевая, работать нельзя. Признак
  надёжный, но смотреть надо и на хост: боевой сервер и сервер с тестовыми
  копиями — разные машины, и на боевом баз с `_dev` просто нет;
- **не подставляйте в `.env` реквизиты, которые нашли в задаче, в переписке или
  на сервере.** То, что реквизиты у вас есть, не значит, что база тестовая;
- **сомневаетесь — не подключайтесь, спросите.** Вопрос стоит минуту, разбор
  инцидента — неделю;
- миграции и сидеры (`migrate`, `db:seed`) на общей базе не запускайте без
  согласования: база у стенда общая, вы меняете её всем сразу. Скрипты из §5
  спрашивают об этом отдельно — там отвечайте «нет», если не договаривались.

## 1. Что должно быть на машине

| Что | Зачем | Проверить | Как поставить |
|---|---|---|---|
| **Git** | получить код | `git --version` | §1.1 |
| **PHP 8.2 или новее** | на нём работает админка | `php -v` | §1.1 |
| **Composer** | зависимости PHP | `composer --version` | §1.1 |
| **jq** | нужен скрипту `deploy.sh` | `jq --version` | §1.1 |
| **Расширения `sqlsrv` и `pdo_sqlsrv`** | без них нет связи с MSSQL | `php -m \| grep sqlsrv` | §1.2 |
| **SSH-ключ в GitHub** | модули и `deploy-scripts` подключаются по SSH | `ssh -T git@github.com` | §1.3 |
| **Доступ в сеть до сервера БД** | база живёт не на вашей машине | см. ниже | — |

**Доступ к репозиториям GitHub** (организация `powbee`) и **реквизиты к тестовой
базе** выдаются отдельно — заявка директору департамента информационных технологий.
Если до сервера БД не достучаться — вопрос к техническому директору: сеть и
доступы его зона.

**Node.js и npm не нужны.** Собранные стили и скрипты лежат в репозитории; сборка
фронта — задача разработчика, не тестировщика.

Всё, что ниже, ставится **один раз на машину**. Инструкция написана под macOS —
именно на нём работают тестировщики; на других системах набор тот же, отличаются
только команды установки.

### 1.1. Homebrew, PHP и остальные инструменты

**Homebrew** — менеджер пакетов для macOS: через него ставится всё остальное.
Проверить, есть ли он:

```bash
brew --version
```

Нет — установить (команда с сайта [brew.sh](https://brew.sh), выполняется одной
строкой, попросит пароль от вашей учётной записи Mac):

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

В конце установки Homebrew печатает две-три строки «Next steps» с командами
`echo ... >> ~/.zprofile` — **их надо выполнить**, иначе `brew` не найдётся в новом
окне терминала. Если попросит инструменты разработчика Apple, согласитесь или
выполните `xcode-select --install` (вместе с ними приезжает и `git`).

Дальше — сами инструменты:

```bash
brew install php@8.3 composer jq
```

**PHP ставим версией явно**, а не просто `brew install php`: тот поставит самую
свежую версию, а админка живёт на Laravel 8, и с новыми PHP у него вылезают
несовместимости. `php@8.3` — то, на чём работает команда; `php@8.2` тоже подойдёт,
ниже — нет.

`php@8.3` — «keg-only» формула: Homebrew её не подключает в `PATH` сам. Одна
строка, чтобы `php` в терминале означал именно её:

```bash
echo 'export PATH="/opt/homebrew/opt/php@8.3/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
```

Путь `/opt/homebrew` — для Mac на Apple Silicon (M1 и новее). На старых Intel-маках
Homebrew живёт в `/usr/local`, тогда и путь будет `/usr/local/opt/php@8.3/bin`.
Свой можно посмотреть командой `brew --prefix`.

Проверка — все четыре команды должны что-то ответить:

```bash
git --version
php -v            # ожидаем 8.3.x
composer --version
jq --version
```

### 1.2. Драйверы MSSQL: `sqlsrv` и `pdo_sqlsrv`

Наша база — Microsoft SQL Server, и PHP умеет с ней разговаривать только через
отдельные расширения. **Их нет ни в macOS, ни в пакете PHP** — ставятся руками,
и это самый частый затык при первом развороте.

Ставится в два слоя: сначала драйвер ODBC от Microsoft, потом расширения PHP
поверх него.

**Шаг 1. Драйвер ODBC.**

```bash
brew tap microsoft/mssql-release
brew install msodbcsql18 mssql-tools18 unixodbc
```

`brew tap` — это «подключить репозиторий Microsoft»: без него следующая команда
не найдёт пакеты. Установка `msodbcsql18` попросит принять лицензию.

**Шаг 2. Расширения PHP.**

```bash
pecl install sqlsrv pdo_sqlsrv
```

`pecl` приезжает вместе с PHP из Homebrew. Сборка занимает минуту-две и
компилируется прямо у вас на машине — это нормально.

Здесь есть подвох: **`pecl` ставит расширение в тот PHP, который сейчас первый
в `PATH`.** Если версий несколько, сначала убедитесь, что `php -v` показывает
8.3, и только потом запускайте `pecl`. Иначе расширение соберётся для другой
версии и в админке не появится.

**Шаг 3. Включить расширения.**

`pecl` обычно дописывает их сам. Проверяем:

```bash
php -m | grep sqlsrv
```

Ожидаемый ответ — две строки:

```
pdo_sqlsrv
sqlsrv
```

Пусто — включаем руками. Узнать, где лежит нужный файл настроек:

```bash
php --ini
```

В строке `Loaded Configuration File` будет путь к `php.ini` (обычно
`/opt/homebrew/etc/php/8.3/php.ini`). Открыть его любым редактором и дописать
в конец две строки:

```ini
extension=sqlsrv
extension=pdo_sqlsrv
```

Сохранить и снова проверить `php -m | grep sqlsrv`.

**Если `php -m | grep sqlsrv` молчит — дальше идти бессмысленно**: админка
запустится, но упадёт на первом же обращении к базе с `could not find driver`.

Ещё две вещи, которые пригодятся потом:

- **после обновления PHP** (`brew upgrade`) расширения могут отвалиться — они
  собраны под конкретную версию. Лечится повторным `pecl install sqlsrv pdo_sqlsrv`;
- **не собирается вовсе** (ошибки компиляции, не находит заголовки `unixodbc`) —
  не воюйте с этим в одиночку, спросите разработчиков админки: у них это уже
  настроено, и разница обычно в одной строке.

### 1.3. SSH-ключ для GitHub

Код мы забираем **по SSH**, а не по логину с паролем. Причина простая: модули
админки подключены сабмодулями по SSH-адресам, и без ключа они не выкачаются,
как бы вы ни клонировали ядро.

SSH-ключ — это пара файлов. **Приватный** лежит только у вас на машине и
заменяет пароль. **Публичный** (с расширением `.pub`) отдаётся GitHub'у. Настройка
одноразовая: сделали — забыли.

Ниже — команды для macOS и Linux. На Windows всё то же самое, но в терминале
**Git Bash** (ставится вместе с Git), а не в PowerShell.

**Шаг 1. Проверить, нет ли ключа уже.**

```bash
ls -la ~/.ssh
```

Если в списке есть `id_ed25519` и `id_ed25519.pub` — ключ у вас есть, переходите
к шагу 4. Пусто или папки нет — шаг 2.

**Шаг 2. Сгенерировать ключ.**

```bash
ssh-keygen -t ed25519 -C "ваша.почта@powbee.ru"
```

Команда задаст три вопроса:

- *куда сохранить* — жмите Enter, путь по умолчанию правильный;
- *passphrase* — пароль на сам ключ. Задайте его: если ноутбук потеряется,
  passphrase — единственное, что отделяет нашедшего от нашего кода. Вводить его
  каждый раз не придётся, см. шаг 3;
- *повторите passphrase* — ещё раз то же самое.

`-C` — просто пометка, чтобы потом понимать, чей это ключ; на работу не влияет.

**Шаг 3. Добавить ключ в агент** (чтобы passphrase не спрашивали постоянно).

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
```

На macOS вместо второй строки:

```bash
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```

— тогда passphrase запомнится в связке ключей и не будет спрашиваться после
перезагрузки.

**Шаг 4. Скопировать публичный ключ.**

```bash
pbcopy < ~/.ssh/id_ed25519.pub      # macOS — сразу в буфер обмена
clip < ~/.ssh/id_ed25519.pub        # Windows, Git Bash
cat ~/.ssh/id_ed25519.pub           # Linux — вывести и скопировать руками
```

Скопировать надо **всю строку целиком**, от `ssh-ed25519` до почты в конце, без
переносов.

**Шаг 5. Добавить ключ в GitHub.**

1. [github.com](https://github.com) → правый верхний угол, ваш аватар → **Settings**;
2. в левом меню — **SSH and GPG keys**;
3. кнопка **New SSH key**;
4. **Title** — имя машины, чтобы потом отличать: «рабочий ноут», «домашний ПК»;
5. **Key type** — `Authentication Key` (значение по умолчанию);
6. **Key** — вставить скопированное на шаге 4;
7. **Add SSH key**. GitHub попросит подтвердить пароль от учётной записи.

**Шаг 6. Проверить.**

```bash
ssh -T git@github.com
```

Первый раз спросит про подлинность сервера — ответьте `yes`. Правильный ответ
выглядит так:

```
Hi <ваш-логин>! You've successfully authenticated, but GitHub does not provide shell access.
```

Слова «does not provide shell access» — это **не ошибка**, а нормальный ответ:
ключ принят.

**Что важно понимать про ключ:**

- **приватный ключ никому не отдаётся.** Файл `id_ed25519` (без `.pub`) не
  пересылается в чат, не прикладывается к задаче, не копируется в репозиторий.
  Отдают только `.pub`;
- **один ключ на машину.** Не переносите ключ с ноутбука на другой компьютер —
  сгенерируйте там свой и добавьте вторым;
- **ключ — это ещё не доступ к нашим репозиториям.** Он подтверждает, что вы —
  это вы; членство в организации `powbee` выдаётся отдельно (§1). Симптом, что
  дело именно в правах, а не в ключе: `ssh -T` здоровается по имени, но
  `git clone` отвечает `Repository not found`. Это вопрос доступа — к директору
  департамента информационных технологий;
- **уже клонировали по HTTPS?** Не надо клонировать заново, достаточно поменять
  адрес в существующей папке:

  ```bash
  git remote set-url origin git@github.com:powbee/pbeadmin.git
  git remote -v
  ```

## 2. Первый разворот: шаг за шагом

Дальше — полная последовательность. Каждый шаг, который требует пояснений, ведёт
в свой раздел.

### 2.1. Клонировать репозиторий

Заведите себе рабочую папку (например, `~/Powbee`) и в ней:

```bash
cd ~/Powbee
git clone git@github.com:powbee/pbeadmin.git
cd pbeadmin
```

Клонируйте **по SSH** (`git@github.com:...`), а не по HTTPS: модули подключены как
git-сабмодули по SSH-адресам, и по HTTPS они потом не выкачаются. Ключ ещё не
настроен или `git clone` отвечает `Permission denied (publickey)` — §1.3.

**Сабмодули сразу выкачивать не надо** — `--recurse-submodules` не используем.
Модулей два с половиной десятка, вам нужны единицы; каждый подключается отдельно
и только тот, который вы тестируете (§4 и §5.2).

О командах гита, которые понадобятся дальше, — §6.

### 2.2. Установить зависимости

```bash
composer install --ignore-platform-reqs
```

Флаг `--ignore-platform-reqs` в проекте штатный: он снимает расхождение версий
PHP в консоли и в вебе.

### 2.3. Создать и заполнить `.env`

```bash
cp .env.example .env
```

Дальше файл надо править руками — что в нём писать, разобрано в §3.
**Пока `.env` не заполнен, следующие шаги работать не будут.**

### 2.4. Сгенерировать ключи

```bash
php artisan key:generate
php artisan jwt:secret
```

Первая команда создаёт ключ шифрования приложения (`APP_KEY`), вторая — секрет для
токенов авторизации. Обе пишут значения прямо в `.env`. Делается один раз.

### 2.5. Завести файл статусов модулей

```bash
echo '{}' > modules_statuses.json
```

Этого файла нет в репозитории (он у каждого свой) — без него админка считает, что
выключены все модули, и это нормальное стартовое состояние. Что это за файл и как
он устроен — §4.

### 2.6. Подготовить хранилище

```bash
php artisan storage:link
chmod -R 777 storage
```

Первая команда делает ссылку на папку с загруженными файлами, вторая снимает
типовую проблему с правами (`failed to open stream` в логе).

### 2.7. Подключить нужные модули

Голое ядро админки — это меньше половины функциональности. Модуль, который вы
тестируете, подключается скриптом `enable-module.sh` — §5.2.

### 2.8. Запустить и открыть в браузере

Как — §7.

## 3. `.env` — что это и как заполнять

### 3.1. Что это за файл

`.env` — файл настроек **вашей конкретной установки** в корне `pbeadmin`. В нём
лежит всё, что отличается от машины к машине и от стенда к стенду: адреса и
реквизиты баз, ключи, адреса внешних сервисов, включённые режимы.

Три вещи, которые надо про него понимать:

1. **Его нет в репозитории и не должно быть.** `.env` в `.gitignore`: внутри
   пароли. Не коммитьте его, не прикладывайте к задаче, не пересылайте в чат.
   Нужно передать коллеге настройки — передавайте имена переменных, а пароли
   он получит там же, где вы.
2. **За образец берётся `.env.example`** — он в репозитории и содержит перечень
   переменных с безопасными значениями-заглушками. Это шаблон, а не рабочий файл.
3. **Приложение читает `.env` при старте.** Поправили — перезапустите сервер
   (§7). Если правка не подхватилась, выполните `php artisan config:clear`.

### 3.2. Основное подключение к базе

Базовый блок для MSSQL выглядит так:

```dotenv
DB_CONNECTION=sqlsrv
DB_HOST=<адрес-тестового-сервера>
DB_PORT=1433
DB_DATABASE=crmAdmin_dev
DB_USERNAME=<ваш-логин>
DB_PASSWORD=<ваш-пароль>
```

Значения в угловых скобках — заглушки: подставлять их как есть бессмысленно,
реквизиты выдаются (§0).

- `DB_CONNECTION=sqlsrv` — обязательно. В `.env.example` по умолчанию стоит
  `mysql`, это наследство шаблона Laravel, у нас MSSQL;
- `DB_HOST` — адрес **тестового** сервера БД, `DB_PORT` — обычно `1433`;
- `DB_DATABASE` — имя базы, **всегда с суффиксом `_dev`** (§0);
- `DB_USERNAME` / `DB_PASSWORD` — ваши личные реквизиты, а не общие. Пароль
  с пробелами или спецсимволами берите в кавычки: `DB_PASSWORD="па роль"`.

**Какую базу и с каким хостом подключать — см. §0.**

### 3.3. Подключение модуля с собственной базой

У части модулей своя база — отдельная от `crmAdmin`. Такой модуль объявляет
собственный набор переменных, и они начинаются с `MODULE_`:

```dotenv
MODULE_CONSENT_DB_HOST=<адрес-тестового-сервера>
MODULE_CONSENT_DB_PORT=1433
MODULE_CONSENT_DB_DATABASE=Consent_dev
MODULE_CONSENT_DB_USERNAME=<ваш-логин>
MODULE_CONSENT_DB_PASSWORD=<ваш-пароль>
```

База у модуля своя и тоже **с суффиксом `_dev`** (`Consent_dev`, `Bi_dev`,
`ContentFactory_dev`). Хост обычно тот же, что у основной базы.

**Имена переменных не угадывайте — модуль объявляет их сам** в файле
`modules/<Модуль>/config/database.php`. Правило именования не всегда очевидно:
у `Consent` это `MODULE_CONSENT_DB_*`, а у `ContentFactory` —
`MODULE_CONTENT_FACTORY_DB_*` (с подчёркиванием внутри имени). Посмотреть, что
ждёт конкретный модуль:

```bash
grep "env(" modules/Consent/config/database.php
```

Если файла `config/database.php` в модуле нет — у модуля нет своей базы, и
подключать ему нечего: он работает в основной.

Заполнять этот блок вручную обычно не приходится: `enable-module.sh` (§5.2)
читает список переменных из модуля и спрашивает недостающие сам.

### 3.4. Что ещё бывает в `.env`

Кроме баз там встречаются токены внешних сервисов, адреса API, почта, признаки
включённых режимов (`USE_*`). Тестировщику это нужно редко и по конкретному
поводу: если проверяемая функциональность требует внешней интеграции, реквизиты
запрашиваются отдельно. Строки `APP_CORE_VERSION`, `MODULE_*_VERSION` и
`APP_MODULES_VERSION` дописывает скрипт деплоя (§5.1) — это справка о том, какие
версии сейчас развёрнуты; руками их не правят.

## 4. Модули: что это и как с ними работать

### 4.1. Что такое модуль

Админка состоит из **ядра** и **модулей**. Ядро — мастер-данные, пользователи,
права, базовые справочники. Модуль — законченный кусок функциональности:
`Consent` (согласия), `ContentFactory` (контент), `Omni`, `Bi`, `Survey`,
`Bots` и другие, всего около двадцати пяти.

Технически каждый модуль — **отдельный git-репозиторий**, подключённый в папку
`modules/<Имя>` как сабмодуль. Отсюда два следствия, которые надо держать в голове:

- у модуля **своя история и свои версии**. Тег `prod-v8.0` у ядра и у модуля —
  это разные коммиты разных репозиториев;
- модуль в клоне может физически отсутствовать (папка пустая), пока его не
  выкачали.

**Набор модулей у каждого клиента свой.** Именно поэтому нельзя «поднять админку
целиком» — можно поднять её в конфигурации конкретного клиента.

### 4.2. `modules_statuses.json`

Файл в корне `pbeadmin`, отвечающий на вопрос «какие модули включены на этой
установке»:

```json
{
    "ContentFactory": true,
    "Consent": true,
    "Omni": false
}
```

- `true` — модуль работает: его пункты меню, маршруты и миграции подключены;
- `false` — модуль выключен, как будто его нет;
- **модуля нет в файле — значит, он выключен.** Пустой `{}` — всё выключено.

Файл не хранится в репозитории: у каждой установки набор свой. Поэтому в новом
клоне его надо создать (§2.5), а рядом лежит `modules_statuses.json.example` —
образец со списком имён.

### 4.3. Включить и выключить модуль

Руками файл лучше не править — есть команды:

```bash
php artisan module:enable Consent     # включить
php artisan module:disable Consent    # выключить
php artisan module:list               # что сейчас включено
```

Имя модуля пишется точно так, как называется папка в `modules/` — `Consent`,
`ContentFactory`, `PharmacyStock`. Регистр важен.

**Включение — это ещё не всё.** Чтобы модуль заработал, нужно: выкачать его код
(сабмодуль), выбрать версию, прописать подключение к его базе, включить, сбросить
кеш шаблонов и накатить его миграции. Полный порядок делает `enable-module.sh` —
§5.2, и им и пользуйтесь. Ручные команды нужны, когда надо быстро выключить
модуль или посмотреть список.

После правки статусов вручную сбрасывайте кеш шаблонов:

```bash
php artisan view:clear
```

## 5. Репозиторий `deploy-scripts`

Отдельный репозиторий с двумя нужными вам скриптами: `deploy.sh` — переключение
всей админки на нужную версию или ветку, `enable-module/enable-module.sh` —
подключение модуля.

Клонируется **рядом** с `pbeadmin`, а не внутрь него:

```bash
cd ~/Powbee
git clone git@github.com:powbee/deploy-scripts.git
cd deploy-scripts
chmod +x deploy.sh enable-module/enable-module.sh
```

Оба скрипта работают не «у себя», а над папкой `pbeadmin` — путь к ней передаётся
аргументом. Чтобы не писать его каждый раз:

```bash
export PBEADMIN_PROJECT_DIR=~/Powbee/pbeadmin
```

### 5.1. `deploy.sh` — переключить админку на нужную версию

Что делает: переключает **ядро и все включённые модули разом** на одну версию —
последний тег `prod-v*`, последний `pre-prod-v*` или указанную ветку. Дальше по
подтверждению обновляет зависимости, накатывает миграции, сеет права, обновляет
Swagger и записывает получившиеся версии в `.env`.

Зачем это тестировщику: **чтобы собрать у себя ровно ту сборку, которую надо
проверить**, и не переключать двадцать репозиториев руками.

```bash
./deploy.sh                          # последние теги prod-v*  — что стоит у клиентов
./deploy.sh --pre-prod               # последние теги pre-prod-v* — то, что готовится к релизу
./deploy.sh --main                   # ядро и модули на ветку main
./deploy.sh --branch CRM-1246        # всё на ветку задачи
./deploy.sh --help                   # справка по флагам
```

Путь к проекту берётся, по порядку: из первого аргумента, из
`PBEADMIN_PROJECT_DIR`, из текущей папки. В двух последних случаях скрипт покажет,
какую папку взял, и спросит подтверждение — прочитайте эту строку, а не жмите
Enter вслепую.

Что надо знать о его поведении:

- **он трогает только включённые модули** — те, у которых в
  `modules_statuses.json` стоит `true`. Выключенный модуль останется на своей
  версии;
- **если в модуле нет запрошенной ветки, он переключится на свою ветку по
  умолчанию.** В итоговом отчёте это помечается как `Ветка: master (вместо main)` —
  проверяйте отчёт, иначе можно тестировать не то, что думаете;
- **каждый опасный шаг спрашивает `[y/N]`**: composer, миграции, сидер прав,
  Swagger. Про миграции на общей базе — см. §0;
- **любая ошибка останавливает скрипт целиком** — это защита от полуобновлённого
  состояния. Остановился — читайте последние строки вывода, там причина;
- **после переключения по тегу вы окажетесь в detached HEAD** — это нормально,
  см. §6.5;
- в конце печатается **сводный отчёт** с версией ядра и каждого модуля. Прикладывайте
  его к багрепорту: «воспроизведено на такой-то сборке» — это он.

### 5.2. `enable-module.sh` — подключить модуль

Что делает — весь порядок включения модуля, который иначе пришлось бы делать
руками и в правильной последовательности:

1. выкачивает сабмодуль `modules/<Модуль>`;
2. переключает его на выбранную версию (`prod`, `pre-prod`, `main` или указанную);
3. дописывает в `.env` параметры подключения к базе модуля — спрашивает только те
   переменные, которых там ещё нет, и предлагает значения основной базы по умолчанию;
4. выполняет `php artisan module:enable <Модуль>`;
5. сбрасывает кеш шаблонов (`view:clear`);
6. накатывает миграции модуля — по подтверждению;
7. запускает сидер прав `RightSeeder` — по подтверждению.

```bash
cd ~/Powbee/deploy-scripts/enable-module

./enable-module.sh Consent ~/Powbee/pbeadmin          # интерактивно: спросит версию и базу
./enable-module.sh --prod Consent ~/Powbee/pbeadmin   # сразу актуальный prod-тег
./enable-module.sh -r pre-prod-v8.0 Bi ~/Powbee/pbeadmin
./enable-module.sh --dry-run Omni ~/Powbee/pbeadmin   # показать, что будет сделано, ничего не меняя
./enable-module.sh --help
```

Что надо знать:

- **`--dry-run` — ваш первый запуск.** Он ничего не меняет и показывает весь план;
- **скрипт не создаёт базу модуля.** Если базы и логина к ней нет — их заводят
  заранее, это не к вам. Симптом: модуль включился, но падает на первом же экране
  с ошибкой подключения;
- **перед правкой `.env` делается резервная копия** в `storage/app/env-backups/`;
- **незакоммиченные изменения в папке модуля останавливают скрипт** — он не станет
  затирать вашу работу;
- в конце скрипт перечислит остальные переменные модуля (токены, адреса внешних
  API), которых нет в `.env`, — их дописывают руками, реквизиты запрашиваются
  отдельно;
- шаг про миграции и `RightSeeder` по умолчанию отвечает «да». На общей тестовой
  базе, где модуль уже разворачивали, отвечайте осознанно — см. §0.

## 6. Git: минимум, который нужен

Гит нужен вам не для того, чтобы писать код, а чтобы **получить нужную версию
кода**. Для этого хватает шести команд.

### 6.1. Где вы находитесь

```bash
git status                # текущая ветка и изменённые файлы
git branch --show-current # только имя ветки
git log --oneline -5      # последние пять коммитов
```

`git status` — первое, что делают, когда что-то идёт не так.

### 6.2. Забрать свежий код

```bash
git pull
```

Забирает изменения с сервера в текущую ветку. Работает, только если вы на ветке
(не на теге) и нет незакоммиченных правок.

```bash
git fetch --all --tags
```

Скачивает всё новое (включая теги), **ничего не меняя** в рабочей папке. Полезно
перед переключением на свежий тег: без `fetch` гит про новый тег ещё не знает.

### 6.3. Переключиться на другую версию

```bash
git checkout main            # на ветку main
git checkout CRM-1246        # на ветку задачи
git checkout prod-v8.0       # на тег (релизную версию)
```

После переключения на **ветку** делайте `git pull` — ветка могла уйти вперёд.
После переключения на **тег** `pull` не нужен: тег неподвижен.

Названия веток задач у нас совпадают с ключом задачи в Трекере — `CRM-1246`.
Точное имя ветки спрашивайте у разработчика или смотрите в Pull Request'е задачи.

### 6.4. Если гит не даёт переключиться

Типовое сообщение — «your local changes would be overwritten». Значит, вы что-то
поправили в файлах проекта. Посмотрите что:

```bash
git status
git diff
```

Если правки не ваши и не нужны — откатите их:

```bash
git checkout -- <файл>    # вернуть один файл
```

Откатывать всё разом или сносить папку — не надо: сначала покажите вывод
`git status` разработчику или мне.

### 6.5. Detached HEAD — это не поломка

После `git checkout prod-v8.0` гит скажет, что вы в состоянии detached HEAD. Это
означает ровно одно: вы смотрите на конкретную зафиксированную версию, а не на
ветку. Для тестирования это нормальное и даже правильное состояние. Вернуться:

```bash
git checkout main
```

### 6.6. Модули — это отдельные репозитории

Команды гита в корне `pbeadmin` **не переключают модули**. У каждого модуля своя
история, и работать с ним надо из его папки:

```bash
cd modules/Consent
git status
git checkout prod-v8.0
```

Из-за этого в `git status` ядра после переключения модулей появляются строки о
изменённых `modules/...` — это не ваши правки, а отметка о том, на какой версии
стоит модуль. Коммитить их не надо; вам вообще не надо ничего коммитить в
`pbeadmin`.

Переключать модули по одному руками обычно не нужно — для этого есть `deploy.sh`
(§5.1).

## 7. Запуск и адрес в браузере

Из корня `pbeadmin`:

```bash
php artisan serve
```

В выводе появится адрес:

```
Starting Laravel development server: http://127.0.0.1:8000
```

Открывайте **http://127.0.0.1:8000** — это и есть ваша админка.

- **порт занят** (`Failed to listen on 127.0.0.1:8000`) — запустите на другом:
  `php artisan serve --port=8001`, адрес станет `http://127.0.0.1:8001`;
- **остановить сервер** — `Ctrl+C` в том же терминале. Терминал во время работы
  занят: команды `artisan` выполняйте во втором окне;
- **вход в админку** — учётной записью из **той базы**, к которой вы подключились
  в `.env`. Локальный стенд не заводит пользователей сам;
- **правки в `.env` подхватываются при перезапуске.** Не подхватились —
  `php artisan config:clear` и снова `php artisan serve`;
- часть функциональности (предпросмотр PDF в `ContentFactory`) требует адреса
  `localhost` вместо `127.0.0.1` — если экран пустой, попробуйте
  **http://localhost:8000**.

## 8. Если не заводится

| Симптом | Причина | Что делать |
|---|---|---|
| `could not find driver` | нет расширения `sqlsrv` | §1.2, проверить `php -m \| grep sqlsrv` |
| `Login failed for user` | неверные реквизиты или нет доступа к серверу | проверить `.env`, §3.2; доступ — к техническому директору |
| `No application encryption key` | не сгенерирован `APP_KEY` | `php artisan key:generate`, §2.4 |
| Пункта меню модуля нет | модуль не включён или не выкачан | `php artisan module:list`, §4.3, §5.2 |
| Модуль включён, но падает на своём экране | не заполнены `MODULE_*` в `.env` или нет базы модуля | §3.3, §5.2 |
| Изменения в `.env` не действуют | кеш конфигурации | `php artisan config:clear` |
| `command not found: php` / `zsh: command not found: brew` | инструменты не подключены в `PATH` | §1.1, шаг с `~/.zshrc` |
| `Permission denied (publickey)` | SSH-ключ не настроен или не добавлен в GitHub | §1.3 |
| `fatal: could not read Username` при выкачивании модуля | репозиторий клонирован по HTTPS | §1.3, шаг «уже клонировали по HTTPS» |
| `ssh -T` здоровается, но `Repository not found` | ключ в порядке, нет доступа к репозиторию | заявка директору департамента ИТ, §1.3 |
| Белый экран после переключения версии | старый кеш шаблонов | `php artisan view:clear` |

Не помогло — приносите **вывод команды целиком**, а не пересказ: строку с ошибкой,
имя ветки или тега (`git status`) и сводный отчёт `deploy.sh`, если переключались им.

## 9. Что не делать

- не подключаться к боевым базам — §0;
- не запускать `migrate`, `db:seed`, `migrate:fresh` на общей тестовой базе без
  согласования: она общая;
- не коммитить и не пересылать `.env` — там пароли;
- не коммитить ничего в `pbeadmin` и его модули: тестировщику это не нужно, а
  случайный коммит с изменёнными версиями модулей ломает сборку остальным;
- не править код, чтобы «проверить гипотезу», — воспроизводите на чистой сборке,
  иначе баг не примут.
