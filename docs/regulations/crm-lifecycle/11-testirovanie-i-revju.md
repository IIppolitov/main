# Этап 11 — Внутреннее тестирование и ревью

## 1. Область применения

Регламент определяет порядок тестирования задач QA-командой и проведения код-ревью тимлидом. Обязателен для QA-инженеров, разработчиков и тимлидов.

## 2. Ответственные и участники

| Роль | Участник | Функции |
|------|----------|---------|
| Ответственный (тестирование) | QA-инженер | Тестирование, управление статусами подзадач |
| Ответственный (ревью) | Тимлид | Код-ревью, слияние кода в основную ветку |
| Участник | Разработчик | Устранение замечаний от QA и тимлида |

## 3. Общие положения

Подзадачи типа **«Тестирование» не создаются**. QA работает напрямую с подзадачами «Разработка» и логирует время в **основную задачу**. Порядок ревью и тестирования различается по командам: для Администрирования — сначала QA, затем ревью; для Приложения — сначала ревью, затем сборка и QA.

## 4. Порядок выполнения

### 4.1. Когда задача попадает на тестирование

- Подзадача «Разработка» в статусе «Можно тестировать»
- QA-инженер назначен исполнителем

### 4.2. Процесс для команды «Администрирование»

Задачи тестируются и закрываются **индивидуально** по мере готовности.

**Шаг 1 — Тестирование QA:**

1. QA переводит задачу в статус **«Тестируется»**, проверяет по Критериям приёмки.
2. Если прошло → **«Готово к ревью»**, фиксирует результат в комментарии.
3. Если не прошло → описывает дефект, переводит в **«На доработку»**, назначает разработчика.

После устранения разработчик возвращает в «Можно тестировать» — QA перепроверяет.

**Шаг 2 — Код-ревью тимлида:**

1. Тимлид переводит задачу в статус **«Ревью»**.
2. Если принято → сливает код в основную ветку, переводит в **«Тест внешний»**.
3. Если отклонено → оставляет замечания в PR, переводит в **«На доработку»**, назначает разработчика.

После устранения: разработчик → «Можно тестировать» → QA (при необходимости) → «Готово к ревью» → тимлид.

---

### 4.3. Процесс для команды «Приложение»

Ревью и тестирование проводятся **пакетно** по всему релизу. Порядок: сначала ревью, затем сборка и тестирование.

**Предусловие:** Все задачи спринта в статусе «Можно тестировать».

**Шаг 1 — Код-ревью тимлида (пакетное):**

1. Тимлид проводит ревью по всем задачам спринта.
2. По каждой задаче: «Можно тестировать» → **«Готово к ревью»** → **«Ревью»**.
3. Если задача принята → ожидает остальных.
4. Если задача отклонена → «На доработку», разработчик устраняет, возвращает в «Можно тестировать», тимлид перепроверяет.

**Шаг 2 — Сборка QA-версии:**

Когда **все** задачи прошли ревью, **CTO** собирает QA-сборку.

**Шаг 3 — Тестирование QA:**

Перед началом QA проверяет:
- [ ] Все задачи спринта прошли ревью
- [ ] QA-сборка собрана CTO
- [ ] Чек-лист задач релиза составлен
- [ ] Регресс включён в чек-лист

1. QA тестирует весь релиз и проводит регресс-тестирование.
2. По каждой задаче: **«Тестируется»** → результат.
3. Если прошло → **«Тест внешний»**.
4. Если не прошло → **«На доработку»**, разработчик устраняет. Цикл начинается заново с Шага 1.

---

### 4.4. Работа с дефектами, не относящимися к конкретной подзадаче

- Единичные случаи → фиксируются в комментарии подзадачи.
- Множественные или сложные дефекты → создаётся отдельная задача типа «Ошибка»; исполнитель — тимлид команды.

## 5. Критерии завершения

- [ ] Все подзадачи «Разработка» в статусе «Тест внешний»
- [ ] Код влит в основную ветку для всех задач
- [ ] Время зафиксировано (QA и тимлид — в основную задачу)

## 6. Учёт трудозатрат

| Кто | Где фиксирует | Обязательность |
|-----|--------------|---------------|
| QA-инженер | Основная задача | Обязательно |
| Тимлид (ревью) | Основная задача | Обязательно |
| Разработчик (доработки) | Подзадача «Разработка» | Обязательно |
