## 1. Область применения

Регламент определяет порядок выпуска задач в производственную среду. Обязателен для Релиз-менеджера, тимлидов и CTO.

## 2. Ответственные и участники

| Роль | Участник | Функции |
|------|----------|---------|
| Ответственный | Релиз-менеджер | Координация релиза, подготовка release notes, контроль полноты |
| Участник | Тимлид | Техническое обеспечение релиза, контроль качества |
| Участник | CTO | Деплой на продакшн-окружение, управление конфигурациями |
| Получатель | КАМ | Информирование клиента о выпуске; предрелизные договорённости с клиентом по подзадаче «Релиз» |

## 3. Общие положения

Финальная техническая точка жизненного цикла задачи. Цель — безопасный и контролируемый выпуск изменений с минимальным влиянием на работоспособность системы.

## 4. Порядок выполнения

### 4.1. Когда задача попадает на этап

- Все подзадачи «Разработка» в статусе «Готово к релизу»

### 4.2. Подготовка к релизу

Релиз-менеджер перед выпуском:
1. Формирует перечень задач для включения в релиз. Состав берётся из проектов
   Трекера, а не из памяти:
   - **Администрирование** — из **карточки релиза** в
     [pbeconsole](../../systems/pbeconsole.md): она уже свела два спринта релиза
     и проект `Релиз Админка <NN>. Вне спринта`, где лежит всё добранное по
     ходу — работа мимо спринтов, поздние обращения поддержки и хотфиксы, уже
     ушедшие в прод в этом релизном цикле ([этап 8](08-nabor-sprintov.md), 4.4).
     Перед сбором обновить состав из Трекера, чтобы снапшот не отставал;
   - **Приложение** — спринт клиента; состав уже сверен тимлидом в задаче
     «Подготовка релиза» ([этап 11](11-testirovanie-i-revju.md), 4.4).
2. Открывает подзадачи **«Релиз»** по включённым задачам, если они есть: у таких
   задач выкатка идёт по плану из подзадачи, а не общим порядком
   ([этап 5](05-ocenka-zadachi.md), 4.3.1). Проверяет, что предрелизные пункты —
   те, что требовали действия клиента, — закрыты. Незакрытый пункт снимает
   задачу с релиза, а не переносит риск на выкатку.
3. Готовит **release notes** (краткое описание изменений, затронутые компоненты, инструкции при необходимости). Для задач с подзадачей «Релиз» источник — она.
   Хотфиксы из проекта «Вне спринта» в release notes попадают наравне с
   остальным: клиент их на проде уже видел, но в перечне изменений релиза они
   должны быть — иначе история версий врёт.
4. Проверяет, что все конфигурации и настройки готовы.
5. Согласовывает время релиза с командами.
6. Уведомляет заинтересованные стороны о времени выпуска.

### 4.3. Процедура выпуска по командам

#### Команда «Администрирование»

**Ритм релизов:** Спринт N + Спринт N+1 → 2 недели на фиксы (во время Спринта N+2) → Релиз.

1. CTO применяет релиз-тег к производственному окружению.
2. CTO контролирует корректность применения конфигураций.
3. После успешного выпуска **Релиз-менеджер** переводит подзадачи «Разработка» в статус **«Демонстрация заказчику»** и передаёт задачи КАМам.

#### Команда «Приложение»

**Схема выпуска: пилот → полный релиз.**

**Предусловие:** задачи «Подготовка релиза» и «Регресс приложения» закрыты на
[этапе 11](11-testirovanie-i-revju.md) (4.4). Незакрытый регресс снимает релиз с
выпуска.

**Пилот:**
1. CTO формирует пилотную версию приложения.
2. Версия распространяется на ограниченную группу пользователей клиента.
3. КАМ отслеживает обратную связь. Минимальный срок пилота — **1 неделя**.
4. КАМ принимает решение о переходе к полному релизу.

**Полный релиз:**
1. CTO публикует версию для всех пользователей клиента.
2. **Релиз-менеджер** переводит подзадачи «Разработка» в статус **«Демонстрация заказчику»**.

**Если в ходе пилота выявлены критические ошибки:**
- Релиз приостанавливается.
- Затронутые задачи возвращаются в «На доработку».
- После исправления задача проходит **полный круг заново**: внутреннее
  тестирование ([этап 11](11-testirovanie-i-revju.md)) → тестирование клиентом
  ([этап 12](12-testirovanie-klientom.md)) → новый пилот.

> Повторный внешний тест не пропускается: клиент подтверждает именно
> исправленную версию, а не ту, которую принимал до правки.

### 4.4. Конфигурации и настройки

Если задача добавила новые конфигурационные параметры:
- CTO убеждается в наличии инструкции по применению.
- Применяет конфигурацию на продуктивном окружении.
- Если конфигурация применяется вручную — это явно отражается в release notes с указанием ответственного.

### 4.5. Учёт времени CTO

Если деплой рутинный (запуск CI/CD, контроль) — логирование по усмотрению. Если выполнялась нестандартная работа (настройка инфраструктуры, устранение инцидента) — **фиксирует в основную задачу** с коротким комментарием.

### 4.6. Запуск задач «Документация»

После успешной выкатки Релиз-менеджер проходит по связям `relates` основной
задачи и по каждой связанной задаче типа **«Документация»** отмечает
комментарием, что изменение в продуктиве и с какой даты.

Это отметка о готовности к работе, а не постановка задачи кому-то: раньше
выкатки мануал не правится — до продуктива поведение системы ещё может
измениться, а опубликованная страница, описывающая несуществующее поведение,
хуже отсутствующей.

### 4.7. Исполнение и закрытие подзадачи «Релиз»

**Подзадача «Релиз» исполняется здесь и только здесь** — в момент выкатки задачи
на продакшен, силами команды релиза. На предыдущих этапах она открыта как рабочий
документ: план дописывается, предрелизные пункты закрываются
([этап 5](05-ocenka-zadachi.md), 4.3.1).

Распределение работ внутри этапа обычное для релиза: **Релиз-менеджер** —
исполнитель подзадачи, ведёт её по плану и отвечает за порядок шагов; **CTO**
применяет изменения на продуктивном окружении (миграции, релиз-тег,
конфигурации, ручные шаги); **тимлид** выполняет шаги, требующие разработки или
ручной работы с данными; **КАМ** к этому моменту уже закрыл пункты, требовавшие
действий клиента (4.2, п. 2).

Время по подзадаче списывают все участники — в неё, а не в основную задачу
(см. 6).

Подзадача закрывается после успешной выкатки, до перевода подзадач «Разработка»
в «Демонстрация заказчику». Если часть плана выполнить не удалось — подзадача
остаётся открытой с комментарием о том, что не сделано и почему: закрытая
подзадача «Релиз» означает, что продуктив приведён в состояние, описанное планом.

## 5. Критерии завершения

- [ ] Изменения успешно выведены в продуктив
- [ ] Подзадачи «Разработка» в статусе «Демонстрация заказчику»
- [ ] Release notes подготовлены
- [ ] Заинтересованные стороны уведомлены о выпуске
- [ ] Подзадача «Релиз» закрыта (если создавалась)
- [ ] По связанным задачам «Документация» проставлена отметка о выкатке (4.6)
- [ ] Админка: состав собран из карточки релиза pbeconsole, проект «Вне спринта» в ней зарегистрирован и синхронизирован (4.2)

## 6. Учёт трудозатрат

| Кто | Где фиксирует | Обязательность |
|-----|--------------|---------------|
| Релиз-менеджер | Основная задача; при наличии подзадачи «Релиз» — в неё | По усмотрению |
| CTO | Основная задача; при наличии подзадачи «Релиз» — в неё | При нестандартной работе |
| Тимлид (шаги выкатки) | Подзадача «Релиз» | Обязательно |

**При наличии подзадачи «Релиз» время идёт в неё, а не в основную задачу.**
Иначе стоимость выкатки растворяется в общей сумме по задаче и сравнить её с
полем «Оценка: деплой» ([этап 5](05-ocenka-zadachi.md), 4.5) нельзя — а именно
на этом сравнении проверяется, чего стоят наши оценки деплоя.
