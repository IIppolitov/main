# Жизненный цикл задачи на доработку CRM-системы — Сводный регламент

## Введение

Документ описывает высокоуровневый процесс обработки задач от создания до закрытия. Для детальной информации по каждому этапу обращайтесь к соответствующему регламенту.

---

## Этап 1. Создание задачи
**Ответственный:** КАМ клиента

Задача инициируется клиентом через КАМа или внутренним заказчиком. КАМ создаёт задачу типа «Улучшение» с обязательными атрибутами (мнемоника клиента в названии и теге, описание бизнес-проблемы в блоке «Цель/Проблема»), назначает исполнителем Product Owner.

**Результат:** Задача в статусе «Открыта», исполнитель — PO.
**Учёт времени:** по усмотрению, в основную задачу.

---

## Этап 2. Валидация
**Ответственный:** Product Owner

PO проверяет качество постановки и соответствие задачи продукту. При положительном решении запускает скрипт, создающий подзадачу «Бизнес Анализ» и назначающий её команде БА. При необходимости уточнений или отмены — фиксирует причины в комментарии и уведомляет автора.

**Результат:** Подзадача «Бизнес Анализ» создана и назначена на БА (или задача возвращена / отменена).
**Учёт времени:** по усмотрению, в основную задачу.

---

## Этап 3. Бизнес-анализ
**Ответственный:** Команда БА

БА собирается 3 раза в неделю по 1 часу (50% нагрузки — небольшие задачи, 50% — крупные). Заполняет структуру постановки (Где / Задача / Детали / Критерии приёмки / Бизнес-постановка / Системная постановка). Создаёт подзадачи «Разработка» (для адм. и/или прилаги) и при необходимости «Дизайн». По завершении переводит подзадачу БА в статус «Согласование КАМ».

**Подзадачи не создаются:** Тестирование, Документация, Релиз.
**Результат:** Подзадача «Бизнес Анализ» в статусе «Согласование КАМ».
**Учёт времени:** обязательно, в подзадачу «Бизнес Анализ».

---

## Этап 4. Согласование проработки
**Ответственный:** КАМ

КАМ передаёт бизнес-постановку клиенту. При согласовании закрывает подзадачу БА и переводит подзадачи «Разработка» / «Дизайн» в статус «Оценка задачи», назначает тимлидов. При замечаниях — возвращает БА на доработку.

**Результат:** Подзадачи «Разработка» / «Дизайн» в статусе «Оценка задачи».
**Учёт времени:** по усмотрению, в основную задачу.

---

## Этап 5. Оценка задачи
**Ответственный:** Релиз-менеджер (координация), тимлиды (оценка)

На сессиях команды заполняют стандартное поле «Оценка» в подзадачах — это часы только на разработку без буфера. РМ берёт эти значения и собирает **таблицу оценки** в описании основной задачи (Разработка / Ревью / QA / Риски / Деплой / Дизайн / БА / Итого), добавляя буферные строки. На основании строки «Итого» заполняет кастомное поле **«Оценка»** основной задачи.

**Результат:** Таблица оценки заполнена, все подзадачи в статусе «Согласование КАМ».
**Учёт времени:** Релиз-менеджер, в основную задачу.

---

## Этап 6. Согласование оценки
**Ответственный:** КАМ

КАМ формирует итоговую цифру (поле «Оценка» + фактически затраченное время БА) и согласовывает с клиентом. При согласовании — подзадачи переводятся в «Готово к разработке». При отказе — возврат на доработку или отмена.

**Результат:** Подзадачи «Разработка» / «Дизайн» в статусе «Готово к разработке».
**Учёт времени:** по усмотрению, в основную задачу.

---

## Этап 7. Сбор задач в клиентские проекты
**Ответственный:** КАМ

КАМ формирует квартальный проект для каждого клиента. Задачи добавляются асинхронно на любом этапе. На начало квартала в проекте остаются только задачи, прошедшие этап 6. КАМ контролирует соответствие объёма договорным обязательствам.

**Результат:** Приоритизированный список задач клиента на квартал.
**Учёт времени:** не требуется.

---

## Этап 8. Набор спринтов
**Ответственный:** Релиз-менеджер

Формирует спринты на основе клиентских проектов. Адм.: 2-недельные спринты, Спринт N + Спринт N+1 → 2 недели фиксов → Релиз. Прилага: месячные спринты по принципу «1 клиент = 1 проект».

**Результат:** Задачи добавлены в Проекты спринтов.
**Учёт времени:** не требуется.

---

## Этап 9. Распределение задач
**Ответственный:** Тимлид

Перед началом спринта тимлид назначает исполнителей на задачи с учётом компетенций, загрузки и технических зависимостей.

**Результат:** Все подзадачи «Разработка» имеют назначенного разработчика.
**Учёт времени:** не требуется.

---

## Этап 10. Разработка
**Ответственный:** Разработчик

Разработчик реализует функционал. После завершения деплоит на стейджинг (адм.) или переводит задачи в «Можно тестировать» (прилага) и назначает QA-инженера. **Код-ревью проводится после тестирования QA, не до.**

**Результат:** Подзадача «Разработка» в статусе «Можно тестировать».
**Учёт времени:** обязательно, разработчик в подзадачу «Разработка».

---

## Этап 11. Внутреннее тестирование и ревью
**Ответственный:** QA-инженер (тестирование), тимлид (ревью)

Подзадачи «Тестирование» не создаются — QA работает напрямую с подзадачами «Разработка».

**Адм.:** Каждая задача тестируется индивидуально по мере готовности.
**Прилага:** Тестируется вся QA-сборка целиком + регресс.

Цепочка статусов: «Можно тестировать» → «Тестируется» → «Готово к ревью» → «Ревью» → «Тест внешний».

**Результат:** Все подзадачи «Разработка» в статусе «Тест внешний», код влит в основную ветку.
**Учёт времени:** обязательно, QA и тимлид — в основную задачу.

---

## Этап 12. Тестирование клиентом
**Ответственный:** КАМ

КАМ передаёт клиенту доступ к тестовому окружению. Адм.: клиент тестирует задачи индивидуально. Прилага: клиент тестирует весь релиз. При успехе — «Готово к релизу», при замечаниях — возврат на доработку.

**Результат:** Подзадачи в статусе «Готово к релизу».
**Учёт времени:** по усмотрению, в основную задачу.

---

## Этап 13. Релиз
**Ответственный:** Релиз-менеджер, CTO

**Адм.:** CTO применяет релиз-тег; задачи переводятся в «Демонстрация заказчику».
**Прилага:** CTO проводит пилот (минимум 1 неделя) → КАМ даёт отмашку → полный релиз → задачи переводятся в «Демонстрация заказчику».

**Результат:** Изменения в продуктиве, release notes готовы.
**Учёт времени:** по усмотрению, CTO — в основную задачу при нестандартной работе.

---

## Этап 14. Демонстрация заказчику
**Ответственный:** КАМ

КАМ демонстрирует выпущенный функционал клиенту. После подтверждения приёмки задача закрывается. Замечания после релиза оформляются как новые задачи («Ошибка» или «Улучшение»), а не как возврат исходной.

**Результат:** Основная задача и все подзадачи закрыты.
**Учёт времени:** по усмотрению, в основную задачу.

---

## Участники процесса

| Роль | Зоны ответственности |
|------|---------------------|
| КАМ | Создание задач, согласование постановки и оценки с клиентом, сбор клиентских проектов, организация внешнего тестирования и демонстрации |
| Product Owner | Валидация задач, создание подзадачи БА, участие в планировании спринтов |
| Команда БА | Бизнес-анализ, создание постановки и подзадач «Разработка» |
| Релиз-менеджер | Организация сессий оценки, заполнение таблицы оценки, набор спринтов, координация релизов |
| Команда разработки Адм. | Разработка задач по адм. (2-недельные спринты) |
| Команда разработки Прилаги | Разработка задач по прилаге (месячные спринты по клиентам) |
| Тимлиды | Оценка задач, распределение между разработчиками, код-ревью |
| Команда QA | Оценка рисков на сессиях, внутреннее тестирование |
| CTO | Деплой на продакшн, управление конфигурациями |
| Клиент | Согласование постановки и оценки, внешнее тестирование, приёмка |

---

## Схема статусов подзадачи «Разработка»

```
Открыта
  → Оценка задачи (задача передана на оценку)
  → Согласование КАМ (оценка выставлена)
  → Готово к разработке (оценка согласована с клиентом)
  → Можно тестировать (разработка завершена, код на стейджинге / QA-сборке)
  → Тестируется (QA начал тестирование)
  → Готово к ревью (QA завершил, задача передана тимлиду)
  → Ревью (тимлид проводит код-ревью)
  → Тест внешний (код влит, задача передана клиенту)
  → Готово к релизу (клиент подтвердил)
  → Закрыта / Демонстрация заказчику (после релиза)

На любом этапе возможно:
  → Требуется информация (нужны уточнения)
  → На доработку (выявлены замечания)
```

## Глоссарий

| Термин | Определение |
|--------|------------|
| Трекер | Яндекс Трекер — система управления задачами |
| Мнемоника клиента | Краткий код клиента (например, SRV), обязательный в названии и теге задачи |
| КАМ | Key Account Manager — менеджер по работе с клиентом |
| БА | Бизнес-аналитик / бизнес-анализ |
| QA | Quality Assurance — тестирование |
| FIFO | First In, First Out — задачи берутся в работу в порядке поступления |
| INVEST | Принципы декомпозиции: Independent, Negotiable, Valuable, Estimable, Small, Testable |
| Стейджинг | Тестовое окружение, максимально приближённое к продуктивному |
| QA-сборка | Тестовая версия приложения, включающая все задачи текущего релиза |
| Пилот | Ограниченное распространение новой версии приложения (мин. 1 неделя) |
| Таблица оценки | Разбивка плановых часов по фазам (Разработка / Ревью / QA / Риски / Деплой / Дизайн / БА), размещается в описании основной задачи |
| Оценка (поле основной задачи) | Кастомное поле: полные плановые трудозатраты (итого из таблицы) — для КАМа и клиента |
