# Этап 12 — Тестирование клиентом

> Первоисточник с тех пор мог измениться — сверяться перед переносом правок обратно.

## 1. Область применения

Регламент определяет порядок внешнего тестирования задач заказчиком. Обязателен для менеджеров клиента и сотрудников, ответственных за коммуникацию с клиентом.

## 2. Ответственные и участники

| Роль | Участник | Функции |
|------|----------|---------|
| Ответственный | Менеджер клиента | Организация тестирования, управление статусами по итогам |
| Участник | Клиент | Тестирование в тестовом окружении, фиксация результатов |
| Участник | Тестировщик | Разбор обратной связи клиента по релизу приложения, заведение багрепортов (4.3.1); разъяснения по сценариям тестирования |
| Консультант | Тимлид | Консультация по техническим вопросам |

## 3. Общие положения

На этом этапе клиент проверяет реализованный функционал в тестовом окружении перед выпуском в продуктив. Цель — получить подтверждение клиента о корректности реализации.

## 4. Порядок выполнения

### 4.1. Когда задача попадает на этап

- Все подзадачи «Разработка» в статусе «Тест внешний»
- Код влит в основную ветку

### 4.2. Передача задач клиенту

Менеджер клиента уведомляет клиента о готовых к тестированию задачах. В сообщении указывает:
- Перечень задач для проверки
- Доступ к тестовому окружению (при необходимости)
- Ссылки на документацию или инструкции (при наличии)

**Передача релиза приложения фиксируется в консоли.** Менеджер клиента переводит
стадию **«Тест у клиента»** карточки релиза в
[pbeconsole](../../systems/pbeconsole.md) в статус «В работе»: фактическая дата
начала стадии — день передачи сборки клиенту, плановая дата окончания — срок
проверки, **не менее трёх рабочих дней**.

Срок живёт полем в консоли, а не строкой в переписке: иначе нельзя ни
напомнить клиенту вовремя, ни посчитать, сколько релизов он держал дольше
согласованного.

> У админки такой стадии нет: клиент принимает задачи поштучно (4.3), объекта
> «переданный релиз» там не возникает.

### 4.3. Особенности по командам

#### Команда «Администрирование»

- Клиент тестирует каждую задачу **индивидуально** по мере её готовности на тестовом сервере.
- Результат передаётся менеджеру клиента по каждой задаче отдельно.

#### Команда «Приложение»

- Клиент тестирует **весь релиз целиком** после получения тестовой версии приложения.
- Результат передаётся менеджеру клиента по итогам проверки всего релиза — одним
  списком, одной задачей (4.3.1).

#### 4.3.1. Обратная связь клиента по релизу приложения

**Форма — одна задача на релиз.** Клиент передаёт замечания единым списком, без
дополнений отдельными сообщениями вдогонку. Менеджер клиента оформляет список
задачей **«Обратная связь клиента»** типа «Тестирование» в очереди `CRM`,
добавляет её в проект релиза и назначает исполнителем тестировщика.

Название: `[Мнемоника]. Обратная связь клиента. Релиз <NN>`.

Как «Подготовка релиза» и «Регресс приложения» ([этап 7](07-sbor-v-proekty.md),
4.5), это задача **на релиз целиком** — родительской задачи у неё нет. Время
разбора тестировщик списывает в неё.

> Дополнения вдогонку — главная причина, по которой обратная связь теряется:
> часть пунктов приходит, когда разбор уже закончен. Правило про единый список
> защищает срок клиента, а не наше удобство.

**Разбор — один рабочий день.** По каждому пункту списка тестировщик заводит
**отдельный багрепорт** по общему порядку
[этапа 11](11-testirovanie-i-revju.md) (4.5) — задачу типа «Ошибка» в очереди
[`BUGREPORTS`](https://tracker.yandex.ru/BUGREPORTS). Форма привязки оттуда же:

- замечание относится к конкретной доработке → багрепорт заводится **подзадачей
  той основной задачи**;
- замечание к конкретной задаче не относится → багрепорт заводится
  самостоятельной задачей.

**В обоих случаях багрепорт добавляется в проект релиза**, и в нём обязательна
ссылка на задачу «Обратная связь клиента»: по ней менеджер клиента собирает итог
для клиента.

> `BUGREPORTS` — не «другой трекер», а внутренний контур качества: задача ещё не
> на проде. Привязка к проекту релиза делает багрепорты видимыми там же, где
> остальной состав релиза, а подзадачей — держит закрытие основной задачи на
> [этапе 14](14-demonstracija-zakazchiku.md).

**Подзадачи «Разработка» при этом в «На доработку» не возвращаются** — это то
самое механическое исключение из [этапа 11](11-testirovanie-i-revju.md) (4.5.3):
тестовая сборка уже у клиента, выдернуть из неё отдельную подзадачу нельзя.
Работа идёт в багрепорте, у него собственный исполнитель, статус и учёт времени.

**Реакция разработки — на следующий рабочий день.** Разработчик просматривает все
заведённые багрепорты и по каждому либо исправляет за один рабочий день, либо
называет реалистичный срок исправления.

**Возврат к клиенту — за менеджером.** По каждому пункту обратной связи менеджер
клиента фиксирует в задаче «Обратная связь клиента» итог: исправлено или
согласован срок. Пункт с согласованным сроком релиз не держит — он переезжает в
следующий, но и потеряться не может: багрепорт остаётся открытым и виден в
проекте релиза.

### 4.4. Варианты решения

**Вариант А — Тестирование успешно**

1. Менеджер клиента переводит подзадачи «Разработка» в статус **«Готово к релизу»**.
2. Результат фиксируется в комментарии.

**Вариант Б — Выявлены замечания**

Порядок ниже относится к **админке**, где клиент принимает задачи поштучно. По
релизу приложения замечания собираются одним списком по 4.3.1; сам порядок
работы с дефектом от этого не отличается.

1. Менеджер клиента фиксирует замечания клиента в комментарии к основной задаче.
2. По каждому замечанию заводится багрепорт по
   [этапу 11](11-testirovanie-i-revju.md) (4.5) — подзадачей основной задачи,
   если замечание относится к конкретной доработке.
3. Соответствующие подзадачи «Разработка» возвращаются в **«На доработку»**,
   исполнителями назначаются разработчики. Собранной сборки у админки нет,
   поэтому исключение 4.5.3 здесь не работает.

Порядок повторного прохода:

1. Менеджер клиента переоткрывает подзадачу «Тестирование» затронутой команды — она закрыта на
   [этапе 11](11-testirovanie-i-revju.md). Статус «Готово к разработке»,
   исполнитель — тестировщик.
2. После устранения замечаний разработчик передаёт задачу так же, как на
   [этапе 10](10-razrabotka.md) (4.4): выбирает ветку и назначает исполнителем тестировщика или тимлида.
3. Задача проходит внутреннее тестирование заново и снова передаётся клиенту.

### 4.5. Работа с общими замечаниями

Замечание, не относящееся к конкретной доработке, оформляется багрепортом по
[этапу 11](11-testirovanie-i-revju.md) (4.5) — самостоятельной задачей типа
«Ошибка» в очереди [`BUGREPORTS`](https://tracker.yandex.ru/BUGREPORTS) с
привязкой к проекту релиза. Исполнитель — тимлид соответствующей команды.

> Задача ещё не на проде, поэтому дефект идёт во внутренний контур качества, а
> не в очереди поддержки — независимо от того, что нашёл его клиент. Заводить
> такие задачи в `BUGREPORTS` вправе не только тестировщик, но и менеджер клиента.

## 5. Критерии завершения

**Тестирование успешно:**
- [ ] Подзадачи «Разработка» в статусе «Готово к релизу»
- [ ] Результат тестирования зафиксирован в комментарии
- [ ] Приложение: стадия «Тест у клиента» в карточке релиза [pbeconsole](../../systems/pbeconsole.md) завершена (4.2)
- [ ] Приложение: по каждому пункту обратной связи есть итог — исправлено или согласован срок (4.3.1)

**Возврат на доработку:**
- [ ] Замечания зафиксированы в комментарии
- [ ] По каждому замечанию заведён багрепорт ([этап 11](11-testirovanie-i-revju.md), 4.5)
- [ ] Подзадачи «Разработка» возвращены в «На доработку» — админка; у приложения не возвращаются (там же, 4.5.3)
- [ ] Исполнители назначены

## 6. Учёт трудозатрат

По усмотрению менеджера клиента. При необходимости — в основную задачу.
