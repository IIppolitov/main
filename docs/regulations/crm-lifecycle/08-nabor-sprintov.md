## 1. Область применения

Регламент определяет порядок формирования разработческих спринтов. Обязателен для Релиз-менеджера, тимлидов и Product Owner.

## 2. Ответственные и участники

| Роль | Участник | Функции |
|------|----------|---------|
| Ответственный | Релиз-менеджер | Формирование спринтов, контроль готовности задач |
| Участник | Product Owner | Приоритизация, согласование состава спринта |
| Участник | Тимлиды | Оценка доступности команды, техническая валидация |
| Консультант | КАМы | Информация о клиентских приоритетах |

## 3. Общие положения

На этом этапе формируется план работ команд разработки на предстоящий период. В спринт попадают только задачи, прошедшие все этапы согласования. Команда принимает обязательство выполнить набранный объём.

## 4. Порядок выполнения

### 4.1. Критерии попадания задачи в спринт

Задача может быть включена в спринт только при выполнении всех условий:
- Подзадачи «Разработка» и «Тестирование» в статусе **«Готово к разработке»**
- В основной задаче заполнено поле **«Согласованная оценка»**

> Оба признака проверяются фильтром, вручную сверять этапы не нужно: статус
> «Готово к разработке» ставится только на [этапе 6](06-soglasovanie-ocenki.md)
> и только после согласования постановки на этапе 4. Дизайн к этому моменту
> утверждён и закрыт по определению — отдельного условия по нему нет.

### 4.2. Параметры спринтов по командам

#### Команда «Администрирование»

| Параметр | Значение |
|---------|---------|
| Длительность спринта | 2 недели |
| Принцип отбора задач | FIFO (если иное не согласовано) |
| Группировка задач | Без разделения по клиентам |
| Ритм релизов | Спринт N + Спринт N+1 → 2 недели на фиксы (во время Спринта N+2) → **Релиз** |

> Спринт N+2 не попадает в этот релиз. Он войдёт в следующий.

#### Команда «Приложение»

| Параметр | Значение |
|---------|---------|
| Длительность спринта | 1 месяц |
| Принцип формирования | По клиентам: 1 проект = 1 клиент |
| Управление объёмом | Команда самостоятельно определяет доступные часы с учётом загрузки и отпусков |
| Задачи техподдержки | Включаются приоритетно |

### 4.3. Процедура набора спринта

1. Релиз-менеджер проводит сессию планирования с тимлидами и PO.
2. Анализируется доступная ёмкость команды (загрузка, отпуска, технический долг).
3. Формируется список задач из клиентских проектов с проверкой критериев готовности.
4. Утверждается финальный состав спринта.
5. Подзадачи «Разработка» и «Тестирование» добавляются в Проект соответствующего спринта в Трекере.
6. Статус подзадач остаётся **«Готово к разработке»** до фактического начала работ.

> Подзадача «Тестирование» набирается в тот же спринт, что и разработка: её оценка —
> часть ёмкости спринта, а не работа «где-то потом».

### 4.4. Изменения в ходе спринта

- Добавление срочных задач — только по согласованию с Релиз-менеджером и тимлидом, с возможной заменой на задачу эквивалентной трудоёмкости.
- Невыполненные задачи возвращаются в бэклог с сохранением приоритетов.
- Изменения фиксируются в комментарии к задаче.

### 4.5. Актуальный график спринтов

Годовой график спринтов утверждается заранее. Релиз-менеджер отвечает за его актуализацию и своевременное информирование команд.

## 5. Критерии завершения

- [ ] Задачи добавлены в Проект соответствующего спринта
- [ ] Все задачи соответствуют критериям готовности
- [ ] Команда подтвердила обязательство по выполнению

## 6. Учёт трудозатрат

Не требуется.
