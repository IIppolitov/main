## 1. Что важно знать про этот проект

Четыре особенности, на которых агент ошибается чаще всего. Держи их в голове, когда
проверяешь его вывод.

**Это не CRM «визитов и врачей».** Основные сущности — `Person` (HCP), `Org` (HCO),
`Consent`, `Campaign`/`PromoCycle`, `Staff`/`User`, `Message`/`Template`, `DrugBrand`/`DrugSKU`,
`Survey`. Слова «визиты», «врачи», «аптеки» в постановках — бизнес-термины, а не таблицы.
Агент, не прочитавший это предупреждение, начнёт искать `visits`.

**MSSQL, database-first.** Именованные схемы, таблицы `schema.tPascalCase`, колонки PascalCase.
Laravel-конвенции здесь не действуют — не давай агенту предполагать имена, пусть смотрит
миграцию и модель. Для новых сущностей — паттерн «Fields».

**Модули — отдельные git-сабмодули.** Правка в `modules/<Module>/` меняет **чужой репозиторий**:
своя ветка, свой PR, потом ручной bump указателя. Агент обязан называть это в отчёте;
если не назвал — спроси прямо, ядро это или модуль.

**Поведение зависит от конфигов клиента.** Один и тот же код ведёт себя по-разному
у Валенты и Байера — из-за значений `pbe`-конфигов, которых локально не видно. Отсюда
`client-env.sh` в разборе (п. 3) и вопрос «это у всех так или только у него» в каждом баге.

## 2. Команда агентов

Восемь ролей в `.claude/agents/`. Вызываются по имени или подхватываются автоматически
по описанию.

| Агент | За что отвечает | Пишет код |
|---|---|---|
| `backend` | Laravel: API, контроллеры, сервисы, модели, Jobs, очереди, интеграции | да |
| `database` | MSSQL: **все миграции монопольно**, схема, структура моделей, паттерн «Fields» | да |
| `frontend` | Blade + AdminLTE 3, jQuery/select2/DataTables, Vue 3, Mix | да |
| `qa` | Контрактные и Feature-тесты, тест-кейсы, регрессия | тесты |
| `analyst` | Постановки, критерии приёмки, User Stories, глоссарий — до разработки | нет |
| `reviewer` | Code review — **обязательный гейт перед PR** | нет |
| `security` | Аудит уязвимостей (SQLi, IDOR, PII/PHI, SSRF) — гейт по триггерам | нет |
| `documentation` | Руководства, Release Notes, техописания; пишет только в `docs/` и `*.md` | нет |

Два правила, которые стоит запомнить сразу:

- **Миграции пишет только `database`.** Не проси `backend` «заодно накинуть миграцию» —
  разделение монопольное и намеренное.
- **Ревьюеры не правят код.** Нашли — доложили, чинит владелец зоны. Просьба «ты же видишь
  ошибку, поправь» ломает смысл гейта.

Суб-агент **не видит твой диалог**. Всё нужное — файлы, имя таблицы `schema.tName`, пункт ТЗ,
вывод предыдущего агента — передаётся в промпт явно. Каждый агент возвращает статус:
`DONE` / `PARTIAL` (что не сделано и почему) / `BLOCKED` (чего не хватает).

## 3. `/bug` — разбор бага

```
/bug SUPPORTDEV-1788                       # один баг
/bug SUPPORTDEV-1788 SUPPORTDEV-1790       # дубли одного симптома от разных клиентов
/bug SUPPORTDEV-1788 --links               # + тела связанных задач, один уровень
```

Что делает: выгружает задачу с комментариями и вложениями, **открывает скриншоты**
(в багрепортах половина информации именно там), определяет клиента по домену админки,
тегу или префиксу темы, снимает его конфиги через `client-env.sh` — и только потом идёт
в код искать причину.

**Несколько ключей — это один разбор, а не два.** Типовой случай: один автор дал шаги
воспроизведения, другой — скриншот с ошибкой и версию; вместе они дают воспроизведение,
которого нет ни в одной задаче по отдельности. Расхождения между задачами агент выносит
отдельным блоком и говорит, какую версию взял за рабочую.

**Команда только читает.** Код не правит, миграции не пишет, веток не заводит — даже если
фикс в одну строку.

### Что делать с результатом

Первым в ответе идёт **сверка понимания**: что прочитано, окружение клиента, как понята
проблема, в чём агент не уверен. Прочитай его до того, как читать разбор кода — именно здесь
ловятся «разбирает не тот экран» и «взял не того клиента».

Дальше — причина со ссылками на файлы и строки, охват (ядро или модуль, один клиент или все),
что чинить и нужна ли миграция. Отчёт технический, для разработчика.

По итогу починки в задачу идёт **нетехнический отчёт** — но его пишут после фикса, не на этом
шаге: без фикса нет блока «как решили».

### Конфиги клиента: `client-env.sh`

Отвечает на вопрос «как оно настроено у того клиента, про которого задача», не заходя в админку:

```bash
.claude/scripts/client-env.sh --resolve vltadmin.powbeecrm.com   # кто это: клиент, мнемоника, инстансы
.claude/scripts/client-env.sh vlt --config LOW_LIQUID            # конфиги админки по подстроке ключа
.claude/scripts/client-env.sh vlt --app --config menu            # конфиги приложения, если симптом там
.claude/scripts/client-env.sh --fleet LOW_LIQUID                 # тот же ключ у остальных клиентов
```

`--fleet` — самый полезный флаг: он отличает общий дефект от клиентской настройки.
Данные — снимки мониторинга (до 5 минут), помеченные ⚠️ устаревшие брать как ориентир,
а не как факт. Отказ скрипта разбор не останавливает: агент помечает «окружение не проверено»
и явно называет выводы, которые от этого зависят.

## 4. `/task` — разбор постановки

```
/task CRM-544                       # постановка
/task CRM-544 SUPPORTDEV-1788       # спека аналитика + задача на разработку = ОДНА постановка
/task CRM-544 --links
```

Главный шаг этой команды — **разделение контура**. Аналитик пишет постановку на всю систему,
а этот репозиторий — только админка и её API. Агент раскладывает требования по корзинам:
ядро (`app/`) — модуль `modules/<Module>` — конфиг и гейтинг — схема БД — **не наше**
(приложение `pbeapp`, IQVIA, МДЛП, Mindbox, SAP) — **стык** (контракты, от которых зависят
соседи).

Дальше он сверяет требования с кодом («реализовано / частично / нет»), определяет охват
(всем клиентам или одному, чем включается, каким должен быть дефолт, кого заденет регрессия)
и собирает **открытые вопросы к аналитику**.

Про вопросы стоит сказать отдельно: это не признак того, что агент не справился. Пять точных
вопросов, отвеченных аналитиком за десять минут, дешевле недели работы по догадке. Возвращать
сырую постановку — нормальная часть процесса, а не конфликт.

## 5. Как идёт задача

```
/task или /bug            → разбор, сверка понимания, открытые вопросы
   ↓ (реализация — отдельной командой, после того как разбор принят)
analyst                   → критерии приёмки и User Stories, если постановка сырая
database                  → только если меняется схема или нужна новая таблица
backend ∥ frontend        → реализация; контракт между ними фиксируется ДО параллельного запуска
qa                        → контрактные и точечные тесты
reviewer ∥ security       → гейты; security — по триггерам
   ↓
человек                   → коммит, PR, ревью человеком
```

**Контракт `backend` ∥ `frontend`.** Перед параллельным запуском фиксируются имена маршрутов
и HTTP-методы, форма payload'а (поля JSON — как их отдаёт JsonResource), права `@can`
и имя blade-шаблона. Владелец контракта — `backend`, фронт его не придумывает. Если контракта
ещё нет — сначала короткий шаг `backend` (маршруты + FormRequest + JsonResource, без логики),
потом параллель. Параллелить «вслепую, потом состыкуем» запрещено: стыковка дороже скелета.

Тривиальное не делегируй: правка одной строки, ответ на вопрос по коду — быстрее сделать
самому.

## 6. Гейты приёмки

Задача с кодом готова, только когда выполнено всё:

1. **Тесты зелёные** — минимум `vendor/bin/phpunit --testsuite Unit` плюс точечные тесты
   затронутого кода. Полный прогон (Feature) — только при доступной dev MSSQL: сьют ходит
   в неё. Не гонял полный — это фиксируется в сводке явно, а не умалчивается.
   ⚠️ `--filter` может зацепить Feature-тест модуля, который тоже пойдёт в dev MSSQL.
2. **Пройден `reviewer`.** Вердиктов, закрывающих задачу, два: «✅ ПРИНЯТО» и
   «⚠️ ПРИНЯТО С ПРАВКАМИ» — во втором случае задача готова только после внесения правок
   и построчной сверки внесённого с предложенным. Отклонилась правка от предложенного —
   идёт повторное ревью. «❌ ОТКЛОНЕНО» — цикл фикс → повторное ревью.
3. **Пройден `security`** по его триггерам: новые и изменённые маршруты (для `external.php`
   и `hook.php` — всегда), auth/SSO/JWT, raw SQL, загрузка файлов, интеграции, выдача PII/PHI.
   Гейт бинарный: PASS или FAIL. HIGH-находка по PII/PHI или auth равна блокеру.
   **Принять риск может только уполномоченный человек** — владелец продукта или ответственный
   за ИБ, названный поимённо. Ни агент, ни разработчик этого не могут; «ладно, выпускаем» —
   не принятие риска.
4. **Новые ключи настроек, статусы и константы покрыты контрактным тестом** (`qa`).
5. **Изменения перечислены пофайлово** с разделением «ядро / `modules/<Module>`» — чтобы
   развести по коммитам и не забыть про сабмодуль.
6. **Матрица приёмки**: каждый критерий приёмки из постановки → чем подтверждён (автотест,
   ручная проверка с результатом, «не проверен» с причиной). Зелёный phpunit сам по себе
   не означает, что постановка выполнена.

Коммиты в Definition of Done не входят — их делает разработчик руками.

## 7. Что запрещено технически

`.claude/settings.json` держит deny-лист, действующий и на основную сессию, и на всех
суб-агентов:

- изменяющие git-команды: `commit`, `add`, `push`, `pull`, `checkout`, `reset`, `restore`,
  `merge`, `rebase`, `stash`, `tag`, `clean`, операции с сабмодулями;
- `gh pr create`, `gh pr merge`, `gh release`;
- релизные скрипты (`make-pre-prod-release.sh`, `make-prod-hotfix.sh`, `checkout-prod.sh`, …);
- разрушительные artisan-команды: `migrate:fresh`, `migrate:refresh`, `migrate:reset`,
  `db:wipe`, `db:seed`, `queue:flush`, `tinker`;
- `rm -rf` и его формы, `composer update`, `npm install/update`.

С подтверждением (ask): `php artisan migrate`, полный `phpunit`, `composer install`, `npm ci`,
`npm run prod`, `git -C`/`--git-dir`/`--work-tree`.

Список работает по префиксу команды и обходится тривиально — поэтому обход считается
нарушением, а не смекалкой (см. п. 4.7 основ).

## 8. Типичные ошибки в этом проекте

| Симптом | Что происходит на самом деле |
|---|---|
| Агент ищет таблицы `visits`, `doctors` | Взял бизнес-термины за имена таблиц. Направь в реальную схему |
| Предполагает Laravel-конвенции имён | Здесь database-first и PascalCase. Пусть смотрит миграцию и модель |
| Правит `modules/<Module>/` и молчит | Это сабмодуль, отдельный репозиторий и отдельный PR. Спроси охват явно |
| «Работает у всех» — а у клиента нет | Не сверил ветку кода с реальным значением `pbe`-конфига. `--fleet` |
| Пусто вместо данных | Смотри фильтры и join-ы, soft-delete (`DeleteDate`), скоуп по правам пользователя |
| Раздел не виден пользователю | Чаще упирается в `@can` и права, а не в логику |
| Предлагает новый сервис с нуля | Не посмотрел `app/Services/` и сервисы модулей: движок кампаний живёт в `modules/Omni/App/Services/Campaign/` |

## 9. Примеры

```
/bug SUPPORTDEV-1788 SUPPORTDEV-1790
/task CRM-544 SUPPORTDEV-1801 --links
```
