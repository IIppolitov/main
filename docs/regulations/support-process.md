## Очереди Трекера и маршрутизация

Обращение приходит по почте и автоматически попадает в очередь **SUPPORT**.
Дальше маршрутизируется:

| Куда | Когда |
|---|---|
| `SUPPORTdev` | Нужно исправление в коде |
| `SUPPORTanalytic` | Импорт/экспорт данных, аналитика, BI |
| `SUPPORTdigital` | Блок «Рассылки» (OMNI) |
| `SUPPORTinfo` | Настройка, информационный запрос по функционалу |
| закрытие в SUPPORT | Информационный запрос — ответ и всё |

## Классификация обращений

Шесть категорий: критическая ошибка (блокер), серьёзная (критичный), средний
приоритет, незначительная, улучшение, информационный запрос. Категория
определяется описанием клиента, массовостью, результатами диагностики и
условиями договора.

**SLA у каждого клиента свой — по договору.** Таблица сроков в этапе 2 Вики
приведена как пример расчёта, а не как норматив; при выставлении критичности и
дедлайна поддержка опирается на договор с конкретным клиентом и
[реестр по клиентам](https://wiki.yandex.ru/homepage/klientskijj-servis/osobennosti-i-faq-po-klientam/).

## Ключевые обязательства по этапам

**Этап 1.** Первичный ответ в срок SLA с подтверждением получения и номером
заявки. Для ошибок 500 — приложить код ошибки (etag) и ссылку на Telescope,
указать среду. Фиксируются категория, результат диагностики, ссылка на созданную
задачу, время первичного ответа.

**Этап 2.** Название по шаблону `[Клиент]. [Компонент] [Описание]`, тег с
мнемоникой клиента, компонент (Приложение / Администрирование / OMNI /
Интеграции), приоритет и дедлайн по договору, **обязательная связь с исходным
обращением SUPPORT**. Описание содержит блоки: где, клиент, среда, под каким
пользователем, Telescope, воспроизводится ли, алгоритм воспроизведения, описание,
массовость, вложения. Напоминания за 2 дня и за 1 день до дедлайна.
Правило «одна ошибка = одна задача».

**Этап 3.** Только критические и серьёзные. Незначительные и улучшения в чат
**не репортируются**. В сообщении: клиент, срочность, суть, дедлайн, ссылка на
задачу, упоминание лида. Нет реакции 15–30 минут — продублировать или связаться
напрямую. Факт уведомления фиксируется комментарием в задаче.

**Этап 4.** Встречи 2 раза в неделю по часу. Организатор — руководитель
техподдержки, участники — тимлиды, консультант — релиз-менеджер, при эскалации —
КАМ клиента. Два основных исхода:

- **в спринт** — статус «Требуется релиз», исполнитель не назначается, в
  комментарии спринт и дата релиза;
- **хотфикс** — назначается исполнитель, в комментарии «Выпуск через хотфикс» с
  датой; для приложения это новая Prod-версия (избегать по возможности), для
  админки — применение напрямую на Prod.

Особые случаи: только конфигурация — статус «Можно тестировать» на поддержку;
не хватает данных — «Требуется информация» на аналитика или автора.
Клиента уведомляют в течение 2 рабочих часов.

## Что стоит помнить об организации процесса

Поддержка (5 чел., Валиева Ангелина) относится к департаменту по работе с
клиентами, разработка — к ИТ. Процесс межведомственный, поэтому и утверждён
тремя лицами. Изменения по существу требуют переутверждения тем же составом —
см. [../backlog.md](../backlog.md).

Процесс описан до принятия решения о способе исправления. Этапа «исправление →
проверка → закрытие обращения → уведомление клиента о выпуске» пока нет, цикл не
замкнут — это в долге.
