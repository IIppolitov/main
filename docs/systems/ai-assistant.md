## Как подключается раздел

Правило из среза, на нём держится вся очередь: **инструмент — тонкая обёртка
над тем же сервисом, который вызывает экран.** Если логика живёт в контроллере,
сначала она выносится в сервис, потом пишется инструмент. Для записи у сервиса
должен быть построитель с сухим прогоном (`DRY_RUN`): карточка в чате показывает
результат прогона, кнопка «Выполнить» повторяет его и пишет.

Отсюда главный вывод разбора кода: **цена раздела определяется не ассистентом,
а состоянием сервисного слоя.** Готов к записи пока только модуль Bots. В ядре
у врачей, организаций, визитов, справочников, пользователей логика в
контроллерах. Каждый раздел ниже начинается с выноса.

Что ещё общее для всех разделов:

- **Видимость — одна, та же, что на экране.** Ассистент не должен ни расширять
  её, ни повторять дыры экранов (см. «Предпосылка» ниже).
- **Агрегаты вместо строк.** Модели уходит сводка; строки — в файл через
  `export_table`. Результат больше 400 символов в следующих ходах заменяется
  заглушкой, так что крупные выдачи модели всё равно не помогут.
- **ПДн врачей и сотрудников — только по решению клиента.** У фармклиентов
  передача ФИО, контактов и согласий в модель требует их согласия и договорной
  основы. Признака «это ПДн» у полей в системе нет — маскирование проектируется
  явно в каждом наборе.
- **Ход синхронный**, внутри HTTP-запроса. Тяжёлые запросы (визиты, национальная
  база врачей) — только с ограниченным периодом и лимитом строк.

**Почему такой порядок.** Визиты и врачи — то, ради чего ассистент нужен
пользователю в полях и его менеджеру; боты были выбраны для среза только потому,
что у них готовы сервисы. Справочники (3) маленькие и нужны первым двум —
их можно вести параллельно. Расписание (4) имеет смысл только после визитов:
дайджест без визитов собирать не из чего. Задачи (5) — самый дешёвый способ
обкатать запись в ядре на модуле с готовыми сервисами.

**Пока не подключаем:** запись настроек инстанса и выдачу ролей (цена ошибки),
валидацию согласий (юридически значимое действие), остатки в аптеках (один
контроллер на 1300 строк с сырым SQL), планирование продаж и KAM (тяжёлые
расчёты, отдельная БД, много клиентских настроек). Чтение согласий и статистику
Омни — после п. 8, по запросу клиентов.

## 0. Предпосылка: видимость врачей и визитов

Разбор кода показал, что экраны врачей и визитов проверяют права по-разному:

- карточка врача и её вкладки открываются по Id с одним правом `person.view` —
  без групп (таргет, перс. база, территория) и без ограничения роли
  (`affectQuery`);
- вкладка визитов на карточке врача показывает визиты **всех** медпредов к этому
  врачу, хотя список визитов ограничен собой и подчинёнными
  (`Activity::visibleUserIds`);
- выгрузка врачей не применяет ограничение роли; список принимает «подчинённого»
  из запроса без проверки подчинения; «добавить к себе» без права; API `getPerson`
  отдаёт всю базу.

Часть из этого может быть намеренной (офлайн-база приложения), часть — нет. Для
ассистента это критично: если он вызывает те же сервисы, что экран, он
унаследует и дыры. Поэтому до наборов 1 и 2 — отдельная задача: выяснить, что
намеренно, и закрыть остальное; единое правило видимости врача и визита вынести
в сервис, на который встанут и экраны, и ассистент.

**Сделано в [CRM-2174](https://tracker.yandex.ru/CRM-2174)** (готово к релизу,
06.10.2026): `EntityVisibilityService` — одно правило видимости врача и
организации для карточки, вкладок, выгрузки, поиска и API; ключ отката
`ENTITY_VISIBILITY_CHECK`. Описание — `../pbeadmin/docs/visibility/README.md`.
Решение владельца продукта: **визиты на карточке видимого врача — все, без
отбора по автору**. Для ассистента отсюда два правила визитов: выборка по
сотрудникам — `Activity::visibleUserIds`, история визитов к врачу — как на
карточке. Попутные находки — BUGREPORTS-294…299.

## 1. Визиты

### Что есть

- Визиты в коде называются **активностями** (`Activity`, представление
  `vActivities` поверх `facts.tEvents` в базе приложения). Всё содержимое визита —
  один JSON на запись; колонок на поля нет. Типы: визит, двойной день, коучинг,
  дистанционный визит, мероприятие и др.; статусы: запланирован, начат, сохранён,
  ждёт одобрения руководителя, завершён, отменён.
- В админке — список, календарь, карта с GPS-нарушениями, план/факт по дням,
  карточка визита, откат статуса, одобрение GPS. Сервиса чтения нет: фильтры,
  видимость и расчёт плана — в `ActivityController` и шаблонах.
- Подчинённые — по `tStaff.BossStaffId`, обход дерева в PHP. Видимость визита —
  по `UserId` автора: `activity.view.own` — свои, `activity.view` — свои и
  подчинённых, `activity.view.all` / `activity.admin` — все.
- **Метрики визитов считает только приложение**, локально: покрытие таргета,
  TCFA, план/факт по циклу. В админке их определений нет, а её план/факт по дням
  считает иначе. Ещё часть метрик (двойные визиты, пустые дни, плохой GPS)
  приходит из внешнего ETL в личный кабинет.

### Главная проблема — смысл полей

Что заполняется на визите, решает приложение, и в основном **кодом под бренд**:
у Valenta, Besins, Mayoly, Alpen Pharma, Acino, Xantis, Prima и частично
Avexima свои формы, у остальных (Servier, Bayer, Roche, Boehringer и др.) общая
с настраиваемым списком полей. Поля пишутся в JSON ключами
вроде `goalsNextVisit`, `remembersMP`, `doctorOnDuty`. Админка знает смысл
только тех полей, что описаны в настройках (`*VisitCustomerFields`, списки
значений); для остальных у неё есть только ключ.

Варианты:

| | Как | Плюс | Минус |
|---|---|---|---|
| А | Словарь полей визита по брендам, собранный из кода приложения, — справка и указания набора | Быстро, без правок приложения | Расходится с кодом при каждой правке формы |
| Б | Приложение публикует описание своей формы в админку (как уже делают настраиваемые бренды) | Источник правды один, словарь не нужен | Правка приложения по всем брендам |
| В | Перенести настройку формы визита в админку для всех брендов | Решает и ассистента, и слабость раздела визитов в админке | Продуктовое решение и большой объём |

**Предложение:** начать с А и только для брендов, где включают ассистента;
словарь вести рядом с набором и сверять при релизе приложения. Б и В — отдельный
продуктовый вопрос о том, где живёт настройка визита; он шире ассистента и
поставлен в [бэклог](../backlog.md#ии-ассистент-в-админке).

### Какие вопросы задают

Права те же, что на экране визитов; «менеджер» — пользователь с подчинёнными по
оргструктуре, «руководство» — с `activity.view.all`.

**Медпред** — про свои визиты:

- сколько визитов сегодня / за неделю / за цикл, сколько осталось до плана;
- кого из таргета ещё не посетил в цикле, к кому не ходил дольше N недель;
- что было на прошлых визитах к врачу X: даты, продукты, показанные слайды,
  комментарии, договорённости на следующий визит (если бренд их пишет);
- какие визиты не закрыты, какие ждут одобрения руководителя, какие с
  нарушением GPS;
- какие презентации я показываю чаще всего, сколько времени на слайдах;
- выгрузи мои визиты за период в Excel.

**Менеджер** — то же по каждому подчинённому, плюс сводка по команде:

- кто отстаёт от плана цикла и насколько; покрытие таргета по каждому;
- визиты, ждущие моего одобрения; GPS-нарушения и визиты далеко от адреса;
- пустые дни, визиты задним числом, визиты без врача;
- мои двойные визиты: с кем, сколько, оценки и планы развития;
- частота визитов по категориям врачей и специальностям против нормы таргета;
- какие презентации команда реально показывает и по каким брендам;
- дайджест на утро: что вчера сделала команда, что сегодня в плане (п. 4).

**Администратор и руководство** — по линиям продвижения, регионам, всей базе:

- охват и частота по линиям, регионам, специальностям, категориям;
- доля дистанционных визитов, динамика по циклам;
- использование CLM по брендам и презентациям;
- качество данных: визиты без врача, без GPS, задним числом, с подменой врача;
- выгрузки для отчётов.

**Чего ассистент не сможет** без отдельной работы: отвечать про поля, смысл
которых знает только код приложения (см. выше); считать метрики, если не
договорились об их определении; отвечать про визиты сотрудника, которого нет в
оргструктуре, как про «подчинённого».

### Что сделать

1. Вынести чтение визитов в сервис: фильтры, период, видимость
   (`visibleUserIds`), выборка по подчинённым; экраны переводятся на него.
2. **Одно определение метрик** — покрытие, частота, план/факт, TCFA — то же,
   что в приложении, с учётом его настроек статистики. Согласовать с БА до кода.
3. Словарь полей визита по брендам (вариант А) — подзадача команде приложения.
4. Набор «Визиты», только чтение: команда пользователя, сводка по периоду,
   список визитов с фильтрами и выгрузкой, карточка визита с расшифровкой полей,
   план/факт и покрытие таргета, непосещённые врачи таргета, GPS-нарушения,
   CLM. Врач в выдаче — Id и маскированное ФИО до решения клиента о ПДн.
5. Производительность: данные в другой базе, фильтры по JSON без индексов —
   период обязателен, агрегаты в SQL; индексы — с DBA.

Запись (одобрить визит, вернуть, одобрить GPS) — следующим шагом, через сухой
прогон и карточку.

## 2. Врачи

### Что есть

- Врач — `Person` (`tPerson`), места работы, специальности, контакты,
  согласия, кастомные поля по клиенту.
- Группы видимости: таргет текущего цикла, перс. база (`tStaffPerson`),
  территория, национальная база — плюс ограничение роли в БД и около 45
  настроек инстанса. Единой точки нет: `PersonVisibilityService` есть, но
  используется только модулем согласий и не учитывает часть правил.
- Список, поиск, карточка, прямое создание/правка, перс. база, выгрузка — в
  контроллерах. Запрос на изменение: правка — в контроллере, отправка,
  маршрутизация и решение — в `ChangeRequest\PersonService` (внешняя проверка
  OneKey/ID360, ручная, автопринятие — [разбор БА](../../../pbeba/docs/kb/admin/change-request-routing.md)).
  Объединение дублей — заявка в контроллере, само слияние в `MergeService`.
- Транзакций нет ни в отправке, ни в решении запроса; сухого прогона нет нигде.
- Медпред в приложении уже создаёт запросы на изменение в веб-админке —
  приложение открывает её экран. Значит, «подготовить запрос голосом или текстом»
  — естественное действие ассистента.

### Что ассистент делает

**Чтение:**

- найти врача по ФИО, специальности, месту работы, городу — в пределах своей
  видимости;
- карточка: места работы, специальности, категория, в каком таргете и у кого в
  перс. базе, статус согласия — без значений контактов;
- мой таргет / моя перс. база: кто в ней, кто деактивирован, у кого нет
  основного места работы;
- мои запросы на изменение: где висит, почему отклонён, что ушло во внешнюю
  проверку; для администратора — очередь на ручной проверке;
- **проверка на дубли** перед созданием: похожие врачи по ФИО, месту работы,
  специальности. Скорингового поиска дублей в системе нет — это новая функция,
  а не обёртка.

**Запись** (через карточку подтверждения):

- подготовить запрос на создание или изменение врача — тот же поток, что на
  экране, с проверкой полноты и маршрутизацией; прямую правку карточки ассистенту
  не даём;
- добавить в перс. базу / убрать из неё — с теми же ограничениями территории;
- подать заявку на объединение дублей; само объединение — только
  администратору и только кнопкой.

**Ещё стоит подумать:** объяснение, почему запрос ушёл именно туда (по настройкам
маршрутизации), качество данных по своей базе, история изменений карточки.

### Что сделать

1. Сервис поиска и видимости врача — один для списка, карточки, выгрузки и
   ассистента (опирается на п. 0).
2. Построитель запроса на изменение с сухим прогоном и транзакцией.
3. Сервис перс. базы и заявки на объединение.
4. Набор «Врачи»: чтение, затем запись.
5. Согласовать с [внутренней валидацией DCR Servier](../projects/tasks/srv-dcr-internal-validation.md):
   она меняет ту же маршрутизацию запроса.

## 3–8. Остальные разделы

Коротко — подробнее в черновиках задач.

- **3. Справочники и продукты.** Специальности, должности, типы и категории
  организаций, бренды, SKU, показания, списки значений. Только чтение. Нужны
  визитам и врачам для подстановок, поэтому идут параллельно им.
- **4. Задания по расписанию.** Пользователь просит «каждое утро в 8:00 —
  итоги вчерашних визитов команды»; планировщик создаёт переписку от его имени
  и выполняет её с его правами и в его лимите. Плюс «отправить себе на почту».
  Механизм ядра, предусмотрен в [CRM-2154](https://tracker.yandex.ru/CRM-2154)
  как следующий срез.
- **5. Задачи (Task).** Мои задачи, просроченные, статистика по исполнителям;
  запись — создать задачу, сменить статус. Сервисы есть, нужен сухой прогон.
- **6. Пользователи, роли, права.** Только чтение: что может пользователь, у
  кого право, в какие роли входит, кто его руководитель, история изменений.
  Скрытые и маскированные пользователи остаются скрытыми.
- **7. Массовые загрузки.** История, статус, ошибки по строкам, объяснение
  ошибки. Повторный запуск — не сейчас.
- **8. Организации и аптеки.** По образцу врачей: поиск, карточка, запросы на
  изменение, дубли. Видимость своя (`org.view.subordinates / all / national`).

## Попутные находки

- **`CLAUDE.md` админки неверно описывает визиты:** «это не CRM визитов…
  visits — бизнес-термины, а не таблицы». Визиты есть — `Activity` /
  `vActivities`. Агент, читающий этот файл, будет искать не там. Правка — в
  задаче по визитам (репозиторий только на чтение).
- Карточка визита ищет название типа визита по коду без привязки к списку
  значений — может показать имя из чужого справочника.
- Массовая загрузка врачей пишет в `tPerson` в обход запросов на изменение,
  проверки дублей и зеркала ПДн.
- Бэкенд синхронизации, который пишет визиты из приложения, не лежит ни в одном
  из наших репозиториев — что он делает с данными при приёме, не проверено.
