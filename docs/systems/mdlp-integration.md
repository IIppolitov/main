## Как работает логин

Вход в МДЛП двухшаговый: сначала берётся одноразовый `code`, затем он меняется
на сессионный токен. Различаются шаги только способом подтвердить, что код
предъявляет тот, кто его запрашивал.

**Шаг 1, общий для всех.** `POST <base>/auth` с телом из `mdlp.vClients`:

```json
{"client_id": "…", "client_secret": "…", "user_id": "…", "auth_type": "PASSWORD"}
```

Ответ — `{"code": "…"}`. Код одноразовый, живёт недолго (срок в документации
МДЛП не указан, наш замер — больше 3 минут, меньше 73).

**Шаг 2, нерезидент.** `POST <base>/token` с телом `{"code": …, "password": …}`,
где пароль лежит в `vClients.Pwd_or_cert`. Ответ — `{"token": …, "life_time": 600}`.
Строка пишется в `mdlp.tAuthParams`. Всё это делает `mdlp.spAuthentication`
одним вызовом, без пауз.

**Дальше** каждый запрос к API несёт заголовок `Authorization: token <токен>`.
Собирает его `mdlp.spGetAuthToken`: для нерезидента он сверяет возраст последнего
токена с `life_time` и временем последнего успешного вызова из `http.tLogs` и при
необходимости берёт новый.

Сессия умирает по двум причинам: истёк `life_time` (600 секунд) либо 30 минут
без обращений — простой МДЛП считает отдельно.

> **Ловушка.** Обе процедуры пишут строку в `tAuthParams` **безусловно**: ответ
> разбирается через `OPENJSON`, и при ошибке в строку ложатся `NULL`. Поэтому
> наличие свежей строки не означает наличие токена — см. «Отказ 1».

## Как работает резидентский логин

У резидента `auth_type` = `SIGNED_CODE`, и пароля нет вовсе. Вместо него код
подтверждается **усиленной квалифицированной электронной подписью**.

Шаг 1 тот же — `POST /auth` даёт `code`. Шаг 2 другой:

```json
{"code": "…", "signature": "<открепленная подпись PKCS#7 в BASE64>"}
```

Подпись ставится по ГОСТ Р 34.10-2012 сертификатом, зарегистрированным в МДЛП.
Требования к ней — документация API, раздел 4.6: стандарт PKCS#7, тип
**открепленная**, кодировка BASE64.

Связь сертификата с учётной записью прямая: **`user_id` в `vClients` — это
отпечаток сертификата**. Для Ксантиса `de99e92a48fbdb78c38c54d19e5ab6221329fb58`,
им же подписывается код. Сменился сертификат — надо менять `user_id` и
перерегистрировать его в МДЛП.

**Где стоит сертификат, там и подписывают.** До 27.08.2025 он был на PBESQL07, и
подпись ставилась локально за десять секунд:

```
csptest -sfsign -sign -in in.txt -out out.txt -my <отпечаток> -detached -base64 -add
```

### Обмен через SFTP — это решение по Ксантису, а не общее правило

Всё, что ниже, относится **только к Ксантису**. Это не «как устроен резидентский
логин в МДЛП», а «как мы вышли из положения, когда сертификат оказался вне нашего
контура». У другого резидента с сертификатом на нашем сервере вся эта обвязка
не нужна вовсе — работает прежняя схема с локальной подписью.

Оговорка при этом почти теоретическая: **Ксантис — единственная резидентская
учётная запись из всех**. Остальные клиенты на сервере (`ClientId` 5, 6, 7, 9,
1009) нерезиденты и входят по паролю. Так что сегодня «резидентский логин» и
«схема Ксантиса» на практике совпадают — важно лишь не спутать их, когда
появится второй резидент.

Схема такая:

| | |
|---|---|
| Сервер обмена | `217.9.144.156`, SFTP, учётная запись `Powbee` |
| Кладём | `/sign/in.txt` — код аутентификации, ровно 36 байт без BOM и перевода строки |
| Забираем | `/sign/out.txt` — открепленная подпись, около 4 КБ в BASE64 |
| Подписывает | планировщик на стороне Ксантиса, запускает `C:\MDLP\powbee-mdlp.bat` |
| Задержка | от минут до суток — такт их планировщика нам не подчиняется |

Из-за задержки между шагами 1 и 2 нельзя просто подождать в шаге задания:
пауза в десять минут допустима, в час — нет. Поэтому там стоит очередь
`mdlp.tSignRequests`, переживающая разрыв; механика и порядок установки —
[pbe-dba/servers/pbesql07/mdlp-sign/](../../../pbe-dba/servers/pbesql07/mdlp-sign/README.md).

Зависимость получается неприятная и её стоит держать в голове: **работоспособность
нашей выгрузки определяется расписанием на чужой машине**. Ни SLA, ни контроля у
нас над ним нет. Обсуждается вариант получше — учётная запись SSH с правом
запускать подпись по требованию; тогда круг становится синхронным и чужое
расписание перестаёт что-либо значить.

### Как это работает сейчас

Собрано 14.09.2026. Механика — в
[pbe-dba/servers/pbesql07/mdlp-sign/](../../../pbe-dba/servers/pbesql07/mdlp-sign/README.md),
здесь управленческий срез.

**Круг подписи автоматизирован.** Между `/auth` и `/token` стоит очередь
`mdlp.tSignRequests` с состояниями `NEW → SENT → SIGNED → DONE`, а ходит в SFTP
скрипт на WinSCP. Ключевая защита — запоминание метки `out.txt` при отправке: в
этот момент там лежит подпись **предыдущего** кода, и прочитать её значит
получить отказ и списать его на «подпись неверна». Ровно на этом отказ и
держался.

**Всё прячется за `mdlp.spResidentEnsureToken`.** Живой токен есть — возвращается
сразу. Нет — процедура проходит круг целиком и ждёт подпись, но **с жёстким
таймаутом**: ожидание без срока однажды уже выключило бэкапы на двух серверах,
провисев 1308 и 1890 часов.

**`spAuthentication` для резидента больше ничего не печатает человеку** — она
отдаёт работу этой процедуре. Причём в режиме «только проверить»: её зовут
существующие задания, где сразу за резидентом идёт нерезидент, и ожидание там
заблокировало бы рабочую выгрузку.

**Резидентская выгрузка вынесена в отдельное задание** `MDLP Xantis Resident`,
ежедневно 04:00: движение каждый день, выбытие по понедельникам, остатки по
средам — то же расписание, что у нерезидентских. Один токен обслуживает создание
всех задач, второй — сбор результатов: два круга подписи за ночь независимо от
числа отчётов.

Существующие задания не тронуты. Строки с `ClientId = 8` в них стали холостыми,
но безвредными — убрать можно отдельной уборкой.

### Чего не хватает до полной автономности

| Что | Состояние |
|---|---|
| Задание `MDLP Xantis Resident` | включено 15.09.2026, ежедневно 04:00 |
| Такт подписи | 30 минут, измерен по меткам 15.09 — не со слов клиента. Круг укладывается в ночь |
| Оповещения при отказе | есть, оператор «ИТ — МДЛП» на обоих резидентских заданиях. Проверены боем 16.09 |
| Запрос кода внутри шагов выгрузки | не встроен: `ClientId = 8` остаётся холостым в нерезидентских заданиях |
| Пересчёт витрин по резидентским данным | не включён намеренно: после возврата второго потока цифры вырастут, и это надо объявить |

Таймаут ожидания подписи — 90 минут, то есть три окна подписи при получасовом
такте. Отказ по таймауту осознанно громкий: лучше письмо наутро, чем тихое
отсутствие данных, которое в прошлый раз прожило девять с половиной месяцев.

**Первая ночь рабочего режима прошла отказом** — и по причине, не имеющей
отношения ни к МДЛП, ни к Ксантису. В рабочем режиме очередь двигает сама
`spResidentEnsureToken` через `xp_cmdshell`, а он при вызывающем-sysadmin
выполняется от учётной записи службы движка, не агента. Права на конфигурацию
транспорта были выданы только агенту — транспорт падал на её чтении, молча
(вызов стоял с `NO_OUTPUT`), и задание полтора часа ждало подпись, которую
некому было ставить. Разбор и правки —
[pbe-dba/servers/pbesql07/mdlp-sign/](../../../pbe-dba/servers/pbesql07/mdlp-sign/README.md),
раздел «Первая ночь рабочего режима».

Мораль третьего такого случая подряд: **проверять надо тем способом, каким
оно будет работать**. Накануне круг гоняли шагом `CmdExec` от агента — там всё
работало.

Второй половиной обмена занимается `mdlp.spAuthenticationResidentHalf`: принимает
код и подпись, зовёт `/token`, кладёт токен.

И третье отличие: резидентский контур ходит **по другому хосту и только по
ГОСТ-TLS** — `api.mdlp.crpt.ru` против `nrz.api.mdlp.crpt.ru` у нерезидента.

## Как работают выгрузки и как данные попадают к нам

МДЛП не отдаёт отчёты синхронно. Схема заявочная: мы просим отчёт, он готовится
на их стороне, мы опрашиваем готовность и потом забираем файл.

```
задание SQL Agent, шаг «API»
│
├─ spAuthentication <клиент>                    токен
├─ spApiRequestGeneralTaskCreate                POST /data/export/tasks
│     тип отчёта + период → строка в tGeneralTasks с ApiId, статус PREPARATION
├─ waitfor delay '00:10:00'                     даём МДЛП время на подготовку
└─ spApiRequestGeneralTasksUpdateStatuses       курсор по незакрытым задачам
      └─ spApiRequestGeneralTaskUpdateStatus    GET /data/export/tasks/<ApiId>
            статус пишется в tGeneralTasks; между задачами пауза 1 минута
            └─ COMPLETED → spApiRequestGeneralTaskResultId
                  GET /data/export/results?task_ids=<ApiId> → ResultApiId
                  └─ spApiRequestGeneralTaskDownload
                        xp_cmdshell → download.ps1 кладёт файл в D:\MDLP\script\
                        └─ spGeneralTaskFilesIntoTables
                              файл → mdlp.tDisposal / tMovement / tStock / tPrices
                              └─ spGeneralTaskBulk*  пересчёт витрин
```

Период задаётся числом «год × 12 + месяц»: сентябрь 2026 — это `24321`. Задания
просят текущий и предыдущий месяц сразу, чтобы подхватывать поздние
корректировки.

Типы отчётов (`mdlp.tGeneralTaskType`):

| Id | Код МДЛП | Что |
|---|---|---|
| 1 | `GENERAL_PRICING_REPORT` | Цены |
| 2 | `GENERAL_REPORT_ON_DISPOSAL` | Выбытие ЛП |
| 3 | `GENERAL_REPORT_ON_MOVEMENT` | Движение ЛП |
| 4 | `GENERAL_REPORT_ON_REMAINING_ITEMS` | Остатки ЛП |
| 5 | `REMAINING_ITEMS_SHELF_LIFE_REPORT` | Остатки по срокам годности |

**Файл забирается не средствами SQL.** `spApiRequestGeneralTaskDownload` вызывает
`xp_cmdshell` и передаёт PowerShell-скрипту `download.ps1` токен, идентификатор
результата и URL. Причина в размере: выгрузки идут десятками мегабайт, а
`MSXML2.XMLHTTP` в `http.spMakeWebRequest` возвращает тело как строку. Отсюда же
зависимость: **`xp_cmdshell` на сервере должен быть включён**, иначе выгрузки
встают.

**Ошибки API разбирает `mdlp.spApiErrorHandler`** и отвечает вызывающему одним из
четырёх решений:

| Ответ | Когда | Что делает вызывающий |
|---|---|---|
| `0` | 200/201/204 с непустым телом | идёт дальше |
| `1` | 200, но `{"total":0,"entries":[]}` | выходит, результата нет |
| `2` | 429 или 503 | ждёт и **повторяет вызов рекурсивно** |
| `-1` | всё прочее | выходит молча |

При `429` пауза берётся из самого ответа МДЛП: обработчик вырезает из текста
ошибки число миллисекунд и ждёт ровно его.

**Куда данные попадают дальше.** Сырые таблицы схемы `mdlp` — это то, что пришло
из МДЛП. Схема `out` — посчитанные витрины (`out.tDisposal`, `out.tMovement`,
`out.tStock`, `out.tMovementChains`, `out.tCrossCheck`), их собирает шаг «BI»
задания, вызывая процедуры в базе `BI_<клиент>`. Оттуда данные и берут дэшборды
Superset.

Наблюдение на будущее: `-1` в обработчике означает «что-то не так, разбирайтесь
сами» — вызывающий просто выходит. Ни записи, ни письма при этом не возникает,
и именно так отказы этой интеграции дожили до аудита.

## Две учётки Ксантиса — один клиент, два потока данных

`ClientId = 7` и `ClientId = 8` принадлежат **одному клиенту**: это две учётные
записи в МДЛП, нерезидентская и резидентская. Так и задумано.

Оба потока грузятся в одни и те же сырые таблицы и помечаются `ClientId`
(`spGeneralTaskBulk*` проставляет его из задачи, но не фильтрует). Витрины
`out.*` и процедуры `report.sp*BI` в `BI_<клиент>` по `ClientId` **не
фильтруют** — они видят объединение. Это штатно.

| Поток | Строк в `mdlp.tStock` | Период |
|---|---|---|
| `ClientId = 7`, не резидент | 59 010 442 | 13.08.2023 – 09.09.2026 |
| `ClientId = 8`, резидент | 71 306 311 | 14.08.2023 – 27.08.2025 |

**Последствие для отчётности, о котором надо помнить.** С 28.08.2025 по
14.09.2026 витрины собирались только по нерезидентской учётке — резидентская
лежала. Когда она вернётся в строй, в текущих периодах данных станет заметно
больше, чем в предыдущих: это возврат второго потока, а не рост показателей.
В ряду будет разрыв, и объяснять его придётся.

### Как устроен шаг выгрузки

У всех клиентских заданий одна форма: шаг 1 «API» в базе `MDLP_<клиент>`, шаг 2

```

spApiRequestGeneralTaskCreate 8, <тип>, <период>     ×2 (текущий и прошлый месяц)
spAuthentication 7              -- не резидент
spApiRequestGeneralTaskCreate 7, <тип>, <период>     ×2
waitfor delay '00:10:00'
spAuthentication 8  → spApiRequestGeneralTasksUpdateStatuses 8
spAuthentication 7  → spApiRequestGeneralTasksUpdateStatuses 7
```

Отсюда и брались две аутентификации за прогон: одна в начале, вторая после
десятиминутной паузы. **`waitfor delay '00:10:00'` — то место, которое не
переживёт асинхронную подпись**: ждать в шаге задания можно десять минут, но не
час и тем более не сутки. Резидентскую часть придётся вынести из этих шагов в
отдельный конвейер с очередью, а `ClientId = 8` из них убрать.

### Как устроена резидентская подпись

Резидентский `/token` принимает `code`, подписанный УКЭП (открепленная подпись
PKCS#7 в BASE64). **Сертификата у нас нет** — он стоит на машине у клиента.
Обмен идёт через SFTP:

| | |
|---|---|
| Сервер | `217.9.144.156:22`, учётная запись `Powbee` (пароль — в парольном менеджере) |
| Кладём | `/sign/in.txt` — код аутентификации |
| Забираем | `/sign/out.txt` — подпись, ~4 КБ |
| Подписывает | планировщик на стороне Ксантиса, **раз в час** |
| Клиент SFTP на PBESQL07 | WinSCP, версия устарела — см. ниже |

До августа 2025 подпись ставилась **локально на сервере** за 10 секунд: в
`spAuthentication` остался закомментированный вызов `xp_cmdshell` →
`D:\MDLP\sign\writeIn.ps1` → задание `MDLP Xantis Sign` → `getFileContent.ps1`.
Переход на подпись у клиента совпал по времени с началом отказа 1.

**Почасовая подпись — узкое место всей схемы.** Когда резидентская выгрузка
работала, токен требовался 2 раза за ночь (02:00 и 02:11), а по неделям 4 раза
(ещё около 02:40). Токен живёт `life_time` = 600 с, простой — 30 минут. При
подписи раз в час за один час доступен один токен на десять минут, а прогон
исторически занимал с 02:00 до 03:12.

**Срок жизни кода измерен 14.09.2026 и зажат между двумя опытами:**

| Ожидание между `/auth` и `/token` | Результат |
|---|---|
| 3 мин 18 с | `200`, токен получен |
| 73 мин | `400`, `api.authentication.error` |

В документации МДЛП срок жизни `code` не указан — проверено по всему тексту
версии 81.0, там оговорены только `life_time` токена (600 с) и 30 минут простоя.
Практический вывод: **подпись раз в час не годится**, код успевает протухнуть.
14.09.2026 Ксантису отправлена просьба перевести планировщик на 15–30 минут.

### Отказ 1 — подпись, 28.08.2025 – 14.09.2026 (закрыт)

Последний успешный `POST /token` на резидентском хосте — **27.08.2025 02:40:30**.
С 28.08.2025 и по сей день на каждый вызов приходит

```
400 {"error_code":"api.authentication.error",
     "error_description":"Ошибка при выполнении операции: Проверьте аутентификационные данные"}
```

Это отказ на шаге подписи: `/auth` отдавал `code` штатно (200), а `/token`
с подписанным кодом МДЛП не принимал. Последняя задача выгрузки для
`ClientId = 8` создана **27.08.2025**; данных резидентского контура нет
больше года.

**Осторожно с `mdlp.tAuthParams` как признаком успеха.** Процедуры пишут туда
строку **безусловно**: ответ разбирается через `OPENJSON`, и когда МДЛП вернул
ошибку, в строку ложатся `NULL` вместо токена. По состоянию на 14.09.2026 у
клиента 8 из 2032 строк пустышек 746, у клиента 7 из 4598 — 2416. Поэтому
«последняя строка в `tAuthParams`» не означает «последний полученный токен»:
последний настоящий резидентский токен получен 27.08.2025 02:40:30, а строки
до 25.11.2025 — следы неудачных попыток.

Хуже другое: `mdlp.spGetAuthToken` для резидента берёт `TOP 1 … ORDER BY id DESC`
без проверки на пустоту и срок — то есть после любой неудачи отдаёт пустой токен
дальше по цепочке. Отдельный дефект, чинить вместе с резидентской веткой.

**Причина: при переносе подписи к клиенту потеряли флаг `-detached`.**

До 27.08.2025 подпись ставилась локально командой
`csptest -sfsign -sign … -my <отпечаток> -detached -base64 -add`. На машине
Ксантиса тот же вызов воспроизвели **без `-detached`**, и подпись стала
присоединённой. МДЛП принимает только открепленную — документация API,
версия 81.0, раздел 4.6: стандарт PKCS#7, тип подписи открепленная. Отсюда и
`api.authentication.error` на каждом обмене.

Флаг добавлен 14.09.2026, в тот же день получен первый настоящий резидентский
токен с августа 2025:

```
16:16:58  /auth   200  код выдан
16:17:10          код положен в /sign/in.txt (36 байт)
16:19:34          подпись готова, 4124 символа, открепленная
16:20:16  /token  200  токен, life_time 600
```

Версия про истёкший сертификат УКЭП, с которой начинали, **не подтвердилась**:
сертификат был действителен всё это время, сменилось только место подписи.

### Отказ 2 — обрыв ГОСТ-канала, 26.11.2025 – 14.09.2026 (закрыт)

Последний успешный ответ от `api.mdlp.crpt.ru` — **25.11.2025 02:16:36**,
первый отказ — **26.11.2025 02:00:01**. С этого момента любой вызов
резидентского хоста падает до отправки данных:

```
0x800C0008  msxml3.dll  The download of the specified resource has failed
```

в `http.tLogs` статус пишется как `12019` (WinInet, `ERROR_INTERNET_INCORRECT_HANDLE_STATE`)
или `0`, тело ответа в `http.tErrors` пустое — ответа не было вовсе.

Причина установлена проверкой обоих хостов снаружи:

| | `api.mdlp.crpt.ru` (резидент) | `nrz.api.mdlp.crpt.ru` (не резидент) |
|---|---|---|
| IP | 194.0.209.20 | 194.0.209.20 — **тот же** |
| Протокол | только TLS 1.2 | TLS 1.3 |
| Шифрсюита | `GOST2012256-GOST89-GOST89` | `AEAD-AES128-GCM-SHA256` |
| Сертификат | `CN=api.mdlp.crpt.ru`, ключ и подпись ГОСТ Р 34.10-2012 | `CN=*.api.mdlp.crpt.ru`, RSA |
| Издатель | **Минцифры России НУЦ подчинённый** | GlobalSign GCC R3 DV TLS CA 2020 |

Резидентский хост говорит только по **ГОСТ-TLS**: клиент, который явно
исключает ГОСТ-шифры, получает `unknown cipher returned` — альтернативы нет.
Это не новость ноября 2025, а штатное требование МДЛП к резидентам, см.
«Почему раньше работало» ниже.

Отсюда следствия:

- это **не проблема учётной записи**: до передачи `client_id` дело не доходит,
  рукопожатие обрывается. Ошибка одинакова на `/auth`, `/token` и `/data/export/*`;
- **не проблема сети**: оба хоста на одном IP и порту, нерезидентский работает;
- на сервере рукопожатие доходит до конца и падает на проверке цепочки
  сертификатов — `CERT_E_UNTRUSTEDROOT`, см. разбор ниже;
- сломано у всех баз сервера одновременно: `MDLP_Alpen` теряет резидентский хост
  25.11.2025 05:23, `MDLP_Boehringer` — 25.11.2025 00:30. На работе этих клиентов
  это не сказалось: они целиком на нерезидентском контуре.

### Причина: недоверенный корень новой цепочки Минцифры

Установлено проверкой на самом сервере 14.09.2026.

Резидентский контур требует ГОСТ-TLS **не с ноября 2025, а всегда**. Цитата из
«Описание API ГИС МДЛП. Протокол обмена интерфейсного уровня», версия 81.0,
раздел 4.5:

> Если Участник, к которому относится пользователь — Резидент, то после процедур
> аутентификации и авторизации все методы API должны вызываться с использованием
> HTTPS протокола. Для взаимодействия по HTTPS используется ГОСТ Р 34.10-2012
> сертификат.

На PBESQL07 стоит **CryptoPro CSP 5.0.12000** (с 01.03.2024) — поэтому ГОСТ-канал
и работал с 2023 года. Сломался он не в криптографии:

| Проверка на сервере | Результат |
|---|---|
| Вызов `MSXML2.XMLHTTP` из PowerShell, нерезидентский хост | `HTTP 400` — канал есть |
| То же, резидентский хост | `The download of the specified resource has failed` |
| Обновления Windows в ноябре 2025 | **не ставились ни одного** |
| `DisableClientExtendedMasterSecret` | не задан |
| `csptest -tlsc -server api.mdlp.crpt.ru -port 443` | **`0x800B0109 CERT_E_UNTRUSTEDROOT`** |

Последняя строка и есть ответ. `csptest` проходит ГОСТ-рукопожатие целиком —
шифры согласованы, сертификат сервера получен и разобран — и падает на самом
последнем действии, проверке цепочки: «chain processed, but terminated in a root
certificate which is not trusted».

Сертификат `api.mdlp.crpt.ru` выпущен `Минцифры России НУЦ подчиненный`, а тот —
корнем `Минцифры России НУЦ корневой` **от 28.05.2025**. В хранилище сервера
лежат корни Минцифры прежней ветки, от 2022 года. ЦРПТ в конце ноября 2025
перевыпустил сертификат на новую цепочку — с этого дня она недоверенная, и
WinInet отдаёт наружу невнятное `0x800C0008`.

Версии, которые проверка **не** подтвердила и которые держать в голове не надо:
дело не в учётной записи, не в сети, не в лицензии КриптоПро и не в Extended
Master Secret — обновлений Windows в тот период вообще не было.

### Цепочка сертификатов резидентского хоста

Понадобится в вариантах 1 и 2: ГОСТ-прокси или внешний клиент должны доверять
издателю. Адреса взяты из расширения Authority Information Access самого
сертификата, а не из поиска — это первоисточник.

| Звено | Субъект | Откуда |
|---|---|---|
| Лист | `CN=api.mdlp.crpt.ru`, `O=ООО ОПЕРАТОР-ЦРПТ` | отдаёт сам сервер |
| Промежуточный | `CN=Минцифры России НУЦ подчиненный`, до 27.05.2030 | `http://nuc-cdp.digital.gov.ru/cdp/subca_gost2025_86cff9e065eb131a38478da511e2172b7ac025f1.cer` |
| Корневой | `CN=Минцифры России НУЦ корневой`, до 24.05.2040, самоподписанный | `http://nuc-cdp.digital.gov.ru/cdp/rootca_gost2025_d8485616c8db8142950c7c928bea37e711a5bdea.cer` |

Зеркало обоих файлов — тот же путь на `nuc-cdp.voskhod.ru`; содержимое совпадает
байт в байт. Отпечаток корневого, с которым надо сверяться после скачивания:

```
SHA-256  5B:51:DB:72:1B:7C:34:95:8E:D7:43:2A:E9:17:A9:12:97:DD:37:50:8B:2C:AE:4F:85:8F:FB:AC:6B:C5:25:EF
```

Это **ГОСТ-ветка** НУЦ Минцифры (ключи и подписи ГОСТ Р 34.10-2012), а не
`Russian Trusted Root CA` с портала госуслуг — тот RSA-корень для обычных
сайтов и к этому хосту отношения не имеет. Файлы в формате DER, расширение
`.cer`; списки отзыва лежат рядом, с расширением `.crl`.

Документация ЦРПТ называет свои источники тех же сертификатов:

| Что | Откуда |
|---|---|
| Оба корневых ГУЦ (продуктовый контур) | `https://www.gosuslugi.ru/crt` |
| Промежуточные КриптоПро | `https://tlsca.cryptopro.ru/tlsca.p7b` |
| Тестовый корневой для песочницы | `https://testgost2012.cryptopro.ru/certsrv/certcarc.asp` |

Ссылки из расширения AIA в таблице выше ведут к тем же звеньям цепочки, но
адресно и без ручного выбора нужного файла.

## Где смотреть при разборе

```sql
-- последние вызовы и статусы
SELECT TOP 50 Id, Url, Method, Status, StatusText, CreateDate
FROM http.tLogs ORDER BY Id DESC;

-- тела ошибок
SELECT TOP 20 l.CreateDate, l.Url, l.Status, e.Response
FROM http.tErrors e JOIN http.tLogs l ON l.Id = e.LogId ORDER BY e.LogId DESC;

-- зависшие задачи выгрузки
SELECT * FROM mdlp.tGeneralTasks WHERE ISNULL(Status,'') <> 'COMPLETED' ORDER BY Id DESC;
```
