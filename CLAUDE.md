# Рабочее пространство директора департамента информационных технологий

Это личный рабочий проект директора департамента информационных технологий.
Claude здесь работает как персональный ассистент: пишет и правит документацию,
регламенты, политики, письма, скрипты (SQL / PowerShell / bash / Python),
помогает с планированием и разбором задач.

> управленческие вопросы, а не пробелы в вводных.

## Кто мы

**Powbee** — ИТ-компания, разрабатывает CRM-систему для фармацевтических
компаний. Клиенты — фармкомпании (Servier, Besins, Valenta, Boehringer,

iOS / Android / web) и **Admin** (админка). Внутренний учёт клиентов и
релизов ведём в собственной консоли.

В компании **36 человек** в четырёх департаментах: Администрация, ИТ (17),
по работе с клиентами (12), Коммерческий (3).

## Три системы

| Система | Что это | Стек | Репозиторий |
|---|---|---|---|
| [pbeadmin](docs/systems/pbeadmin.md) | Админка CRM: мастер-данные, согласия, кампании, интеграции | PHP 8.2 / Laravel 8 / MSSQL | `../pbeadmin` |
| [pbeapp](docs/systems/pbeapp.md) | Приложение CRM: web + iOS + Android, 16 брендов | Angular 18 / Capacitor 6 | `../pbeapp` |
| [pbeconsole](docs/systems/pbeconsole.md) | Внутренняя консоль: клиенты, релизы, мониторинг | PHP 8.2 / Laravel 13 / MSSQL | `../pbeconsole` |

**У каждой системы есть собственный `CLAUDE.md` в её репозитории — он и есть
источник истины по коду.** Паспорта в [docs/systems/](docs/systems/) — это
управленческий срез (назначение, риски, владельцы), а не копия технического
контекста. Нужны детали по коду — читай `../<система>/CLAUDE.md`, не пересказывай
его сюда. Читай — но не правь: три репозитория открыты отсюда только на
чтение, изменения идут задачей в Трекер (см. «Правила работы для Claude»).

Сквозная связка: `pbeadmin` — источник данных для `pbeapp`; `pbeconsole` ведёт
учёт того, какая версия обеих частей поставлена какому клиенту.

**Рядом с тремя системами — четыре вспомогательных репозитория.** Ни один
не продукт, все правятся отсюда свободно: запрет на правку касается только трёх
продуктовых репозиториев.

| Репозиторий | Что это | Круг |
|---|---|---|
| `../pbeba` (`github.com/powbee/pbeba`) | рабочее пространство бизнес-анализа: обвязка Claude Code для постановок, шаблон из [CRM-1449](https://tracker.yandex.ru/CRM-1449), правила письма, база знаний о механике системы | БА, владелец продукта, тимлиды |
| `../pbemanual` (`github.com/powbee/pbemanual`) | пользовательский мануал: постранично по разделам, публикуется в Вики | БА, тестировщики, поддержка, менеджеры клиента |
| `../pbedataengineer` (`github.com/powbee/pbedataengineer`) | рабочее пространство дата-инженерии: обвязка Claude Code для дэшбордов Superset, SQL датасетов, выгрузки дэшбордов в YAML, база знаний по данным | дата-инженеры |
| `../pbe-dba` (`github.com/powbee/pbe-dba`) | эксплуатация SQL Server: бэкапы, выгрузка копий наружу, очистка, наблюдение, репликация, провижининг доступов (`sql/provisioning/`) | DBA, технический директор, директор департамента ИТ |

Слои знания разведены намеренно: мануал отвечает «как этим пользоваться»,
`pbeba/docs/kb/` — «как это устроено и от чего зависит», `pbedataengineer/docs/kb/` —
«откуда берётся цифра». Второе и третье наружу не идут. `pbe-dba` стоит особняком:
это не обвязка агента, а эксплуатационные скрипты под серверы БД; сюда 31.08.2026
переехала система провижининга доступов из `automation/sql/`.
Открытые вопросы по всем трём — в [docs/backlog.md](docs/backlog.md), разделы
«Бизнес-анализ с агентом» и «Claude Code в дата-инженерии».

**Система — надолго, проект — на срок.** Крупные клиентские проекты внутри
этих систем (заказная разработка под конкретного клиента) описываются отдельно
в [docs/projects/](docs/projects/): срок, заказчик, оценка, ход процесса. Один
проект может затрагивать несколько систем — поэтому проекты лежат рядом с
системами, а не внутри них.

## Где лежат исходные материалы

Регламенты, требования и задачи компании живут не в этом репозитории, а в
**Яндекс Трекере** и **Яндекс Вики**. Для чтения оттуда есть утилиты — не проси
пользователя копировать текст вручную, вытаскивай сам:

```bash
automation/scripts/tracker-issue.sh CRM-544              # задача Трекера в markdown
automation/scripts/wiki-page.sh <slug|ссылка>            # страница Вики в markdown
automation/scripts/wiki-page.sh <slug> --comments        # + комментарии к странице
automation/scripts/wiki-page.sh <slug> --raw | jq -r .content \
  | automation/scripts/wiki2md.py                        # + перевод разметки Вики в чистый md
```

Обе принимают несколько объектов за вызов и понимают ссылку целиком.
Подробности, настройка доступа и ограничения — [automation/scripts/README.md](automation/scripts/README.md).

Занятость команд собирается оттуда же:

```bash
automation/scripts/team-load.py --team ba qa --days 14   # кто чем занят, часы против нормы
automation/scripts/github-activity.py --days 14          # активность разработки в GitHub
```

Текст из Вики приходит в разметке Вики (`{% note %}`, таблицы `#| |#`) — для
перевода в чистый markdown есть `wiki2md.py`.

**Часть регламентов мы ведём у себя, а не в Вики** — жизненный цикл задачи CRM,
описание очередей Трекера и инструкции по работе с Claude Code для команд
разработки. Это рабочие копии, ответственный за них — директор
департамента информационных технологий; правим здесь, потом переносим в Вики.
Указатель и порядок обновления —
[docs/regulations/README.md](docs/regulations/README.md).

## Наблюдение за занятостью команд

Четыре подразделения департамента [без назначенного руководителя](docs/company/it-department.md),
и загрузка тестировщиков и БА не планируется никем. Вместо статусов и встреч —
снимок фактов плюс состояние, которое ведём.

| Слой | Что | Где |
|---|---|---|
| Факты | задачи, статусы, часы, PR | `reports/team-load-*` и `reports/github-activity-*`, вне git |
| Состояние | кто чем занят, что запланировано, где риск | [docs/company/team-load.md](docs/company/team-load.md) |
| Норма | как должно планироваться | [регламент, этапы 8 и 9](docs/regulations/crm-lifecycle/) |

Обновление — командой **`/pbe-zagruzka`** раз в неделю и перед набором спринта.
Она собирает оба снимка и переписывает состояние, **сохраняя ручные разделы**:
«Отсутствия», «Решения по распределению» и пометки в карточках людей — их не
знает ни один источник, и потерять их значит обнулить смысл документа.

Границы источников, которые надо держать в голове:

- **присутствие и списание — разные величины.** Консоль (`GET /hours`) отдаёт время
  за компьютером по StaffCop, Трекер — списанные часы. Складывать нельзя; смысл
  в их отношении. Календарная норма остаётся запасным вариантом на случай, когда
  консоль недоступна;
- **`staffcopBound` при нулевом присутствии — сломанный агент, а не простой.**
  Вывода о загрузке человека из такой строки делать нельзя;
- **окна теста прилаги живут в релизах консоли**, а не в статусах задач: приложение
  выпускается скоупом, и подзадача «Тестирование» ждёт стадии «Внутренний QA»
  релиза клиента. Незаданные плановые даты показываются предупреждением;
- **в GitHub нет БА и тестировщиков** — они не в организации `powbee`, пустая
  активность у них означает «источник не про них»;
- **в Вики активности нет вообще** — API не отдаёт ни ленту изменений, ни автора
  правки, только `modified_at` конкретной страницы.

Документ внутренний: в Вики не публикуется, наружу не идёт. Это инструмент
планирования, а не рейтинг людей.

## Первоисточники: где чья правда

Каждый тип факта имеет **один** первоисточник. Остальные документы ссылаются на
него и не копируют содержимое — копия молча разойдётся с оригиналом.

| Тип факта | Первоисточник | Пример |
|---|---|---|
| Процесс: кто что делает, статусы, сроки, очереди | [docs/regulations/](docs/regulations/) | «задача попадает в спринт только при согласованной оценке» |
| Люди: кто исполняет роль, состав команд, подчинение | [docs/company/](docs/company/) | «релиз-менеджер — Гаранжина Полина» |
| Код и архитектура продукта | `../<проект>/CLAUDE.md` | «Angular 18.2, Capacitor 6» |
| Расхождения и открытые вопросы | [docs/backlog.md](docs/backlog.md) | «по регламенту одно, фактически другое» |

**Имена людей в регламенты не вписываем** — регламент утверждается подписями и
меняется медленно, а состав быстро. В регламенте роль, в оргструктуре — кто её
исполняет.

**Регламент читается без нашего рабочего пространства.** В тексте регламента не
упоминаются ни скрипты и их имена (`tracker-lint.py`, `automation/scripts/…`), ни
коды их правил (`Р-1`, `Б-4`), ни файлы репозитория, ни ссылки в
[бэклог](docs/backlog.md) — даже слово «скриптом» в описании шага лишнее.
Регламент описывает **кто что делает**, а не чем это делается.

Причина: документ утверждается подписями и уезжает в Вики, где у читателя нет ни
репозитория, ни доступа к скриптам, — ссылка ведёт в никуда, а код правила ни о
чём не говорит. Открытый вопрос называется в тексте своими словами («порядок пока
не установлен»); автоматические проверки и связь с бэклогом живут в наших
документах — [docs/company/](docs/company/),
[automation/scripts/README.md](automation/scripts/README.md), самом бэклоге.
Перед коммитом правок в [docs/regulations/](docs/regulations/) прогонять
`grep -rn "скрипт\|automation/\|\.py\b\|backlog" docs/regulations/`.

Ссылки между документами проверяются скриптом — после переименований запускать
`automation/scripts/check-links.py` (код возврата 1, если что-то отвалилось).

**Расхождение нормы и практики фиксируем явно.** Документ вправе сказать «по
регламенту X, фактически Y» — это ценный факт, а не ошибка. Прятать его, приводя
всё к регламенту, нельзя: именно так расхождения и доживают до аудита.

## Правила работы для Claude

- **Продуктовые репозитории — только на чтение.** Из этого рабочего
  пространства не править файлы в `../pbeadmin`, `../pbeapp`, `../pbeconsole`
  и не создавать там новые. Читать код и их `CLAUDE.md` — нужно; писать —
  нельзя, даже если правка на одну строку и даже в `pbeconsole`, где владелец
  проекта единственный разработчик. Изменение в продукте оформляется задачей
  в Трекере (описание, ожидаемый результат, очередь), черновик патча — в
  теле задачи или во временных файлах, но не коммитом мимо процесса.
  Причина: правка в обход Трекера не видна команде — нет постановки, оценки,
  ревью и следа в [жизненном цикле задачи CRM](docs/regulations/crm-lifecycle/).
- **Язык** — русский. Документы деловые, без воды и канцелярита.
- **Формат документов** — Markdown. Заголовок, дата, версия, ответственный
  в шапке; далее по существу.
- **Никаких секретов в репозитории.** Пароли, ключи, строки подключения,
  токены — только в `.env` (в `.gitignore`) или в парольном менеджере.
  В документах — плейсхолдеры вида `<SERVICE_ACCOUNT_PASSWORD>`.
- **Персональные данные** — минимум: должность и роль важнее ФИО там, где
  документ пойдёт вовне.
- **Не выдумывать факты.** Если для документа не хватает вводных (владелец
  системы, SLA, номер сервера) — спросить или оставить явный маркер
  `TODO: уточнить`.
- **Точность в скриптах.** SQL под MSSQL — идемпотентный, с `@DryRun`, где
  применимо; изменения прав и схемы — с журналированием.
- **Письма — всегда в двух форматах.** Черновик письма кладётся в
  [reports/](reports/) как `pismo-<тема>-<дата>.md` — его удобно вычитывать и
  править здесь; рядом тем же именем `.rtf`, собранный
  `automation/scripts/md2rtf.py`, — он же кладётся в буфер обмена и вставляется
  в почту обычным Cmd+V без остатков markdown-разметки. Не предлагать пользователю
  вычищать `##` и `**` руками и не отдавать письмо только текстом в чат.
- Перед созданием нового документа проверить, нет ли уже похожего — обновить
  существующий, а не плодить дубли.
- **Открытые вопросы — в [docs/backlog.md](docs/backlog.md)**, а не россыпью по
  документам. Закрытые переносить в раздел «Закрыто» с решением и датой, не
  удалять: иначе тот же вопрос поднимется заново через полгода.
- **Конспекты чужих документов помечать как конспекты.** Регламенты компании
  живут в Вики; копии здесь — «общими мазками» для памяти, спорное решается по
  первоисточнику. Не выдавать конспект за норматив.

## Консоль Powbee — заметки и напоминания

Могу заводить пользователю заметки и напоминания в консоли Powbee через её API.

**Когда.** Пользователь просит запомнить или напомнить: «напомни <дата> <что>»,
«запиши, что…», «что у меня висит», «закрой напоминание про…». Это заметка
в консоли, а не файл в проекте.

- База: `https://console.powbeecrm.com/api/v1`
- Токен: Keychain macOS — `security find-generic-password -s pbe-console-api -w`
  (положить в `PBE_CONSOLE_API_TOKEN`, заголовок `X-Console-Token`)
- Справочник: `GET /api/v1/docs` — читать оттуда, здесь не дублировать.

**До первого вызова помнить:**
1. Действую от имени владельца токена. Завести заметку коллеге нельзя.
2. Даты — только абсолютные, московские. «завтра», «в пятницу», «через неделю»
   вычисляю САМ и передаю как `2026-09-15 10:00:00`. Консоль не угадывает.
3. Домен один — заметки и цели дня. Клиентов, релизов, задач Трекера, часов там нет.
4. Создав заметку, называю пользователю её `id`: идемпотентности нет, повтор при
   обрыве связи создаст дубль.
5. Ошибки разбираю по `error.code`, не по тексту. Что делать при каждом — в блоке
   `errors` манифеста.

**Токен не печатать в вывод, не писать в файлы, не коммитить.**
