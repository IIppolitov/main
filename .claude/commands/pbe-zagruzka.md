Обнови состояние занятости команд: **$ARGUMENTS**

Процесс описан в [docs/company/team-load.md](../../docs/company/team-load.md),
раздел «Как это работает» — он первичен, эта команда его исполняет. Расходятся —
прав документ.

> Аргументы прокидывай в скрипты как есть. Пусто — значит `--team ba qa --days 14`.

## 1. Прочитай текущее состояние

Открой `docs/company/team-load.md` **целиком** до запуска скриптов. Оттуда берётся
то, чего нет ни в Трекере, ни в GitHub и что нельзя потерять при обновлении:

- раздел «Отсутствия» — причина отсутствия, которую присутствие StaffCop показать
  не может: оно скажет «был 8 дней из 10», но не скажет, отпуск это или болезнь;
- раздел «Решения по распределению» — журнал «кому что отдали и почему»;
- пометки в карточках людей — «просел из-за Омни Роше», «просил не давать прилагу».

Ничего из этого скрипт не знает. **Стереть эти разделы при обновлении — потерять
единственное, ради чего документ ведётся.**

## 2. Собери факты

```
automation/scripts/team-load.py <аргументы> --forecast --save
automation/scripts/github-activity.py --days <столько же> --save
```

`--forecast` обязателен, когда в охвате тестирование: без него «в плане» —
это куча из тридцати задач без признака, придёт она или нет.

Скрипты кладут `.md` и `.json` в `reports/` (папка вне git). Читай `.json` — он
компактнее и не требует разбора таблиц.

GitHub не ответил за таймаут — это лимит поиска (30 запросов в минуту), а не
поломка. Повтори один раз; не вышло — обновляй по одному Трекеру и напиши об
этом в шапке документа.

## 3. Обнови документ

Перепиши `docs/company/team-load.md`, сохранив ручные разделы из п. 1.

По каждому человеку — четыре строки, не больше: **делает**, **ждёт его**,
**в плане**, **риск**. Ключи задач ставь ссылками на Трекер. Цифры бери из
снимка, не пересчитывай на глаз.

Правила, которые важнее краткости:

- **Расхождение с прошлым снимком фиксируй явно.** «Было 3 задачи в очереди, стало
  11» — это и есть смысл ведения состояния. Просто переписать цифру значит потерять
  тренд.
- **Не выдумывай причину.** «Присутствие 52 ч, списано 7» — пиши так и добавляй
  «причина неизвестна», а не «вероятно, был занят прилагой». Если причина есть в
  разделе «Отсутствия» — сошлись на неё.
- **Флаги скрипта переноси, а не переписывай.** «Залипло 230 дней» — это факт из
  Трекера, а не оценка.
- **Раздел «Ничьё» переноси целиком.** Задачи, ждущие теста без назначенного
  тестировщика, — главный источник срывов: они не видны ни одному человеку в
  своей карточке.

## 4. Что сказать в ответе

Три пункта, коротко:

1. Что изменилось с прошлого обновления — по каждой команде одной строкой.
2. Что требует решения сегодня: перегруз, залипшие задачи, «ничьё».
3. Чего не хватило для картины — незаполненные оценки, отсутствия без пометки,
   недоступный источник.

Не пересказывай документ целиком: он уже написан, пользователь его откроет.

## Ограничения источников

- **Присутствие и списание — разные величины.** Присутствие из консоли (StaffCop)
  уже учитывает отпуска и выходные, списанное из Трекера — нет. Не складывай их и
  не подменяй одно другим: смысл в отношении. Календарная норма используется, только
  когда консоль недоступна, и тогда скрипт пишет причину в шапке — перенеси её в
  документ, иначе цифры будут читаться как полноценные.
- **Нулевое присутствие при `staffcopBound` — сломанный агент.** Пиши «второго
  контура по человеку нет», а не «человек не работал».
- **Окна теста прилаги — в разделе «Релизы приложения».** Приложение выпускается
  скоупом: подзадача «Тестирование» ждёт стадии «Внутренний QA» релиза клиента, а
  не статуса соседней разработки. Просроченные окна и незаданные плановые даты
  переноси в документ дословно — по клиенту без даты объём теста приходит без
  предупреждения.
- **В GitHub нет БА и тестировщиков** — они не входят в организацию `powbee`.
  Пустая активность у них означает «источник не про них», а не «ничего не делал».
- **В Вики активности нет вообще**: API не отдаёт ни ленту изменений, ни автора
  правки. Не пытайся её собрать.
