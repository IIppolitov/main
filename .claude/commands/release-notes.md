Собери релизные документы по проектам Трекера: **$ARGUMENTS**

Процесс описан в `docs/release-notes/` (пути — от корня рабочего пространства) —
он первичен, эта команда его исполняет. Расходятся — прав `process.md`.
Прочитай `process.md` и `razbor-zadachi.md` перед началом, а не по ходу.

> Продуктовые репозитории — **только на чтение**: `fetch`, `log`, `show`, `grep`.
> Никаких `pull`, `checkout`, правок файлов в `../pbeadmin` и `../pbeapp`.

## 1. Перечень задач

```
automation/scripts/tracker-project-report.py $ARGUMENTS
```

Аргументы передавай как есть — принимаются и номера, и ссылки, и несколько проектов.
Дата релиза: из `--date`, иначе сегодняшняя.

Выпиши задачи с колонками «Задача», «Клиент», «Тема». Клиента со знаком `?`
пометь как требующий проверки — тег не проставлен, мнемоника взята из темы.

## 2. Тела задач

```
automation/scripts/tracker-issue.sh <все ключи через пробел> --links
```

`--links` нужен ради подзадач «Релиз»: в них лежит план выкатки, и он первичен
по отношению к твоим выводам из кода.

## 3. База сверки — актуальный prod-тег

```
git -C ../pbeadmin fetch --tags --prune origin
git -C ../pbeadmin for-each-ref --sort=-creatordate --format='%(creatordate:short) %(refname:short)' 'refs/tags/prod-v*' | head -5
```

Верхняя строка — база. Сверяйся **по тегу**, не по `main` и не по рабочему
дереву: в `main` есть то, что в релиз не едет, а каталоги сабмодулей отстают.
Тег запиши в шапку обоих документов. Кода нет — так и напиши в шапке, факты бери
из подзадач «Релиз».

По каждой задаче:

```
git -C ../pbeadmin log <TAG> --grep='<KEY>' --name-only --pretty=format:'' | sort -u
```

Не нашлась в ядре — пройди по сабмодулям. Для каждого затронутого модуля сравни
указатель в теге с коммитом задачи (`ls-tree <TAG> modules/<M>` →
`merge-base --is-ancestor`): влитая в `main` модуля задача без бампа указателя на
продуктив не попадает. Не нашлась нигде — блокер релиза, так и напиши.

## 4. Разбор

Каждую задачу — по девяти вопросам из `razbor-zadachi.md`. Особое внимание:

- **тип переключателя**: env-ключ (`.env.example`, `env()`) или ключ настроек
  админки (`config/pbe.php`, `config('pbe.KEY.value')`) — действия разные;
- **дефолт ключа** — от него зависит, надо ли что-то делать остальным клиентам;
- **`env()` внутри миграции** — задаёт жёсткий порядок шагов;
- **сабмодули** — сверять указатель в теге, а не факт мерджа в `main`.

## 5. Документы

По шаблонам `docs/templates/release-actions.md` и `docs/templates/patch-notes.md`,
в `reports/RELEASE_ACTIONS_<дата>.md` и `reports/PATCH_NOTES_<дата>.md`.
Группировка по клиентам, в конце «Все клиенты».

Release actions — сначала, patch notes — по ним.

## 6. Проверка и отчёт

Пройди чек-лист самопроверки из `process.md`, п. 6. В ответе пользователю —
коротко: сколько задач, сколько закрыто конфигами, сколько без действий, и
**список того, что осталось неясным**, с адресатом вопроса.

Факты не выдумывай: не хватает вводных (какая база, чей планировщик, кто гоняет
загрузки) — это строка в разделе «Открытые вопросы до релиза», а не догадка в
теле документа. Расхождения выноси явно, не приглаживай.
