Собери релизные документы по проектам Трекера: **$ARGUMENTS**

Процесс описан в `docs/release-notes/` (пути — от корня рабочего пространства) —
он первичен, эта команда его исполняет. Расходятся — прав `process.md`.
Прочитай `process.md` и `razbor-zadachi.md` перед началом, а не по ходу.

> Продуктовые репозитории — **только на чтение**: `fetch`, `log`, `show`, `grep`.
> Никаких `pull`, `checkout`, правок файлов в `../pbeadmin` и `../pbeapp`.

## 0. Цель документа

**RELEASE_ACTIONS — это чек-лист «что не забыть сделать руками».** Всё, что делает
`deploy.sh` (соседний проект `../deploy-scripts`), в исполняемую часть не попадает:

| Делает `deploy.sh` сам | Значит, в чек-листе этого нет |
|---|---|
| переключает ядро на последний `pre-prod-v*` / `prod-v*` | — |
| переключает **каждый активный модуль на его собственный последний тег** (`sort -V \| tail -1`) | указатели сабмодулей не отслеживаются вообще |
| `composer install --ignore-platform-reqs` | — |
| `php artisan migrate --force` | миграции ядра и модулей — не пункт релиза |
| `php artisan db:seed --class=RightSeeder --force` | «прогнать сидер» — не пункт релиза |
| `php artisan l5-swagger:generate`, версии в `.env` | — |

Ручными остаются: правки `.env` и установки на сервере, значения конфигов в админке,
**выдача прав людям** (сидер права заводит, но никому не выдаёт), разовые команды и правки
данных, создание справочных значений руками, переустановка вебхуков, проверка
`modules_statuses.json` (файла нет в git, он свой у каждого клиента; выключенный модуль
`deploy.sh` пропускает молча).

Справочное — миграции, задачи, модули, сводки — оставляем, но **приложением в конце**,
с пометкой «для сверки, а не для исполнения».

## 1. Перечень задач

Первоисточник состава релиза — **карточка релиза в консоли**, а не догадка по названиям
проектов. Релиз нумеруется версией (`v9.0 «Сентябрь 2026»`), и один релиз = **три проекта
Трекера**: два спринта «Спринт Админка N» плюс «Релиз Админка NN. Вне спринта».
Нумерация спринтов и релизов не совпадает.

```
TOKEN=$(security find-generic-password -s pbe-console-api -w)
curl -s -H "X-Console-Token: $TOKEN" https://console.powbeecrm.com/api/v1/admin-releases
curl -s -H "X-Console-Token: $TOKEN" https://console.powbeecrm.com/api/v1/admin-releases/<id>
```

Карточка отдаёт `sprints` (даты начала и конца) и полный перечень задач с `sprintId` —
по датам сопоставь спринты с проектами Трекера и прогони отчёт:

```
automation/scripts/tracker-project-report.py <три номера проектов>
```

Сошлись числа задач по каждому спринту — перечень верный. Дата релиза: из `--date`,
иначе `plannedReleaseDate` из карточки.

Выпиши задачи с колонками «Задача», «Клиент», «Тема». Клиента со знаком `?`
пометь как требующий проверки — тег не проставлен, мнемоника взята из темы.

## 2. Тела задач

```
automation/scripts/tracker-issue.sh <все ключи через пробел> --links
```

`--links` нужен ради подзадач «Релиз»: в них лежит план выкатки, и он первичен
по отношению к твоим выводам из кода.

Блоки «Действия при релизе» и «Изменения для пользователя» лежат **не в описании**, а в
полях задачи с префиксом `697bc5297d4f716731e75dc9--`: `releaseActions`, `externalChanges`,
`internalChanges`, `testPlan`, `linksToPullRequests`. Из `releaseActions` и собирается
исполняемая часть документа.

## 3. База сверки — теги, которые возьмёт деплой

Сверяемся ровно по тому, что выберет `deploy.sh`: **`git tag -l '<префикс>-v*' | sort -V | tail -1`**
в ядре и отдельно в каждом модуле. Сортировка **по версии, а не по дате**: `sort -V` даёт
`prod-v9.0`, а `--sort=-creatordate` может вернуть `prod-v8.0`, если релизный тег поставлен
на более старый коммит. Это не придирка — на v9.0 так и вышло.

```
git -C ../pbeadmin fetch --tags --prune origin
for m in ../pbeadmin/modules/*/; do git -C "$m" fetch --tags --prune origin; done

git -C ../pbeadmin tag -l 'prod-v*' | sort -V | tail -1
for m in ../pbeadmin/modules/*/; do
  echo "$(basename $m): $(git -C "$m" tag -l 'prod-v*' | sort -V | tail -1)"
done
```

Релизный `prod-v*` уже проставлен — он и есть база. Не проставлен (документы готовятся
заранее) — базой служит последний `pre-prod-v*`, и в шапке это оговаривается. Предыдущий
продуктивный тег пишется рядом как справка. Всё — в шапку обоих документов.

По каждой задаче ищем **внутри тега**, а не в `origin/main`:

```
git -C ../pbeadmin log <TAG> --grep='<KEY>' --name-only --pretty=format:'' | sort -u
```

Не нашлась в ядре — тем же способом по модулям, каждый по своему тегу:

```
for m in ../pbeadmin/modules/*/; do
  MT=$(git -C "$m" tag -l 'prod-v*' | sort -V | tail -1)
  [ -n "$MT" ] && git -C "$m" log "$MT" --oneline --grep='<KEY>' -i -1 | sed "s|^|$(basename $m) $MT |"
done
```

**Искать по содержимому тега, а не сравнивать SHA из `origin/main`.** В релизную ветку
коммиты приезжают перебазированными, SHA другой — `merge-base --is-ancestor` по коммиту из
`main` даёт ложное «не входит». На v9.0 так ошибочно «выпали» четыре задачи.

**Указатели сабмодулей не проверяем — за ними не следят, и `deploy.sh` их не читает.**
Он берёт последний тег каждого модуля отдельно.

Не нашлась нигде — блокер релиза, так и напиши. Но сначала перепроверь по тексту темы и по
номеру PR: ключ задачи в сообщении коммита стоит не всегда.

Ещё две ловушки при обходе модулей:

- каталог модуля может быть подключён к чужому репозиторию (`git -C <m> remote get-url origin`
  против `.gitmodules`) — каталог, смотрящий на `pbeadmin.git`, даёт ложные совпадения по
  коммитам ядра;
- модуль **без единого `prod-*` тега** `deploy.sh` откатывает на ветку по умолчанию и тащит
  всё, что там есть. Это пункт «проверить до запуска деплоя», а не мелочь.

## 4. Разбор

Каждую задачу — по девяти вопросам из `razbor-zadachi.md`. Особое внимание:

- **тип переключателя**: env-ключ (`.env.example`, `env()`) или ключ настроек
  админки (`config/pbe.php`, `config('pbe.KEY.value')`) — действия разные;
- **дефолт ключа** — от него зависит, надо ли что-то делать остальным клиентам;
- **`env()` внутри миграции** — задаёт жёсткий порядок шагов;
- **модули** — сверять последний тег модуля, а не указатель и не факт мерджа в `main`;
- **новое право** — сидер его заводит, но **не выдаёт**: «раздать право X» это отдельный
  ручной пункт, и без него функция не работает ни у кого.

## 5. Документы

По шаблонам `docs/templates/release-actions.md` и `docs/templates/patch-notes.md`,
в папку сегодняшнего дня: `reports/<день>/RELEASE_ACTIONS.md` и
`reports/<день>/PATCH_NOTES.md`.
Группировка по клиентам, в конце «Все клиенты».

Порядок разделов в RELEASE_ACTIONS — по приоритету исполнения, а не по типу факта:

1. что `deploy.sh` делает сам (коротко, чтобы это не искали в чек-листе);
2. 🔴 решить до запуска деплоя (блокеры, теги модулей, `modules_statuses.json`);
3. до деплоя: `.env` и установки на сервере;
4. после деплоя: конфиги в админке, по клиентам;
5. после деплоя: действия, которых нет ни в одном скрипте (права, разовые команды,
   правки данных, вебхуки);
6. что в релиз не едет и почему — таблицей;
7. открытые вопросы с адресатом;
8. чек-лист по инстансам одной страницей;
9. **приложения (справочно)**: миграции, права сидера, модули и их теги, все задачи релиза.

Release actions — сначала, patch notes — по ним.

## 6. Проверка и отчёт

Пройди чек-лист самопроверки из `process.md`, п. 6. В ответе пользователю —
коротко: сколько задач, сколько требует ручных действий, сколько уедет само, и
**список того, что осталось неясным**, с адресатом вопроса.

Факты не выдумывай: не хватает вводных (какая база, чей планировщик, кто гоняет
загрузки) — это строка в разделе «Открытые вопросы до релиза», а не догадка в
теле документа. Расхождения выноси явно, не приглаживай.
